# Справочник: диагностика и восстановление

Команды для администратора и второй линии поддержки. Порядок работы при любом сбое: **1)** найти неисправный компонент и **сохранить сведения** (`scripts/diag.sh`); **2)** выполнить **минимальное** действие; **3)** проверить результат. Не начинайте с перезапуска всего или пересборки — так теряются сведения о причине.

Все команды — из каталога установки (`APP_ROOT`, например `/opt/peregovorka`). Скрипты сами берут параметры из `.env` и работают только со своим compose-проектом. Вместо скриптов можно вызывать Docker Compose напрямую (раздел 2); переменные: `P` — `COMPOSE_PROJECT_NAME`, путь к каталогу установки — `APP_ROOT`.

Обозначения: ⚠ — команда изменяет систему; ⛔ — опасно, удаляет данные, в диагностике не использовать. В последнем столбце — что команда вывела на тестовом экземпляре.

## 1. Найти экземпляр

| Команда | Что показывает | Пример результата |
| --- | --- | --- |
| `docker compose ls` | compose-проекты сервера и путь к их `compose.yml`; каталог установки — на уровень выше `deployment/` | — |
| `docker ps --format '{{.Names}}\t{{.Label "com.docker.compose.project.working_dir"}}' \| grep backend` | контейнеры `backend` и каталоги установок (несколько экземпляров на одном сервере — несколько строк) | — |
| `grep -E '^(COMPOSE_PROJECT_NAME\|APP_PUBLIC_URL\|DATA_ROOT\|WEB_PORT)=' .env` | имя проекта, адрес, каталог данных, порт | — |
| `systemctl list-units 'peregovorka-updater*'` | службы помощника обновлений (по одной на проект) | — |

## 2. Контейнеры и службы

| Команда | Что делает | Влияние | Пример результата |
| --- | --- | --- | --- |
| `scripts/status.sh` | состояние и health сервисов, версия, последние развёртывания; код 0 — все `healthy` | нет | Все 6 `healthy`, код 0 |
| `scripts/status.sh --wait 180` | ждать `healthy` до 180 с | нет | После перезапуска backend — 21 с |
| `docker compose -p P --project-directory APP_ROOT/deployment --env-file APP_ROOT/.env -f APP_ROOT/deployment/compose.yml ps` | то же без скрипта | нет | — |
| `docker inspect -f '{{.State.Health.Status}} {{.RestartCount}} {{.State.OOMKilled}}' P-backend-1` | здоровье, число перезапусков, остановка по нехватке памяти | нет | — |
| ⚠ `scripts/ctl.sh restart <сервис>` | перезапуск контейнера **без** применения изменений `.env` | см. таблицу ниже | Backend снова `healthy` за 21 с; изменённая переменная `.env` в контейнер **не** попала |
| ⚠ `scripts/ctl.sh start <сервис>` | создать/пересоздать контейнер по текущему `.env` из уже собранного образа (так применяются правки `.env`) | как перезапуск | После правки `ASR_CPU_THREADS` значение в контейнере новое (с 0.50.1; в 0.49.x падало «No such image …:dev» — [Известные проблемы](Известные-проблемы)) |
| ⚠ `scripts/ctl.sh stop [сервис]` | остановить; данные, тома, образы не удаляются | сервис недоступен | — |
| ⚠ `scripts/rebuild.sh <сервис>` | пересобрать образ тем же способом, что обновление, и перезапустить | перезапуск сервиса | — |

Что прерывает перезапуск сервиса (по устройству продукта; измерено только время возврата backend — 21 с):

| Сервис | Последствия для пользователей |
| --- | --- |
| `web` | несколько секунд страница и API недоступны; встречи продолжаются (медиа идёт мимо web), участники переподключают сигнализацию |
| `backend` | 5–20 с ошибок интерфейса и API; встречи продолжаются, стенограмма догоняет |
| `asr` | пауза распознавания в идущих встречах; звонки не прерываются |
| `livekit` | **все идущие встречи прерываются**, участники переподключаются сами (плашка «Переподключение…») |
| `postgres`, `redis` | краткая недоступность всего приложения; Redis: сессии в памяти не теряются (хранятся на диске), но очереди повторятся |

## 3. Журналы

| Команда | Что показывает | Пример результата |
| --- | --- | --- |
| `scripts/logs.sh backend --tail 200` | последние строки backend, секреты замаскированы | — |
| `scripts/logs.sh asr -f` | журнал в реальном времени (Ctrl+C — выход) | — |
| `scripts/logs.sh backend --tail 2000 \| grep -E '"level": ?"(ERROR\|CRITICAL)"'` | только ошибки backend (журнал в JSON) | — |
| `scripts/logs.sh backend --tail 500 \| grep "Origin отклонён"` | отказы по адресу («Недопустимый Origin») | — |
| `scripts/logs.sh livekit --tail 300 \| grep -E 'ERROR\|WARN'` | ошибки медиасервера | — |
| `cat $DATA_ROOT/updater/report.txt` | итог последнего обновления по этапам | — |
| `tail $DATA_ROOT/state/deploy-history.log` | история развёртываний (время, commit, миграции); файл появляется после первого `update.sh`, после установки его нет; итог установки — `$DATA_ROOT/state/last-update.state` | — |

Журналы Docker хранятся драйвером `json-file` в `/var/lib/docker/containers/<id>/` и при пересоздании контейнера удаляются: перед `ctl.sh start` или обновлением сохраните нужное (`diag.sh`).

## 4. Диагностический пакет для поддержки

```bash
scripts/diag.sh                    #
scripts/diag.sh --no-public        # без обращения к публичному адресу
```

На тестовом экземпляре: пакет ~25 КБ, 12 разделов (README.txt описывает каждый), проверка на утечку секретов пройдена, `sha256sum -c` — OK. В пакете: версии, контейнеры, ресурсы (память, swap, OOM, диск, inode, размеры каталогов и базы, `docker stats`, перезапуски), ответ API локально и через публичный адрес, DNS, цепочка TLS, история обновлений, хвосты журналов, глубокая проверка backend. Нет: паролей, токенов, ключей, содержимого встреч. Если скрипт сообщает «обнаружено значение секрета — архив НЕ создан», сообщите разработчикам **текст сообщения** (в 0.49.x так было на любой установке с паролем Redis — исправлено в 0.50.1).

Передача: внутренним каналом организации; SHA-256 — отдельным сообщением; не в открытые трекеры.

## 5. Проверки приложения

| Команда | Что проверяет | Пример результата |
| --- | --- | --- |

| `curl -s http://127.0.0.1:WEB_PORT/api/v1/health/ready` | PostgreSQL (занятость пулов), Redis, LiveKit, ASR (модель и конвейер); 503 — что-то из ядра недоступно | `ready` |
| `curl -s http://127.0.0.1:WEB_PORT/api/v1/version` | версия, commit, время сборки | — |
| `scripts/verify.sh` | итоговая проверка: контейнеры, nginx, права, health, прокси, сигнализация; код 1 — есть FAIL | PASS, 6 предупреждений (параметры ядра, потоки ASR) |
| `scripts/smoke-test.sh` | сквозная проверка с тестовой встречей; `PASS` — код 0; код 3 — работает, но не прошла внешняя часть (каталог, публичный адрес) | На 0.50.0 `--no-public`: `Smoke test: PASS`, код 0; в 0.49.x не настроенный каталог давал ложный FAIL и код 3 |
| `scripts/ports.sh --format md` | перечень портов и правил межсетевого экрана по `.env` | — |
| `docker compose … exec -T postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB> -c "select count(*) from meetings;"` | база отвечает, число встреч | — |

## 6. Сеть, DNS, HTTPS

| Команда | Что проверяет | Пример результата |
| --- | --- | --- |
| `getent ahosts meet.example.org` | куда указывает имя **с сервера** (split DNS) | — |
| `curl -sS -o /dev/null -w '%{http_code} %{ssl_verify_result}\n' https://meet.example.org/api/v1/version` | доступен ли публичный адрес с сервера, доверен ли сертификат (0 — да) | Если имя не разрешается — `curl: (6)` |
| `openssl s_client -connect meet.example.org:443 -servername meet.example.org -showcerts </dev/null \| grep -c 'BEGIN CERTIFICATE'` | сколько сертификатов отдаёт прокси: 1 при промежуточном CA — цепочка неполная | — |
| `echo \| openssl s_client -connect meet.example.org:443 -servername meet.example.org 2>/dev/null \| openssl x509 -noout -enddate -ext subjectAltName` | срок и имена сертификата | — |
| `ss -ltnu \| grep -E ':(WEB_PORT\|LIVEKIT_TCP_PORT\|LIVEKIT_UDP_PORT)\b'` | слушаются ли порты | — |
| `nc -vz <сервер> <LIVEKIT_TCP_PORT>` **с компьютера пользователя** | доступен ли порт медиа TCP | — |
| `python3 scripts/netprobe.py https://registry.npmjs.org/` | доступность источника сборки по этапам (DNS, TCP, прокси, TLS, загрузка) | — |

UDP с сервера проверить нельзя: достоверно — войти во встречу с компьютера вне сети организации и открыть «Администрирование → Обзор → Диагностика клиентов» (шёл ли звук по UDP или TCP).

## 7. Ресурсы

| Команда | Что смотреть | Пример результата |
| --- | --- | --- |
| `free -h; swapon --show` | доступная память, swap | — |
| `cat /proc/pressure/memory` | давление памяти (`avg60` > 10 — нехватка) | — |
| `journalctl -k -n 400 \| grep -iE 'out of memory\|oom-kill'` | остановки процессов ядром по нехватке памяти | — |
| `df -h DATA_ROOT; df -i DATA_ROOT` | свободное место и inode (меньше 30 ГБ — обновление и установка не начнутся) | — |
| `sudo du -sh DATA_ROOT/*` | что занимает место (без root каталоги `postgres` и `redis` не подсчитываются — проверено; с `sudo`) | — |
| `docker stats --no-stream $(docker ps -q --filter label=com.docker.compose.project=P)` | процессор и память контейнеров проекта | — |
| `docker system df` | место под образы, контейнеры, кэш сборки | — |
| `uptime; nproc` | нагрузка и число ядер | — |

Освобождение места без риска: старые копии в `BACKUP_DIR` (кроме последних), старые архивы `diagnostics/`, выгрузки в `DATA_ROOT/exports` по решению владельца данных. `update.sh` сам очищает кэш сборки и старые образы **своего** проекта. Не выполняйте `docker system prune` и `docker volume prune` — они затрагивают все проекты сервера.

## 10. Опасные команды (не для диагностики)

| Команда | Почему опасна |
| --- | --- |
| `docker compose … down -v` | удаляет тома проекта |
| `docker system prune`, `docker volume prune`, `docker image prune -a` | затрагивают **все** проекты сервера |
| `rm -rf DATA_ROOT/...` | удаляет базу, записи, модели |
| `scripts/restore.sh` | заменяет базу; данные после копии теряются |
| `git reset --hard`, `git clean` в каталоге установки | удаляют локальные изменения и `.env` (не отслеживается Git, но `git clean -x` удалит) |
| Ручная правка `APP_MASTER_KEY` | зашифрованные данные перестают читаться |
