# Как опубликовать сервис в интернете: порты и проверка

*Для кого: администратор Peregovorka и сетевой администратор.*

## Зачем это нужно

Чтобы пользователи подключались из-за пределов локальной сети, на межсетевом экране нужно открыть нужные порты и не открыть лишних. Peregovorka строит точный перечень правил по настройкам именно вашего сервера. Другие порты в `.env` дают другой перечень.

## Когда пригодится

- Сервер должен быть доступен из интернета сотрудникам и гостям.
- Сетевому администратору нужна заявка на открытие портов.
- Страница открывается, а звука и видео у внешних пользователей нет.

## Что потребуется

- Настроенный HTTPS: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).
- Права администратора сервера.
- Компьютер или телефон вне сети организации для окончательной проверки.
- Перед публикацией прочитайте [Защита публичного сервера](Защита-публичного-сервера-Peregovorka).

## Где найти

**Администрирование → Система → Сетевая доступность**. То же в терминале: `scripts/ports.sh`. Команда читает только `.env` и работает без веб-интерфейса и Docker.

## Как это сделать

### Получите перечень

1. Откройте **Администрирование → Система → Сетевая доступность**.
2. Нажмите **Скопировать заявку для сетевого администратора** или **Скопировать список**. Кнопки **Скачать** выгружают перечень в файл TXT, CSV или Markdown.
3. Либо выполните на сервере:

   ```bash
   scripts/ports.sh
   scripts/ports.sh --format request          # заявка сетевому администратору
   scripts/ports.sh --format csv --out ports.csv
   scripts/ports.sh --live                    # плюс адреса интеграций из базы: каталог, почта, SMB, Exchange
   ```

Перечень делит правила на входящие (на межсетевом экране перед сервером) и исходящие (с сервера). Он показывает протокол, порт, обязательность, компонент и назначение, предупреждения и порты, которые наружу публиковать нельзя.

### Откройте порты

Обычно получается так:

| Порт | Зачем | Открывать |
| --- | --- | --- |
| HTTPS 443 | страница, API, сигнализация | всем пользователям |
| `LIVEKIT_UDP_PORT`, UDP | основной путь звука и видео | всем пользователям |
| `LIVEKIT_TCP_PORT`, TCP | запасной путь для сетей, где UDP закрыт | всем пользователям |
| SIP и RTP | только при включённой телефонии | только адресам АТС, см. [SIP-телефония](Как-подключить-SIP-телефонию) |

Наружу не публикуются `WEB_PORT`, `NGINX_LISTEN_PORT`, LiveKit API, PostgreSQL, Redis, служба распознавания речи. Полный справочник: [Справочник: порты и сеть](Справочник-порты-и-сеть).

### Настройте NAT

За NAT пробросьте UDP `LIVEKIT_UDP_PORT` и TCP `LIVEKIT_TCP_PORT` на сервер без смены номера и протокола. Сервер звонков сообщает клиентам именно эти номера.

Публичный адрес сервер определяет сам, либо задайте `LIVEKIT_PUBLIC_IP`. Клиенты получают и его, и адрес в локальной сети, поэтому офис подключается напрямую. Готовые правила проброса и проверки есть в блоке **Медиасоединения: адреса для звука и видео** и в команде:

```bash
sudo scripts/medianet.sh check
```

Подробнее: [Справочник: порты и сеть](Справочник-порты-и-сеть#адреса-для-звука-и-видео-nat).

### Проверьте снаружи

Блок **Проверка с сервера** устанавливает соединение изнутри. Оно не проходит внешний NAT и межсетевой экран и не доказывает доступность из интернета. Для UDP внешней проверки без участия клиента не существует.

Достоверная проверка:

1. Войдите в тестовый звонок с устройства вне сети организации, например через мобильную сеть.
2. Откройте **Сетевая доступность → Медиасоединения**. Там будет адрес сервера, через который пошёл звук, и протокол UDP или TCP.
3. То же видно в **Администрирование → Обзор → Диагностика клиентов**.

## Что получится

Внешний участник входит в комнату, слышит и видит других. В **Диагностика клиентов** виден протокол. Если показан TCP, звонок работает, но UDP снаружи закрыт: проверьте проброс.

## Если не получается

| Что видно | Причина | Что сделать |
| --- | --- | --- |
| Страница открывается, звука нет | закрыты порты LiveKit | откройте UDP и TCP из перечня |
| Звонок идёт только по TCP | UDP закрыт снаружи | проверьте проброс UDP |
| Звонок «подключается» бесконечно | неверный публичный адрес | задайте `LIVEKIT_PUBLIC_IP`, выполните `scripts/medianet.sh check` |
| Предупреждение о частном `LIVEKIT_NODE_IP` за NAT | сервер объявляет внутренний адрес | см. раздел про NAT |
| CGNAT у провайдера | входящие соединения невозможны | нужен публичный адрес или другая схема подключения |
| «Проверить с сервера» успешна, снаружи нет | проверка изнутри не проходит внешний экран | используйте проверку с внешнего устройства |

## Ограничения

Используется один экземпляр LiveKit. Отдельный сервер TURN и распределённые схемы штатной установкой не поддерживаются: правила для них составляются вручную. STUN используется только для определения публичного адреса за NAT.

Внешнего подключения через настоящий NAT и межсетевой экран организации автоматическая проверка не даёт. Такая проверка выполняется только на вашей инфраструктуре.
