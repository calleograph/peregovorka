# Защита публичного сервера Peregovorka

*Для кого: администратор сервера, сетевой инженер, служба ИБ.*

## Зачем это нужно

Сервер, доступный из интернета, постоянно сканируют и пробуют на подбор паролей. В Peregovorka есть встроенный слой защиты для всего, что проходит через приложение. Он не заменяет сетевой межсетевой экран, внешний WAF и защиту от DDoS.

| Ступень | Что делает | Где настраивается |
| --- | --- | --- |
| Встроенный слой приложения | Защита входа, CAPTCHA, блокировка адресов, ограничение по подсетям, лёгкий WAF, журнал событий безопасности | **Администрирование → Безопасность** |
| Внешняя сетевая защита | Закрытие портов, которые не идут через приложение. Фильтрация по странам и репутации, защита от DDoS, промышленный WAF | Межсетевой экран, NAT, внешний прокси и WAF вашей организации |

## Когда пригодится

- Вы публикуете сервер в интернете.
- Сервис должен быть доступен только из офисов и VPN.
- В журнале появились сканирование или подбор паролей.
- Перед сервером стоит внешний прокси, балансировщик, WAF или CDN.
- Пользователь пожаловался на отказ, и нужно найти правило, которое его отклонило.

## Что потребуется

- Права администратора Peregovorka.
- HTTPS уже настроен: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).
- Список адресов офисов, VPN и прокси.
- Доступ к внешнему межсетевому экрану или сотрудник, который им управляет.
- SSH-доступ к серверу на случай аварийного восстановления.

## Где найти

Все разделы находятся в **Администрирование → Безопасность**:

| Раздел | Назначение |
| --- | --- |
| **Сеть и IP-адреса (прокси, WAF)** | Как сервер определяет настоящий адрес клиента |
| **Защита входа от перебора**, **CAPTCHA** | Подробно: [Как настроить безопасность входа](Как-настроить-безопасность-входа) |
| **Доверенные подсети** | Доступ только с разрешённых адресов |
| **Защита веб-приложения (WAF)** | Встроенный лёгкий WAF |
| **События и блокировки** | Сводка, журнал, вкладка блокировок |
| **Заблокированные адреса** | Та же страница, сразу на вкладке блокировок |
| **Хранение журнала безопасности** | Срок и размер журнала |

Перечень портов для вашей установки показывает **Администрирование → Система → Сетевая доступность** и команда `scripts/ports.sh --format md`.

## Как это сделать

Выполняйте шаги по порядку. Шаг 1 важнее остальных: от него зависят счётчики, блокировки и подсети.

### Шаг 1. Настройте определение адреса клиента

За прокси приложение видит адрес прокси, а заголовок `X-Forwarded-For` может написать кто угодно. Поэтому сервер верит заголовкам только от доверенных узлов.

**Доверенные прокси** и **разрешённые клиентские сети** разные настройки. Первые сообщают настоящий адрес клиента, вторые решают, кого пускать.

1. Откройте **Безопасность → Сеть и IP-адреса (прокси, WAF)**.
2. В поле **Откуда брать адрес клиента** оставьте **Автоматически (рекомендуется): X-Forwarded-For от доверенных прокси**, если нет особых причин менять значение.
3. Если перед сервером стоит WAF, CDN или прокси с публичным адресом, добавьте его адреса в поле **Доверенные прокси (reverse proxy, WAF, балансировщики)**.
4. Если адреса прокси нельзя перечислить, укажите их число в поле **Дополнительных прокси в цепочке**.
5. Сохраните настройки. Они применяются в течение нескольких секунд.
6. Откройте сервис с компьютера вне внутренней сети и посмотрите блок **Что сервер видит сейчас**. В строке **Ваш адрес для сервера** должен быть адрес этого компьютера.

Варианты источника адреса:

| Значение | Когда выбирать |
| --- | --- |
| **Автоматически (рекомендуется): X-Forwarded-For от доверенных прокси** | Обычная схема с nginx хоста |
| **Только X-Forwarded-For** | Цепочку задаёт ваш прокси |
| **Только X-Real-IP** | Прокси передаёт только этот заголовок |
| **Только Forwarded (RFC 7239)** | Прокси использует стандартный заголовок |
| **Свой заголовок (WAF/CDN)** | CDN передаёт адрес своим заголовком, например `CF-Connecting-IP`. Имя задаётся в поле **Имя заголовка** |
| **Адрес соединения (прокси нет, сервер доступен напрямую)** | Заголовки не используются совсем |

Как сервер защищается от подмены:

- Контейнер web всегда сам записывает заголовок `X-PG-Peer` с адресом подключившегося узла. Подделать его снаружи нельзя.
- Если этот узел не доверенный, заголовки о клиенте игнорируются.
- Цепочка `X-Forwarded-For` читается справа налево, доверенные прокси пропускаются. Левую часть цепочки пишет клиент, поэтому она не используется.
- Прямое подключение к backend извне невозможно: его порт не публикуется. Заголовки такого подключения тоже не учитываются.

В автоматическом режиме частные и локальные адреса считаются доверенными, поэтому nginx хоста работает без настройки. Если вы откроете контейнер web прямо в локальную сеть через `WEB_BIND_ADDR` без прокси, клиент из частной сети сможет подставить чужой адрес. В такой схеме выберите **Адрес соединения (прокси нет, сервер доступен напрямую)**.

Пример для nginx перед контейнером web. Порт возьмите из `WEB_PORT` в `.env`. Полный шаблон: `deployment/nginx/site.tls.conf.tpl`.

```nginx
location / {
    proxy_pass http://127.0.0.1:<WEB_PORT>;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
    proxy_read_timeout 120s;
}
```

Для `/api/v1/ws` и `/livekit/` дополнительно нужны заголовки `Upgrade` и `Connection` и `proxy_read_timeout 3600s`. Шаблон уже содержит эти блоки. Подробно: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).

### Шаг 2. Закройте лишние порты снаружи

Встроенный слой видит только трафик приложения. Всё перечисленное ниже закрывается внешним межсетевым экраном.

1. Получите перечень портов: `scripts/ports.sh --format md`.
2. Оставьте снаружи только HTTPS и нужные порты медиа `LIVEKIT_UDP_PORT` и `LIVEKIT_TCP_PORT`.
3. SIP и RTP открывайте только для адресов АТС.
4. Убедитесь, что PostgreSQL, Redis, SSH и порт web не опубликованы в интернет.

TURN в Peregovorka не используется. Раздел **Сетевая доступность** строит перечень правил, но доступность из настоящего интернета он не доказывает.

Рекомендации для внешнего WAF и защиты от DDoS:

- Внешний WAF с OWASP Core Rule Set начните в режиме detection-only.
- Исключите из его правил `/api/v1/ws`, `/livekit/`, загрузку больших файлов и `/api/v1/admin/config/`.
- Исключите из правил SQLi и XSS тела с произвольным текстом: чаты, протоколы, инструкции.
- Передавайте настоящий адрес клиента заголовком и добавьте адреса WAF в **Доверенные прокси (reverse proxy, WAF, балансировщики)**.
- Защиту от DDoS обеспечивает оператор связи или сервис фильтрации. Встроенный слой её не заменяет.

### Шаг 3. Настройте защиту входа

Выполните статью [Как настроить безопасность входа](Как-настроить-безопасность-входа). Для публичного сервера сделайте второй фактор обязательным хотя бы для администраторов.

### Шаг 4. Ограничьте доступ подсетями, если нужно

По умолчанию ограничение выключено, сайт открыт из любых сетей при обычных правилах авторизации. Включайте его, только если сервис не должен быть доступен снаружи ваших сетей.

Перед включением учтите:

- Трансляции: страница зрителя обращается к API и попадает под ограничение. Отдельного исключения для зрителей нет.
- Гости: **Не ограничивать гостевые ссылки** снимает ограничение только с адресов `/api/v1/guest/` и `/api/v1/captcha/`. Остальные запросы встречи, включая WebSocket событий, остаются под ограничением. Проверьте гостевой вход из внешней сети, прежде чем на это рассчитывать.

Порядок включения:

1. Откройте **Безопасность → Доверенные подсети**.
2. В блоке **Разрешённые адреса и подсети** добавьте сети организации. Кнопка **Мой адрес** подставляет ваш адрес. Поддерживаются адреса и подсети IPv4 и IPv6, например `192.0.2.10`, `198.51.100.0/24`, `2001:db8::/32`. Подсеть `/0` не принимается.
3. Проверьте, что рядом с **Ваш адрес для сервера** стоит **входит в разрешённые**.
4. При необходимости включите **Не ограничивать гостевые ссылки** и **Не ограничивать публичный API**.
5. Включите **Ограничить доступ к Peregovorka разрешёнными IP-адресами и подсетями**.
6. Нажмите **Подтвердить** в появившемся блоке. По умолчанию на это даётся 5 минут.

Защита от самоизоляции:

- Пустой список включить нельзя.
- Если ваш адрес не входит в список, появится окно **Вы можете потерять доступ**. Продолжение требует кнопки **Понимаю риск, продолжить**.
- Без подтверждения ограничение выключается само по окончании пробного срока.
- Изменение, которое отрезает вас, тоже требует подтверждения и заново запускает пробный срок.
- Пока ограничение включено, последнюю включённую сеть удалить или отключить нельзя.

Посетитель из неразрешённой сети получает нейтральную страницу **Доступ ограничен** с кодом 403 и текстом «Доступ к сервису ограничен. Обратитесь к администратору организации.». Списка сетей она не раскрывает. Внутренний трафик контейнеров и `/api/v1/health` ограничение не затрагивает.

Что охватывает ограничение:

| Охвачено | Не охвачено, закрывайте внешним экраном |
| --- | --- |
| Интерфейс и API `/api` | Статические файлы интерфейса |
| WebSocket событий и чатов | Сигналинг LiveKit `/livekit/` |
| Загрузки и выгрузки через приложение | Порты медиа `LIVEKIT_UDP_PORT` и `LIVEKIT_TCP_PORT` |
| Гостевые ссылки | Файлы потока `/hls/`, `/llhls/` и `/cdn-origin/`, их отдаёт контейнер web напрямую |
| Публичный API `/api/public` | SIP и RTP, у них свои списки адресов |
| API надстройки Outlook и календаря | SSH, PostgreSQL, Redis и другие порты сервера |

Блок **Что охватывает ограничение** в интерфейсе ещё называет порты TURN и диапазон 50000–60000. TURN не используется, а порты медиа задаются параметрами `LIVEKIT_UDP_PORT` и `LIVEKIT_TCP_PORT`. Сверяйтесь с `scripts/ports.sh`.

Если ограничение закрыло вход администратору, выполните на сервере в каталоге установки:

```bash
sudo scripts/security-reset.sh
```

Команда выключает ограничение, сохраняет список сетей и пишет событие в журнал аудита. Параметр `--unblock-all` дополнительно снимает все блокировки адресов.

Если контейнер backend не запускается, используйте способ, независимый от базы: добавьте `IP_ACCESS_DISABLE=1` в `.env` и выполните `sudo scripts/ctl.sh restart backend`. Потом уберите параметр и перезапустите backend снова, иначе настройки раздела не вернутся.

### Шаг 5. Включите встроенный WAF

Встроенный WAF защищает API от массового сканирования и типовых автоматических атак. Это не промышленный WAF. Если перед сервером стоит настоящий WAF, оставьте здесь **Наблюдение** или **Выключен**.

1. Откройте **Безопасность → Защита веб-приложения (WAF)**.
2. Оставьте режим **Наблюдение**. Это значение по умолчанию.
3. Понаблюдайте несколько дней за срабатываниями в **События и блокировки**.
4. Добавьте исключения для ложных срабатываний.
5. Переключите режим на **Защита**.
6. Эвристики переводите в **Блок** по одной, только после просмотра их срабатываний.

| Режим | Что происходит |
| --- | --- |
| **Выключен** | Запросы не проверяются |
| **Наблюдение** | События записываются, запросы не блокируются, даже если правило переведено в **Блок** |
| **Защита** | Проверенные правила блокируют анонимные запросы. Эвристики остаются в наблюдении, пока вы не переведёте их в **Блок** |

| Правило | Тип | Что ловит |
| --- | --- | --- |
| **Выход за пределы каталога (../)** | проверенное | `..`, закодированные варианты и NUL в пути и строке запроса |
| **Недопустимый метод HTTP** | проверенное | TRACE, CONNECT, нестандартные методы |
| **Проба служебных путей** | проверенное | `.env`, `.git`, `phpinfo`, `wp-admin`, `actuator` и подобные пути под `/api` |
| **Признаки SQL-инъекции в строке запроса** | эвристика | `union select`, `or 1=1`, `sleep()` и другие признаки |
| **Признаки XSS в строке запроса** | эвристика | `<script`, `javascript:`, `onerror=` |
| **Признаки внедрения команд** | эвристика | пути к системным файлам, подстановки команд |
| **Известные сканеры в User-Agent** | эвристика | sqlmap, nikto, nmap, masscan, nuclei и другие |
| **Перебор путей и идентификаторов** | эвристика | много ответов 404 и 405 с адреса за минуту |

Для каждого правила есть режимы **По режиму**, **Выключено**, **Наблюдение** и **Блок**. Порог перебора задаёт поле **Перебор путей: ответов 404/405 в минуту**, по умолчанию 40. Срок блокировки задаёт **Блокировка при переборе, минут**, по умолчанию 10.

Границы WAF:

- Проверяются только запросы к `/api/`. WebSocket правилами WAF не проверяется.
- Смотрятся только метаданные: путь, строка запроса, метод, User-Agent, частота ответов 404 и 405.
- Тела запросов не сканируются, потому что чаты и протоколы содержат произвольный текст. Защиту от инъекций дают параметризованные запросы и экранирование вывода.
- Блокируются только запросы без признака входа: cookie сессии, гостевого токена, заголовка авторизации или ключа API. На этом шаге проверяется наличие признака, а не его подлинность. Поэтому WAF отсекает массовое сканирование, но не целенаправленную атаку.

Исключения задаются в блоке **Исключения**: поля **Пути (по одному в строке, начало пути)** и **Адреса и подсети**, кнопка **Сохранить исключения**.

### Шаг 6. Наблюдайте за событиями

**Безопасность → События и блокировки** показывает плитки за сутки: заблокированные адреса, неудачные входы, отклонённые входы, показанные и пройденные CAPTCHA, отказы по подсетям, срабатывания WAF. Ниже видны режимы защиты и предупреждения, например о выключенной защите входа.

Таблица событий фильтруется полями **Период**, **IP-адрес**, **Учётная запись**, **Тип события**, **Результат**, **Причина / правило**. Кнопки **Выгрузить CSV** и **JSON** выгружают до 50 000 строк, и выгрузка записывается в журнал аудита.

Пароли, токены, гостевые ссылки и cookie в журнал не попадают. Срок хранения и размер задаёт **Хранение журнала безопасности**: 30 дней и 200 000 строк по умолчанию.

Частота записи ограничена, чтобы атака не заполнила журнал. Если часть событий пропущена, сводка покажет предупреждение. Перечень событий: [Справочник: журнал аудита и события](Справочник-журнал-аудита-и-события).

### Управление блокировками

Откройте **Безопасность → Заблокированные адреса**. В таблице видны адрес, причина, неудачи за сутки, начало, окончание, правила и последние события.

- **Посмотреть активность** показывает хронологию адреса за двое суток с объяснением правил.
- **Снять блокировку** снимает только блокировку. Счётчики неудач и история повторов остаются. Если подбор продолжится, адрес будет заблокирован снова и дольше.
- **Заблокировать вручную** требует адрес, срок и причину. Срок выбирается из списка, максимум **7 суток (максимум)**. Бессрочных блокировок нет.

Нельзя заблокировать собственный адрес и доверенные прокси. Общий адрес блокируется только после подтверждения **Всё равно заблокировать**.

Блокировка закрывает вход и анонимные обращения с адреса. Уже вошедшие пользователи не отключаются. Автоматически блокируются только адреса, не похожие на общий NAT.

### Что ещё защищает API

Это работает всегда и не требует настройки:

- права проверяются на сервере на каждом запросе;
- изменяющие запросы проверяются по токену CSRF и заголовку Origin;
- у ключей публичного API свои права, лимиты и списки адресов;
- неверный пароль комнаты при гостевом входе ограничен по частоте;
- создание временной переговорки и гостевой вход защищаются CAPTCHA по настройкам раздела **CAPTCHA**.

## Что получится

- Блок **Что сервер видит сейчас** показывает настоящий адрес клиента.
- Снаружи открыты только нужные порты.
- В **События и блокировки** виден включённый статус защиты, режим CAPTCHA и WAF.
- Изменения правил безопасности записаны в журнал аудита.

## Если не получается

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| Все сотрудники выглядят одним адресом | Прокси с публичным адресом не объявлен доверенным или не передаёт адрес | Вернитесь к шагу 1 и посмотрите предупреждения блока **Что сервер видит сейчас** |
| Администратор потерял доступ после включения подсетей | Его адрес не вошёл в список | Подождите конец пробного срока или выполните `sudo scripts/security-reset.sh` |
| Значок **включено, но не действует** | Пробный срок вышел без подтверждения или список пуст | Добавьте сети и включите ограничение заново |
| Гость или зритель видит **Доступ ограничен** | Его сеть не разрешена | Добавьте сеть. Для внешних участников ограничение по подсетям может не подойти |
| Запрос отклоняется кодом `request_blocked` | Сработало правило WAF | Найдите событие и переведите правило в **Наблюдение** либо добавьте исключение |
| Много ложных срабатываний WAF | Режим **Защита** включён слишком рано | Переключите весь WAF в **Наблюдение**: это действует в течение нескольких секунд на всех экземплярах |
| Заблокирован офис | Общий NAT не объявлен | Снимите блокировку и добавьте адрес в **Адреса и подсети общих выходов** |
| Отказ из-за подсети, причина неясна | Адрес вне списка | Найдите событие **Отказ: адрес вне разрешённых подсетей** по IP-адресу |

Разбор ложного срабатывания всегда начинается с поиска события в **События и блокировки** по IP-адресу или по полю **Причина / правило**.

## Что проверено и что нет

| Что | Статус |
| --- | --- |
| Пороги, обход через cookie и User-Agent, подмена заголовков, срок и одноразовость CAPTCHA, блокировка и её повторы, отказ Redis, общий адрес | Проверено в ограниченном сценарии: автотесты, браузер и приложение на тестовом экземпляре |
| Подсети с автооткатом и аварийной командой, WAF в обоих режимах, журнал и выгрузка | Проверено в ограниченном сценарии: автотесты и браузер на тестовом экземпляре |
| Настоящие внешние прокси и WAF | Требует дополнительного тестирования: заголовки эмулировались |
| Настоящая сеть IPv6 | Требует дополнительного тестирования |
| Тысячи входов в минуту за одним NAT | Требует дополнительного тестирования: предел общего адреса проверен тестом на пороге, а не нагрузкой |
| Защита от целенаправленного распознавания картинки CAPTCHA | Не заявляется |
| Внешний тест на проникновение | Записей о его проведении нет |
