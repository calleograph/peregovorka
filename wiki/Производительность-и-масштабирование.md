# Производительность и масштабирование

*Для кого: администратор, архитектор, руководитель внедрения.*

На этой странице собраны самые важные цифры о нагрузке: что измеряли, на чём, сколько времени и какой получился результат. Другие страницы ссылаются сюда. Подробности об эфирах: [Производительность и требования к серверу для трансляций](Производительность-и-требования-к-серверу-для-трансляций). Планирование сервера: [Системные требования](Системные-требования).

## Главное

- **Вместимость всей системы неизвестна.** Сквозного испытания, где на одном сервере одновременно идут встречи, медиа, распознавание, запись, эфир и протоколы, не было.
- Нагрузочные замеры сделаны разработчиком на одной машине, генератор нагрузки стоял там же, настоящей сети не было. Ни один замер не сделан на отдельном физическом сервере с настоящими пользователями.
- **Числа нельзя переносить с одной службы на всю систему.** 2000 относится только к приложению без медиа, 1500 только к раздаче с узла CDN.
- Сырых результатов прогонов в репозитории нет, остались только итоговые таблицы. Где длительность не записана, это сказано прямо.
- Основной замер приложения сделан на версии 0.32.0 и на текущей версии не повторялся.

## Что на самом деле значит число 2000

**Это замер версии 0.32.0 без звука и видео.** Работали только `backend`, PostgreSQL и Redis, нагрузка шла по HTTP и WebSocket. LiveKit, ASR, TLS, nginx и настоящего LDAP в прогоне не было. Виртуальная машина: 8 vCPU, 14 ГиБ. База в tmpfs, то есть в памяти. Генератор нагрузки стоял на той же машине. **Система целиком на такой аудитории не испытывалась.**

Сверх этого:

- Вход пользователей выполнялся до начала измерений, не больше 100 одновременно. Утренний наплыв входов в цифры не попал.
- Поток реплик в рабочей фазе отсутствовал, запись и файловые хранилища не участвовали.
- Длительность прогона не записана. Приход идёт внутри длительности, поэтому неизвестно, был ли установившийся режим.
- Предел настройки **Максимум участников** 2000 ограничивает вход в комнату. Это не вместимость.

Сервера 8 vCPU и 16 ГБ в этом замере не было. Такая конфигурация для приложения без медиа, ASR и записи получена расчётом и не прогонялась. Статус: расчётная оценка. Обещанием она не является.

### Распознавание речи, ASR

Нагрузка считается **по одновременно говорящим**, а не по встречам. На каждого участника с микрофоном работает свой конвейер, модель одна на всю службу. По умолчанию одновременно идёт одно распознавание (`ASR_MAX_CONCURRENT_INFERENCE=1`), очередь на 64 сегмента (`ASR_QUEUE_SIZE`). Сегменты сверх очереди отбрасываются, их видно в счётчиках. `ASR_CPU_THREADS=0` занимает все ядра и подходит только выделенному серверу.

## Как масштабировать

Сначала наращивайте основной сервер, потом выносите то, что выносится штатно. Адреса внутренних служб заданы в `deployment/compose.yml` жёстко, поэтому перенос остального на другую машину потребует менять поставку.

| Компонент | Можно вынести штатно | Что для этого есть | Чего нет |
|---|---|---|---|
| Раздача эфира | **да** | [Узлы CDN](Узлы-CDN): установка по SSH из администрирования, ключи подписи, переход при отказе. [Сторонний CDN](CDN-для-массовых-мероприятий). Внешние площадки RTMP | служебные запросы зрителей всё равно идут на основной сервер; Safari и iPhone с узлом не проверены |
| Языковая модель | **да, только так** | подключение по API, в том числе к своему серверу в сети организации | встроенной модели нет |
| Хранение записей | **да** | SMB, внешние тома NFS и iSCSI: [Подключение внешних хранилищ](Подключение-внешних-хранилищ) | `live/tmp` остаётся на локальном диске; запись на сетевое хранилище под нагрузкой не проверялась |
| Обратный прокси | **да** | внешний прокси перед портом `web`: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS) | |
| `backend` | только процессы на одном сервере | `BACKEND_WORKERS`. Установщик ставит половину vCPU на `standalone`, четверть на `shared-host`, от 1 до 8. Сессии, события и блокировки уже в Redis | несколько контейнеров за балансировщиком в поставке нет. Два экземпляра проверялись только на чатах на одной машине |
| PostgreSQL | **нет** | контейнер на основном сервере, `POSTGRES_MAX_CONNECTIONS` | `POSTGRES_HOST: postgres` задан в `compose.yml`, из `.env` не меняется |
| Redis | **нет** | контейнер на основном сервере | `REDIS_HOST: redis` задан в `compose.yml`; те же адреса в настройках Egress и SIP |
| LiveKit | **нет** | один узел, `cpu_shares`, параметры ядра | **несколько узлов в поставке нет.** Адрес `ws://livekit:7880` и webhook заданы в `compose.yml`. Одна комната живёт на одном узле |
| Egress | **нет** | профиль `video` на основном сервере | общие тома `live` и `recordings` с `backend` и `web`, адреса `livekit`, `redis`, `web` внутри сети проекта |
| MediaMTX | **нет** | профиль `lowlat` | адрес `mediamtx` внутри сети проекта, nginx обращается к нему напрямую |
| ASR | **нет** | потоки `ASR_CPU_THREADS`, `compose.gpu.yml` на этом же сервере, GPU не проверялся | `ASR_INTERNAL_URL: http://asr:8090` задан в `compose.yml`, том `recordings` общий |
| Резервный сервер | **нет** | восстановление из копии: [Резервное копирование и аварийное восстановление](Резервное-копирование-и-аварийное-восстановление) | автоматического переключения нет |

Что это значит на практике:

- **Больше сотрудников без встреч.** Увеличьте `BACKEND_WORKERS` и ядра. Значение должно уместиться в `POSTGRES_MAX_CONNECTIONS`, иначе `backend` сам уменьшит пулы.
- **Больше зрителей эфира.** Переносите аудиторию на узлы CDN или площадки. Основной сервер останется точкой служебных запросов.
- **Больше участников встреч.** Предел задаёт один сервер с одним узлом LiveKit. Единственный штатный путь: более мощный сервер. Определите предел испытанием.
- **Больше говорящих с распознаванием.** Подбирайте потоки `scripts/asr-bench.sh`. Выделенного сервера ASR в поставке нет.

Под нагрузкой проверены только процессы в одном контейнере, больше всего 6. Несколько контейнеров это другой сценарий, он не проверялся.

## Как система защищает звонки

Защита есть в настройках, но в смешанной нагрузке она не измерялась. Статус всего раздела: требует дополнительного тестирования.

- Тяжёлые фоновые задачи (сведение записи, волновая форма, протокол, карта) идут очередью: `HEAVY_CONCURRENCY`, по умолчанию 2, значение 0 подбирает число по ядрам и памяти. Если сервер занят, идёт встреча, задача ждёт не дольше `HEAVY_MAX_DEFER_SECONDS`, 30 минут.
- Веса процессора: `livekit` и `livekit-egress` по 8192, `asr` 512, остальные 1024. Это вес, а не предел.
- Новый эфир не начнётся, если нагрузка Egress выше **85 %**. Идущие службы эта проверка не останавливает.
- Пулы соединений с базой разделены: запросы пользователей и фоновые задачи. При нехватке соединений приложение отвечает `503` с `Retry-After`, а не `500`.
- Одиночные фоновые задачи выполняет один процесс, ведущий экземпляр. Он определяется арендой в Redis.
- Страница **Администрирование → Обзор → Производительность** показывает занятость пулов, соединения PostgreSQL, отказы 503, нагрузку LiveKit.

## Профили показа экрана и презентации

Профили: «Чёткость» (слайды, текст), «Сбалансированный», «Плавность» (видео), «Экономный 720p» (презентации). Профиль не меняет кодек и число слоёв на лету. Поведение проверено живым сценарием на настоящем LiveKit. Интерфейс презентации проверен на списке из 1000 записей, в одном браузере и без WebRTC: это не нагрузка на 1000 зрителей. Статус нагрузки на 1000 зрителей: требует дополнительного тестирования.

## Что вы можете сделать

- Измерьте время входа по этапам на вашем сервере: **Обзор → Технические показатели**, блок **Время входа в комнату**.
- Подберите `ASR_CPU_THREADS` по задержке: `scripts/asr-bench.sh`.
- Примените рекомендации по ядру: [Справочник: порты и сеть](Справочник-порты-и-сеть).
- Образ `web` собирается с `worker_connections 8192` и `worker_rlimit_nofile 32768`. Внешний прокси перед ним настройте так же: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).
- Проведите испытание по [Матрице нагрузочных испытаний](Матрица-нагрузочных-испытаний) до запуска в работу.
