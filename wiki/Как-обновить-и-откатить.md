# Как обновить и откатить

*Для кого: администратор.*

**Что получится:** сервер работает на новой версии без потери данных, а при сбое возвращается к прежней. Обновляйте вне рабочих часов: на время пересоздания контейнеров идущие встречи прерываются (клиенты переподключаются сами).

## Что нужно заранее

- Помощник обновлений (служба systemd от root) установлен: обычная установка ставит его сама. Проверка: `./scripts/updater.sh status`.
- Свободное место для копии базы и новых образов.
- Копия `.env` с `APP_MASTER_KEY` вне сервера ([Как сделать резервную копию и перенести сервер](Как-сделать-резервную-копию-и-перенести-сервер)).

## Проверить наличие обновления

```bash
cd /opt/peregovorka
./scripts/check-updates.sh      #
```

Скрипт покажет число новых коммитов и список, новые параметры `.env.example` (только имена), наличие миграций и новые версии LiveKit и SDK. В браузере: **Администрирование → Обновления и версии**, кнопка «Что нового» показывает изменения между установленной и доступной версиями.

## Обновить из браузера

1. **Администрирование → Обновления и версии → «Обновить проект»**.
2. Следите за ходом в окне: этапы и построчный вывод; окно переживает перезапуск сервиса.
3. После окончания прочитайте карточку «Отчёт о последнем обновлении» (кнопка «Скачать отчёт»).

Автоматическое обновление (**по умолчанию выключено**): переключатель, время запуска (по умолчанию 00:00 по часовому поясу из «Общих настроек») и «ждать окна без встреч» (по умолчанию 6 часов, допустимо 1–23). Идущие встречи не прерываются: пока они есть, обновление откладывается и проверяется каждые 30 секунд.

## Обновить из терминала

```bash
cd /opt/peregovorka
sudo ./scripts/update.sh --dry-run    #
sudo ./scripts/update.sh              #
```

Ожидаемый результат: итог из четырёх частей — `Update`, `Deployment`, `Health`, `Integrations`. Код возврата: `0` всё в порядке; `3` обновление выполнено, но интеграции требуют внимания (версия установлена, сервисы работают); `1` остановка или сбой.

Проверено 2026-10-29 на тестовом экземпляре (0.50.0 — тег без публикации, код совпадает с выпуском 0.50.1; отличие — решение по версии одного компонента) (профиль `shared-host`, от обычного пользователя, без `sudo`): `update.sh --yes` 0.49.9 → 0.50.0 — 6 минут (сборка backend, asr, web с кэшем слоёв, LiveKit не пересобирался, миграций нет), итог «успешно», `SMOKE TEST ПРОЙДЕН`, отчёт в `DATA_ROOT/updater/report.txt`; `rollback.sh --yes` обратно к 0.49.9 — 37 секунд без пересборки (образы `prev-…`), проверка схемы базы «0051 известна коду»; повторный `update.sh --yes` — 139 секунд. Не проверялось: обновление с миграциями на реальной базе, обновление кнопкой в браузере (помощник не установлен на этом экземпляре).

Скрипт по порядку: определяет текущий коммит, получает новые (с повторами при сетевых сбоях), **сохраняет локальные изменения** в `DATA_ROOT/backups/local-changes-…` и в `git stash` (не применяет их автоматически), сравнивает `.env` с `.env.example` по именам, делает копию `.env.backup-…` (права 600), переходит на целевую версию (`git merge --ff-only` на ветке или `git checkout --detach <тег>` на релизном теге), добавляет только безопасные новые параметры в `.env`, выполняет `preflight`, проверяет модели (ничего не скачивает повторно), собирает образы, делает копию базы, выполняет миграции, запускает сервисы, ждёт healthcheck, выполняет `verify` и `smoke-test`. `.env` не заменяется никогда; `git reset --hard`, удаление `DATA_ROOT` и моделей и пересоздание тома PostgreSQL не выполняются.

Параметры: `--ref SHA|TAG`, `--pull`, `--force-build`, `--no-backup`, `--skip-models`, `--no-nginx`, `--skip-smoke`, `--wait СЕК`, `--stash`, `--skip-netcheck`.

## Канал обновления

| Что стоит на сервере | С чем сравнивается | Как обновляется |
| --- | --- | --- |
| HEAD на релизном теге `vX.Y.Z` (обычная установка) | самый новый тег на GitHub | `git checkout --detach <тег>`; `main` не используется |
| ветка с upstream | upstream | `git merge --ff-only` |
| HEAD на обычном коммите | не определяется | обновление **останавливается без изменений** и подсказывает `./scripts/update.sh --ref <тег|SHA>` |

Вернуть сервер на релизы: `./scripts/update.sh --ref vX.Y.Z`.

## Что происходит при сбое

Обновление транзакционное. До переключения кода проверяются источники сборки (npm, PyPI, PyTorch, GitHub, apt) из тех же базовых образов, в которых идёт сборка; если источник недоступен и зависимости менялись, обновление останавливается **до** переключения кода.

| Сбой | Результат |
| --- | --- |
| сеть при сборке | повтор упавшего сервиса (до 3 попыток); разовый тайм-аут перепроверяется; сборка в сети хоста — только если мост Docker не отвечает и после повторных проверок и Docker позволяет так собирать (иначе остановка до сборки с причиной); готовое не пересобирается |
| миграция | приложение остановлено до копии базы; база **точно** возвращается к копии (текущая сохраняется как `<имя>_failed_<время>`), затем откат кода и образов |
| healthcheck | автоматический возврат базы (если схема менялась) и `rollback.sh` |
| обрыв (Ctrl+C, SSH, перезагрузка) | повторить `./scripts/update.sh`: все этапы идемпотентны |

Если миграция нужна, а копия отключена (`--no-backup`), обновление останавливается до изменения схемы.

## Откатить

```bash
./scripts/rollback.sh                 #
./scripts/rollback.sh --to <SHA>      # к конкретному коммиту
```

**Откат кода не откатывает базу.** `rollback.sh` возвращает код и образы без пересборки. Если после обновления применена новая миграция, скрипт останавливается (код возврата 3): старый образ поверх новой схемы может не запуститься или испортить данные. Варианты: восстановить базу из копии `pre-<sha>` (`scripts/restore.sh <файл>`; данные после копии потеряются), затем откатить код; либо остаться на новой версии. `.env` при откате не восстанавливается автоматически.

## «Исправить автоматически»

Кнопка в «Состоянии системы» и «Обновлениях и версиях» показывает проблему, причину и действие. Помощник выполняет только фиксированный белый список: права каталогов данных, устаревший nginx-site (с `nginx -t` и откатом), параметры ядра (только `standalone`), недостающие программы (только `standalone`), «обновление установлено не полностью», образы с `commit unknown`, отставание базы от программы, давно не выполнявшаяся проверка. Произвольных команд из браузера нет. Если помощника нет:

```bash
cd /opt/peregovorka && sudo ./scripts/updater.sh install --yes
```

## Версии LiveKit и компонентов

LiveKit в production закреплён проверенной версией (`deployment/compat.env`): устаревший тег или `latest` заменяется, более новый конкретный тег остаётся с предупреждением. Каждая новая версия каждого компонента проходит ревизию при выпуске; решения и отсрочки — `docs/DEPENDENCIES.md` и раздел «Версии компонентов» в админке. Не собирайте образы командой `docker compose build` напрямую: используйте `./scripts/rebuild.sh`.

## Типичные ошибки

| Симптом | Что делать |
| --- | --- |
| «Обнаружены локальные изменения» | на сервере ничего не правят вручную: убрать правки или `--stash` |
| «Detached HEAD: укажите --ref…» (старая версия скриптов) | один раз `sudo ./scripts/update.sh --ref vX.Y.Z` |
| «Обновление установлено не полностью» | повторить обновление или нажать «Исправить автоматически» |
| `commit=unknown` | `./scripts/rebuild.sh` или `update.sh --force-build` |
