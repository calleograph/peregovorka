# Как обновить и откатить

*Для кого: администратор сервера.*

## Зачем это нужно

Обновление ставит новую версию без потери данных, а при сбое возвращает прежнюю. Откат нужен, если новая версия не устроила.

## Когда пригодится

- Вышел новый выпуск.
- После обновления что-то работает хуже.
- Обновление прервалось.

## Что потребуется

- Окно без важных встреч: при пересоздании контейнеров идущие встречи прерываются, клиенты подключаются сами.
- Помощник обновлений для кнопки в браузере. Проверка: `sudo scripts/updater.sh status`.
- Свободное место: 15 ГБ на диске Docker и `MIN_FREE_DISK_GB` (30 ГБ), если данные на том же диске. Обновление само чистит кэш, см. [Мало места на диске](Решение-проблем-обновления#мало-места-на-диске).
- Копия `.env` с `APP_MASTER_KEY` вне сервера: [Как сделать резервную копию и перенести сервер](Как-сделать-резервную-копию-и-перенести-сервер).

**`sudo`.** После установки одной командой `.env` принадлежит root, поэтому запускайте `update.sh` и `rollback.sh` через `sudo`. На общем сервере, где `.env` принадлежит вашему пользователю из группы `docker`, `sudo` не нужен.

## Где найти

**Администрирование → Система → Обновления и версии**. В терминале: `scripts/check-updates.sh`, `scripts/update.sh`, `scripts/rollback.sh`.

## Как это сделать

### Проверить наличие обновления

Операция ничего не меняет.

```bash
cd /opt/peregovorka
sudo scripts/check-updates.sh
```

Скрипт покажет новые коммиты, новые параметры `.env.example` (только имена), миграции и новые версии LiveKit и SDK. В браузере кнопка **Что нового** показывает изменения между установленной и доступной версиями.

### Обновить из браузера ⚠

1. Откройте **Обновления и версии** и нажмите **Обновить проект**.
2. Подтвердите. Ход виден в окне: этапы и построчный вывод. Окно можно закрыть, обновление продолжится на сервере.
3. После окончания прочитайте **Отчёт о последнем обновлении**. Кнопка **Скачать отчёт** сохраняет его в файл.

Автоматическое обновление по умолчанию выключено. В разделе задаются переключатель, время запуска (00:00 по часовому поясу из **Общих настроек**) и ожидание окна без встреч (6 часов, допустимо 1–23). Пока идут встречи, запуск откладывается и проверяется каждые 30 секунд.

### Обновить из терминала ⚠

```bash
cd /opt/peregovorka
sudo scripts/update.sh --dry-run    # план, ничего не меняет
sudo scripts/update.sh              # обновление
```

**Последствия.** Встречи прерываются на время перезапуска. Файл `.env` не заменяется: новые безопасные параметры дописываются в конец, остальные перечисляются в итоге. Локальные изменения файлов проекта сохраняются в `DATA_ROOT/backups/local-changes-…` и `git stash` и автоматически не применяются. `git reset --hard`, удаление `DATA_ROOT` и моделей не выполняются.

### Параметры `update.sh`

| Параметр | Когда применять | Последствия |
| --- | --- | --- |
| `--dry-run` | перед обновлением | только план; `git fetch` допустим |
| `--yes` | запуск без терминала | не спрашивает подтверждение |
| `--ref SHA\|TAG` | нужна конкретная версия или возврат на канал выпусков | ставит указанную версию |
| `--force-build` | нужно пересобрать образы, например `commit=unknown` | все образы собираются заново, дольше |
| `--pull` | хотите обновить базовые образы | сборка с нуля и скачивание `postgres` и `redis`, намного дольше. Образы закреплены дайджестом, поэтому пользы от параметра обычно нет |
| `--no-backup` | копия базы только что сделана | копия не создаётся. Если нужна миграция, обновление остановится до изменения схемы |
| `--skip-models` | модель проверять не нужно | проверка моделей пропускается |
| `--skip-preflight` | проверка ошибочно мешает, причину вы понимаете | проблемы места и конфигурации всплывут позже |
| `--skip-netcheck` | проверка источников сборки ложно отказывает | сборка может упасть уже на этапе загрузки |
| `--no-nginx` | сайт nginx ведёте вручную | свой сайт nginx не обновляется |
| `--skip-smoke` | сквозная проверка мешает, например нет доступа к публичному адресу | итог будет неполным, проверьте систему сами |
| `--wait СЕК` | службам нужно больше времени на запуск | ожидание готовности, по умолчанию 180 с |
| `--stash` | совместимость со старыми версиями | сохранение локальных правок теперь выполняется всегда |

### Понять итог

Итог состоит из четырёх частей: `Update`, `Deployment`, `Health`, `Integrations`.

| Код возврата | Значение |
| --- | --- |
| `0` | всё в порядке |
| `3` | версия установлена, службы работают, интеграции требуют внимания |
| `1` | остановка или сбой |

Отчёт лежит в `DATA_ROOT/updater/report.txt`.

### Откатить ⚠

```bash
cd /opt/peregovorka
sudo scripts/rollback.sh --dry-run    # что будет сделано
sudo scripts/rollback.sh              # к предыдущей версии
sudo scripts/rollback.sh --to <SHA>   # к конкретному коммиту
```

**Откат кода не откатывает базу.** Скрипт возвращает код и образы без пересборки. Если после обновления применена новая миграция, скрипт останавливается с кодом 3: старый образ поверх новой схемы может не запуститься или испортить данные.

В этом случае есть два пути:

1. ⛔ Восстановить базу из копии `pre-<sha>` командой `restore.sh`, затем откатить код. Всё, что появилось после копии, будет потеряно.
2. Остаться на новой версии и исправить проблему обновлением.

`.env` при откате автоматически не восстанавливается: путь к копии выводится в конце. Чтобы снова получать обновления, запустите `update.sh`. Он пойдёт к самому новому выпуску.

### Канал обновления

| Что стоит на сервере | С чем сравнивается | Как обновляется |
| --- | --- | --- |
| HEAD на релизном теге `vX.Y.Z`, обычная установка | самый новый тег на GitHub | `git checkout --detach <тег>` |
| ветка с upstream | upstream | `git merge --ff-only` |
| HEAD на обычном коммите | самый новый тег на GitHub | автопочинка переводит сервер на выпуски, локальные коммиты сохраняются |

Вернуть сервер на выпуски: `sudo scripts/update.sh --ref vX.Y.Z`.

### Что происходит при сбое

До переключения кода проверяются источники сборки (npm, PyPI, PyTorch, GitHub, apt). Если источник недоступен, а зависимости менялись, обновление останавливается до переключения.

| Сбой | Результат |
| --- | --- |
| сеть при сборке | повтор упавшей службы, до 3 попыток; готовое не пересобирается |
| миграция | приложение остановлено, база точно возвращается к копии, текущая сохраняется как `<имя>_failed_<время>`, затем откат кода и образов |
| проверка здоровья | возврат базы, если схема менялась, и `rollback.sh` |
| обрыв (Ctrl+C, SSH, перезагрузка) | повторите ту же команду, этапы можно выполнять снова |

### «Исправить автоматически»

Кнопка в **Обзор** и **Обновления и версии** показывает проблему, причину и действие. Помощник выполняет только фиксированный список, произвольных команд из браузера нет. Перечень — [Справочник: скрипты и команды](Справочник-скрипты-и-команды#исправления). Если помощника нет:

```bash
cd /opt/peregovorka && sudo scripts/updater.sh install --yes
```

### Версии компонентов

LiveKit закреплён проверенной версией (`deployment/compat.env`): устаревший тег или `latest` заменяется, более новый конкретный тег остаётся с предупреждением. Решения по версиям — `docs/DEPENDENCIES.md`. Не собирайте образы через `docker compose build`: используйте `sudo scripts/rebuild.sh`.

## Что получится

- `sudo scripts/verify.sh` без `FAIL`, `Smoke test: PASS`.
- `/api/v1/version` и раздел **Обновления и версии** показывают новую версию.
- Пробная встреча проходит.

Обновление с миграциями на настоящей рабочей базе проверяйте сначала на копии.

## Если не получается

| Симптом | Что делать |
| --- | --- |
| «Detached HEAD: укажите --ref…» на старой версии скриптов | один раз `sudo scripts/update.sh --ref vX.Y.Z` |
| «Обновление установлено не полностью» | повторите обновление или **Исправить автоматически** |
| `commit=unknown` | `sudo scripts/rebuild.sh` или `update.sh --force-build` |
| Обновление остановилось | отчёт и [Решение проблем: обновление и службы сервера](Решение-проблем-обновления) |
| `rollback.sh` пишет «Нет сведений о предыдущей версии» | откатывать не к чему или укажите `--to <SHA>` |
