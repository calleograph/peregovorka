# Разбор эксплуатационных случаев

> Относится к версии 0.50.0 · проверено 2026-10-29 · уровень проверки: 1–3 (причины взяты из журнала разработки `HISTORY.md` и сверены с кодом; там, где указано, воспроизведены на стенде разработчика или тестами; на серверах организаций — по сообщениям администраторов) · тип страницы: справочник

Что это: реальные проблемы, которые уже возникали на тестовых и рабочих стендах, — подтверждённая причина, признаки, как диагностировать, как устранить и как убедиться, что работа восстановлена. Каждый случай помечен: **подтверждено** (причина установлена по коду, журналу или воспроизведением) или **предположение** (наиболее вероятная причина, не доказанная). Для кого: администратор и вторая линия поддержки.

Команды выполняются из каталога установки (`APP_ROOT`, например `/opt/peregovorka`); перечень и отметки о проверке — [[Справочник: диагностика и восстановление|Справочник-диагностика-и-восстановление]].

## Сеть, TLS и прокси

### 1. Неполная цепочка сертификатов на reverse proxy

- **Подтверждено** (0.26.0, стенд с Outlook). Браузеры доверяют сайту, а проверки с сервера пишут `unable to get local issuer certificate`: прокси отдаёт только сертификат сайта без промежуточного. Браузеры докачивают недостающий промежуточный сертификат по ссылке AIA, OpenSSL, Python, Outlook на части систем и Android — нет.
- **Признаки:** в браузере на рабочей станции всё открывается; не работает надстройка Outlook, проверка HTTPS в «Администрирование → Интеграции → Microsoft Outlook», вебхуки или приложения на телефонах; `curl https://…` с сервера ругается на сертификат.
- **Диагностика:** `scripts/diag.sh` → `network.txt`, строка «сертификатов в цепочке, которую отдаёт сервер»: 1 при сертификате от промежуточного CA — цепочка неполная. Вручную: `openssl s_client -connect meet.example.org:443 -servername meet.example.org -showcerts </dev/null` — число блоков `BEGIN CERTIFICATE` и `Verify return code`. «Администрирование → Интеграции → Microsoft Outlook» (блок проверки HTTPS) называет состояние `incomplete_chain` и предлагает «Скачать fullchain.pem».
- **Устранение:** на прокси указать файл полной цепочки (сертификат сайта + промежуточные, без корня). Исправляется на прокси, не в Peregovorka.
- **Проверка:** число сертификатов в цепочке ≥ 2, `Verify return code: 0 (ok)`; проверка HTTPS в разделе Microsoft Outlook — без замечаний.
- **Внутренний CA** (рабочие станции доверяют по групповой политике, контейнер — нет) — это не неполная цепочка: укажите CA в `OUTLOOK_CHECK_CA_FILE`, сертификат сайта в доверенные не добавляется.

### 2. «Недопустимый Origin» после переноса сервера или смены адреса

- **Подтверждено** (0.18.2, установка третьей стороны за внешним прокси; 0.38.1 — после переноса). Каждый изменяющий запрос, вход и WebSocket сверяются с `APP_PUBLIC_URL` и `ALLOWED_ORIGINS`. После переноса приложение открывают по новому имени, IP или через SSH-туннель — адрес не совпадает.
- **Признаки:** страница открывается, вход отвечает «Недопустимый Origin» (HTTP 403), WebSocket закрывается кодом 4403; в ответе входа назван адрес, по которому нужно открывать приложение.
- **Диагностика:** `scripts/logs.sh backend --tail 500 | grep "Origin отклонён"` — какой адрес пришёл.
- **Устранение:** открыть по адресу из `APP_PUBLIC_URL`; если нужен второй адрес — добавить его в `ALLOWED_ORIGINS` (формат `https://host[:порт]`, через запятую) и перезапустить backend: `scripts/ctl.sh restart backend`. Опечатка в списке остановит backend с понятным сообщением в журнале. Проверка Origin и CSRF не отключается.
- **Проверка:** вход проходит; в журнале нет новых «Origin отклонён».

### 3. LiveKit за внешним HTTPS-прокси: страница работает, встреча не подключается

- **Подтверждено** (0.1.x — 0.33.0; несколько случаев). Причины, встречавшиеся на практике:
  1. прокси не передаёт WebSocket Upgrade для `/livekit/` (ответ `400`/`426` вместо `101`);
  2. ошибка в nginx образа `web` 0.1.x (самоссылка `map` при непустом `X-Forwarded-Proto`, ответы 499) — исправлено, проверяется при каждой сборке;
  3. адрес сигнализации с самоподписанным сертификатом: через VPN устройства ему не доверяли (0.17.x);
  4. медиа пытались провести через HTTP-прокси — медиа идёт только напрямую на `LIVEKIT_NODE_IP` по UDP/TCP.
- **Признаки:** комната «подключается» бесконечно; плашка подключения висит на этапе «сигнал» (1–3) или «звук и видео» (4).
- **Диагностика:** `scripts/smoke-test.sh` — строки `/rtc/v1` (400 с `join_request` — норма, 404 — устаревший LiveKit) и «WebSocket /rtc» (101 — норма) напрямую, через web и через публичный адрес: виновник — то звено, где код меняется. «Состояние системы» называет этап (DNS, TCP, TLS, авторизация, прокси, маршрут). Проверка идёт **с сервера** и не доказывает доступность с устройства пользователя.
- **Устранение:** требования к прокси — [[Как настроить reverse proxy и HTTPS|Как-настроить-reverse-proxy-и-HTTPS]]; порты медиа открыть напрямую ([[Справочник: порты и сеть|Справочник-порты-и-сеть]]).
- **Проверка:** `smoke-test.sh` — `PASS`; тестовая встреча двух участников с разных сетей, плашка подключения исчезает за несколько секунд.

### 4. Разные ответы API изнутри сервера и снаружи

- **Подтверждено** (0.26.0). Сервер обращается к собственному публичному имени и получает другой ответ или `ConnectError`: split DNS (внутри имя указывает на другой адрес), hairpin NAT не настроен, по имени отвечает другой экземпляр. Проверки «с сервера» тогда ложно сообщают о недоступности, а пользователи работают.
- **Признаки:** проверки в администрировании (Outlook, LiveKit, публичный адрес) пишут «недоступно», хотя с рабочей станции всё открывается; версия на странице «Система → Обновления и версии» не совпадает с тем, что видят пользователи.
- **Диагностика:** `scripts/diag.sh` → `network.txt`: ответ `/api/v1/version` локально (`127.0.0.1:WEB_PORT`) и через публичный адрес — версия, commit и IP, на который ушёл запрос; `getent ahosts <имя>` на сервере и `nslookup <имя>` на рабочей станции.
- **Устранение:** согласовать DNS (внутренняя зона или запись в `/etc/hosts` сервера, по решению сетевого администратора); если по имени отвечает другой экземпляр — исправить маршрутизацию прокси. Режим HTTPS для проверок определяется настройками установки, а не заголовком запроса администратора.
- **Проверка:** версия и commit локально и через публичный адрес совпадают.

### 5. Звонок рвётся через VPN (`ERR_CONNECTION_RESET`)

- **Подтверждено** (0.1.x): причина — Path MTU на VPN-адаптере, не программа. После `MTU=1250` на адаптере всё заработало.
- **Признаки:** только у пользователей VPN; в «Диагностике клиентов» — сброс на сетевом уровне.
- **Устранение:** уменьшить MTU VPN-адаптера (Windows: `netsh interface ipv4 set subinterface "<адаптер>" mtu=1250 store=persistent`) — решение сетевого администратора.
- **Проверка:** встреча через VPN без обрывов 10 минут.

## Почта и Exchange

### 6. SMTP: «нет соединения», хотя сервер отвечает

- **Подтверждено** (0.49.5). Сервер предлагал только неподдерживаемый способ входа; ошибка `No suitable authentication method found` из библиотеки классифицировалась как сетевая. Microsoft Exchange часто предлагает `AUTH LOGIN` только **после** STARTTLS, а без TLS — только NTLM.
- **Признаки:** «Почта: сервер SMTP → Проверить соединение» (до 0.49.5) писала «нет соединения»; письма не уходят.
- **Диагностика:** «Администрирование → Интеграции → Почта: сервер SMTP → Проверить соединение» показывает способы входа до и после STARTTLS и ответ сервера.
- **Устранение:** включить STARTTLS; выбрать способ входа: «Пароль (LOGIN/PLAIN)» или «Windows NTLM (Microsoft Exchange)» (только NTLMv2 и только по TLS). Подробно — [[Как настроить хранилища и почту|Как-настроить-хранилища-и-почту]].
- **Проверка:** тестовое письмо доставлено; в журнале отправки — успех.

### 7. Календари Exchange (EWS) и надстройка Outlook

- **Подтверждено:** EWS до 0.27.0 поддерживал только Basic — при Windows-аутентификации ошибка авторизации (исправлено: NTLM, Kerberos, автоопределение). Надстройка в классическом Outlook 2016/2019 с Exchange 2019 показывала «Ошибка надстройки»: панель работает во встроенном IE 11, без `X-UA-Compatible` страница открывалась в режиме IE 7 (исправлено в 0.32.1). Успешный вход в EWS не даёт прав на календари организаторов — нужны права «Рецензент» или ограниченная имперсонация.
- **Не проверено:** работа с настоящим Exchange и Outlook — только тестами и живыми сценариями в Chromium.
- **Диагностика и устранение:** [[Диагностика типичных ошибок Outlook|Outlook-Диагностика-типичных-ошибок]]; события надстройки в «Администрирование → Интеграции → Microsoft Outlook» (маячки «панель открыта»).

## Сборка, обновление, откат

### 8. Сборка падает: недоступен или медленный npmjs.org

- **Подтверждено** (0.33.0): `npm ci` падал с `ETIMEDOUT`: с хоста загрузка останавливалась, Node.js 20+ при отсутствии IPv6 тратил время на попытки IPv6; ошибка не распознавалась как сетевая, повторов не было. Исправлено: проверка источников до переключения кода, повторы, `ipv4first`.
- **Подтверждено** (0.49.4): после одного тайм-аута через мост Docker установщик выбирал сборку в сети хоста, а BuildKit без разрешения `network.host` падал с `additional privileges requested`. Исправлено: повторные проверки моста, проверка возможности сборки в сети хоста до её выбора.
- **Признаки:** обновление или установка останавливаются на этапе `build` с указанием источника (npm, PyPI, PyTorch, GitHub, apt).
- **Диагностика:** вывод `update.sh` (этап и источник); `python3 scripts/netprobe.py` проверяет DNS, TCP, прокси, TLS и загрузку до конкретного файла.
- **Устранение:** восстановить доступ к источнику или настроить прокси для Docker; повторить ту же команду — готовые этапы пропускаются. Сборка в сети хоста выбирается автоматически только при доказанной необходимости.
- **Проверка:** этап `build` — `[ok]`; `scripts/verify.sh` — все проверки `PASS`.

### 9. Неудачное обновление и откат на рабочую версию

- **Подтверждено** (0.18.2): установка по тегу (отсоединённый HEAD) не обновлялась — «Detached HEAD», `TARGET: unbound variable`. Исправлено: канал обновления по релизным тегам; старым скриптам один раз нужен `update.sh --ref vX.Y.Z`.
- **Подтверждено** (0.32.0): «Обнаружены локальные изменения» — файл скрипта правили вручную на сервере. Исправлено: изменения сохраняются (патч, архив, stash) и обновление продолжается; старым скриптам один раз нужен `--stash`.
- **Подтверждено** (0.33.0, тестами со сбоями): сбой миграции или healthcheck после обновления — база точно возвращается к копии, снятой при остановленном приложении (текущая сохраняется как `<имя>_failed_<время>`), затем `rollback.sh`.
- **Признаки:** обновление завершилось ошибкой; версия в интерфейсе прежняя или сервис нездоров.
- **Диагностика:** `$DATA_ROOT/updater/report.txt` (итог по этапам), `scripts/status.sh`, `scripts/verify.sh`.
- **Устранение:** [[Как обновить и откатить|Как-обновить-и-откатить]]: повторить `update.sh` (идемпотентен) или `rollback.sh`. **Откат кода не откатывает базу**: при новой миграции `rollback.sh` останавливается (код 3).
- **Проверка:** `status.sh` — все сервисы `healthy`; `verify.sh` — `PASS`; тестовая встреча.

### 10. BuildKit неисправен на сервере

- **Подтверждено** (стенд разработчика 2026-10-29 и ранее): `BuildKit is enabled but the buildx component is missing or broken` или ошибки containerd при экспорте. Установщик и `update.sh` сами переходят на классический сборщик (`[warn] FALLBACK … legacy builder`). Это неисправность Docker, не проекта.
- **Устранение:** не требуется для работы; при желании поставить пакет `docker-buildx-plugin` (решение администратора сервера).

## Ресурсы сервера

### 11. Исчерпание соединений PostgreSQL и ответы 500 под нагрузкой

- **Подтверждено** (0.25.0 → исправлено в 0.27.0): фоновые задачи держали соединение с базой во время обращения к модели, гонка при одновременном создании встречи. Теперь при нехватке соединений — `503` с `Retry-After`, а не `500`.
- **Диагностика:** «Администрирование → Обзор → Производительность» (раздел базы данных) (занятость пулов, `idle in transaction`); `scripts/logs.sh backend | grep -i pool`.
- **Устранение:** `POSTGRES_MAX_CONNECTIONS ≥ BACKEND_WORKERS × (пулы) + 10` (формула в `.env.example`), затем `scripts/ctl.sh restart backend`. Подбор — [[Производительность и масштабирование|Производительность-и-масштабирование]].

### 12. Память, swap, диск, Docker

- **Подтверждено** по коду и стенду: нехватка места при сборке — `update.sh` сам освобождает кэш сборки и старые образы **своего** проекта (кроме работающих и предыдущих); `preflight.sh` не начинает установку при свободном месте меньше `MIN_FREE_DISK_GB` (30 ГБ). Без swap нехватка памяти завершает процесс в контейнере (OOM) — контейнер перезапускается сам (`restart: unless-stopped`), идущие встречи этого компонента прерываются.
- **Предположение:** зависания при активной локальной языковой модели на сервере 8 ГБ без swap — модель занимает до `LLM_LOCAL_MEM` (3,5 ГБ); не воспроизводилось.
- **Диагностика:** `scripts/diag.sh` → `resources.txt` (swap, OOM в журнале ядра, `docker stats`, перезапуски и `oom=true` у контейнеров, inode, размеры каталогов данных).
- **Устранение:** освободить место (старые выгрузки и копии в `DATA_ROOT/backups`, `docker image prune` **не** выполнять для чужих образов); уменьшить `LLM_LOCAL_THREADS`/`LLM_LOCAL_MEM` или отключить локальную модель; добавить swap или память.
- **Проверка:** свободно больше 30 ГБ; в `resources.txt` нет новых OOM; `status.sh` — `healthy`.

### 13. Ограничение числа участников

- **Подтверждено** (0.19.0): предел 200 был зашит в коде, теперь настройка комнаты 1–2000. Сервер не пускает участника сверх «Максимум участников»: «В комнате нет свободных мест» (HTTP 409, код `room_full`); гости считаются вместе с сотрудниками. 2000 — граница настройки, а не гарантия: вместимость определяют процессор и сеть узла LiveKit (замеры — [[Производительность и масштабирование|Производительность-и-масштабирование]]).

## Перенос и сохранность данных

### 14. Перенос на другой сервер: модели, права, конфигурация, записи

- **Подтверждено** (0.38.1, установка третьей стороны на чистой Ubuntu 24.04): модель распознавания не готовилась (исправлено: этап `models`); каталог моделей, скопированный другим пользователем или с umask 077, недоступен контейнеру ASR (uid 10001) — `PermissionError` на `/models/...` (исправлено: установщик выставляет права 755/644 и проверяет чтение до запуска).
- **Подтверждено** (0.40.0): после переноса файлы записей и материалов скопированы, а в приложении встреч нет — база не переносилась или переносилась отдельно от файлов. Добавлен паспорт встречи `manifest.json` и «Восстановление материалов».
- **Ловушка проверки на стенде 2026-10-29:** `install.sh --models-from` ждёт каталог, где лежат **сами файлы** модели (`…/models/gigaam`), а не родительский.
- **Порядок без потери данных:** [[Резервное копирование и аварийное восстановление|Резервное-копирование-и-аварийное-восстановление]] (раздел «Перенос на другой сервер»).
- **Проверка:** количество встреч и записей в «Истории» до и после совпадает; запись открывается в плеере; протокол скачивается.

## Встреча, звук, видео

### 15. Нет микрофона, камеры или показа экрана

- **Подтверждено:** без HTTPS браузер не даёт микрофон и экран; «Устройство занято» — микрофон занят другой программой (в том числе монопольно в Windows) или сбой драйвера; LiveKit при пропаже устройства делал одну попытку и молча выключал микрофон — с 0.49.9 страница сообщает об этом и сама пробует включить микрофон снова.
- **Открытый вопрос:** в приложении для Windows сбои микрофона встречаются чаще, чем в Edge; причина **не установлена** ([[Известные проблемы|Известные-проблемы]]).
- **Диагностика:** «Устройства → Для поддержки: подробная проверка микрофона» (отчёт копируется); «Администрирование → Обзор → Диагностика клиентов»; для приложения Windows — «Настройки → Диагностика → Сохранить отчёт».
- **Устранение:** [[Руководство технической поддержки|Руководство-технической-поддержки]], сценарий «Нет звука или видео».

### 16. Нет стенограммы или протокола

- **Подтверждено** (0.24.1 → 0.24.2): контейнер ASR был `healthy`, но стенограмма пустая — в образе не было `onnxruntime` для детектора речи; исключение терялось. Теперь самопроверка образа при сборке и старте, `/readyz` ASR отвечает 503 при сбое конвейера, «модель готова» отличается от «транскрибация готова».
- **Подтверждено** (0.48.4): «пустой ответ» внешней модели — модель тратила лимит ответа на рассуждения; исправлено настройкой «Рассуждения модели» (по умолчанию выключены) и определением окна контекста.
- **Подтверждено:** протокол не создаётся для встречи без реплик, чата и схемы (событие `protocol_skipped`) — это не сбой.
- **Диагностика:** `scripts/logs.sh asr --tail 300`; `/api/v1/health/ready` (поле `asr`); причина в строке документа в «Истории»; журнал событий, категория `llm`.
- **Устранение:** [[Как настроить языковые модели|Как-настроить-языковые-модели]]; права и наличие модели — `sudo scripts/models.sh`.
