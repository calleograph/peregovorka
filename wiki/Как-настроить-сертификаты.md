# Как настроить сертификаты

*Для кого: администратор сервера.*

## Зачем это нужно

Браузер даёт сайту микрофон и экран только по HTTPS. Сертификат подтверждает, что пользователь пришёл на ваш сервер. Peregovorka использует сертификаты в трёх местах, и путать их нельзя:

| Какой сертификат | Для чего | Где настраивается |
| --- | --- | --- |
| Сертификат сайта | HTTPS для пользователей и звонков | nginx хоста или ваш внешний прокси |
| Сертификаты центров (CA) | доверие к серверам каталога и почты | **Интеграции → Каталог: сертификаты (CA)** |
| CA для проверок Outlook | сервер доверяет внутреннему центру при проверке своего адреса | файл `DATA_ROOT/ca/outlook-ca.pem` |

Подпись приложения для Windows — отдельная тема: [Как развернуть приложение Windows в организации](Как-развернуть-приложение-Windows-в-организации).

## Когда пригодится

- После установки стоит самоподписанный сертификат.
- Срок сертификата подходит к концу.
- Сменилось имя сервера.
- Подключаете LDAPS или почту с внутренним центром.

## Что потребуется

- DNS-имя сервера. Проверка: `getent hosts meet.example.org`.
- Файл сертификата с **полной цепочкой**: сертификат сайта и промежуточные, без корневого.
- Закрытый ключ, доступный только root.
- `sudo` на сервере.

Встроенного выпуска Let's Encrypt на основном сервере нет. Сертификат получаете вы, продление — тоже ваша задача.

## Где найти

- Сертификат сайта на nginx хоста: параметры `NGINX_TLS_CERT` и `NGINX_TLS_KEY` в `.env`.
- Самоподписанный сертификат установщика: `DATA_ROOT/tls/server.crt` и `server.key`, срок 825 дней.
- Сертификаты центров: **Администрирование → Интеграции → Каталог: сертификаты (CA)**.
- Требования к внешнему прокси: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).

## Как это сделать

### Установить свой сертификат на nginx хоста ⚠

**Назначение.** Заменить самоподписанный сертификат или перейти на доменное имя.

**Условия.** Запись DNS уже указывает на сервер. Если меняется адрес, пользователи со старым адресом перестанут входить.

**Порядок.**

1. Положите файлы на сервер и закройте ключ.

   ```bash
   sudo mkdir -p /etc/ssl/peregovorka
   sudo cp fullchain.pem privkey.pem /etc/ssl/peregovorka/
   sudo chmod 600 /etc/ssl/peregovorka/privkey.pem
   ```

2. Проверьте, что ключ подходит к сертификату: хеши должны совпасть.

   ```bash
   sudo openssl x509 -noout -pubkey -in /etc/ssl/peregovorka/fullchain.pem | sha256sum
   sudo openssl pkey -pubout -in /etc/ssl/peregovorka/privkey.pem | sha256sum
   ```

3. Укажите пути в `/opt/peregovorka/.env` (`sudo nano /opt/peregovorka/.env`). Если меняется адрес, задайте и его. Изменяйте строки, которые уже есть в файле: дописанная в конец копия строки приведёт к тому, что скрипты и контейнеры прочитают разные значения.

   ```bash
   NGINX_TLS_CERT=/etc/ssl/peregovorka/fullchain.pem
   NGINX_TLS_KEY=/etc/ssl/peregovorka/privkey.pem
   APP_PUBLIC_URL=https://meet.example.org
   LIVEKIT_PUBLIC_URL=wss://meet.example.org/livekit
   NGINX_SERVER_NAME=meet.example.org
   ```

4. Обновите сайт nginx. Если адрес не менялся, первая команда не нужна.

   ```bash
   cd /opt/peregovorka
   sudo scripts/ctl.sh start
   sudo scripts/install.sh --profile standalone --from nginx
   ```

   На общем сервере вместо `standalone` укажите `shared-host`. Вторая команда выполняет и следующие этапы: итоговую проверку и проверку помощника обновлений. Сайт nginx создаётся заново и проверяется `nginx -t`. В конце скрипт сообщит, что администратор уже создан: пароль при этом не меняется.

**Последствия.** `ctl.sh start` пересоздаёт службы, которые используют адрес. Открытые страницы переподключаются. Старый адрес перестаёт работать с ошибкой «Недопустимый Origin».

### Продлить сертификат ⚠

Если пути не менялись, замените файлы и перечитайте их:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Новые соединения получают новый сертификат. Контейнеры перезапускать не нужно.

### Сертификат на внешнем прокси

Если TLS завершает прокси организации, установите сертификат там. В Peregovorka ничего менять не нужно. Проверьте `APP_PUBLIC_URL` и требования к заголовкам: [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).

### Добавить сертификат центра для LDAPS и почты

1. Откройте **Интеграции → Каталог: сертификаты (CA)**.
2. Нажмите **Добавить сертификат** и выберите файл `.pem`, `.crt` или `.cer`, до 256 КБ.
3. Нажмите **Разобрать сертификат** и проверьте сведения.
4. Нажмите **Добавить в набор**.

Добавляйте корневой и промежуточные сертификаты центра. Сертификат самого сервера интерфейс пометит предупреждением. Этот набор используют подключения LDAPS и проверка почтового сервера.

### Доверять внутреннему центру в проверках Outlook

Если сертификат сайта выдан центром организации, рабочие станции могут ему доверять, а контейнер `backend` нет. Положите цепочку в файл на сервере:

```bash
sudo cp corp-ca.pem /srv/peregovorka-data/ca/outlook-ca.pem
sudo chown 10001:10001 /srv/peregovorka-data/ca/outlook-ca.pem
```

Другой файл можно указать переменной `OUTLOOK_CHECK_CA_FILE` в `.env`. Это путь внутри контейнера `backend`, поэтому файл должен лежать в подключённом каталоге.

### Что происходит с сертификатом при восстановлении

Каталог `DATA_ROOT/tls` входит в архив файлов `backup.sh --with-recordings` и `--full`. Команда `restore.sh --files` заменяет его файлами старого сервера, а прежний каталог откладывает как `tls.before-restore-<время>`. Если у нового сервера другое имя, после восстановления сертификат не подойдёт: поставьте нужный файл по этой странице и перезагрузите nginx.

В архив не входят сертификат внешнего прокси и свой сертификат, который лежит вне `DATA_ROOT/tls`, например в `/etc/ssl/peregovorka`. Храните их копии отдельно.

## Что получится

Проверка:

```bash
openssl s_client -connect meet.example.org:443 -servername meet.example.org </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -enddate
sudo scripts/smoke-test.sh
```

- Команда показывает ваше имя, ваш центр и срок в будущем.
- Строка `TLS (публичный URL)` в `smoke-test.sh` — `OK`.
- Браузер открывает сайт без предупреждения, звонок подключается.

## Если не получается

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| `nginx -t` не проходит | неверный путь или ключ не от этого сертификата | проверьте пути и совпадение хешей |
| Браузер работает, а Outlook, телефоны и Python пишут об ошибке | неполная цепочка | укажите файл с промежуточными сертификатами |
| Звонки не подключаются на части устройств | устройство не доверяет сертификату | поставьте корневой сертификат на устройство или возьмите сертификат доверенного центра |
| Вход отвечает 403 | адрес не совпал с `APP_PUBLIC_URL` | проверьте `.env`, примените правку |
| LDAPS: ошибка TLS | нет CA или имя сервера не совпало | добавьте CA, проверьте подключение в разделе каталога |

Разбор — [Решение проблем: HTTPS и обратный прокси](Решение-проблем-HTTPS-и-прокси). Цепочку показывает `sudo scripts/diag.sh`, файл `network.txt`.
