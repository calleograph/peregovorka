# Установка на чистый сервер

*Для кого: администратор, у которого сервер отдан под Peregovorka (профиль `standalone`).*

**Что получится:** рабочая система: проверенные сервисы, HTTPS на вашем имени, звонки из нужных сетей, интеграции, резервные копии и порядок обновления. Шаги идут в том порядке, в каком их надо делать, и у каждого есть проверка результата.

## Какой у вас случай

| Случай | Что читать |
| --- | --- |
| Новый сервер под Peregovorka | эта страница, сверху вниз |
| На сервере уже работают другие приложения | [Установка на общий сервер](Установка-на-общий-сервер) |
| Система уже стоит, нужна новая версия | [Обновление существующей системы](#обновление-существующей-системы) |
| Сервер потерян или база повреждена | [Восстановление из резервной копии](#восстановление-из-резервной-копии) |
| Нужно только попробовать за час | [Быстрый старт](Быстрый-старт) |

## Шаг 1. Требования к серверу

Минимум: Ubuntu 22.04 или новее либо Debian 12 или новее, x86_64, 4 vCPU, 8 ГБ памяти, 30 ГБ свободного места, права `sudo`. Подробно — [Системные требования](Системные-требования).

```bash
. /etc/os-release; echo "$PRETTY_NAME"; uname -m; nproc
free -g | awk '/Mem:/ {print $2 " ГБ памяти"}'
df -h /srv
```

**Ожидаемый результат:** система из списка, `x86_64`, не меньше 4 ядер и 8 ГБ, в строке диска не меньше 30 ГБ в столбце `Avail`.

**Типовая ошибка.** На диске меньше 30 ГБ установка остановится на этапе `preflight`. Подключите диск и смонтируйте его до установки, например в `/srv`.

## Шаг 2. Подготовка операционной системы

Установщик не запускает `apt upgrade` и не перезагружает сервер, поэтому обновите систему сами.

```bash
sudo apt update && sudo apt upgrade -y
timedatectl | grep -E "synchronized|Time zone"
sudo ss -ltnp | grep -E ':443 ' || echo "порт 443 свободен"
```

**Ожидаемый результат:** `System clock synchronized: yes`, порт 443 свободен. Неверное время ломает TLS, вход и коды второго фактора.

Если записей будет много, заранее смонтируйте отдельный диск под каталог данных и укажите его при установке через `--data`. Каталог должен быть локальным путём Linux; сетевое хранилище подключается отдельно на шаге 12.

**Типовая ошибка.** Порт 443 занят другим сайтом: сервер не чистый, используйте [Установку на общий сервер](Установка-на-общий-сервер) или выберите другой порт через `--https-port`.

## Шаг 3. Проверка сетевой доступности

Для установки серверу нужны исходящие соединения.

```bash
for u in https://github.com https://registry-1.docker.io/v2/ https://pypi.org \
         https://registry.npmjs.org https://download.docker.com \
         https://download.pytorch.org https://cdn.chatwm.opensmodel.sberdevices.ru/GigaAM/; do
  printf '%s ' "$u"; curl -sS -o /dev/null -m 15 -w '%{http_code}\n' "$u" || true
done
```

**Ожидаемый результат:** у каждого адреса есть трёхзначный код, в том числе `401`, `403` или `404`. Важен сам ответ, а не его значение. Сообщение `curl: (6)`, `curl: (7)` или `curl: (28)` означает, что адрес недоступен.

**Типовые ошибки.**

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `curl: (6)` | не работает DNS сервера | проверьте `resolvectl status`, настройте DNS |
| `curl: (7)` или `(28)` | закрыто межсетевым экраном | откройте исходящий 443/tcp до этих адресов ([полный перечень](Архитектура-Порты-и-сервисы)) |
| Недоступен только источник модели | закрытая сеть | подготовьте модель заранее ([Закрытая сеть](#закрытая-сеть)) |

## Шаг 4. Получение проекта и подготовка конфигурации

Скачайте установщик. Сам проект он получит на шаге 5.

```bash
wget -O install.sh https://raw.githubusercontent.com/calleograph/peregovorka/main/install.sh
chmod +x install.sh
./install.sh --help
```

**Ожидаемый результат:** выводится справка с параметрами.

Файл `.env` руками готовить не нужно: установщик создаёт его сам, со случайными секретами и правами 600. Заранее решите только адрес. Если DNS-имя уже есть, укажите его сразу: так не придётся менять адрес на шаге 9.

| Параметр | Значение |
| --- | --- |
| `--host ИМЯ_ИЛИ_IP` | адрес, по которому сервер открывают в браузере; по умолчанию основной IP сервера |
| `--https-port N` | порт HTTPS, по умолчанию 443 |
| `--dir КАТАЛОГ` | куда установить проект, по умолчанию `/opt/peregovorka` |
| `--data КАТАЛОГ` | каталог данных, по умолчанию `/srv/peregovorka-data` |
| `--ref ВЕРСИЯ` | версия или ветка; по умолчанию последний выпуск, `main` — свежая разработка |
| `--skip-models` | не скачивать модель распознавания сейчас |
| `--yes` | не задавать вопросов |

## Шаги 5–7. Установка, настройка и запуск

Эти три шага выполняет одна команда. Обычно она работает 10–30 минут.

```bash
sudo ./install.sh --host meet.example.org
```

| Шаг | Что делает установщик |
| --- | --- |
| 5. Компоненты | проверяет систему, ставит Docker, Compose, Buildx, nginx и утилиты командой `apt install`; скачивает проект в `/opt/peregovorka` |
| 6. Настройка | создаёт `.env` и самоподписанный сертификат, каталоги данных, параметры ядра для WebRTC в `/etc/sysctl.d/99-peregovorka.conf`; подбирает свободные порты; определяет публичный адрес для звонков; скачивает модель GigaAM |
| 7. Запуск | собирает образы, запускает PostgreSQL и Redis, выполняет миграции, запускает остальные сервисы, включает nginx последним; проверяет систему; ставит помощника обновлений; создаёт локального администратора |

**Ожидаемый результат:** блок «УСТАНОВКА ЗАВЕРШЕНА» и «ПЕРВИЧНЫЙ ВХОД» с адресом, логином `admin` и первичным паролем. Пароль показывается один раз и только в терминале.

Откройте адрес в браузере именно с `https://`. Самоподписанный сертификат вызовет предупреждение: подтвердите переход. Войдите и задайте новый пароль: не короче 12 символов, не менее двух видов символов, без имени пользователя.

Установщик ничего не меняет в межсетевом экране: порты открываются на шаге 10.

**Если установка прервалась.** Запустите ту же команду ещё раз: завершённые этапы пропускаются, данные не удаляются. Сбой печатается строкой вида `FAIL stage=build service=backend subsystem=docker-buildkit`, а при падении сервиса показываются конец его журнала, вероятная причина и действие.

Этапы установщика: `prerequisites → preflight → dirs → kernel → models → pull → build → database → migrations → services → healthcheck → nginx → firewall → verify → helper → report`. Продолжить с нужного этапа можно так:

```bash
cd /opt/peregovorka
sudo scripts/install.sh --profile standalone --from ЭТАП
```

Флаг `--force-build` пересобирает образы, `--dry-run` показывает план и ничего не меняет.

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `FAIL stage=preflight` | мало места или памяти, занят порт | прочитать строку `FAIL` выше: она называет проблему |
| `FAIL stage=models` | недоступен источник модели | запустить повторно; докачка продолжится. В закрытой сети — [подготовить модель из каталога](#закрытая-сеть) |
| `FAIL … subsystem=registry-network` | недоступен Docker Hub или зеркало | повторить, скачанное сохраняется |
| `FAIL … subsystem=docker-buildkit` | сбой BuildKit или containerd | установщик сам переходит на старый сборщик; если не помогло — [Диагностика](Диагностика) |
| Пароль не показан | проверка нашла ошибку | установка не завершена; прочитать ошибку, исправить и запустить снова |

Потеряли пароль: `sudo /opt/peregovorka/scripts/admin-reset.sh`.

### Закрытая сеть

Скачайте файлы `v3_e2e_rnnt.ckpt` и `v3_e2e_rnnt_tokenizer.model` на другом компьютере, перенесите на сервер и подготовьте модель из каталога:

```bash
cd /opt/peregovorka
sudo scripts/install.sh --profile standalone --from models --models-from /путь/к/gigaam
```

Готовой считается только пара из двух файлов. Загрузка идёт с докачкой, размер сверяется с `Content-Length`, а страница HTML вместо файла отвергается и сохраняется как `*.failed`. Контрольные суммы по умолчанию не сверяются, потому что файлы источника могут обновляться; при необходимости задайте `GIGAAM_CKPT_SHA256` и `GIGAAM_TOKENIZER_SHA256` в `.env`.

## Шаг 8. Проверка состояния системы

```bash
cd /opt/peregovorka
sudo ./scripts/status.sh
sudo ./scripts/verify.sh
sudo ./scripts/smoke-test.sh
```

**Ожидаемый результат:**

| Команда | Успех |
| --- | --- |
| `status.sh` | все сервисы `running`, `health=healthy`, строка «Все сервисы работают» |
| `verify.sh` | нет `FAIL`, строка `Peregovorka deployment verified` |
| `smoke-test.sh` | итоговая строка `Smoke test: PASS` |

В браузере откройте **Администрирование → Обзор → Состояние системы**: PostgreSQL, Redis, LiveKit и ASR зелёные. ASR становится зелёным через 1–2 минуты после запуска.

На этом шаге допустимы предупреждения про TLS: сертификат пока самоподписанный. Код возврата `smoke-test.sh`: `0` — ошибок нет, `3` — система работает, но есть проблема внешнего окружения (каталог, прокси, сертификат), `1` — сбой самой системы.

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Сервис `unhealthy` | ошибка при запуске | `./scripts/logs.sh backend --tail 200`, замените имя сервиса |
| ASR не готов | загружается или нет модели | подождать 2 минуты; затем `sudo scripts/models.sh` |
| «Недопустимый Origin» при входе | открыт не адрес из `APP_PUBLIC_URL` | [Диагностика](Диагностика) |

## Шаг 9. Домен и TLS

Браузер даёт микрофон и экран только по HTTPS. С самоподписанным сертификатом звонки подключаются лишь на устройствах, которые ему доверяют, поэтому для работы нужен сертификат доверенного центра.

1. Создайте запись DNS и проверьте её.

   ```bash
   getent hosts meet.example.org
   ```

   **Ожидаемый результат:** адрес вашего сервера или внешнего прокси.

2. Положите на сервер сертификат с полной цепочкой и закрытый ключ. Ключ доступен только root (`chmod 600`).

3. Укажите их в `/opt/peregovorka/.env`. Если при установке был задан IP, смените и адрес.

   ```bash
   APP_PUBLIC_URL=https://meet.example.org
   LIVEKIT_PUBLIC_URL=wss://meet.example.org/livekit
   NGINX_SERVER_NAME=meet.example.org
   NGINX_TLS_CERT=/etc/ssl/peregovorka/fullchain.pem
   NGINX_TLS_KEY=/etc/ssl/peregovorka/privkey.pem
   ```

4. Примените изменения. Первая команда пересоздаёт контейнеры по новому `.env`, вторая обновляет сайт nginx.

   ```bash
   cd /opt/peregovorka
   sudo scripts/ctl.sh start backend web
   sudo scripts/install.sh --profile standalone --from nginx
   ```

5. Проверьте сертификат.

   ```bash
   openssl s_client -connect meet.example.org:443 -servername meet.example.org </dev/null 2>/dev/null \
     | openssl x509 -noout -subject -issuer -enddate
   sudo ./scripts/smoke-test.sh
   ```

   **Ожидаемый результат:** ваше имя, ваш центр сертификации, срок в будущем; строка `TLS (публичный URL)` — `OK`.

Новый сертификат применяется командой `sudo nginx -t && sudo systemctl reload nginx`. Встроенного выпуска Let's Encrypt на основном сервере нет. Порт 80 установщик не открывает, поэтому адрес вводят с `https://`.

Если TLS завершает внешний прокси, настройте его по странице [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS): там же требования к WebSocket и заголовкам.

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `nginx -t` не проходит | неверный путь или ключ не от этого сертификата | проверить пути в `.env` и `openssl x509 -noout -pubkey` |
| Браузер пишет о неполной цепочке | в файле нет промежуточных сертификатов | собрать `fullchain` |
| Страница открывается, вход отвечает 403 | адрес не совпал с `APP_PUBLIC_URL` | проверить `.env` и повторить пункт 4 |

## Шаг 10. LiveKit и медиасоединения

Страница идёт через 443, а звук и видео — напрямую на сервер, минуя HTTP-прокси. Это самая частая причина ситуации «страница открылась, а звука нет».

1. Посмотрите свои порты. Установщик берёт 17881/tcp и 17882/udp, а если они заняты, выбирает другие.

   ```bash
   cd /opt/peregovorka
   sudo grep -E '^LIVEKIT_(TCP|UDP)_PORT=|^LIVEKIT_NODE_IP=|^LIVEKIT_PUBLIC_IP=' .env
   ```

2. Откройте порты на всех межсетевых экранах по пути к серверу. Для `ufw`:

   ```bash
   sudo ufw allow 443/tcp
   sudo ufw allow 17881/tcp
   sudo ufw allow 17882/udp
   ```

3. Если сервер за NAT, пробросьте те же порты без смены номера. Точные правила напечатает проверка.

   ```bash
   sudo scripts/medianet.sh check
   ```

   **Ожидаемый результат:** порты слушаются, межсетевой экран не мешает, показан публичный адрес и готовые правила проброса. UDP снаружи с самого сервера не проверить: окончательная проверка — звонок на шаге 13.

4. Если адрес определён неверно, задайте его явно. Если звонки нужны только внутри сети, укажите `off`. Идущие встречи прервутся.

   ```bash
   sudo scripts/medianet.sh apply --public-ip 192.0.2.10
   ```

5. Сменить порты можно только согласованно:

   ```bash
   sudo scripts/medianet.sh ports --tcp 7881 --udp 7882
   ```

Схемы размещения за NAT, DMZ и VPN — [Публикация во внешний контур](Архитектура-Публикация-во-внешний-контур). Все порты — [Порты и сервисы](Архитектура-Порты-и-сервисы).

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Страница открылась, звука нет | закрыты медиапорты | пункты 2–3 |
| Звонок работает только в локальной сети | нет проброса или неверный публичный адрес | `sudo scripts/medianet.sh check` |
| Признаки CGNAT или двойного NAT | провайдер не даёт внешний адрес или NAT в два слоя | [Решение проблем звонков и сети](Решение-проблем-звонков-и-сети) |
| Правка `.env` не подействовала | изменения применяет `medianet.sh apply` | выполнить пункт 4 |

**Ожидаемый результат:** у каждой подключённой интеграции кнопка проверки показывает успех, а «Состояние системы» не содержит ошибок по ней.

## Шаг 12. Хранилища и резервирование

**Хранилища, по необходимости.** Записи и протоколы хранятся в `DATA_ROOT`. Сетевая папка SMB подключается в разделе **Администрирование → Хранилища**: [Как настроить хранилища и почту](Как-настроить-хранилища-и-почту).

**Резервные копии, обязательно для рабочей эксплуатации.** Сделайте первую копию сразу и перенесите её с сервера.

```bash
cd /opt/peregovorka
sudo scripts/backup.sh --keep 14 --with-env
```

**Ожидаемый результат:** строка `Резервное копирование завершено.`, в `/srv/peregovorka-data/backups` есть файл `.dump` и его `.sha256`.

Копия `.env` из `--with-env` содержит `APP_MASTER_KEY`. Без этого ключа зашифрованные настройки после восстановления не читаются. Перенесите её в сейф паролей и не держите рядом с дампами. Настройки также выгружаются в файл `.pgcfg` из интерфейса. Расписание, сроки хранения и проверка копий — [Резервное копирование и аварийное восстановление](Резервное-копирование-и-аварийное-восстановление).

## Обновление существующей системы

Обновляйте вне рабочих часов: идущие встречи прерываются, клиенты переподключаются сами.

```bash
cd /opt/peregovorka
./scripts/check-updates.sh          # что нового
sudo ./scripts/update.sh --dry-run  # план, ничего не меняет
sudo ./scripts/update.sh            # обновление
sudo ./scripts/verify.sh
```

То же самое делается из браузера: **Администрирование → Обновления и версии → «Обновить проект»**.

**Ожидаемый результат:** итог из четырёх частей: `Update`, `Deployment`, `Health`, `Integrations`. Код возврата `0` — всё в порядке, `3` — версия установлена, но интеграции требуют внимания, `1` — обновление остановлено.

Перед миграцией скрипт сам делает копию базы, а при сбое возвращает базу и код. Подробности, параметры и откат — [Как обновить и откатить](Как-обновить-и-откатить).

## Восстановление из резервной копии

Сначала определите, что именно потеряно. Выбирайте самое малое действие: восстановление базы теряет всё, что появилось после копии.

| Что случилось | Что нужно | Что делать |
| --- | --- | --- |
| Сервис не работает, данные целы | ничего | `scripts/ctl.sh start` или [сценарии отказов](Архитектура-Резервирование-и-восстановление) |
| Неудачное обновление | автоматическая копия `pre-…` | `update.sh` возвращает систему сам; иначе [Как обновить и откатить](Как-обновить-и-откатить) |
| Повреждена база | дамп `.dump`, тот же `APP_MASTER_KEY` | `scripts/restore.sh <файл.dump>` |
| Потеряны настройки | `.pgcfg` и его пароль | импорт в интерфейсе: [Резервная копия конфигурации](Как-сделать-резервную-копию-и-перенести-сервер) |
| Сервер потерян целиком | дамп, `.env`, архив файлов | порядок ниже |

Восстановление на новом сервере:

1. Установите **ту же версию**, что была: выполните шаги 1–8 с параметром `--ref vX.Y.Z`.
2. Перенесите из старого `.env` как минимум `APP_MASTER_KEY` и примените: `scripts/ctl.sh start backend`. Адреса, порты и `DATA_ROOT` оставьте от нового сервера.
3. Проверьте файлы копии: `sha256sum -c <файл.dump>.sha256`.
4. Восстановите базу: `scripts/restore.sh <файл.dump>`.
5. Верните файлы: `sudo tar -C <DATA_ROOT> -xzf <архив файлов>`, затем выставьте владельца ([пошагово](Резервное-копирование-и-аварийное-восстановление)).
6. Настройте адрес, DNS и сертификат: шаг 9. Если сервер получил новый адрес, повторите шаг 10.

**Ожидаемый результат:** `scripts/verify.sh` и `scripts/smoke-test.sh` без ошибок, количество встреч совпадает с прежним, старые записи открываются, тестовая встреча проходит. Старый сервер не удаляйте ещё неделю.

Если базы нет, а файлы и паспорта встреч сохранились: [Как восстановить материалы после переноса](Как-восстановить-материалы-после-переноса).
