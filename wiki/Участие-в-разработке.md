# Участие в разработке

*Для кого: разработчик.*

Страница помогает собрать проект, прогнать тесты и узнать правила предложения изменений. Устройство системы: [Как устроена Peregovorka](Как-устроена-Peregovorka).

Файла `CONTRIBUTING` в репозитории нет. Ниже собраны правила из `CLAUDE.md`, `docs/VERSIONING.md` и `docs/PRIVACY_OF_CONFIG.md`. Порядок принятия сторонних предложений не описан: обсудите изменение в Issues до начала работы.

## Что нужно заранее

- Python 3.12 и новее, Node.js 24, npm; для скриптов нужен Bash.
- Docker нужен только для проверок установки на реальном контейнере. Тесты скриптов используют подставной Docker.
- Для приложения Android: JDK и Android SDK, см. `docs/ANDROID.md`.

## Состав репозитория

| Каталог | Содержимое |
| --- | --- |
| `backend/` | FastAPI, миграции Alembic, тесты |
| `asr-service/` | служба распознавания |
| `frontend/` | React и TypeScript (Vite) |
| `desktop/` | приложения для Windows и Linux (Electron) |
| `mobile/android/` | приложение для Android |
| `deployment/` | `compose.yml`, шаблоны nginx, `compat.env` |
| `scripts/`, `tests/scripts/` | скрипты установки и эксплуатации, их тесты |
| `tests/live/` | живые сценарии против тестового экземпляра |
| `tests/perf/` | инструменты нагрузочных замеров |
| `docs/` | техническая документация |
| `wiki/` | исходники этой вики |

## Собрать и проверить

```bash
# backend
cd backend && pip install -r requirements-dev.txt && pytest

# ASR (torch и GigaAM не нужны: подставные провайдер и VAD)
cd asr-service && pip install -r requirements-dev.txt && pytest

# frontend
cd frontend && npm ci && npm test && npm run build

# скрипты
bash tests/scripts/run.sh

# приложение для Windows (из каталога desktop/)
npm ci && npm run typecheck && npm test
npm run dev                      # из исходников
npm run preview                  # собранная программа без установщика + проверки
```

LDAP в тестах подменяется. Полный прогон `backend` занимает заметное время: запускайте сначала тесты изменённого модуля.

## Правила изменений

1. Приоритеты: надёжность, работающая функциональность, скорость, безопасность, затем новые возможности.
2. Не называйте проверенным то, чего не запускали. В описании изменений разделяйте: «проверено запуском», «автотест», «code review», «не проверено».
3. Изменения страницы комнаты — только с живой проверкой в браузере (`tests/live/`).
4. В репозиторий не попадают частные данные: только `example.org`, `192.0.2.x` и подобные. Перед фиксацией запускайте `python3 scripts/check_private_data.py`; в CI есть отдельное задание `private-data`.
5. Схема базы меняется только миграциями Alembic (`backend/migrations/versions`), «расширяющими»; тест `test_migrations.py` проверяет совпадение со схемой моделей.
6. Историю git не переписывайте без согласия владельца.
7. Зависимости закреплены точными версиями; новые версии проходят ревизию при выпуске (`scripts/deps.py review`, `docs/DEPENDENCIES.md`).

## Выпуск версий

Схема `MAJOR.MINOR.PATCH`, единственный источник версии: файл `VERSION`. Перед каждым выпуском: `VERSION` → CHANGELOG языком пользователя → HISTORY → PROJECT → README → docs → CI → release. `CHANGELOG.md` написан для пользователя, `HISTORY.md` для разработчика, `README.md` служит витриной. Подробности: `docs/VERSIONING.md`. Приложения версионируются отдельно: теги `desktop-vX.Y.Z` для Windows и Linux, `android-vX.Y.Z` для Android.

## Вики

Исходники лежат в `wiki/`, правила в `wiki/_meta/Редакционный-стандарт.md`. Перед выпуском запустите `python3 scripts/check_wiki.py`. Числа о нагрузке и вместимости пишутся только с условиями и статусом замера. Схемы сверяются с `deployment/compose.yml` и `frontend/nginx.conf`: при изменении служб и путей правьте их в том же изменении.

## Стиль

Комментарии и документы пишутся на русском. Один термин означает одно понятие. Названия функций и параметров пишутся как в продукте.
