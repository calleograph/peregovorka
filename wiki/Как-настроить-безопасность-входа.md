# Как настроить безопасность входа

*Для кого: администратор.*

**Что получится:** включена двухфакторная защита, локальная CAPTCHA, заданы сроки сеансов и лимиты попыток. Модель защиты — [Безопасность и приватность](Безопасность-и-приватность).

## Что нужно заранее

- Права администратора.
- Копия мастер-ключа `APP_MASTER_KEY` в защищённом месте: им шифруются секреты двухфакторной защиты ([Справочник: конфигурация](Справочник-конфигурация)).

## Включить двухфакторную аутентификацию (TOTP)

Одноразовые коды по RFC 6238 (6 цифр, шаг 30 секунд) работают с Google Authenticator, Microsoft Authenticator, FreeOTP, Aegis и другими приложениями.

1. **Администрирование → Безопасность → Вход и сеансы** → выберите политику:

| Политика | Результат |
| --- | --- |
| Отключена | функция скрыта, код при входе не спрашивается |
| По желанию | каждый включает сам в «Личный кабинет → Двухфакторная аутентификация» |
| Обязательна администраторам, всем или группам каталога | после пароля пользователь попадает на экран настройки; пока 2FA не включена, сессия годится только для настройки (остальные запросы отвечают `403 totp_enrollment_required`) |

   Политика действует и на локального администратора. Изменение не разлогинивает открытые сеансы: требование применяется при следующем входе.

2. Пользователь включает 2FA: пароль → QR-код (секрет до подтверждения хранится в Redis 10 минут) → код из приложения → **10 резервных кодов** (показываются один раз).

Вход: пароль верен → одноразовая заявка (5 минут, 5 попыток) → код или резервный код → сеанс. Секрет шифруется AES-256-GCM ключом `APP_MASTER_KEY`; резервные коды хранятся как HMAC-SHA256 и гасятся одним условным обновлением. Расхождение часов допускается ±30 секунд.

**Потеряно устройство.** Есть резервный код — войдите им и создайте новые. Нет кодов — администратор в «Пользователи» нажимает «сбросить» (нужен его пароль). Единственный локальный администратор — на сервере `./scripts/admin-reset.sh` (новый пароль и сброс 2FA).

**Ограничения.** Потеря `APP_MASTER_KEY` требует сбросить 2FA у всех. WebAuthn и ключи доступа не реализованы. Секреты 2FA и резервные коды в резервную копию настроек не входят: после восстановления на новом сервере пользователи настраивают 2FA заново.

## Защита входа от перебора и CAPTCHA

Защита работает **на сервере** и не зависит от браузера: закрытие окна, режим инкогнито, очистка cookie, смена User-Agent и перезапуск не сбрасывают счётчики. Они хранятся в Redis и общие для всех экземпляров backend.

**Администрирование → Безопасность → Защита входа от перебора** — независимые счётчики:

| Счётчик | Что делает |
| --- | --- |
| по учётной записи | `alice`, `ALICE`, `EXAMPLE\alice`, `alice@example.org` — одна запись; после порога попытки с **незнакомых** адресов перестают доходить до каталога (AD не блокируется нашими попытками), с привычного адреса пользователь входит как обычно |
| по IP-адресу (IPv6 — по сети /64) | CAPTCHA, замедление ответа, затем временная блокировка адреса; повторные блокировки вдвое длиннее, но не больше потолка |
| по паре «запись + адрес» | CAPTCHA для этого сочетания |
| по интенсивности запросов | лимит запросов ко входу с адреса в минуту; всплеск со всех адресов включает CAPTCHA для всех |
| по числу разных записей с одного адреса | признак подбора по списку: адрес блокируется |

Учётная запись целиком **не блокируется**: иначе чужую запись можно было бы «залочить» несколькими запросами. Общие адреса (NAT, прокси: с адреса вошло несколько разных пользователей, либо адрес указан администратором) целиком не блокируются — для них остаются CAPTCHA и замедление. Успешный вход сбрасывает счётчики записи и пары, но не адреса. Сообщения не раскрывают, существует ли запись и какое правило сработало.

**Администрирование → Безопасность → CAPTCHA.** По умолчанию — **картинка с символами**: после заданного числа неудачных попыток (по адресу, по записи или по их паре) сервер не принимает вход, пока пользователь не введёт символы. Задача одноразовая, привязана к адресу клиента и к назначению, живёт ограниченный срок (по умолчанию 3 минуты); неверный ответ сжигает картинку. Внешних сервисов нет. Если CAPTCHA недоступна, пользователь видит понятную ошибку, а вход не разрешается без проверки. CAPTCHA — не единственная защита: перебор ограничивается и без неё.

| Режим | Когда проверка нужна |
| --- | --- |
| Никогда | никогда |
| После серии неудач (по умолчанию) | после N (по умолчанию 5) неудач по любому из счётчиков в окне (по умолчанию 15 минут) |
| Всегда | перед каждым входом, входом гостя и созданием временной переговорки |

Вид «вычислительная задача» (доказательство работы, формат ALTCHA) оставлен для особых случаев: браузер решает её незаметно, и это слабая защита — её решает и бот.

**Проверить CAPTCHA.** Кнопка «Проверить CAPTCHA» на странице «Безопасность → CAPTCHA» открывает настоящую проверку с текущими настройками: можно увидеть картинку, пройти её и получить ответ сервера («Проверка пройдена», «Неверный ответ», «Срок проверки истёк»). В окне видно, какой режим и порог действуют, доступно ли хранилище проверок и шрифт картинки — так понятно, почему проверка не работает. Тестовые попытки не считаются неудачными входами, не блокируют вашу запись и не отключают защиту; пройденная здесь проверка на входе не принимается.

Если защитное хранилище (Redis) недоступно, вход закрывается сообщением «Защита входа временно недоступна», а не открывается без ограничений; уже идущие конференции вход не затрагивает.

## Настроить сеансы

| Параметр (`.env`) | По умолчанию | Назначение |
| --- | --- | --- |
| `SESSION_IDLE_TIMEOUT_SECONDS` | 28800 | неактивность до выхода (8 часов) |
| `SESSION_ABSOLUTE_TIMEOUT_SECONDS` | 86400 | предельная жизнь сеанса (24 часа) |
| `COOKIE_SECURE` | `true` | флаг Secure у cookie |

Прежние `LOGIN_MAX_FAILURES_*`, `LOGIN_FAILURE_WINDOW_SECONDS` и `LOGIN_LOCKOUT_SECONDS` с версии 0.41.4 **не используются**: пороги задаются в разделах «Защита входа от перебора» и «CAPTCHA». На учётную запись допускается до 5 сеансов (настраивается), список устройств — «Активные устройства». Администратор может завершить сеансы пользователя.

Порог защиты каталога («неудач по учётной записи») держите ниже порога блокировки в вашем AD ([Как подключить Active Directory](Как-подключить-Active-Directory)).

## Локальный администратор

Единственная локальная учётная запись — аварийный администратор (`admin`). Пароль не короче 12 символов, не менее двух видов символов, не содержит имя пользователя. Восстановление доступа:

```bash
sudo /opt/peregovorka/scripts/admin-reset.sh
sudo /opt/peregovorka/scripts/admin-reset.sh --create # создать администратора, если его нет
```

Скрипт выдаёт новый случайный пароль (его нужно заменить при входе), завершает старые сеансы, снимает блокировку и пишет событие в аудит.

## Журнал аудита

Все изменения политики, 2FA и CAPTCHA пишутся в аудит: `auth.totp_enable`, `auth.totp_disable`, `auth.totp_failed`, `auth.backup_code_used`, `auth.totp_backup_regenerate`, `auth.totp_reset`, `captcha.rejected`. Список — [Справочник: журнал аудита и события](Справочник-журнал-аудита-и-события).

## Типичные ошибки

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Код не принимается | расхождение часов более 30 секунд, тот же код уже использован | синхронизировать время на устройстве |
| CAPTCHA или блокировка у всех сразу | сервер видит один и тот же адрес (прокси или WAF не объявлен доверенным) | «Безопасность → Сеть и IP-адреса»: блок «Что сервер видит сейчас», добавить прокси в «Доверенные прокси» |
| Блокирован адрес сотрудника | подбор с этого адреса или общий NAT | «Заблокированные адреса» (с 0.42.0) либо подождать; общие адреса — в «Защита входа → Общие адреса» |
| Пользователь потерял устройство | нет кодов | сброс 2FA администратором |
