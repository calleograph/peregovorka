# Руководство системного администратора

> Относится к версии 0.50.1 · проверено 2026-10-29 · уровень проверки: 3 (установка профилем `shared-host` от обычного пользователя, управление сервисами, применение `.env`, резервное копирование и восстановление выполнены на тестовом экземпляре стенда разработчика; отметки ○ на связанных страницах — не запускалось; на серверах организаций и за настоящим внешним прокси эта редакция не проверялась) · тип страницы: практическое руководство

Результат: вы понимаете, из чего состоит Peregovorka, как она связана с сетью, и можете установить, проверить, сопровождать, обновить, откатить, восстановить и перенести экземпляр, зная последствия каждого действия. Для кого: системный администратор, который принимает систему в эксплуатацию. Сведения о продукте — [технический паспорт](https://github.com/calleograph/peregovorka/blob/main/docs/TECHNICAL_PASSPORT.md); сведения о вашем экземпляре — заполненный [паспорт экземпляра](https://github.com/calleograph/peregovorka/blob/main/docs/STAND_PASSPORT_TEMPLATE.md) (хранится у вас, не в репозитории).

## 1. Из чего состоит система

| Сервис compose | Что делает | Публикуется наружу | Данные |
| --- | --- | --- | --- |
| `web` | интерфейс, nginx: `/api`, `/livekit` (сигнализация звонков), HLS | `WEB_BIND_ADDR:WEB_PORT` (обычно `127.0.0.1`, за прокси) | — |
| `backend` | API, вход, встречи, протоколы, интеграции, фоновые задачи | нет | `DATA_ROOT/{recordings,exports,chat-files,avatars,branding,ca,live,updater}` |
| `asr` | распознавание речи (подключается к встречам как участник LiveKit) | нет | `DATA_ROOT/models` (чтение), `recordings` |
| `livekit` | медиасервер WebRTC | `LIVEKIT_TCP_PORT/tcp`, `LIVEKIT_UDP_PORT/udp`; API — только `127.0.0.1:LIVEKIT_HTTP_PORT` | — |
| `postgres` | база данных | нет | `DATA_ROOT/postgres` |
| `redis` | сессии, очереди, координация | нет | `DATA_ROOT/redis` |
| `llm-local`, `livekit-sip`, `livekit-egress` | локальная языковая модель, телефония, видеозапись — **по включению** | SIP — порты SIP/RTP | `DATA_ROOT/models/llm`, `recordings`, `live` |

Схема взаимодействия — [[Как устроена Peregovorka|Как-устроена-Peregovorka]]. Контейнеры называются `<COMPOSE_PROJECT_NAME>-<сервис>-1`; на одном сервере может работать несколько экземпляров с разными именами проекта и портами.

Где что лежит:

| Что | Где |
| --- | --- |
| Каталог установки (код, скрипты, `.env`) | `APP_ROOT` (например `/opt/peregovorka`); найти: `docker compose ls` — путь к `deployment/compose.yml` |
| Параметры и секреты | `APP_ROOT/.env`, права 600 ([[Справочник: конфигурация|Справочник-конфигурация]]) |
| Данные | `DATA_ROOT` (например `/srv/peregovorka-data`) |
| Резервные копии | `BACKUP_DIR` (по умолчанию `DATA_ROOT/backups`) |
| Пакеты диагностики | `APP_ROOT/diagnostics` |
| Помощник обновлений | служба `peregovorka-updater-<проект>` (если установлена) |

## 2. Сеть

```
Пользователь ──443/tcp──► ваш reverse proxy (TLS) ──► [nginx хоста :NGINX_LISTEN_PORT] ──► web 127.0.0.1:WEB_PORT
Пользователь ──LIVEKIT_UDP_PORT/udp, LIVEKIT_TCP_PORT/tcp──► адрес LIVEKIT_NODE_IP (напрямую, мимо HTTP-прокси)
```

| Требование | Почему |
| --- | --- |
| DNS-имя и доверенный сертификат с **полной цепочкой** | без HTTPS браузер не даёт микрофон и экран; неполная цепочка ломает телефоны, Outlook и проверки сервера ([[Разбор эксплуатационных случаев|Разбор-эксплуатационных-случаев]], случай 1) |
| Прокси передаёт WebSocket для `/livekit/` и `/api/v1/ws`, таймаут чтения ≥ 1 ч, `X-Forwarded-Proto` | иначе встреча не подключается или рвётся ([[Как настроить reverse proxy и HTTPS|Как-настроить-reverse-proxy-и-HTTPS]]) |
| `LIVEKIT_NODE_IP` — адрес, **доступный клиентам** | его LiveKit сообщает клиентам для медиа; частный адрес не работает из интернета |
| Порты медиа открыты от клиентов до сервера | UDP — основной путь, TCP — запасной (медленнее) |
| `APP_PUBLIC_URL` совпадает с адресом в браузере (или он есть в `ALLOWED_ORIGINS`) | иначе «Недопустимый Origin» |

**TURN/STUN.** Внешние серверы STUN/TURN не используются, встроенный TURN LiveKit установщиком не настраивается. Клиенты, которым разрешён только исходящий 443/tcp через прокси, к медиа не подключатся — нужен доступ к `LIVEKIT_TCP_PORT` или `LIVEKIT_UDP_PORT`. Настройка TURN на 443 требует отдельного имени и сертификата и в этой версии не поддерживается установщиком.

Перечень портов и правил для межсетевого экрана по вашему `.env`: `scripts/ports.sh --format md` (✔). Публикация в интернет — [[Как опубликовать сервис в интернете|Как-опубликовать-сервис-в-интернете]].

## 3. Требования

Минимум: 4 vCPU, 8 ГБ памяти, 30 ГБ свободно в `DATA_ROOT`, Ubuntu 22.04+/Debian 12+ x86_64, Docker с Compose v2. Подробно и расчёт под нагрузку — [[Системные требования|Системные-требования]], [[Производительность и масштабирование|Производительность-и-масштабирование]].

Параметры ядра для медиа (`net.core.rmem_max`, `wmem_max`, `netdev_max_backlog`, `vm.overcommit_memory`) установщик меняет только в профиле `standalone`; на общем сервере — решение администратора: `scripts/tune-kernel.sh` показывает значения, `sudo scripts/tune-kernel.sh --apply` применяет.

## 4. Установка

| Путь | Когда | Документ |
| --- | --- | --- |
| Одной командой `sudo bash install.sh` | чистый сервер, всё ставится само, самоподписанный сертификат | [[Установка на чистый сервер|Установка-на-чистый-сервер]] |
| Мастер `scripts/setup.sh --profile shared-host` | сервер с другими приложениями; мастер подбирает порты и генерирует секреты | [[Установка на общий сервер|Установка-на-общий-сервер]] |
| Вручную: `.env` + `scripts/install.sh --profile …` | особые требования, закрытая сеть | ниже |

### Ручная установка (проверено 2026-10-29)

1. Получить код конкретного выпуска: `git clone --depth 1 --branch vX.Y.Z https://github.com/calleograph/peregovorka.git /opt/peregovorka`.
2. `cp .env.example .env && chmod 600 .env` и задать: `COMPOSE_PROJECT_NAME`, `INSTALL_PROFILE`, `APP_PUBLIC_URL`, `APP_ROOT`, `DATA_ROOT`, **`BACKUP_DIR`** (в образце — `/srv/peregovorka-data/backups`; укажите `<DATA_ROOT>/backups`, иначе `backup.sh` не сможет писать), порты `WEB_PORT`, `LIVEKIT_HTTP_PORT`, `LIVEKIT_TCP_PORT`, `LIVEKIT_UDP_PORT`, `LIVEKIT_NODE_IP`, `LIVEKIT_PUBLIC_URL`; все значения `CHANGE_ME_…` — случайными (например, `openssl rand -base64 32` для `APP_MASTER_KEY`, `openssl rand -hex 24` для остальных); `NGINX_MANAGE=no`, если nginx хоста не нужен; LDAP можно оставить пустым и подключить каталог в интерфейсе.
3. Проверка без изменений: `scripts/install.sh --profile shared-host --dry-run` (✔).
4. Установка: `scripts/install.sh --profile shared-host` (✔). В закрытой сети модель распознавания — заранее скачанные файлы: `--models-from <каталог с v3_e2e_rnnt.ckpt и v3_e2e_rnnt_tokenizer.model>` (каталог **с самими файлами**). Сбой этапа — повторить ту же команду или `--from <этап>`: готовые этапы пропускаются.
5. Администратор: `scripts/bootstrap-admin.sh` (✔; пароль показывается один раз).
6. Reverse proxy и сертификат на ваш прокси; затем `scripts/smoke-test.sh` (✔).

На стенде установка заняла около 40 минут (сборка образов: backend 11,5 мин, asr 8,5 мин, web 1,5 мин, livekit 1 мин; без Buildx — автоматически классическим сборщиком). Результат: 6 сервисов `healthy`, итоговая проверка PASS; предупреждения — параметры ядра и `ASR_CPU_THREADS=0` (на общем сервере задайте половину ядер).

## 5. Повседневная работа

| Задача | Команда | Последствия |
| --- | --- | --- |
| Проверить состояние | `scripts/status.sh` | нет |
| Посмотреть журнал | `scripts/logs.sh <сервис> --tail 200` | нет |
| Итоговая и сквозная проверка | `scripts/verify.sh`, `scripts/smoke-test.sh` | smoke создаёт и удаляет тестовую встречу |
| Перезапустить сервис | `scripts/ctl.sh restart <сервис>` | см. [[Справочник: диагностика и восстановление|Справочник-диагностика-и-восстановление]], раздел 2; `livekit` прерывает встречи |
| **Применить изменения `.env`** | `scripts/ctl.sh start <сервис>` (пересоздаёт контейнер); `restart` изменений **не применяет** | как перезапуск |
| Остановить / запустить всё | `scripts/ctl.sh stop`, `scripts/ctl.sh start` | система недоступна; данные сохраняются |
| Собрать пакет для поддержки | `scripts/diag.sh` | нет |
| Резервная копия | `scripts/backup.sh` | нет (база не блокируется) |

Расписание регулярных задач: ежедневная копия базы, еженедельная копия файлов, ежемесячная проверка `scripts/check-updates.sh`, ежеквартальная проверка восстановления — [[Резервное копирование и аварийное восстановление|Резервное-копирование-и-аварийное-восстановление]].

Мониторинг: `https://<адрес>/api/v1/health/ready` (HTTP 200 и `"status":"ready"`), свободное место в `DATA_ROOT`, срок сертификата, успешность копий; в интерфейсе — «Администрирование → Обзор» ([[Мониторинг и журналы|Мониторинг-и-журналы]]).

## 6. Операции: последствия и проверка

| Операция | Остановка сервиса | Влияние на пользователей | Условия | Проверка результата | Документ |
| --- | --- | --- | --- | --- | --- |
| Обновление (`scripts/update.sh` или кнопка в «Система → Обновления и версии»; на стенде 0.49.9 → 0.50.0 — 6 мин) | да, на время перезапуска (с миграциями — дольше) | встречи прерываются | свободно ≥ 30 ГБ; нет важных встреч; помощник установлен — для кнопки | итог в `DATA_ROOT/updater/report.txt`; `verify.sh`, `smoke-test.sh`; версия в `/api/v1/version` | [[Как обновить и откатить|Как-обновить-и-откатить]] |
| Повторное развёртывание той же версии (`scripts/update.sh --ref HEAD` или `scripts/rebuild.sh`) | да | встречи прерываются | — | `verify.sh` | там же |
| Откат (`scripts/rollback.sh`; на стенде — 37 с) | да | встречи прерываются | была предыдущая версия; без новой миграции (иначе код 3) | `status.sh`, версия | там же |
| Восстановление после неудачного обновления | да | недоступность до конца | отчёт обновления сохранён | как после обновления | там же; [[Разбор эксплуатационных случаев|Разбор-эксплуатационных-случаев]], случай 9 |
| Восстановление базы (`scripts/restore.sh`) | backend, asr, web — на время восстановления (на стенде 44 с) | недоступность; **данные после копии теряются** | решение владельца; тот же `APP_MASTER_KEY` | `status.sh`, вход, «История» | [[Резервное копирование и аварийное восстановление|Резервное-копирование-и-аварийное-восстановление]] |
| Перенос на другой сервер | да, на время переноса | недоступность | та же версия на новом сервере | количества встреч и записей совпадают | там же, раздел 6 |
| Смена адреса | backend, web — перезапуск | вход по старому адресу перестанет работать | DNS, сертификат, прокси готовы | вход по новому адресу | [[Как настроить reverse proxy и HTTPS|Как-настроить-reverse-proxy-и-HTTPS]] |

**Сохранность данных.** Ни один штатный скрипт не удаляет `DATA_ROOT`, тома и модели и не выполняет `docker prune`. Данные PostgreSQL и Redis лежат в каталогах хоста (`DATA_ROOT/postgres`, `DATA_ROOT/redis`), а не в томах Docker, поэтому пересоздание контейнера (`ctl.sh start`, обновление) их не трогает. Опасные команды перечислены в справочнике (раздел 10) и в обычной работе не нужны.

## 7. Если что-то сломалось

1. **Сохранить сведения:** `scripts/diag.sh` (пакет без секретов) и текст ошибки.
2. **Найти компонент:** `scripts/status.sh` (какой сервис нездоров) → `scripts/logs.sh <сервис> --tail 300` → `scripts/verify.sh`.
3. **Минимальное действие:** перезапуск одного сервиса; правка `.env` + `ctl.sh start <сервис>`; восстановление прав на модели `sudo scripts/models.sh`; только потом — обновление, откат или восстановление.
4. **Проверить:** `status.sh` — `healthy`; `smoke-test.sh`; тестовая встреча двух участников.
5. **Записать** в паспорт экземпляра, что случилось и что сделано.

Симптомы и решения — [[Разбор эксплуатационных случаев|Разбор-эксплуатационных-случаев]] и [[Диагностика]]; порядок для первой линии — [[Руководство технической поддержки|Руководство-технической-поддержки]].

**Помощник обновлений без каталога установки.** Если каталог установки удалили, а служба `peregovorka-updater-<проект>` осталась, она бесконечно перезапускается с ошибкой «Unable to locate executable» (наблюдалось на стенде разработчика: 15 000+ перезапусков). Удалить её: `sudo systemctl disable --now peregovorka-updater-<проект>.service && sudo rm /etc/systemd/system/peregovorka-updater-<проект>.service && sudo systemctl daemon-reload` (○). При живом каталоге — `sudo scripts/updater.sh uninstall`.

## 8. Безопасность и интеграции

- Секреты: `.env` (600), в базе — зашифрованно ключом `APP_MASTER_KEY`; храните копию `.env` отдельно от копий базы.
- Каталог AD, почта, хранилища, календари Exchange, Outlook, языковые модели — страницы раздела «Руководства: администратор»; что и куда уходит из системы — [[Справочник для проверки ИБ|Справочник-для-проверки-ИБ]].
- Обновляйте по выпускам: `scripts/check-updates.sh`, раздел «Система → Обновления и версии».
