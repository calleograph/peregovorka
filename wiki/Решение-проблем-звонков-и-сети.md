# Решение проблем: звонки и сеть

*Для кого: администратор сервера и сетевой администратор.*

Страница сайта и API идут через HTTPS (порт 443 и обратный прокси), а звук, видео и показ экрана — **напрямую** на сервер (адреса — в «Сетевая доступность → Медиасоединения»): UDP-порт `LIVEKIT_UDP_PORT` (основной путь) и TCP-порт `LIVEKIT_TCP_PORT` (запасной). Через HTTP-прокси медиа не ходит. Поэтому «сайт открывается, а встреча не подключается» почти всегда означает проблему с портами медиа или с WebSocket сигнализации.

Точный перечень портов по настройкам вашего сервера и готовая заявка сетевому администратору — в **Администрирование → Система → Сетевая доступность**.

## Комната «подключается» бесконечно

**Что видно.** Плашка «Подключение · …» над панелью встречи не исчезает. Нажмите на неё: в ней видны этапы со временем.

**Где застряло:**
- **Этапы 1–3 («сигнал»)** — не проходит WebSocket `/livekit/`. Обратный прокси не передаёт заголовки Upgrade или режет долгие соединения. Требования к прокси — [Как настроить reverse proxy и HTTPS](Как-настроить-reverse-proxy-и-HTTPS).
- **Этап 4 («звук и видео»)** — закрыты или не проброшены порты медиа на пути от пользователя к серверу, либо клиентам объявляется недоступный адрес (сервер за NAT без публичного адреса, CGNAT у оператора).

**Проверка с сервера** (нужен SSH, потому что проверяются маршруты самого сервера): `sudo scripts/smoke-test.sh`. Строка `/rtc/v1` с ответом 400 и `join_request` — норма; 404 означает устаревший LiveKit. Строка «WebSocket /rtc» с ответом 101 — норма. Проверка идёт напрямую, через web и через публичный адрес: неисправно то звено, на котором код меняется.

Проверка с сервера не доказывает доступность портов с устройства пользователя. Её подтверждает только встреча с компьютера из нужной сети.

**Что сделать.** Запустите `sudo scripts/medianet.sh check` или нажмите «Проверить медиасоединения» в «Сетевая доступность». Там видны адреса, которые получают клиенты, нужный проброс портов (номер не меняется), признаки CGNAT и двойного NAT и что делать. Пересчитать адреса и пересоздать LiveKit: ⚠ `sudo scripts/medianet.sh apply` (идущие звонки прервутся). Задать публичный адрес явно: `--public-ip <IPv4>`. Команда `ctl.sh restart` пересоздаёт контейнер, но адреса не пересчитывает, поэтому после правки адресов в `.env` нужна `medianet.sh apply`. Порядок настройки — [Как настроить LiveKit](Как-настроить-LiveKit).

## Сервер звонков не отвечает (в разделах «Видеозапись», «Трансляции» и в «Обзоре»)

Контейнер `livekit` остановлен или не проходит проверку здоровья. В разделе «Видеозапись» есть кнопка **«Перезапустить LiveKit»**. ⚠ Все идущие звонки прервутся на несколько секунд. Если LiveKit снова падает, нужен журнал (SSH): `sudo scripts/logs.sh livekit --tail 300`.

## Вход в комнату занимает 5 секунд и больше

**Почему.** Чаще всего устаревший LiveKit: клиент сначала пробует новый адрес `/rtc/v1`, получает 404 и только потом откатывается на старый.

**Проверка.** `smoke-test.sh`, строка «LiveKit /rtc/v1: маршрут». Время этапов — в плашке подключения и в **Обзор → Технические показатели**, блок **Время входа в комнату**.

**Что сделать.** Обновите сервер: `update.sh` сам ставит проверенную версию LiveKit.

## Звонок рвётся только у пользователей VPN (`ERR_CONNECTION_RESET`)

**Почему.** Слишком большой MTU на VPN-адаптере: крупные пакеты теряются. Программа тут ни при чём.

**Что сделать.** Сетевой администратор уменьшает MTU адаптера. Помогало значение 1250: в Windows `netsh interface ipv4 set subinterface "<адаптер>" mtu=1250 store=persistent`. Ещё проверьте, что VPN пропускает UDP до `LIVEKIT_NODE_IP`. По TCP звонок тоже заработает, но хуже переносит потери.

## Звук прерывается, показ экрана «замирает»

- «Администрирование → Обзор → Диагностика клиентов» показывает причину по каждому пользователю: потери, сеть, процессор.
- Для показа слайдов выберите профиль «Чёткость», для видео — «Плавность» (Администрирование → Система → Демонстрация экрана).
- Сетевые параметры ядра сервера должны быть не ниже рекомендованных. Если «Обновления и версии → Исправить автоматически» показывает «Параметры сети сервера ниже рекомендованных» — примените исправление.

## Проверки из администрирования пишут «недоступно», а у пользователей всё работает

**Почему.** Сервер обращается к собственному публичному имени и попадает не туда: внутренний DNS даёт другой адрес, не настроен hairpin NAT, по имени отвечает другой экземпляр.

**Проверка.** `sudo scripts/diag.sh`, файл `network.txt`: ответ `/api/v1/version` изнутри и через публичный адрес — версия и адрес, на который ушёл запрос.

**Что сделать.** Согласовать DNS (внутренняя зона или запись в `/etc/hosts` сервера — по решению сетевого администратора).

## «Это подключение закрыто: участник с тем же идентификатором вошёл повторно»

**Что должно быть.** Один пользователь может одновременно находиться в одной комнате с нескольких устройств и из нескольких вкладок: например, с компьютера показывать экран, а с телефона говорить. У каждого подключения свой участник, и вход второго не закрывает первое. Другие подключения того же пользователя видны в списке участников с пометкой устройства; звук своего другого устройства на этом не воспроизводится (чтобы не было эха), а если на двух ваших устройствах одновременно включены микрофоны, страница об этом предупреждает — подключение при этом не блокируется.

**Что было раньше (до 0.53.1).** Приложение для Android (и любой клиент, не присылавший идентификатор экземпляра) получало того же участника LiveKit, что и первая вкладка браузера, поэтому сервер звонков закрывал вкладку этим сообщением. Теперь клиент без идентификатора получает собственного участника по сеансу входа, приложение для Android (0.1.3+) присылает идентификатор установки, а вкладки браузера не используют один идентификатор дважды: «Дублировать вкладку» получает новый.

**Если сообщение всё же появилось.** Страница сама один раз входит снова новым подключением. Если сообщение повторяется чаще раза в полминуты, закройте лишние вкладки и сообщите администратору: в журнале сервера звонков (`sudo scripts/logs.sh livekit`) строка `DUPLICATE_IDENTITY` называет участника, а «Диагностика клиентов» — его устройство.
