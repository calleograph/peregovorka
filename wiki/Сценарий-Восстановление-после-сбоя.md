# Сценарий: восстановление после сбоя

*Для кого: администратор сервера и владелец данных.*

## Зачем это нужно

При сбое легко сделать хуже: перезапустить всё и потерять журналы или восстановить базу, когда хватило бы одной службы. Сценарий помогает определить, что сломано, и выбрать самое малое действие.

## Когда пригодится

- Сайт или встречи не работают.
- Обновление закончилось сбоем.
- Повреждена база или диск.
- Сервер потерян целиком.

## Что потребуется

- Доступ к серверу с `sudo` или новый сервер.
- Набор копии: дамп `.dump`, копия `.env`, архив файлов `.tar.gz`.
- Решение владельца данных, если нужна база из копии: всё, что появилось после копии, будет потеряно.

## Где найти

- Состояние: **Администрирование → Обзор → Обзор** и `sudo scripts/status.sh`.
- Итог обновления: **Система → Обновления и версии** и `DATA_ROOT/updater/report.txt`.
- Копии: `BACKUP_DIR`, по умолчанию `DATA_ROOT/backups`, и каталог вне сервера.

## Как это сделать

### Шаг 1. Сохраните сведения

Журнал контейнера исчезает вместе с контейнером, поэтому сначала соберите пакет. Операция ничего не меняет.

```bash
cd /opt/peregovorka
sudo scripts/diag.sh
sudo scripts/status.sh
```

Если каталог установки цел, но диск полон, сначала посмотрите `df -h`. Если сервер недоступен, переходите к таблице.

### Шаг 2. Выберите действие

| Что случилось | Действие | Потеря данных |
| --- | --- | --- |
| Одна служба нездорова | [перезапустить её](Как-управлять-службами#перезапустить-одну-службу-) | нет |
| Контейнер удалён | ⚠ `sudo scripts/ctl.sh start` | нет |
| Сервер перезагрузился, контейнеры не поднялись | ⚠ `sudo scripts/ctl.sh start` | нет |
| Диск заполнен | освободить место, см. [Справочник: диагностика и восстановление](Справочник-диагностика-и-восстановление#7-ресурсы) | нет |
| Обновление оборвалось | ⚠ повторить `sudo scripts/update.sh` | нет |
| Обновление завершилось сбоем | читать отчёт, [Как обновить и откатить](Как-обновить-и-откатить) | обычно нет |
| Нет модели распознавания | ⚠ `sudo scripts/models.sh`, затем `sudo scripts/ctl.sh restart asr` | нет |
| Записи пропали с SMB | вернуть файлы на ресурс из копии, **Целостность хранилищ** | файлы после копии |
| База повреждена, сервер цел | шаг 3 | всё после копии |
| Сервер потерян | шаг 4 | всё после копии |
| Базы нет, файлы целы | [Как восстановить материалы после переноса](Как-восстановить-материалы-после-переноса) | встречи без паспорта |

### Шаг 3. Восстановите базу на том же сервере ⛔

**Условия.** Решение владельца данных принято. Есть дамп и тот же `APP_MASTER_KEY`. Контейнер `postgres` запущен: `sudo scripts/ctl.sh start postgres`.

```bash
cd /opt/peregovorka
sudo sh -c 'cd /srv/peregovorka-data/backups && sha256sum -c peregovorka-db-20261029-021500.dump.sha256'
sudo scripts/restore.sh /srv/peregovorka-data/backups/peregovorka-db-20261029-021500.dump
```

Имя файла подставьте своё. Скрипт просит ввести имя проекта и делает страховочный дамп с меткой `pre-restore`.

**Последствия.** Сайт недоступен на время работы. Копия разворачивается в отдельную базу и проверяется, затем базы меняются именами. Если приложение не заработало на восстановленной базе той же версии схемы, прежняя возвращается сама. Прежняя база остаётся рядом как `<имя>_before_restore_<время>` и занимает столько же места.

Если вернуть надо и файлы, добавьте `--files <архив>` и выполните пересоздание контейнеров из шага 4, пункт 5.

### Шаг 4. Восстановите сервис на новом сервере ⛔

1. Сверьте контрольные суммы набора в каталоге, где лежит копия: `sha256sum -c <файл>.sha256`. Файл `.sha256` хранит имя без пути, поэтому запускайте команду рядом с файлами.
2. Установите **ту же версию**, что была. Каталог установки заранее не клонируйте: установщик сделает это сам.

   ```bash
   wget -O install.sh https://raw.githubusercontent.com/calleograph/peregovorka/main/install.sh
   chmod +x install.sh
   sudo ./install.sh --host meet.example.org --ref vX.Y.Z
   ```

   Первичный пароль администратора можно не сохранять: база будет заменена.

3. Перенесите секрет. В новом `/opt/peregovorka/.env` замените значение в строке `APP_MASTER_KEY` значением из старого `.env`. Новую строку не дописывайте.

   **Не копируйте `.env` целиком.** `POSTGRES_PASSWORD` задаётся при первом создании базы, поэтому старый пароль к новому каталогу `postgres` не подойдёт. Адреса, порты, `DATA_ROOT` и пароли служб оставьте от нового сервера.

4. Примените ключ:

   ```bash
   cd /opt/peregovorka
   sudo scripts/ctl.sh restart backend
   ```

5. Положите дамп и архив на новый сервер и восстановите их одной командой.

   ```bash
   sudo scripts/restore.sh /путь/peregovorka-db-20261029-021500.dump \
     --files /путь/peregovorka-files-20261029-021500.tar.gz
   ```

   Распаковывать архив вручную не нужно. Команда распаковывает его рядом, откладывает прежние каталоги как `<каталог>.before-restore-<время>` и выставляет владельцев.

   Контейнеры приложения пересоздаются сами, чтобы увидеть новые каталоги.

6. Если адрес изменился, настройте его. Архив заменил каталог `tls` файлами старого сервера, поэтому сертификат надо проверить: [Как настроить сертификаты](Как-настроить-сертификаты). Свой сертификат из другого каталога в архив не входит, перенесите его отдельно.
7. Подключите заново внешние тома и хранилища: [Внешние тома](Внешние-тома).
8. Проверьте настройки интеграций: SIP и другие подключения к старому адресу.

### Шаг 5. Проверьте результат

```bash
sudo scripts/verify.sh
sudo scripts/smoke-test.sh
```

Затем вручную:

- войдите в систему;
- сравните число встреч с прежним;
- откройте 2–3 старые записи и протокол;
- проведите встречу двух участников;
- откройте **Хранение и журналы → Целостность хранилищ**.

### Шаг 6. Уберите страховочные копии ⛔

Сделайте это после приёмки, обычно через неделю работы. До тех пор на диске занято вдвое больше места.

```bash
cd /opt/peregovorka
sudo docker compose -p <проект> --project-directory deployment --env-file .env -f deployment/compose.yml \
  exec postgres dropdb -U <POSTGRES_USER> <имя>_before_restore_<время>
sudo sh -c 'ls -d /srv/peregovorka-data/*.before-restore-*'
sudo rm -rf /srv/peregovorka-data/recordings.before-restore-<время>
```

`<проект>` и `<POSTGRES_USER>` возьмите из `.env`, после установки одной командой оба равны `peregovorka`. Точное имя базы печатает `restore.sh`. Команда `ls` показывает все отложенные каталоги, удалите каждый так же, как `recordings`. Перед удалением каталогов убедитесь, что восстановленные файлы открываются: вернуть удалённое нельзя.

## Что получится

- `verify.sh` без `FAIL`, `Smoke test: PASS`.
- Количества встреч совпадают, старые материалы открываются.
- В паспорте экземпляра записано, что случилось и что сделано.

## Если не получается

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| `pg_restore` или проверка копии отказали | дамп повреждён, рабочая база не тронута | возьмите предыдущий набор |
| `Дамп не читается`, а контрольная сумма сошлась | контейнер `postgres` не запущен | `sudo scripts/ctl.sh start postgres`, повторите |
| `pg_dump завершился с ошибкой` при восстановлении | база повреждена, страховочный дамп не снимается; `restore.sh` остановился, ничего не изменив | пропустить этот дамп нельзя: восстанавливайте на новом сервере, шаг 4 |
| Сервер предупреждает о другой схеме | копия от другой версии | поставьте нужную версию: `rollback.sh` или `update.sh --ref` |
| Зашифрованные настройки не читаются | другой `APP_MASTER_KEY` | впишите ключ из копии `.env` |
| Приложение не подключается к базе | скопирован старый `POSTGRES_PASSWORD` | верните пароль нового сервера |
| Файлы встреч не открываются | архив не восстановлен, контейнеры не пересозданы или хранилище не подключено | шаг 4, пункты 5 и 7 |
| «Недопустимый Origin» | новый адрес не совпал с `APP_PUBLIC_URL` | [Решение проблем: HTTPS и обратный прокси](Решение-проблем-HTTPS-и-прокси) |
