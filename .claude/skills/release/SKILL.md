# Выпуск версии Peregovorka

Главное правило: **CHANGELOG — для пользователя. HISTORY — для разработчика. README — витрина продукта.** Полные правила — [docs/VERSIONING.md](../../../docs/VERSIONING.md).

Пройди шаги по порядку и не пропускай ни одного, даже если о нём не просили:

1. **VERSION.** Решить: patch (законченный проверенный блок, исправления) или minor (заметный функциональный этап). Только для документации версию не поднимать.
2. **CHANGELOG.md, раздел `## Unreleased`.** Подразделы `### Новые возможности`, `### Улучшения`, `### Исправления`, `### Для администраторов` (пустые не писать).
   Простым языком: что появилось и чем полезно, что стало лучше. Никаких имён классов и файлов, «тест падал», «CI был красный», деталей рефакторинга.
   В «Для администраторов» — порты, миграции, требования, ручные действия, изменения доступа и API.
3. **HISTORY.md** — технический журнал выпуска: причины, решения, что и как проверено (реально проверено / автотест / code review / не проверено), ограничения.
4. **PROJECT.md** — состояние, ближайшие планы, известные проблемы.
5. **README.md** — проверить: новые ключевые возможности, устаревшие скриншоты (≤ 2, без ошибок на снимке), Быстрый старт, требования и порты, интеграции, API, ссылки на docs/. Изменилось — обновить в этом же выпуске.
6. **docs/** — обновить затронутые документы.
7. **Проверки** — тесты backend и frontend, сборка; при изменениях комнаты — живые сценарии `tests/live/`; после push — зелёный CI.
8. **Выпуск** — `./scripts/release.sh patch|minor` (переносит Unreleased в раздел версии, пишет VERSION, коммит «Релиз X.Y.Z», тег), затем `./scripts/release.sh push`.

В отчёте владельцу перечисли, что сделано на каждом шаге, и честно отметь непроверенное.
