# Electron-клиент для Windows: проверенные решения

Общие правила Electron (contextIsolation, preload, IPC) — навык `electron-development`; его разделы Auto Updates (`electron-updater`) и Testing (Spectron/Playwright) здесь **не применяются** — см. «Проверки окна» и references/signing-updates.md. Здесь — то, что на практике ломалось у Windows-клиента и как это
предотвращено. Подробности: [references/windows-pitfalls.md](references/windows-pitfalls.md) (ловушки Windows и CI),
[references/signing-updates.md](references/signing-updates.md) (подпись, ключи, обновления, корпоративные сборки).

## Три режима — одна команда на каждый
1. **Разработка:** Electron из исходников + наблюдение за файлами: правка интерфейса → сборка (esbuild, доли секунды) и `Page.reload` окна по CDP;
   правка главного процесса или preload → перезапуск Electron. Журнал главного процесса — в терминал.
2. **Предварительная проверка:** `electron-builder --dir` (asar, предохранители, значки — как в выпуске, но без установщика) и проверки **на собранной
   программе** с пустым профилем. Под Linux ещё `--win dir -c.win.signAndEditExecutable=false` → архив для запуска на Windows без Wine.
3. **Выпуск:** только после 1–2 и зелёной предварительной проверки на Windows: EXE/MSI, подпись, установка/обновление/удаление в CI, публикация.
Исправление интерфейса не должно требовать сборки установщика, серверного CI и выпуска.

## Обязательная проверка первого запуска
* Пустой профиль — стандартный ключ Chromium `--user-data-dir=<tmp>`: Electron переносит туда `userData` (настройки, журналы); своего кода не нужно.
* Ожидать **реальный** локальный экран (заголовок мастера), а не «окно открылось»; провал — любые ошибки консоли окна (`Runtime.exceptionThrown`,
  `console.error`, `Log.entryAdded` level=error) и строки ERROR в журнале главного процесса.
* Проверять **мутацией**: убрать из сборки CSS/JS — проверка обязана упасть.
* Запуск без сети и без доступного сервера: локальные настройки, переключение организаций, диагностика должны работать (адреса TEST-NET `192.0.2.x`).
* Под Linux пути Windows не проверяются: обязательна та же проверка на Windows (CI `windows-latest` или машина разработчика).

## Локальная оболочка `app://`
* Свой протокол + CSP — лучше `file://`. Путь → адрес **только** `url.pathToFileURL()`; ручная склейка `file://`+путь на Windows даёт
  `file://C%3A/…` (диск становится именем хоста) → «not found», а под Linux всё работает. Модульный тест с `path.win32` и кириллицей в пути.
* Окно не должно оставаться пустым: через несколько секунд после загрузки проверить отрисовку (с повторами — первый запуск под антивирусом медленный),
  `did-fail-load` / `render-process-gone` → диалог «Повторить / Журналы / Выйти».
* Каждая команда, которую вызывает оболочка, должна быть в списке разрешённых каналов preload и иметь обработчик — проверять тестом по исходникам.

## Проверки окна: CDP, а не Playwright
Playwright `_electron` требует `--inspect` главного процесса, а предохранитель `EnableNodeCliInspectArguments=false` (так и должно быть в выпуске) его
закрывает. Окна доступны по `--remote-debugging-port`: небольшой клиент CDP на WebSocket (Node ≥ 22) — `Runtime.evaluate`, `Page.reload`,
`Page.captureScreenshot` **с пределом времени** (в сеансе без рабочего стола снимок может не прийти никогда), `Emulation.setDeviceMetricsOverride` для
масштабов 150/200 %. Вёрстку проверять кодом: горизонтальная прокрутка страницы и **внутри блоков**, обрезанный текст, наложения элементов, разные
высоты однотипных кнопок; снимки всё равно смотреть глазами.

## Диагностика «пустое окно / not found / не запускается»
Ключ `--debug-log` (или переменная окружения): журнал главного процесса в терминал, пути (`userData`, `app.getAppPath()`, наличие файлов оболочки),
`preload-error`, `console-message` окна оболочки (предупреждения и ошибки — в журнал всегда), ответы протокола 404, `uncaughtException`/`unhandledRejection`.
Отчёт без интерфейса `--diagnostics=<файл>` с разделом «отрисована ли оболочка» — его же проверяет CI у установленной программы.

## Ловушки (кратко; подробно — в references)
* Реестр (`HKLM\SOFTWARE\Policies\…`): **не `reg query`** — печатает в кодировке консоли, кириллица → «????». `reg export` пишет UTF-16 → разбор файла.
* `.ps1` для Windows PowerShell 5.1 — только UTF-8 **с BOM**; PowerShell 7 под Linux ошибку не покажет.
* MSI через COM `WindowsInstaller.Installer`: освобождать **все** объекты (база, представления, записи) и `GC.Collect()` — иначе signtool: «file is being used».
* EXE-установщик поверх установленного MSI — запретить (`customInit`, код выхода 2): две копии программы.
* В окружении агента может стоять `ELECTRON_RUN_AS_NODE=1` — снимать перед запуском Electron; Chromium запрещает порты 1 и 9.
* **Устройства (камера, микрофон, динамики):** `deviceId` Chromium у каждого адреса сайта свой — выбор из окна оболочки (`app://shell`) не подойдёт странице организации. Хранить и передавать **название** устройства (`label`), страница сопоставляет его сама. Названия видны без `getUserMedia`, только если обработчик проверки разрешений (`setPermissionCheckHandler`) отвечает «да» на `media`.
* **Мост страницы организации:** `peregovorkaDesktop.api` остаётся `1` — веб-интерфейс принимает мост только при `api === 1` (`frontend/src/desktop.ts`); поднять число значит отключить уведомления у всех старых серверов. Новое — отдельными свойствами с проверкой наличия (`media`, `openSoundSettings`).
* **Разрешения на устройства для оболочки** выдаются только главному окну и только адресу `app://shell/` (сессия по умолчанию иначе отказывает всем): окно выбора экрана и индикатор их не получают.
* Системные окна Windows (`rundll32 … mmsys.cpl,,1`, `ms-settings:`) — только фиксированные команды по закрытому перечню видов; под Linux проверяются лишь отказ неизвестного вида и «только Windows», сам запуск — вручную на Windows.
* Проверки с устройствами под Xvfb: запускать приложение с `--use-fake-device-for-media-stream` (поддельные микрофоны и камера Chromium, шкала уровня оживает); `check.mjs av` и `tests/live/desktop_av.py`.
