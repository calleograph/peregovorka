# Подпись приложения Windows, корпоративные сборки и ключи обновлений

Два разных ключа — две разные задачи:

| | Сертификат подписи кода (Authenticode) | Ключ обновлений (Ed25519) |
| --- | --- | --- |
| Что подписывает | `Peregovorka.exe`, установщики EXE и MSI | манифест `update.json` новых версий |
| Кто проверяет | Windows (SmartScreen, UAC, AppLocker, «Доверенные издатели») | само приложение перед загрузкой и установкой обновления |
| Где закрытая часть | хранилище Windows подписывающего узла или секрет CI (PFX) | секрет CI `DESKTOP_UPDATE_KEY` или файл на подписывающем узле |
| Что публикуется | открытый сертификат `.cer` | открытый ключ (base64), встроенный в сборки |

Закрытые ключи, PFX и пароли **никогда** не попадают в репозиторий, журналы CI, установочные пакеты, базу данных Peregovorka и браузер.
CI проверяет это перед публикацией (шаг «В пакетах нет закрытых ключей и паролей»).

## Режимы подписи в CI (`.github/workflows/desktop.yml`)

| Что настроено | Вид сборки | Выпуск по тегу `desktop-vX.Y.Z` |
| --- | --- | --- |
| ничего | неподписанная | «Тестовая сборка», предварительный |
| самоподписанный сертификат (издатель = субъект) | подписанная тестовая | «Тестовая сборка», предварительный, с `Peregovorka-publisher.cer` |
| сертификат удостоверяющего центра | доверенная | обычный выпуск |
| `DESKTOP_RELEASE_MODE=trusted` + нет сертификата УЦ или ключа обновлений | — | **сборка падает** (а не публикует молча неподписанное) |

На ветках без секретов CI создаёт на своей машине **одноразовые** тестовый сертификат и ключ обновлений, чтобы проверять весь путь подписи
и обновления; они исчезают вместе с машиной и в выпуски по тегу не попадают.

Проверки CI: назначение Code Signing, наличие закрытого ключа, срок; `Get-AuthenticodeSignature` и `signtool verify /pa` для `Peregovorka.exe`, EXE и MSI;
для самоподписанного — что **до** установки доверия подпись не считается доверенной (на компьютерах сотрудников так и будет, пока администратор не
распространит сертификат); обновление установленного приложения из самого приложения; агент подписи (см. ниже).

### Настройка владельцем проекта (один раз)

1. Подписывающий узел издателя (Linux/macOS с OpenSSL 3) — собственный сертификат и ключ обновлений:

   ```bash
   desktop/signing/signing-node-init.sh            # → ~/.local/share/peregovorka-signing (права 0700/0600), повторный запуск ничего не перезаписывает
   ```

   Создаются `publisher.pfx` + `publisher.pfx.pass` (RSA 3072, SHA-256, EKU 1.3.6.1.5.5.7.3.3, 3 года), `publisher.cer` (только открытая часть),
   `update-key.pem` + `update-key.pub` (Ed25519), `meta.json` (издатель, срок, серийный номер, отпечатки SHA-1/SHA-256).

2. Секреты и переменные репозитория (Settings → Secrets and variables → Actions) — например, `gh` из каталога ключей:

   ```bash
   cd ~/.local/share/peregovorka-signing
   base64 -w0 publisher.pfx | gh secret set WINDOWS_CERT_PFX
   gh secret set WINDOWS_CERT_PASSWORD < publisher.pfx.pass
   gh secret set DESKTOP_UPDATE_KEY < update-key.pem
   gh variable set DESKTOP_UPDATE_PUBKEY --body "$(cat update-key.pub)"
   # необязательно: метка времени (подпись остаётся действительной после истечения сертификата)
   gh variable set WINDOWS_TIMESTAMP_URL --body "http://timestamp.example.org"
   ```

3. Сертификат от удостоверяющего центра (когда появится): тот же `WINDOWS_CERT_PFX`/`WINDOWS_CERT_PASSWORD`, затем `gh variable set DESKTOP_RELEASE_MODE --body trusted`.
   **Ключ обновлений при этом не меняется** — иначе установленные клиенты перестанут принимать обновления (смена ключа — в docs/DESKTOP.md, «Обновления»).

Секреты GitHub — хранилище «доверенного CI». Если организация не хранит ключи в CI, подписывайте на своём узле (агент, ниже) — CI тогда собирает
неподписанные пакеты, а подпись выполняет узел.

## Подписывающий агент и раздел администрирования

**Администрирование → Windows-клиент → Подпись и корпоративные сборки** (только администраторы сервера; все действия — в журнале аудита).

Устройство:

* **Подписывающий узел** — выделенный компьютер Windows организации с агентом `desktop/signing/Peregovorka-Signer.ps1` (PowerShell 5.1 или 7).
  Закрытый ключ — в `Cert:\LocalMachine\My` этого узла, в том числе неэкспортируемый; сервер его не получает.
* Подключение — одноразовым кодом из раздела (`Enroll`); агент получает свой токен (на сервере — только SHA-256; на узле — DPAPI LocalMachine,
  каталог `%ProgramData%\Peregovorka\Signer` доступен только администраторам и SYSTEM). `Install` регистрирует задачу планировщика от SYSTEM.
* Агент **сам опрашивает** сервер по HTTPS и выполняет только задания четырёх видов: `create_cert`, `register_cert`, `check_cert`, `build`.
  Параметры — данные (название, адрес сервера организации, флаги), не команды. Удалённого выполнения команд нет.
* Источник исходных пакетов задаётся **на узле** (`-ReleaseBase`, по умолчанию выпуски издателя), не сервером. Каждый пакет сверяется с `SHA256SUMS.txt`
  выпуска и, если задан `-PublisherThumbprint`, с подписью издателя; изменённый или неподтверждённый пакет не подписывается.
* Сервер принимает результат, только если SHA-256 загруженных файлов совпадает с отчётом агента и подпись EXE/MSI действительна на узле **выбранным
  сертификатом**. Сведения о сертификате (издатель, срок, назначение, отпечатки) сервер берёт из самого сертификата (DER), а не со слов агента.
* Отключить узел — «Отключить»: токен перестаёт действовать, невыполненные задания отменяются.

Вкладки раздела:

* **Сертификаты** — узлы и сертификаты: тип (собственный / организации), издатель, кем выдан, серийный номер, SHA-256, назначение, срок, цепочка
  и пробная подпись на узле, доступность ключа (без содержимого). «Создать собственный сертификат», «Подключить сертификат компании» (по отпечатку),
  «Проверить сертификат», «Скачать публичный сертификат (.cer)», «Сделать активным / заменить текущий».
* **Корпоративные установщики** — мастер выпуска: организация, адрес сервера, версия, сертификат, политика обновлений, автозапуск, разрешение добавлять
  организации, EXE/MSI → подписанные пакеты, SHA-256, скачивание. Настройки организации вписываются в таблицу `Property` копии MSI **до** подписи
  (те же свойства, что принимает `msiexec`: `SERVERS`, `ALLOWADDSERVERS`, `AUTOSTART`, `UPDATEMODE`, `UPDATEURL`); EXE переподписывается без изменений,
  а настройки к нему — файлом политик `.reg` (или GPO по шаблону ADMX). Отдельного кода приложения для организации нет. Публичные выпуски GitHub
  корпоративные сборки не заменяют.
* **Обновления** — канал издателя (адрес и **открытый** ключ проверки) и корпоративный канал этого сервера: администратор публикует версию, сервер
  проверяет подпись манифеста и SHA-256 установщика и раздаёт их как есть по `https://<сервер>/api/v1/desktop/channel/update.json` (для политики
  `UpdateUrl`). Подменить обновление через сервер нельзя: клиент проверяет подпись издателя сам.
* **Диагностика подписи** — связь с узлами, signtool, закрепление издателя, истекающие сертификаты, неуспешные задания с причиной, команды проверки.
* **Инструкции** — AD CS, GPO, развёртывание MSI, замена сертификата (тот же текст, что ниже, с кнопками копирования).

### Сертификат из корпоративного УЦ (Microsoft AD CS)

1. Шаблон с назначением **Code Signing** (копия «Подписывание кода»), ключ RSA 3072+ или ECDSA P-256, без экспорта ключа.
2. Право выпуска (Enroll) — только учётной записи подписывающего узла или группе уполномоченных администраторов.
3. Запрос на узле (имя шаблона — пример; шаблон должен существовать в вашем AD CS; выполняет уполномоченный администратор):

   ```powershell
   Get-Certificate `
     -Template "PeregovorkaCodeSigning" `
     -CertStoreLocation "Cert:\LocalMachine\My"
   ```

4. Проверка назначения и закрытого ключа:

   ```powershell
   Get-ChildItem Cert:\LocalMachine\My |
   Where-Object {
       $_.HasPrivateKey -and
       $_.EnhancedKeyUsageList.ObjectId -contains "1.3.6.1.5.5.7.3.3"
   } |
   Select-Object Subject, Thumbprint, NotAfter
   ```

5. Регистрация: «Подключить сертификат компании» → отпечаток, затем «Проверить сертификат».
6. Пробный выпуск и проверка подписи:

   ```powershell
   Get-AuthenticodeSignature .\Peregovorka-Setup-1.0.1-meet.example.org.exe | Format-List Status, SignerCertificate
   signtool verify /pa /v .\Peregovorka-1.0.1-meet.example.org-x64.msi
   ```

7. Доверие — групповой политикой (ниже). Закрытый ключ корневого УЦ не нужен и не запрашивается.

PFX от любого УЦ импортируется **на узле** (пароль вводится там же, ключ становится неэкспортируемым): `.\Peregovorka-Signer.ps1 ImportPfx -Path C:\Temp\codesign.pfx`.

### Доверие через групповые политики

*Конфигурация компьютера → Политики → Конфигурация Windows → Параметры безопасности → Политики открытого ключа*:

* **Доверенные корневые центры сертификации** — корневой сертификат УЦ организации (для собственного сертификата Peregovorka — его `.cer`);
* **Промежуточные центры сертификации** — промежуточные УЦ цепочки;
* **Доверенные издатели** — сертификат издателя (`.cer` из раздела).

Peregovorka не меняет доверенные корневые сертификаты на компьютерах сотрудников и не вносит изменения в доменные политики — это делает администратор.

### Замена сертификата

Новый сертификат выпускается **на того же издателя** (то же имя субъекта) до истечения старого; его `.cer` заранее распространяется в «Доверенные
издатели»; затем «Сделать активным». Установленные клиенты продолжают обновляться: приложение сверяет имя издателя, а не отпечаток. Подписи с меткой
времени остаются действительными и после истечения старого сертификата.

## Что проверено и что требует корпоративного стенда

Автоматически: серверные тесты `backend/tests/test_signing.py` (права и аудит, токен агента — только хеш и отзыв, сертификаты без EKU / истёкшие /
подменённые, приём только подтверждённых и правильно подписанных пакетов, две организации с разными сертификатами, корпоративный канал с проверкой подписи);
протокол агента — живой прогон PowerShell 7 против стенда; на Windows CI — собственный неэкспортируемый сертификат, отказ для сертификата без Code Signing
и истёкшего, отказ для изменённого пакета, корпоративные MSI/EXE двух организаций с разными сертификатами, установка корпоративного MSI.

Требует корпоративного стенда и не может быть объявлено проверенным без него: сертификат настоящего AD CS (шаблон, цепочка, отзыв), распространение
доверия GPO на компьютеры сотрудников, SmartScreen для сертификата УЦ, развёртывание MSI групповой политикой, агент как задача от SYSTEM на узле домена.
