# Версии и выпуск

Схема: `MAJOR.MINOR.PATCH`, пока проект до 1.0 — см. «Какую часть версии менять» ниже.

> **Главное правило документации: CHANGELOG — для пользователя. HISTORY — для разработчика. README — витрина продукта.**
> Оно действует постоянно и выполняется при каждом выпуске без напоминаний.

## Три документа — три читателя

| Документ | Читатель | Что в нём | Чего в нём быть не должно |
| --- | --- | --- | --- |
| [CHANGELOG.md](../CHANGELOG.md) | пользователь и администратор | что появилось, что стало лучше, что исправлено, что нужно знать администратору | имена классов и файлов, детали рефакторинга, «тест падал», «CI был красный», «stash перенесён», длинные объяснения причин |
| [HISTORY.md](../HISTORY.md) | разработчик | технический журнал: причины, решения, что проверено и как, известные ограничения | — |
| [README.md](../README.md) | тот, кто впервые открыл проект | короткая продуктовая страница: что это, сильные стороны, быстрый старт, ссылки в `docs/` | справочник на сотни строк, внутренние подробности |

### Формат раздела CHANGELOG

```text
## 0.11.0 (дата)

### Новые возможности
- Что теперь можно сделать — одной-двумя фразами, зачем это полезно.

### Улучшения
- Что стало удобнее, быстрее, стабильнее.

### Исправления
- Исправлена ошибка, из-за которой … (как это выглядело для пользователя, а не как устроено внутри).

### Для администраторов
- Новые порты, миграции, системные требования, ручные действия, изменения доступа и API. Коротко, но не скрывать.
```

Пустые подразделы не пишутся. Язык — понятный обычному пользователю: не «`Journal.stop()` больше не крутится при database is locked», а «Исправлена ошибка, из-за которой
приложение могло долго завершать работу при временной блокировке базы данных». Подзаголовки раскладываются по группам окна «Что нового» перед обновлением
(`backend/app/services/changelog.py`), поэтому их названия менять не нужно.

### README — что проверять при каждом заметном выпуске
- появились ли новые ключевые возможности (блок возможностей наверху и раздел «Возможности»);
- не устарели ли скриншоты (не больше двух — комната и администрирование, без сообщений об ошибках, на стенде с вымышленными данными);
- не изменились ли «Быстрый старт», требования и порты;
- не появились ли новые интеграции или разделы API;
- не появились ли новые документы в `docs/`, на которые нужна ссылка.

Если что-то изменилось — README обновляется **в том же выпуске**. Структура: описание → блок сильных сторон → Быстрый старт → Возможности → Скриншоты →
Архитектура → API → Интеграции → Установка → Безопасность → Документация. Подробности — ссылками в `docs/`.

## Единый источник версии

**Файл [`VERSION`](../VERSION)** (одна строка `X.Y.Z`). Всё остальное берётся из него:

| Где | Как |
| --- | --- |
| образы backend, asr, web | `update.sh`, `rebuild.sh`, `install.sh` читают `VERSION` (`scripts/lib/common.sh → host_version_info`) и передают `APP_VERSION` при сборке; commit — из git (`APP_GIT_COMMIT`), время — `APP_BUILT_AT` |
| интерфейс | строка «`0.1.4 · 6123022`» на экране входа, в «Состоянии системы» и в «Обновления и версии» (версия образа · первые 7 символов commit) |
| `/api/v1/version`, `/version.json`, ASR `/readyz` | те же значения, запечённые в образ |
| страница «Обновления и версии» | «Установлено на сервере» и «Опубликовано на GitHub» — версия и commit; при наличии новой версии показано, что в ней нового (разделы CHANGELOG новее установленной) |
| `frontend/package.json` и `package-lock.json` | обновляет `release.sh` |
| git-тег и GitHub Release | тег `vX.Y.Z` создаёт `release.sh`; workflow `.github/workflows/release.yml` публикует релиз с описанием из CHANGELOG |
| проверка | `./scripts/release.sh check` (и CI-задача `version`): `VERSION` = верхний раздел CHANGELOG = `package.json`; на сборке тега — тег = `vVERSION` |

В `.env` версия и commit **не задаются** (старые строки `APP_VERSION`/`APP_GIT_COMMIT` в существующем `.env` игнорируются: значения берутся из репозитория).

## Как выпустить версию — чек-лист

Выполняется перед каждым выпуском, по порядку:

1. **VERSION** — какую часть версии поднять (patch / minor), см. ниже. Сам файл меняет только `release.sh`.
2. **CHANGELOG** — раздел `## Unreleased` написан пользовательским языком в формате выше.
3. **HISTORY** — технические подробности выпуска: причины, решения, проверки, ограничения.
4. **PROJECT** — актуальны состояние, планы и известные проблемы.
5. **README** — проверен по списку выше и обновлён, если нужно.
6. **docs/** — затронутые документы обновлены (новые возможности, порты, API, настройки).
7. **CI** — зелёный на коммите выпуска; живые сценарии `tests/live/` прогнаны, если менялась комната.
8. **Выпуск** — `./scripts/release.sh patch|minor`, затем `./scripts/release.sh push`.

Подробно о шагах выпуска:

1. По ходу работы дописывайте заметные изменения в раздел `## Unreleased` файла `CHANGELOG.md`.
2. `./scripts/release.sh patch` — следующая версия (`minor` — `0.2.0`; либо явная: `./scripts/release.sh 0.2.0`). Скрипт требует чистое рабочее дерево и непустой «Unreleased»,
   переименовывает его в `## X.Y.Z (дата)`, оставляя пустой «Unreleased» сверху, пишет `VERSION` и `frontend/package*.json`, делает commit «Релиз X.Y.Z» и аннотированный тег `vX.Y.Z`.
3. `./scripts/release.sh push` — отправляет ветку и тег. CI проверяет согласованность, workflow «Release» создаёт GitHub Release `Peregovorka X.Y.Z`.

Версию меняет **только** `release.sh` — руками `VERSION` править не нужно. Каждый выпуск, который попадает на серверы, должен получать новую версию: так по интерфейсу сразу видно,
какая редакция установлена и что изменилось. CI напоминает (замечание в задаче `version`), если после последнего тега есть новые коммиты без новой версии.

## Что видит администратор при обновлении

* `./scripts/update.sh` и веб-обновление собирают образы с новой версией; итог печатает `Version: 0.1.3 → 0.1.4`, а `./scripts/verify.sh` сверяет версию и commit образов с `VERSION` и git HEAD
  (расхождение — предупреждение с советом `./scripts/rebuild.sh`).
* `commit unknown` при штатной сборке невозможен: `update.sh` и `rebuild.sh` останавливаются, если commit определить нельзя (определение устойчиво к «dubious ownership»
  и работает без команды `git`, читая `.git`). «unknown» остаётся только у образа, собранного вручную `docker compose build` — интерфейс помечает его «собран вне штатного обновления».
* Теги и релизы GitHub есть начиная с `0.1.4`; описания `0.1.0 … 0.1.3` в CHANGELOG составлены ретроспективно.

## Какую часть версии менять
Версия — `MAJOR.MINOR.PATCH`; пока проект до 1.0:
* **patch** (`0.8.1`, `0.8.2`) — исправления и небольшие пакеты доработок интерфейса, не вводящие нового крупного функционального блока: `./scripts/release.sh patch`;
* **minor** (`0.9.0`) — следующий существенный функциональный этап (новый блок возможностей); `./scripts/release.sh minor`.
Не поднимать minor при каждой мелкой доработке.
