# Peregovorka для Windows — устройство и разработка

Настольное приложение для Windows 10/11 (x64), которое подключается к корпоративным серверам Peregovorka. Веб-версия работает как прежде. Приложение не
вводит отдельной бизнес-логики: интерфейс встреч, чатов, истории и администрирования — тот же веб-интерфейс сервера, открытый в изолированном окружении,
а приложение добавляет то, чего нет в браузере: несколько организаций сразу, трей, уведомления Windows, сохранённый вход, ссылки `peregovorka://`,
выбор экрана, установщики и корпоративные политики.

Документы: для пользователя — [DESKTOP_USER.md](DESKTOP_USER.md), для администратора — [DESKTOP_ADMIN.md](DESKTOP_ADMIN.md), для поддержки —
[DESKTOP_SUPPORT.md](DESKTOP_SUPPORT.md). История изменений клиента — [desktop/CHANGELOG.md](../desktop/CHANGELOG.md) (версия клиента своя, см. ниже).

## Архитектура

```
┌──────────────────────── главное окно (BrowserWindow, обычная рамка Windows) ────────────────────────┐
│ оболочка app://shell (доверенная,      │  страница сервера организации — WebContentsView            │
│ из пакета приложения):                 │  раздел persist:org-<id>, песочница, без Node.js,          │
│ организации, мастер, настройки,        │  мост preload-org: notify / setState / onCommand           │
│ диагностика                            │  (неактивные организации — скрыты, но работают)            │
└────────────────────────────────────────┴────────────────────────────────────────────────────────────┘
главный процесс (Node.js): организации, сохранённый вход (DPAPI), трей, уведомления, ссылки, обновления, политики, журнал
```

| Часть | Где | Что делает |
| --- | --- | --- |
| Главный процесс | `desktop/src/main/` | Окно и раскладка (`window.ts`), организации и их разделы, разрешения, навигация, загрузки (`orgs.ts`), сохранённый вход (`trust.ts`), проверка сервера (`probe.ts`), трей и автозапуск (`tray.ts`), уведомления (`notify.ts`), выбор экрана и индикатор (`picker.ts`), обновления (`updater.ts`, `updateCore.ts`), политики и настройки (`settings.ts`), диагностика (`diagnostics.ts`), журнал (`log.ts`). |
| Общие правила | `desktop/src/common/` | Чистые функции с тестами: адреса и «тот же сервер» (`urls.ts`), ссылки `peregovorka://` (`links.ts`), политики реестра (`policy.ts`), положение окна (`bounds.ts`), маскирование (`redact.ts`), совместимость (`version.ts`), ошибки сети (`neterr.ts`), без повторов уведомлений (`dedupe.ts`). |
| Оболочка | `desktop/src/shell/` | Боковая панель организаций, мастер подключения, состояние «нет связи», настройки, диагностика, окно выбора экрана, индикатор. Без фреймворка; разметка без `innerHTML`. Токены оформления — общие с веб-интерфейсом (`frontend/src/tokens.css`), пиктограммы — из `frontend/src/components/Icons.tsx` (собираются при сборке), шрифты Inter/Manrope — локально. |
| Мосты | `desktop/src/preload/` | `shell.ts` — закрытый перечень команд оболочки; `org.ts` — три действия для страницы сервера. |
| Веб-интерфейс | `frontend/src/desktop.ts`, `desktopMeetings.ts` | Платформенный слой (в браузере ничего не делает): уведомления чатов и встреч, состояние, команды. |
| Сервер | `backend/app/api/desktop.py` | `/api/v1/desktop/info` (совместимость), `trust` / `resume` / `forget` (сохранённый вход). |

### Почему страница сервера, а не встроенная копия интерфейса

Интерфейс всегда той же версии, что и API сервера: клиент и сервер выпускаются независимо, совместимость определяет уровень протокола приложения
(`/api/v1/desktop/info` → `api`, `min_client`). Локальный веб-сервер не поднимается. Страница сервера — недоверенное содержимое: ей не дают ни Node.js,
ни файловой системы, ни секретов приложения и других организаций.

## Безопасность

* Каждое окно и представление: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`, без `<webview>`.
* Оболочка — схема `app://shell` из пакета приложения, строгий CSP (`script-src 'self'`, без `unsafe-inline`/`unsafe-eval`), раздел по умолчанию без разрешений.
* IPC: главный процесс принимает команду, только если отправитель — нужное окно, главный фрейм и адрес (оболочки — `app://shell/`, организации — её origin);
  все поля проверяются (типы, длины, перечни).
* Навигация страницы — только в пределах своего сервера; внешние `http(s)`/`mailto`/`tel` — в системном браузере; `file:`, `javascript:` и прочие — никогда.
  Окна, которые открывает страница своего сервера, получают те же ограничения и тот же раздел.
* Разрешения раздела организации: камера/микрофон, полный экран, запись в буфер обмена, выбор динамика — только её адресу; веб-уведомления, геолокация,
  USB/HID/последовательные порты и прочее — запрещены. Показ экрана — только через окно выбора приложения.
* TLS: решение о доверии принимает Chromium по хранилищу сертификатов Windows; проверка не отключается ничем (ключи Chromium, `setCertificateVerifyProc`,
  `certificate-error` не принимают недоверенный сертификат). Единственное чтение сертификата в обход — показ «кем выдан» человеку **после** отказа
  (`probe.ts`, `certDetails`), данные по такому соединению не передаются.
* Предохранители Electron в сборке (`electron-builder.yml`): нет запуска как Node.js, нет `NODE_OPTIONS` и отладчика по ключу, код только из asar с проверкой
  целостности, cookie шифруются DPAPI.
* `desktop/scripts/security-check.mjs` в CI не даёт этого незаметно ослабить.

## Сохранённый вход (доверенное устройство)

Пароль в приложении не вводится и не хранится: вход — обычная страница входа сервера (AD, локальная учётная запись, 2FA, смена пароля, лимит сеансов).
После полноценного входа главный процесс просит у сервера **токен устройства** (`POST /api/v1/desktop/trust` с cookie и CSRF этой организации). Сервер
выдаёт его только приложению: запрос без `Origin` и с `Sec-Fetch-Site` = `none` или без него — так помечает запросы сетевой модуль главного процесса,
а страницу браузер всегда помечает иначе, поэтому даже XSS на странице токен не получит. Токен хранится в `%APPDATA%\Peregovorka\trust\<id>.bin`,
зашифрованный DPAPI текущего пользователя Windows (`safeStorage`).

При запуске: действующий сеанс → страница; иначе `POST /api/v1/desktop/resume` → новый сеанс (cookie — в раздел этой организации) и **новый** токен,
прежний гаснет (захват `GETDEL`, одновременный повтор не откроет два сеанса). Сервер проверяет то же, что при входе: учётная запись активна, в каталоге не
отключена, пароль в каталоге не менялся (`pwdLastSet`), правила допуска пропускают. Срок — `auth_security.desktop_trust_days` (по умолчанию 30, 0 —
выключено) **от входа паролем**, продления срок не сдвигают. Отзыв: выход, завершение сеанса в «Активных устройствах», «Выйти на остальных», смена
пароля, отключение учётной записи, удаление организации в приложении. 401 — токен забывается и показывается вход этой организации; 503 (каталог
недоступен) — токен сохраняется, приложение повторит позже. Устройство в «Активных устройствах» подписано «Peregovorka для Windows X.Y.Z».

## Уведомления

* Чаты: `chatStore` вызывает `desktopNotify`, когда страницу не видно (окно свёрнуто, в трее, открыта другая организация). Метка — `chat:<переписка>:<номер>`.
* Встречи (`desktopMeetings.ts`, опрос раз в 2 мин): скоро начало (за 10 мин), новая встреча в календаре, перенос, отмена, готов протокол — сравнением снимков
  «Предстоящих встреч» и «Истории». Первый опрос после входа только запоминает состояние.
* Главный процесс: одно событие — одно уведомление (организация + метка, 10 мин), «Не беспокоить», без звука, скрытие текста, политики; нажатие открывает
  нужную организацию и раздел (`?chat=<id>` открывает переписку). Режим фокусировки Windows применяет сама Windows.

## Ссылки `peregovorka://`

`peregovorka://open?url=<обычная ссылка встречи>` — ссылка не несёт команд. Разрешены только `https`, без логина/пароля в адресе, один параметр `url`,
пути `/`, `/history`, `/rooms/<…>`, `/m/<…>`, `/p/<…>`, `/guest/<…>`, `/history/<id>`. Сервер ссылки сопоставляется с подключёнными организациями; если
такой нет — мастер подключения с этим адресом (если политика разрешает). На странице встречи из календаря в браузере на Windows есть «Открыть в приложении»;
обычная ссылка продолжает работать в браузере.

## Первый запуск и локальная оболочка

Мастер подключения, список организаций, настройки, диагностика и обновления — часть установленного приложения (`app://shell/`, файлы из `app.asar`):
они открываются без сети и без доступного сервера. Шаги: приветствие → адрес сервера («Проверить подключение», «Продолжить», «Назад»; проверки HTTPS,
сертификата, совместимости API) → вход на странице сервера (его способы входа: домен, локальная учётная запись, 2FA) → интерфейс организации.
Следующие запуски открывают последнюю организацию; истёкший вход — форма входа этой организации, а не мастер.

`app://shell/…` отдаёт `protocol.handle` из каталога `dist/shell` пакета; путь превращается в `file:`-адрес только через `pathToFileURL`
(`src/common/shellfile.ts`). **Выпуск 1.0.0** склеивал адрес вручную — на Windows получалось `file://C%3A/…` (буква диска как имя хоста), и окно вместо мастера
показывало `not found`; на Linux путь начинается с `/`, поэтому испытания под Linux дефект не видели. Теперь: модульный тест с путями Windows, проверка
отрисовки оболочки через 3 с после загрузки (иначе — диалог «Повторить / Папка журналов / Выйти», не пустое окно), раздел `shell` в отчёте
`--diagnostics`, и испытание **установленного** EXE в Windows CI (`scripts/win-e2e.mjs`, со снимками окна).

## Обновления

Обновление — **полным установщиком** поверх установленной версии (отдельные файлы программы не заменяются). Порядок: проверка канала (автоматически раз в
несколько часов, «Проверить обновления» в настройках и в трее) → номер версии и список изменений, уведомление «Доступна новая версия Peregovorka» →
«Скачать обновление» (повтор после сетевой ошибки, проверка свободного места) → проверка → «Установить обновление»: приложение запускает установщик
(`/S --updated --force-run`), закрывается, установщик обновляет программу и запускает её снова. Данные (`%APPDATA%\Peregovorka`: организации, настройки,
сохранённые входы) установщик не трогает.

Доверие: манифест `update.json` + подпись `update.json.sig` (Ed25519, **отдельный ключ обновлений**, не сертификат подписи кода). Открытые ключи
встраиваются при сборке (`PEREGOVORKA_UPDATE_PUBKEY`, несколько через запятую — для смены ключа), поэтому источник не важен: канал издателя
(`desktop-channel` в GitHub Releases), корпоративный канал сервера Peregovorka или зеркало (политика `UpdateUrl`; установщик тогда берётся рядом
с манифестом). Установщик сверяется по размеру и SHA-256 из подписанного манифеста; если установленная программа подписана Authenticode, новый установщик
должен быть подписан тем же издателем (имя субъекта). Откат: предлагается только версия новее установленной. Во время встречи и показа экрана приложение
не перезапускается. Сборка без ключа обновлений ничего не устанавливает сама — показывает «Скачать установщик вручную». Установки MSI обновляет
администратор новым MSI; EXE поверх MSI не ставится (код выхода 2), чтобы не появилось двух копий.

Смена ключа обновлений: выпуск N несёт старый и новый открытые ключи (`DESKTOP_UPDATE_PUBKEY=старый,новый`) и подписан старым; после того как клиенты
обновились до N, манифесты подписываются новым, а старый ключ убирается из следующих сборок.

Подпись установщиков, собственный сертификат и сертификат организации, подписывающий агент и корпоративные сборки — [DESKTOP_SIGNING.md](DESKTOP_SIGNING.md).

## Сборка и проверки

```bash
cd desktop
npm ci
node build.mjs                 # dist/: main.js, preload-*.js, shell/ (оболочка), assets/ (значки из frontend/public)
npx tsc --noEmit               # типы
npm test                       # модульные тесты (node:test): адреса, ссылки, политики, окно, маскирование, обновления, уведомления
node scripts/security-check.mjs
npx electron .                 # запуск из исходников (Linux: нужен X-сервер; переменная ELECTRON_RUN_AS_NODE должна быть пустой)
```

Установщики собираются только на Windows (CI `.github/workflows/desktop.yml`): `electron-builder --win nsis` → EXE, WiX 5 (`installer/msi`) → MSI.
CI ставит, обновляет и удаляет оба пакета на настоящей Windows и запускает собранную программу: `--diagnostics=<файл>` (в том числе без сети —
правило брандмауэра), `scripts/win-e2e.mjs` по CDP (мастер, ошибки адреса и сертификата, настройки, тема, обновление из приложения через канал на HTTPS;
снимки окна — артефакт `peregovorka-windows-screens`), подписывающий агент (`signing/Peregovorka-Signer.ps1`) и корпоративный MSI.

Живой сценарий на стенде: `tests/live/desktop_app.py` (настоящий Electron по CDP, главный процесс — через инспектор с ключом `--e2e`, доступным только
при запуске из исходников). Ключи разработчика (только из исходников): `--e2e`, `--allow-http-loopback` (HTTP для `127.0.0.1`/`localhost` стенда),
`PEREGOVORKA_USER_DATA`, `PEREGOVORKA_POLICY_FILE` (политики JSON вместо реестра).

## Производительность

Неактивные организации не перезагружаются и не закрываются (иначе пропали бы уведомления); переключение — только видимость представления.
Камера и микрофон заняты только во время встречи или проверки устройств на странице. Пороги — регрессионные проверки живого сценария
`tests/live/desktop_app.py` (базовые замеры — Linux, стенд с отладочной сборкой интерфейса, две организации):

| Показатель | Замер | Порог |
| --- | --- | --- |
| Запуск до показа окна | 0,4–0,5 с | ≤ 3 с |
| Переключение организации (главный процесс) | 2 мс | ≤ 50 мс |
| Память, две организации в простое (все процессы) | 0,95–1,2 ГБ | ≤ 1,5 ГБ |
| Процессор в фоне, окно скрыто | 0,4–0,6 % | ≤ 5 % |
| Куча оболочки после 20 открытий настроек | ±0,2 МБ | рост < 5 МБ |

На Windows те же проверки выполняются в CI для собранной программы частично (время запуска ≤ 15 с на виртуальной машине CI); полноценные замеры на
типовом рабочем компьютере — при приёмке.

## Версии и выпуск клиента

Версия — `desktop/package.json`, история — `desktop/CHANGELOG.md`, тег — `desktop-vX.Y.Z` (серверные `vX.Y.Z` и канал обновления сервера не затрагиваются).
Совместимость: клиент знает уровни протокола `CLIENT_API` (`src/common/version.ts`), сервер сообщает `api` и `min_client`. Режимы подписи выпуска
(без сертификата / самоподписанный / сертификат УЦ) и настройка секретов CI — [DESKTOP_SIGNING.md](DESKTOP_SIGNING.md). Выпуск без сертификата УЦ
помечается «Тестовая сборка» и публикуется как предварительный — его нельзя выдавать за доверенный корпоративный выпуск.
