# Соединения PostgreSQL, масштабирование и нагрузочные испытания

## Что было не так (0.25.0–0.26.0) и что исправлено в 0.27.0

| Проблема | Последствие | Исправление |
| --- | --- | --- |
| Генерация карты разговора держала одну `AsyncSession` весь этап LLM (минуты) | соединение PostgreSQL «idle in transaction» на всё время работы модели; при нескольких картах — исчерпание пула, HTTP 500 | `conv_map.py`: читаем данные → **закрываем сессию** → LLM без транзакции → короткая транзакция для сохранения |
| Протокол/резюме: сессия жила во время очереди «heavy» (до 10 мин), обезличивателя и модели, выгрузки в хранилище | то же | `protocols.py`: `release(db)` перед каждой долгой сетевой операцией |
| Хранилища файлов (`SELECT storage_profiles` и далее обращение к SMB/WebDAV/диску): транзакция жила, пока идёт ввод-вывод | «14 транзакций после `SELECT storage_profiles`» | `filestore.py`: после чтения профиля соединение возвращается в пул до работы с хранилищем |
| Одновременный первый вход многих людей в комнату без встречи: после `rollback()` код обращался к «протухшему» ORM-объекту | **HTTP 500 (MissingGreenlet)** у 20–70 % входов в момент старта собрания (на SQLite не воспроизводится) | `meetings.join`: объекты перечитываются после rollback; тест `tests/perf/race_join.py` |
| Два одновременных «Построить карту» | HTTP 500 (уникальный ключ) | `conv_map.request`: повтор использует созданную запись; второе задание не запускается |
| Один пул соединений для запросов пользователей и фоновых задач, размеры пула — значения SQLAlchemy по умолчанию | фоновая обработка вытесняет обычные запросы | отдельные пулы: «запросы пользователей» и «фоновые задачи»; размеры — по ядрам или из настроек (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_BG_POOL_SIZE`) |
| Нехватка соединений = ответ 500 | массовые 500 | таймаут ожидания `DB_POOL_TIMEOUT_S` → **503 с `Retry-After`**; потеря соединения с БД — тоже 503 (счётчики в «Производительность») |
| Redis: предел соединений клиента по умолчанию | `MaxConnectionsError` → 500 при ≥1000 пользователей | ожидающий пул (`REDIS_MAX_CONNECTIONS`, 0 = по пулу БД) |
| Настройки читались из БД 3–5 раз на каждый запрос | лишняя нагрузка на PostgreSQL и процессор | кэш групп настроек на 3 с (сброс при записи) |
| `healthy` = «процесс жив» | контейнер «здоров» при недоступной БД | `/health/live` — процесс; `/health/db` (проверка контейнера) — PostgreSQL и Redis через **отдельный** мини-пул; `/health/ready` — плюс LiveKit/ASR; статус `degraded`, когда пул занят на 90 % |
| Фоновые задачи на каждом экземпляре | дубли писем, заданий, синхронизаций при нескольких экземплярах | **ведущий** экземпляр (аренда в Redis, `services/leader.py`): одиночные задачи выполняет один процесс; HTTP обслуживают все |
| Тяжёлых задач одновременно всегда 2 | не использует ядра | `HEAVY_CONCURRENCY=0` — по ядрам и памяти (1 задача на ≈1 ГиБ, не больше половины ядер) |

Страховки: `idle_in_transaction_session_timeout` (`DB_IDLE_IN_TX_TIMEOUT_S`, 120 с) и `statement_timeout` (`DB_STATEMENT_TIMEOUT_S`, 300 с) задаются на соединение; соединение, удержанное дольше `DB_HOLD_WARN_S` (20 с), пишется в журнал с указанием **какой запрос или задача его держала**.

## Контроль (Администрирование → Производительность → «База данных»)
Занятость пулов (запросы / фоновые), соединения PostgreSQL и предел `max_connections`, активные/простаивающие, **idle in transaction** (число и возраст самой долгой), отказы 503 из-за пула и из-за недоступности БД, долгие удержания, роль экземпляра (ведущий/нет). Доступность БД проверяется отдельным пулом: исчерпание основного не маскируется.

## Настройка под установку
| Параметр (.env) | Значение по умолчанию | Смысл |
| --- | --- | --- |
| `BACKEND_WORKERS` | 1 | процессов backend в контейнере (или запустите несколько контейнеров backend за балансировщиком) |
| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` | 0 = `max(10, min(40, 3×ядер))` и столько же сверх | пул запросов пользователей на процесс |
| `DB_BG_POOL_SIZE` | 0 = `max(4, min(12, ядер))` | пул фоновых задач на процесс |
| `POSTGRES_MAX_CONNECTIONS` | 300 | должен быть ≥ процессы × (пул + запас + фоновый пул + запас) + 10 |
| `HEAVY_CONCURRENCY` | 0 (авто) | тяжёлых фоновых задач одновременно |

Ограничений числа учётных записей и пользователей в коде нет. Реальные пределы — ресурсы сервера, `max_connections`, лицензии сторонних компонентов и медиасервер (LiveKit): они **не** ограничиваются приложением и показываются отдельно.

**Несколько экземпляров.** Сессии, события и блокировки — в Redis; одиночные фоновые задачи — у ведущего. Ограничение: протокол/карта, запущенные на одном экземпляре, **отменяются и показывают ход** только через него (состояние задания в памяти процесса) — за балансировщиком включайте «липкость» для `/api/v1/meetings/*/protocols` или используйте один процесс для фонового ведущего. Для NTLM в EWS — привязка соединения.

## Нагрузочные испытания
Воспроизводимо: `tests/perf/run_matrix.sh <python> <каталог> "100:1:40 500:4:60 …"` (Docker: PostgreSQL 16, Redis 7; настоящий backend; тестовый каталог пользователей; LLM-заглушка отвечает 4 с). Нагрузка: каждый пользователь входит, подключается к комнате и каждые ~4 с (экспоненциально) читает список комнат/историю/чат/стенограмму, пишет в чат; администратор опрашивает «Производительность»; одновременно 8 формирований протоколов и карт. Генератор — aiohttp (httpx упирается в ~200 запросов/с на ядро и сам становится узким местом).

**Стенд:** один сервер 8 vCPU / 14 ГиБ, **на нём же** PostgreSQL, Redis и генератор нагрузки (то есть процессору backend достаётся меньше половины ядер). Медиа (LiveKit) в испытании **не участвует**.

| Пользователей | Процессов backend | p50 / p95 / p99 запросов, мс (установившийся режим) | Доля ошибок | Ресурсы backend |
| ---: | ---: | --- | ---: | --- |
| 100 | 1 | 27 / 61 / 138 | 0 % | CPU ≈ 0,5 ядра, 241 МБ |
| 500 | 1 | 5 509 / 13 092 / 15 716 | 1,2 % (503, пул) | CPU 1 ядро (насыщение), 300 МБ |
| 500 | 4 | **59 / 337 / 852** | **0 %** | CPU ≈ 2,5 ядра, 1,1 ГБ |
| 1000 | 4 | 1 652 / 10 485 / 16 345 | 0,8 % (503) | ≈ 3,5 ядра, 1,3 ГБ |
| 2000 | 4 | 5 096 / 20 266 / 22 730 | **37 %** (503) | ≈ 3,1 ядра, 1,5 ГБ |
| 2000 | 6 | 3 153 / 22 152 / 25 739 | **30 %** (503) | ≈ 4,3 ядра, 2,1 ГБ |

**Вывод (честный).** На этом стенде **подтверждена работа 500 одновременно активных пользователей без ошибок** (4 процесса backend), 100 — с запасом. **2000 пользователей в этой конфигурации не достигнуто**: при 1000–2000 процессор стенда (общий с PostgreSQL и генератором) исчерпан, очередь запросов растёт, транзакции удерживаются дольше, пул соединений заполняется, и приложение отвечает 503 вместо 500 (контролируемая деградация). Нужны либо больше ядер под backend (отдельный от БД и генератора сервер; несколько экземпляров), либо дальнейшая оптимизация горячих путей (вход в комнату, список комнат, история — ORM-нагрузка, `audit`/журнал на каждое действие). Это **следующий этап**; цель 2000 пользователей остаётся целью, а не подтверждённым свойством. Видео/аудио для 2000 подключений требует отдельного испытания с настоящим LiveKit и клиентами и соответствующей инфраструктуры (см. docs/PERFORMANCE.md) — здесь не проверялось.

## Регрессионные проверки в выпуске
* CI, задача `perf-smoke`: настоящие PostgreSQL и Redis, смешанная нагрузка + одновременная генерация протоколов и карт; падает при доле 5xx > 0,5 % или при `idle in transaction` дольше 5 с; плюс гонка одновременного входа (`race_join.py`).
* Тесты `test_no_database_connection_is_held_while_the_model_is_working` (карта) и `test_protocol_generation_holds_no_database_connection…` (протокол): во время запроса к модели и обезличивателю занятых соединений быть не должно (проверено, что на прежнем коде тест падает).
* Перед выпуском: `tests/perf/run_matrix.sh` на стенде выпуска (минимум 100 и 500), результаты — в отчёт о релизе.
