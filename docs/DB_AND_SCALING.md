# Соединения PostgreSQL, масштабирование и нагрузочные испытания

## Что было не так (0.25.0–0.26.0) и что исправлено в 0.27.0

| Проблема | Последствие | Исправление |
| --- | --- | --- |
| Генерация карты разговора держала одну `AsyncSession` весь этап LLM (минуты) | соединение PostgreSQL «idle in transaction» на всё время работы модели; при нескольких картах — исчерпание пула, HTTP 500 | `conv_map.py`: читаем данные → **закрываем сессию** → LLM без транзакции → короткая транзакция для сохранения |
| Протокол/резюме: сессия жила во время очереди «heavy» (до 10 мин), обезличивателя и модели, выгрузки в хранилище | то же | `protocols.py`: `release(db)` перед каждой долгой сетевой операцией |
| Хранилища файлов (`SELECT storage_profiles` и далее обращение к SMB/WebDAV/диску): транзакция жила, пока идёт ввод-вывод | «14 транзакций после `SELECT storage_profiles`» | `filestore.py`: после чтения профиля соединение возвращается в пул до работы с хранилищем |
| Одновременный первый вход многих людей в комнату без встречи: после `rollback()` код обращался к «протухшему» ORM-объекту | **HTTP 500 (MissingGreenlet)** у 20–70 % входов в момент старта собрания (на SQLite не воспроизводится) | `meetings.join`: объекты перечитываются после rollback; тест `tests/perf/race_join.py` |
| Два одновременных «Построить карту» | HTTP 500 (уникальный ключ) | `conv_map.request`: повтор использует созданную запись; второе задание не запускается |
| Один пул соединений для запросов пользователей и фоновых задач, размеры пула — значения SQLAlchemy по умолчанию | фоновая обработка вытесняет обычные запросы | отдельные пулы: «запросы пользователей» и «фоновые задачи»; размеры — по ядрам или из настроек (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_BG_POOL_SIZE`) |
| Нехватка соединений = ответ 500 | массовые 500 | таймаут ожидания `DB_POOL_TIMEOUT_S` → **503 с `Retry-After`**; потеря соединения с БД — тоже 503 (счётчики в «Производительность») |
| Redis: предел соединений клиента по умолчанию | `MaxConnectionsError` → 500 при ≥1000 пользователей | ожидающий пул (`REDIS_MAX_CONNECTIONS`, 0 = по пулу БД) |
| Настройки читались из БД 3–5 раз на каждый запрос | лишняя нагрузка на PostgreSQL и процессор | кэш групп настроек на 3 с (сброс при записи) |
| `healthy` = «процесс жив» | контейнер «здоров» при недоступной БД | `/health/live` — процесс; `/health/db` (проверка контейнера) — PostgreSQL и Redis через **отдельный** мини-пул; `/health/ready` — плюс LiveKit/ASR; статус `degraded`, когда пул занят на 90 % |
| Фоновые задачи на каждом экземпляре | дубли писем, заданий, синхронизаций при нескольких экземплярах | **ведущий** экземпляр (аренда в Redis, `services/leader.py`): одиночные задачи выполняет один процесс; HTTP обслуживают все |
| Тяжёлых задач одновременно всегда 2 | не использует ядра | `HEAVY_CONCURRENCY=0` — по ядрам и памяти (1 задача на ≈1 ГиБ, не больше половины ядер) |

Страховки: `idle_in_transaction_session_timeout` (`DB_IDLE_IN_TX_TIMEOUT_S`, 120 с) и `statement_timeout` (`DB_STATEMENT_TIMEOUT_S`, 300 с) задаются на соединение; соединение, удержанное дольше `DB_HOLD_WARN_S` (20 с), пишется в журнал с указанием **какой запрос или задача его держала**.

## Контроль (Администрирование → Производительность → «База данных»)
Занятость пулов (запросы / фоновые), соединения PostgreSQL и предел `max_connections`, активные/простаивающие, **idle in transaction** (число и возраст самой долгой), отказы 503 из-за пула и из-за недоступности БД, долгие удержания, роль экземпляра (ведущий/нет). Доступность БД проверяется отдельным пулом: исчерпание основного не маскируется.

## Настройка под установку
| Параметр (.env) | Значение по умолчанию | Смысл |
| --- | --- | --- |
| `BACKEND_WORKERS` | установщик: половина vCPU (1–8); в шаблоне 1 | процессов backend в контейнере (или несколько контейнеров backend за балансировщиком). Один процесс — до ~500 активных пользователей, 4 процесса — 2000 (замеры ниже) |
| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` | 0 = `max(10, min(40, 3×ядер))` и столько же сверх | пул запросов пользователей на процесс |
| `DB_BG_POOL_SIZE` | 0 = `max(4, min(12, ядер))` | пул фоновых задач на процесс (сюда же — журнал аудита запросов) |
| `POSTGRES_MAX_CONNECTIONS` | установщик: 300–600 по числу процессов; в шаблоне 300 | должен быть ≥ процессы × (пул + запас + фоновый пул + запас + 2) + 10. **Если меньше — backend сам уменьшает автоматически подобранные пулы** под предел (предупреждение `db_pool_over_limit` в журнале); явно заданные `DB_*POOL*` не меняются |
| `HEAVY_CONCURRENCY` | 0 (авто) | тяжёлых фоновых задач одновременно (на процесс) |

Ограничений числа учётных записей и пользователей в коде нет. Реальные пределы — ресурсы сервера, `max_connections`, лицензии сторонних компонентов и медиасервер (LiveKit): они **не** ограничиваются приложением и показываются отдельно.

**Несколько процессов и экземпляров.** Сессии, события, блокировки, «один микрофон на человека», слово в презентации — в Redis; одиночные фоновые задачи — у ведущего (аренда в Redis; идентификатор `узел:процесс:метка` виден в «Производительности»). С 0.32.0 и **состояние формирования документов общее**: владелец задания (протокол, резюме, карта) раз в 5 с продлевает ключ `job:alive:*` с ходом выполнения; «Остановить» из любого процесса доходит до владельца (`job:cancel:*`); прерванным («сиротой») считается только задание без живого ключа — его закрывает ведущий раз в минуту и любой процесс при запуске. Признаки «файлы встречи обрабатываются» и «запись слушают» тоже в Redis — перенос записей между хранилищами (ведущий) не удаляет источник, который проигрывается через другой процесс. «Липкость» балансировщика больше не нужна; для NTLM в EWS — привязка соединения.

**Сбои.** Клиент Redis повторяет команду при обрыве до 6 раз (0,1→1 с): перезапуск Redis проходит незаметно; дольше — ответ 503 с `Retry-After` (а не 500), счётчик в «Производительности». Потерянные соединения PostgreSQL отбраковываются при выдаче из пула (`pool_pre_ping`).

**nginx (контейнер web).** `worker_connections 8192`, `worker_rlimit_nofile 32768`: 2000 WebSocket событий через прокси — около 4000 соединений, предела 1024 по умолчанию не хватало.

## Нагрузочные испытания
Воспроизводимо: `[PROFILE=heavy|client] [RAMP=20] tests/perf/run_matrix.sh <python> <каталог> "100:1:40 500:4:60 …"` (Docker: PostgreSQL 16, Redis 7; настоящий backend; тестовый каталог пользователей; LLM-заглушка отвечает 4 с; одновременно 8 формирований протоколов и карт). Генератор — aiohttp. Два профиля нагрузки:

* **heavy** (прежняя матрица): все входят в комнаты в одну секунду, затем каждый пользователь раз в ~4 с (экспоненциально) читает список комнат/историю/чат/стенограмму или пишет в чат. Это намного чаще, чем действует человек.
* **client** (с 0.32.0) — как настоящий браузер: приход за `RAMP` секунд; у участника встречи — открытие комнаты (resolve, join, аватарки, слово, руки, чат, стенограмма, события входа), WebSocket событий с подпиской и пингом раз в 30 с, `/health/ready` раз в 15 с, метрики раз в 30 с, сообщение в чат в среднем раз в 2 мин; 15 % людей — на странице списка комнат (обновление раз в 10 с, изредка история).

Цена каждого запроса без конкуренции (CPU процесса на запрос): `tests/perf/endpoint_cost.py`. Сбои под нагрузкой: `tests/perf/fault_run.sh`. Медиасервер: `tests/perf/livekit_load.sh`.

**Стенд:** одна виртуальная машина 8 vCPU (QEMU, упрощённая модель процессора: одно обращение к PostgreSQL через asyncpg стоит ~0,18 мс CPU, обычный Python примерно вдвое медленнее современного сервера) / 14 ГиБ; **на ней же** PostgreSQL, Redis и генератор нагрузки. Данные PostgreSQL — в tmpfs (на стенде не было места на диске): **стоимость fsync в замерах не учтена**. Абсолютные числа — нижняя оценка для такого класса машин.

### Вывод (честный)
* **Приложение (HTTP, WebSocket, база, фоновые задачи) — 2000 одновременно активных пользователей на одном сервере 8 vCPU с 4 процессами backend подтверждены** в модели «как браузер» при приходе за минуту: 0 % ошибок, p95 1,4–2,1 с. Массовый вход всех в одни 20 с — 0,1–0,2 % ответов 503 с `Retry-After` (клиент повторяет), вход в комнату до 7–8 с в середине пика. Сбой процесса, базы на 10 с и перезапуск Redis — без ошибок у пользователей.
* **Медиа на 2000 — не один узел такого класса.** На этой машине LiveKit тратит ~1 ядро на ~90–100 потоков видео 720p зрителям и ~0,3 ядра на совещание из 10 человек с двумя камерами. Одна комната живёт на одном узле LiveKit: презентация для тысяч зрителей — это мощный отдельный узел и/или нижний слой simulcast для зрителей; много совещаний — несколько узлов LiveKit (комнаты распределяются через Redis). Это оценка по замерам на ВМ с генератором на том же хосте, не проверка на реальной инфраструктуре.
* **Не проверено:** нагрузка с настоящими браузерами и WebRTC в нужном масштабе; PostgreSQL на диске (fsync), на отдельном сервере; несколько контейнеров backend за внешним балансировщиком (проверены 4 процесса в одном контейнере — тот же механизм Redis); LiveKit в несколько узлов; сервер современнее этой ВМ.

**Рекомендуемая отправная точка на 2000 активных пользователей:** сервер приложения 8 vCPU / 16 ГиБ (`BACKEND_WORKERS=4`, `POSTGRES_MAX_CONNECTIONS` ≥ 300 — установщик подбирает сам), PostgreSQL на SSD (лучше — отдельный сервер), LiveKit — отдельные узлы по расчёту медиа выше, ASR — по числу одновременных встреч с транскрибацией (`scripts/asr-bench.sh`).

## Корпоративные чаты (0.35.0)

* Каждая вкладка вошедшего сотрудника держит один WebSocket `/api/v1/ws` с подпиской на свой личный канал (`user:<id>:events`); в процессе backend
  по-прежнему один подписчик Redis (`EventHub`), так что 2000 пользователей — это 2000 каналов pub/sub, а не 2000 соединений с Redis. Клиент не закреплён
  за экземпляром: событие публикуется в Redis и доходит до подписчика на любом экземпляре.
* Присутствие — одна запись Redis на активного пользователя раз в 30 с (≈ 70 записей/с на 2000 активных), без записи в PostgreSQL.
* Нагрузка на PostgreSQL: список переписок — постоянное число запросов (4–5) независимо от их количества; лента — страница по 50; поиск — индекс GIN,
  выдача не больше 200; счётчик непрочитанных считается по индексу `(chat_id, id)`. Аудит не пишется на каждое сообщение.
* Замер (одна машина, PostgreSQL 16 и Redis 7 во временных контейнерах, два экземпляра backend, `tests/live/chats_multi_instance.py`): доставка между
  экземплярами ~0,05–0,1 с; переписка 200 тысяч сообщений — поиск 34–97 мс (первый на холодном кэше 0,8 с), последняя страница 39 мс, список 118 мс.
  Нагрузочного испытания чатов на 2000 одновременно активных пользователей не было.

## Регрессионные проверки в выпуске
* CI, задача `perf-smoke`: настоящие PostgreSQL и Redis, смешанная нагрузка + одновременная генерация протоколов и карт; падает при доле 5xx > 0,5 % или при `idle in transaction` дольше 5 с; плюс гонка одновременного входа (`race_join.py`).
* Тесты `test_no_database_connection_is_held_while_the_model_is_working` (карта) и `test_protocol_generation_holds_no_database_connection…` (протокол): во время запроса к модели и обезличивателю занятых соединений быть не должно (проверено, что на прежнем коде тест падает).
* `perf-smoke` при сбое показывает в аннотации первую трассировку журнала сервера и частые ошибки; `race_join.py` печатает тело ответа, отличного от 200.
* Тесты сверки быстрых путей с прежними правилами: `test_list_equivalence.py` (история = прямой доступ; список комнат без ORM = вывод через ORM); `test_jobs_across_processes.py` (два процесса: ход, отмена, «сироты», карта, признаки файлов); `test_pool_plan.py`.
* Перед выпуском: `tests/perf/run_matrix.sh` на стенде выпуска (минимум 100 и 500, оба профиля), результаты — в отчёт о релизе.
