# Видеозапись встреч (LiveKit Egress)

Состояние проверки на 0.48.3: **проверено на настоящем LiveKit Egress v1.15.0 (изолированный контур на host-сети и затем реальный `deployment/compose.yml` с профилем `video` — мостовая сеть, healthcheck, пользователь 10001: запись 720p, 16 из 16 проверок; LiveKit 1.13.10, Redis, Egress в Docker, LiveKit 1.13.10, Redis, Egress в Docker, два браузера с фейковыми камерами и «докладчик» с демонстрацией экрана 1920×1080)**: запись в MP4 H.264 High + AAC, раскладка «экран — основное место, участники — миниатюры», остановка и итог, падение службы посреди записи, режим «автоматически», удаление, отдача с перемоткой. **Не проверено:** настоящие люди и камеры (материал синтетический), конференции с десятками участников, длительные записи (часы), несколько одновременных записей, SMB-хранилище для больших файлов, Windows-клиент, работа за корпоративным прокси. Подробности и результаты — ниже.

## Что это
Два независимых вида записи встречи:

| | Аудиозапись | Видеозапись |
|---|---|---|
| Что пишется | звук каждого участника, затем общая запись `m4a` | **один MP4 (H.264 + AAC)** со всей встречей: сетка участников, при показе экрана он занимает основное место, остальные — миниатюры |
| Кто пишет | служба распознавания (ASR) | LiveKit Egress (браузер внутри контейнера «смотрит» комнату) |
| Включение в комнате | «Разрешить запись аудио», «Начинать запись автоматически», пункт «Аудиозапись» в «Ещё» | режим «Видеозапись»: выключена / вручную / автоматически, пункт «Видеозапись» в «Ещё» |
| Индикатор у всех | «АУДИОЗАПИСЬ» | «ВИДЕОЗАПИСЬ» |

Видео не зависит от аудио и транскрибации: можно писать любую комбинацию. Готовая запись — обычная запись встречи (`recordings.kind = mix_video`, `has_video`): тот же плеер в «Истории» (перемотка, скачивание по правам), та же выгрузка во внешнее хранилище, перенос и резервная копия.

## Общая сцена записи (0.53.0)
Запись раскладывает кадр не встроенным шаблоном Egress, а служебной страницей приложения `/rec/template` (открывается в браузере внутри Egress по адресу `RECORDER_BASE_URL`, по умолчанию `http://web:8080`, с подписанным токеном встречи `rt`; `backend/app/services/rec_scene.py`, `frontend/src/recorder/`). Страница входит в комнату наблюдателем, воспроизводит звук и раз в 0,5–0,7 с читает состояние сцены (`GET /api/v1/rec/state?rt=…`: сцена ведущего, признак работы над доской, схема и её патчи).

Порядок выбора сцены (`frontend/src/recorder/scene.ts`, повторяет `rec_scene.py`): сцена ведущего («Показать всем») → показ экрана → доска, пока над ней работают (правка за последние 25 с) → говорящий и миниатюры. Схема рисуется тем же редактором draw.io и тем же `BoardSync`, что у участников, но только на чтение. Доска «только руководителям» в запись не попадает. Выключатель — «Записывать общую сцену» в настройках видеозаписи (`video.scene_template`); свой шаблон `template_url` главнее.

**Проверено на настоящем Egress (тестовый экземпляр):** `tests/live/scenario_video_board.py` — запись 110 с: участники → правки на доске в настоящем редакторе (доска в кадре через 1–4 с после первой правки) → возврат к участникам после паузы → «Показать всем» → показ экрана → участники; кадры проверяются по цвету сцены, звук и видео — по сигналу, одновременному со сменой цвета; MP4 — ffprobe (H.264 High, AAC), Range/416/скачивание, воспроизведение и перемотка настоящим `<video>`. **Не проверено:** большие встречи (десятки участников) с доской, Windows Server SMB как хранилище MP4 в этом сценарии (SMB-доставка проверена в 0.52.0), несколько одновременных записей с доской.

## Режимы комнаты
- **Выключена** (по умолчанию).
- **Вручную** — руководитель (или администратор) нажимает «Видеозапись: выключена» в меню «Ещё». Запись идёт **с текущего момента**; остановка и повторный запуск дают новый файл-фрагмент, прежний сохраняется.
- **Автоматически** — запись начинается, когда в комнате появился человек, и закрывается, когда комната опустела. Если руководитель остановил запись вручную, автозапуск её не перебивает (до конца встречи). Пустая комната не записывается.
- Презентационная комната при создании (и при смене типа на «презентация») получает режим «автоматически», если видеозапись включена администратором и в комнате нет шифрования; режим можно сменить.
- Качество: 720p или 1080p (на комнату; по умолчанию — из «Администрирование → Видеозапись»).

Не поддерживается: комнаты со сквозным шифрованием (у сервера нет ключа) и с шифрованием хранилища; сервер отказывает понятным текстом, а включить шифрование в комнате с видеозаписью нельзя, не отключив её.

## Установка службы
Служба — отдельный контейнер `livekit-egress` (профиль compose `video`, образ `livekit/egress:v1.15.0`, ≈ 1,3 ГБ). Он связан с LiveKit через общий Redis (db 1, как у SIP) и пишет файлы в том записей (`/out` = `${DATA_ROOT}/recordings`). Портов наружу нет.

**Из администрирования (с 0.52.0):** Администрирование → Видеозапись (или Трансляции), карточка «Видеоподсистема (LiveKit Egress)» → «Установить и включить» / «Повторить запуск» / «Восстановить настройки» / «Перезапустить службу» / «Выключить». Действие выполняет помощник обновлений по белому списку (`scripts/lib/complib.sh`, `backend/app/services/server_components.py`): окно подтверждения с последствиями, ход в карточке, запись в аудит `system.component`. Фактическое состояние службы backend берёт из `components.json` помощника (переменная окружения `VIDEO_ENABLED` контейнера backend после включения устаревает).

Через SSH (если помощник недоступен):
```bash
sudo scripts/video.sh enable    # скачивает образ, подключает LiveKit к Redis, запускает службу (LiveKit перезапускается: идущие встречи прервутся)
scripts/video.sh status
sudo scripts/video.sh disable
```
Затем в приложении: **Администрирование → Видеозапись → «Включить видеозапись встреч»**, и режим в настройках комнаты → «Встреча и запись» → «Видеозапись».

**Хранение (с 0.52.0):** «Где хранить готовые видеозаписи» — `audio` (как аудиозаписи: то же хранилище, подпапка `Video/`; без хранилища аудио — диск сервера), `profile` (профиль из «Файловых хранилищ», подпапка `Video/`), `local`. Egress пишет MP4 на том записей; после финализации файл копируется в хранилище, размер сверяется всегда, SHA-256 копии — перед удалением локального файла (`keep_local_copy=false`). Сбой — `export_status=failed`, файл остаётся локально, повтор — «Повторить выгрузку записей» и плановая уборка. `recordings.export_area` (миграция 0052) хранит, где лежит копия: видеозаписи, выгруженные до 0.52.0, остаются в `Audio/` (`export_area=audio`) и читаются оттуда; перенос «на локальный диск и обратно» кладёт их в `Video/`. Сегменты HLS эфира (`${DATA_ROOT}/live`) — отдельный том с отдельной уборкой; во внешние хранилища они не выгружаются. Обновление (`scripts/update.sh`) заранее скачивает образ, если видеозапись включена; без интернета или места — предупреждение, остальное обновляется.

Требования: на каждую одновременную запись ≈ 2–4 ядра процессора и 1–2 ГБ памяти (`cpu_cost` Egress 3,0; предел одновременных записей задаётся в приложении), `cap_add: SYS_ADMIN` для песочницы Chrome, `shm_size: 1gb`, свободное место на томе записей. GPU не нужен.

## Защита от перегрузки и потери данных
- Перед стартом проверяются: функция включена, режим комнаты, шифрование, **предел одновременных записей**, **свободное место** (по умолчанию ≥ 10 ГБ), **квота** объёма видео, наличие людей в комнате и связь с LiveKit.
- Старый файл никогда не удаляется при нехватке места или превышении квоты — новая запись просто не начинается, администратор видит предупреждение в «Администрирование → Видеозапись».
- Предел одной записи (по умолчанию 6 часов): файл закрывается, при режиме «автоматически» следующий фрагмент начинается сам.
- Остановка встречи останавливает запись; итог файла приходит от LiveKit (webhook `egress_ended`) либо находится фоновой сверкой (каждые 10 с) — **после перезапуска сервера, потери webhook или падения Egress запись не остаётся «вечно идущей»**: берётся то, что лежит на диске (готова), либо помечается «ошибка» с причиной.
- Срок хранения: общий (`Видеозапись → Хранить видеофайлы`, 0 = до удаления) и срок аудио комнаты; идущую запись по сроку не удаляют.
- Временных файлов приложение не создаёт: файл пишет Egress сразу в итоговый каталог; сломанные фрагменты видны в списке со статусом «ошибка».

## Диагностика
- Администрирование → Видеозапись: сколько записей идёт, готовых и с ошибкой, занято места, свободно на томе, предупреждения.
- Нет кнопки «Видеозапись» в меню: функция выключена, у комнаты режим «выключена», нет прав руководителя или идёт гостевой вход.
- Проверки по цепочке (`backend/app/services/media_checks.py`): видеоподсистема на сервере → функция в приложении → LiveKit (`list_rooms`) → Egress подключён (`list_egress`) → место. Выключенная подсистема — состояние `off` с действием, зависимые проверки — `skipped`.
- «Служба видеозаписи недоступна»: первая непройденная проверка в разделе; журнал — `scripts/logs.sh livekit-egress`.
- Запись «ошибка: Egress не создал файл»: проверьте права записи в `${DATA_ROOT}/recordings` для пользователя внутри контейнера Egress и что том смонтирован как `/out`.
- Журнал событий («Хранилище записей»): `video_started`, `video_stopped`, `video_failed`, `video_auto_failed`.

## Качество, размер и нагрузка (измерено на настоящем Egress)
Условия: ≈ 42 с записи, две камеры (фейковые устройства Chrome) и «докладчик» с показом экрана 1920×1080 (слайд с мелким моноширинным текстом 15 px, 10 к/с) в середине записи; H.264 High, 30 кадров/с, AAC 48 кГц; хост — 20 ядер без AVX. Материал синтетический: у живых людей и движения в кадре битрейт обычно выше, а у статичных слайдов ниже.

| Профиль | Разрешение | Размер за 42 с | Средний битрейт | Размер в час | Процессор Egress (среднее / пик) | Память Egress (пик) | Читаемость мелкого текста при показе экрана |
|---|---|---|---|---|---|---|---|
| 720p | 1280×720 | 6,6 МБ | 1,24 Мбит/с | ≈ 0,56 ГБ | ≈ 1,4 ядра / 2,4 | ≈ 0,8 ГБ | текст 15 px (в источнике) читается с трудом: экран вписывается в ≈ 56 % масштаба |
| 1080p | 1920×1080 | 9,2 МБ | 1,73 Мбит/с | ≈ 0,78 ГБ | ≈ 2,4 ядра / 3,5 | ≈ 0,5 ГБ | текст 15 px читается свободно (≈ 83 % масштаба) |

Выводы: на одну одновременную запись закладывайте **≈ 2 ядра (720p) и ≈ 3–4 ядра (1080p)** и около 1 ГБ памяти; размер файла для расчёта диска — **до ≈ 1 ГБ в час в 720p и ≈ 1,5 ГБ в час в 1080p** (запас на движение в кадре; верхний предел кодировщика — 2,5 и 4,5 Мбит/с видео, то есть ≈ 1,2 и ≈ 2,1 ГБ/час). Рекомендация: **720p по умолчанию, 1080p — для комнат, где показывают документы, таблицы и код мелким шрифтом**. Сравнение на ваших реальных встречах (живые камеры, ваши слайды) всё равно стоит сделать при первом включении.

## Раскладка кадра (наблюдение)
- Участники с включённой камерой — крупно говорящий и колонка миниатюр слева; при показе экрана он занимает основное место, миниатюры остаются слева; после окончания показа возвращается вид участников.
- **Если у всех участников камеры выключены, кадр чёрный** (стандартный шаблон Egress показывает только видеодорожки, имён и аватаров нет). Звук при этом пишется. Для встреч без камер используйте свой шаблон (`Свой шаблон раскладки` в «Администрирование → Видеозапись», адрес https страницы шаблона Egress) либо принимайте запись как «звук с показом экрана».

## Требования, найденные при проверке на настоящем Egress
- **Адрес LiveKit для медиа (`LIVEKIT_NODE_IP`) должен быть не петлевым** (не `127.0.0.1`) и доступным из контейнера Egress: Chrome внутри Egress не использует петлевые ICE-адреса, и запись завершается ошибкой «Start signal not received».
- **Egress запускается от uid 10001** (как backend и ASR; в compose `user: "10001:0"` и `tmpfs` для `/home/egress`). Под его стандартным uid 1001 каталоги встречи создавались с правами 755: backend не мог удалить видеофайл, а звук не мог писаться в уже созданную папку.
- Аудио записывается в **AAC** (проверено ffprobe); при значении кодека по умолчанию Egress выбирает Opus, который плееры в MP4 поддерживают хуже.
- Файл манифеста Egress (`EG_….json`) не создаётся (`disable_manifest`).
- После падения службы Egress LiveKit ещё долго считает запись активной (обнаружено на практике); приложение закрывает такую запись само по пропаже рекордера из комнаты (≈ через 35–60 с после падения), файл без индекса MP4 помечается «ошибка: файл не читается».

## Что не проверено
- Настоящие люди, веб-камеры и микрофоны (материал — синтетический), конференции на десятки участников, записи длительностью в часы, несколько одновременных записей (нагрузка суммируется — проверьте предел `max_concurrent` на своём железе).
- Перенос больших видеофайлов в SMB-хранилище (используется тот же код, что у аудио), резервное копирование и восстановление файлов видео, переход по меткам стенограммы к видео на реальной записи.
- Свой шаблон раскладки (поле адреса принимается и передаётся в `custom_base_url`, сам шаблон не писался и не проверялся).
- Windows-клиент (меню «Ещё», индикаторы), Safari/Firefox как плееры MP4.
- Несколько экземпляров backend под нагрузкой.
