# Подпись приложения для Android и площадки распространения

Состояние на 2026-10-31: **все публичные выпуски, начиная с 0.1.4, подписываются одним постоянным ключом организации**. Сборка по тегу без ключа или с другим
сертификатом останавливается — временные ключи для публичных выпусков больше не используются.

## Ключ

| | |
| --- | --- |
| Хранилище | PKCS12, alias `peregovorka`, RSA 4096, сертификат `CN=Peregovorka, O=Peregovorka`, действителен до 2056-10-21 |
| Отпечаток сертификата (SHA-256, открытая информация) | `30:01:6B:BA:36:8B:F7:15:C6:F2:7A:63:D0:DE:D9:00:26:96:57:38:7F:1E:A8:66:C6:D4:F2:71:21:C7:3D:49` — закреплён в `mobile/android/release-cert.sha256` |
| Где используется | секреты GitHub Actions `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` |
| Резервная копия | у владельца (вне репозитория); инструкция восстановления — в самой копии (`ВОССТАНОВЛЕНИЕ.md`) |

Ключ, пароли и файл хранилища никогда не попадают в Git, журналы CI, выпуски и сборки.

## Что делает CI (`.github/workflows/android.yml`)

1. Тег `android-vX.Y.Z` без секретов подписи — сборка падает (публичный выпуск временным ключом запрещён). На ветках без секретов собирается отладочный APK только для проверок.
2. APK и AAB подписываются постоянным ключом (схемы подписи v2/v3: `minSdk` 26).
3. `scripts/android_release_check.py --expect-key release --expect-cert …`: пакет, рост `versionCode`, сертификат совпадает с закреплённым; сравнение с предыдущим выпуском
   с GitHub. Сертификат другой у выпуска после выпуска с постоянным ключом — **выпуск останавливается**. Первый выпуск с постоянным ключом после временных (0.1.4 после 0.1.3)
   получает на странице заметку: один раз удалить прежнюю версию, дальше обновления ставятся поверх.
4. На эмуляторах (Android 10, 14, 16) `update-over-test.sh`: отладочная сборка — обновление поверх и сохранность данных приложения; сборка с постоянным ключом — установка версии
   с меньшим `versionCode`, затем текущей поверх (`adb install -r`): приложение обновлено без переустановки (`firstInstallTime` не изменился).

## Площадки

Чтобы приложение, установленное из одного источника, обновлялось из другого, **на всех площадках APK должен быть подписан одним и тем же сертификатом**.

| Площадка | Что загружается | Подпись | Действия владельца |
| --- | --- | --- | --- |
| GitHub Releases (сейчас) | APK | постоянный ключ, CI | не нужны |
| RuStore | APK или AAB | RuStore требует, чтобы обновление было подписано тем же ключом, что первая загрузка. Загружайте APK из выпуска GitHub (он уже подписан постоянным ключом); если консоль RuStore попросит ключ для AAB — передавайте этот же ключ | регистрация разработчика и приложения в RuStore Console; первая загрузка APK |
| Google Play | AAB (обязательно для новых приложений), Play App Signing обязателен | Play подписывает установочные файлы **ключом подписи приложения**. При создании приложения выберите **использовать собственный ключ** («Export and upload a key from Java keystore», инструмент PEPK) и загрузите постоянный ключ — тогда приложения из Play и из GitHub/RuStore имеют один сертификат и обновляют друг друга. Если позволить Google создать свой ключ, установленное из Play и из GitHub станет несовместимым | создание приложения в Play Console; экспорт ключа через PEPK; отдельный **ключ загрузки** (upload key) — генерируется при первой загрузке, его можно сменить через поддержку Google, ключ подписи — нет |

Требования площадок меняются: перед первой публикацией сверьте текущие правила консоли. Если площадка потребует свою схему, которая не позволяет загрузить собственный
ключ подписи, выпуск на ней будет несовместим с остальными источниками — это нужно решить до первой публикации, не после.

## Если ключ потерян или скомпрометирован

- Потерян (нет ни секретов CI, ни резервной копии): обновления поверх установленных версий выпустить нельзя; придётся выпустить приложение с новым ключом и попросить всех
  удалить прежнее. Поэтому резервная копия хранится в двух местах.
- Скомпрометирован: Android поддерживает смену ключа с сохранением обновлений (APK Signature Scheme v3, «линия ротации» `apksigner rotate`): новый ключ подписывается старым,
  выпуск несёт оба. Это делается по отдельному плану, не в обычном выпуске.
