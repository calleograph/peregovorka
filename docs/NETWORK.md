# Сетевые порты и публикация в интернете

Какие порты нужно открыть, чтобы Peregovorka работала у пользователей и гостей, зависит от конкретной установки: адреса и порты задаёт `.env`, режим HTTPS, телефония и подключённые интеграции. Поэтому перечень не зашит в документацию, а **строится по настройкам вашего сервера**.

## Где посмотреть

* **В веб-интерфейсе:** Администрирование → Система → **Сетевая доступность** (кнопка «Показать необходимые порты» есть и в «Обзоре»). Страница показывает порты по направлениям (входящие на межсетевом экране перед сервером и исходящие с сервера), протокол, порт или диапазон, обязательность, компонент, назначение, откуда и куда идёт соединение, примечания про NAT и WebRTC, предупреждения о настройке и список портов, которые наружу публиковать нельзя.
* **В терминале (без веб-интерфейса и без Docker):** `scripts/ports.sh` читает только `.env`:

```bash
scripts/ports.sh                          # текст
scripts/ports.sh --format md --out ports.md    # Markdown, CSV (--format csv), JSON (--format json)
scripts/ports.sh --format request         # текст заявки сетевому администратору
scripts/ports.sh --live                   # дополнительно адреса интеграций из базы: каталог, почта, SMB, Exchange… (нужен запущенный backend)
```

Веб-страница и команда используют один и тот же код (`backend/app/services/netrules.py`, только стандартная библиотека), поэтому перечни совпадают. Команда `python -m app.cli network` в контейнере `backend` делает то же, что `--live`.

## Что учитывается

| Из конфигурации | На что влияет |
| --- | --- |
| `APP_PUBLIC_URL` | порт HTTPS (443 или указанный), предупреждения про http и localhost |
| `NGINX_TLS_CERT` | HTTPS завершает nginx установщика или внешний reverse proxy (в заявке — на что вести порт 443) |
| `LIVEKIT_PUBLIC_URL` | отдельный адрес сигнального соединения LiveKit даёт отдельное правило |
| `LIVEKIT_NODE_IP`, `LIVEKIT_PUBLIC_IP`, `LIVEKIT_MEDIA_MODE`, `LIVEKIT_UDP_PORT`, `LIVEKIT_TCP_PORT` | порты медиа, адреса для клиентов и режим (за NAT — какие адреса объявляются) |
| `INSTALL_PROFILE`, `WEB_PORT`, `NGINX_LISTEN_PORT`, `LIVEKIT_HTTP_PORT` | режим установки и порты, которые наружу публиковать нельзя |
| `SIP_ENABLED`, `SIP_SIGNALING_PORT`, `SIP_RTP_START/END`, `SIP_ALLOWED_CIDRS` | правила телефонии (только если включена) |
| `LDAP_URIS` и настройки интеграций | исходящие соединения сервера: каталог, SMTP, SMB, Exchange, внешние модели, получатели событий |

## Что перечень НЕ доказывает

* **Перечень — не проверка сети.** Он показывает, что нужно сделать; создана ли уже нужная запись на межсетевом экране, он не знает.
* **Проверка «с сервера» не подтверждает доступ из интернета.** Кнопка «Проверить с сервера» открывает соединение изнутри (контейнер → LiveKit, сервер → адрес интеграции). Такое соединение не проходит внешний NAT и межсетевой экран, поэтому в ответе об этом сказано прямо.
* **UDP снаружи без участия клиента проверить нельзя:** закрытый порт и порт без ответа выглядят одинаково. Достоверная проверка — войти в звонок с компьютера вне сети организации (например, через мобильную сеть) и открыть «Диагностика клиентов»: видно, шёл ли звук по UDP или по TCP.
* **Один экземпляр LiveKit.** Несколько узлов или отдельный TURN-сервер штатной установкой не поддерживаются; для такой схемы правила составляются вручную. TURN приложение не использует; STUN — только для определения публичного адреса за NAT (ниже).

## Медиасоединения: адреса ICE

LiveKit сообщает клиентам адреса сервера в кандидатах ICE: по ним идут звук, видео и показ экрана. LiveKit работает в сети Docker, где его
«внутренний» адрес — адрес контейнера (172.x), недоступный клиентам. Поэтому адреса готовит одна общая логика:
`backend/app/services/medianet.py`. Её вызывают `scripts/setup.sh`, `scripts/update.sh`, `scripts/medianet.sh` и раздел «Сетевая доступность».

| Режим (`LIVEKIT_MEDIA_MODE`) | Когда | LiveKit | Клиенты получают |
| --- | --- | --- | --- |
| `direct` | публичный адрес прямо на интерфейсе (`LIVEKIT_NODE_IP`) | `node_ip` = этот адрес | его |
| `nat-stun` | частный адрес, `LIVEKIT_PUBLIC_IP=auto`, STUN ответил | `use_external_ip: true` (STUN при каждом запуске), `advertise_internal_ip: true`, адрес сервера в локальной сети добавлен на интерфейс контейнера | публичный адрес **и** `LIVEKIT_NODE_IP` |
| `nat-manual` | `LIVEKIT_PUBLIC_IP=<IPv4>` | `node_ip` = заданный, `advertise_internal_ip: true` | заданный **и** `LIVEKIT_NODE_IP` |
| `lan` | `LIVEKIT_PUBLIC_IP=off` или публичный адрес не определён | `node_ip` = `LIVEKIT_NODE_IP` | только `LIVEKIT_NODE_IP` |

* **Почему два адреса.** Пользователи из интернета идут на публичный адрес через проброс, пользователи офиса — на адрес в локальной сети
  напрямую. «Петля» NAT на маршрутизаторе не нужна. Буквальное `advertise_internal_ip` в контейнере объявило бы адрес контейнера,
  поэтому `deployment/livekit/entrypoint.sh` добавляет на интерфейс контейнера `LIVEKIT_NODE_IP` (/32). Пакеты на него приходят через
  опубликованные порты Docker; для этого нужна возможность `NET_ADMIN`.
* **STUN недоступен.** С `use_external_ip: true` LiveKit без ответа STUN не запускается вообще. Поэтому `entrypoint.sh` проверяет STUN
  заранее, а если тот не ответил, запускает LiveKit с последним известным публичным адресом (`LIVEKIT_RTC_NODE_IP`). Если публичный адрес
  не определился уже при установке, включается режим `lan` с предупреждением и действием: задать `LIVEKIT_PUBLIC_IP`.
* **Явные настройки сохраняются.** `LIVEKIT_PUBLIC_IP`, `LIVEKIT_STUN_SERVERS` и порты задаёт администратор, остальное
  (`LIVEKIT_MEDIA_MODE`, `LIVEKIT_RTC_*`) вычисляется. Если `LIVEKIT_NODE_IP` нет на интерфейсах сервера, обновление заменяет его адресом
  маршрута по умолчанию. Прежняя схема (`.env` без `LIVEKIT_PUBLIC_IP`, внешний адрес в `LIVEKIT_NODE_IP`) переносится: адрес уходит в `LIVEKIT_PUBLIC_IP`. Повторный
  запуск установщика и обновления `.env` не меняет.
* **Порты.** Номер внутри контейнера равен опубликованному и сообщаемому клиентам. Источник один — `LIVEKIT_TCP_PORT`/`LIVEKIT_UDP_PORT`
  в `.env`, из них строятся публикация Docker, конфигурация LiveKit, перечень портов и правила проброса. Сменить согласованно:
  `sudo scripts/medianet.sh ports --tcp N --udp N` (проверка занятости, `.env`, пересоздание LiveKit и backend).

```bash
scripts/medianet.sh check            # режим, адреса, STUN, слои NAT (CGNAT/двойной), порты Docker, что LiveKit объявляет по журналу,
                                     # медиапорт по публичному адресу; с sudo — ещё межсетевой экран (DOCKER-USER, ufw)
sudo scripts/medianet.sh apply [--public-ip auto|off|IPv4]    # пересчитать и пересоздать LiveKit и backend (идущие звонки прервутся)
sudo scripts/medianet.sh ports --tcp 17881 --udp 17882         # сменить порты медиа согласованно
```

В веб-интерфейсе: «Сетевая доступность → Медиасоединения» показывает режим, адреса, правила проброса и проверки (кнопка «Проверить
медиасоединения»). Ещё там видны **фактические адреса ICE настоящих клиентов**: клиент сообщает адрес сервера из выбранной пары, и раздел
сверяет его с объявляемыми.

**Пределы проверки.** Проверка с сервера не проходит внешний NAT. Если соединение с медиапортом по публичному адресу установилось, порт
открыт. Если нет, это ничего не доказывает: многие маршрутизаторы не пропускают «петлю». Признаки CGNAT (`100.64.0.0/10` на пути) и
двойного NAT (несколько частных узлов) — эвристика по ответам маршрутизаторов. Частные адреса бывают и у маршрутизаторов провайдера без
NAT. Достоверно — звонок с устройства вне сети организации.

**Испытание** в модели сети — `tests/live/medianet/run.sh` (только Docker). Сценарии:
* сервер с публичным адресом;
* NAT с пробросом;
* офис и интернет одновременно;
* TCP при закрытом UDP;
* явный адрес при отказе STUN;
* отказ STUN;
* порты не проброшены;
* CGNAT;
* перенос прежней схемы.

Клиенты — LiveKit SDK со звуком и видео, межсетевой экран у клиентов, без «петли» NAT.

## NAT и публикация

* LiveKit сообщает клиентам тот же номер порта, что на сервере: на межсетевом экране порт пробрасывается на `LIVEKIT_NODE_IP` **без смены номера и протокола**.
* Публичный адрес в `LIVEKIT_NODE_IP` не пишут — его определяет `LIVEKIT_PUBLIC_IP` (см. «Медиасоединения» выше).
* Медиа по HTTP-прокси не ходит: через reverse proxy проходит только HTTPS (страница, API, сигнальное соединение).
* TCP-порт медиа — запасной путь для сетей, где UDP закрыт; без него такие пользователи не смогут говорить, качество по TCP хуже.
