# Установка и обновление Peregovorka

Для кого: администратор, который ставит систему и затем обновляет её. Подробности по портам, AD, данным и диагностике — в [DEPLOYMENT.md](../DEPLOYMENT.md).
Обновления везде идут **только через Git** — ручное копирование каталогов не используется.

Есть **два пути**, и выбирать нужно один:

| Путь | Когда | Что делает администратор |
| --- | --- | --- |
| **[Обычная установка на чистый сервер](#обычная-установка-на-чистый-сервер--рекомендуемый-путь)** — рекомендуемый | сервер отдан под Peregovorka: чистая Ubuntu 24.04 или Debian 12/13 | три команды; **полностью автоматически**, предварительно ничего не готовится |
| **[Shared-host / экспертная установка](#shared-host--экспертная-установка)** | на сервере уже работают другие сайты и сервисы (свой nginx, Docker, порты) | ручная подготовка: Docker, порты, прокси, параметры ядра — решения администратора |

Обновление, откат и диагностика (разделы 3–6) для обоих путей одинаковы.

## Обычная установка на чистый сервер — рекомендуемый путь

**Нужно:** сервер с Ubuntu 24.04 (Ubuntu 22.04+ и Debian 12/13 тоже подходят), не меньше 4 процессоров, 8 ГБ памяти и 30 ГБ диска (модель распознавания речи ~1–2 ГБ + записи), доступ в интернет, права `root`/`sudo`.
**Заранее ничего устанавливать не нужно** — ни Docker, ни Compose, ни Buildx, ни nginx, ни git, ни утилиты.

```bash
wget -O install.sh https://raw.githubusercontent.com/calleograph/peregovorka/main/install.sh
chmod +x install.sh
sudo ./install.sh
```

Что делает установщик (всё — без вопросов, кроме первого «Продолжить?»):

1. определяет систему (Ubuntu / Debian и версию) и отказывается, если она не поддерживается, — до любых изменений;
2. `apt update` и установка **всего необходимого** по манифесту [`scripts/lib/prereqlib.sh`](../scripts/lib/prereqlib.sh): Docker Engine + Compose + Buildx (из официального репозитория Docker для вашего дистрибутива), nginx, git, curl, openssl, ca-certificates и системные утилиты, которые используют скрипты проекта. Манифест проверяется тестом: если в скриптах появляется новая программа, которой нет в манифесте, тест падает. `apt upgrade`, `autoremove` и перезагрузка **не выполняются**;
3. создаёт каталоги данных с нужными владельцами и правами и применяет **параметры ядра** для звука и видео (`/etc/sysctl.d/99-peregovorka.conf`);
4. скачивает проект с GitHub (последний релиз; `--ref main` — свежая разработка) в `/opt/peregovorka`, создаёт `.env` с **случайными секретами** (без вопросов, права 600) и самоподписанный сертификат HTTPS;
5. скачивает модели — распознавания речи и **встроенную локальную языковую модель Qwen3 1.7B** (~1,3 ГБ, [LOCAL_LLM.md](LOCAL_LLM.md); без интернета её загрузка пропускается с явным сообщением, остальное продолжается), собирает образы, запускает базу и выполняет миграции, затем остальные сервисы, включает nginx;
6. выполняет **полную проверку** (`verify` и `smoke-test`): контейнеры, PostgreSQL, Redis, миграции, ASR с тестовым распознаванием, LiveKit, веб-интерфейс, тестовая комната;
7. ставит **помощника обновлений** (служба systemd от root) — он нужен кнопкам «Обновить» и «Исправить автоматически» в браузере;
8. создаёт локального администратора и **только после успешной проверки** печатает «УСТАНОВКА ЗАВЕРШЕНА» с состоянием сервисов, адресом, логином и первичным паролем. Если проверка нашла ошибку, пароль не показывается, установка не считается завершённой, а повторный запуск `sudo ./install.sh` продолжает с того места.

Параметры (`./install.sh --help`): `--host`, `--https-port`, `--dir`, `--data`, `--ref`, `--skip-models`, `--yes`. Для `scripts/install.sh` — также `--models-from КАТАЛОГ` (закрытая сеть) и `--skip-admin`. LDAP, сертификаты CA, группы администраторов, хранилище и почта в `.env` **не вводятся** — это делается в браузере ([ADMIN_SETUP.md](ADMIN_SETUP.md)).

**Потеряли пароль?** `sudo /opt/peregovorka/scripts/admin-reset.sh` — официальный механизм: новый случайный пароль (при входе его нужно заменить), завершение старых сеансов, снятие блокировки входа, запись в аудит; LDAP и ручная правка БД не нужны (`--create` создаст администратора, если его нет; `--username` — другой логин).

**Обновление:** кнопка в «Администрирование → Обновления и версии» либо `cd /opt/peregovorka && sudo ./scripts/update.sh` (раздел 3).

## Shared-host / экспертная установка

Только для сервера, где уже работают другие сайты и сервисы и нельзя ничего менять без решения администратора. В профиле `shared-host` установщик **не ставит** Docker и nginx, **не меняет** параметры ядра и файрвол, не трогает чужие site-файлы
и контейнеры; он показывает точный список недостающего и ждёт ваших действий. Для обычного отдельного сервера этот путь не нужен.

**Подготовьте заранее:**

| Что | Зачем |
| --- | --- |
| Сервер Ubuntu/Debian x86_64, ≥ 4 ядра, ≥ 8 ГБ RAM, ≥ 30 ГБ диска | запуск контейнеров; GPU необязателен |
| Docker + Compose plugin (Buildx желателен) и системные утилиты (`scripts/prereq.sh --check --profile shared-host` покажет, чего не хватает) | в shared-host ставятся вручную |
| DNS-имя, например `meet.<ваш домен>`, и HTTPS-сертификат (или внешний прокси с HTTPS) | **без HTTPS браузер не даст микрофон и экран** |
| Свободные порты: веб (TCP), ICE/TCP и ICE/UDP LiveKit, loopback-порт LiveKit API | значения подбирает мастер и проверяет на занятость |
| (по желанию) сервис обезличивания, ключ LLM, SMB-ресурс | протоколы |

Мастер shared-host спросит и параметры каталога (LDAPS, сервисная учётная запись, CA, группа администраторов) — они попадут в `.env` как прежняя настройка и будут работать сразу; позже их можно перенести в управляемые настройки кнопкой «Перенести настройки» (Администрирование → Подключения LDAP) и дальше менять в браузере.

```bash
git clone --depth 1 --branch <версия> https://github.com/calleograph/peregovorka.git /var/www/projects/peregovorka
cd /var/www/projects/peregovorka
scripts/setup.sh --profile shared-host
```

`<версия>` — тег последнего релиза с [страницы релизов](https://github.com/calleograph/peregovorka/releases) (`vX.Y.Z`).
Мастер сам: задаёт вопросы (имя экземпляра, DNS-имя, каталог данных), **подбирает и проверяет свободные порты**, **генерирует все секреты** (вручную `.env` править не нужно), готовит модель, запускает `preflight` и показывает план `install --dry-run`;
**применяет только после вашего «y»**. Гарантии для соседних проектов: свой compose-проект и каталоги, один новый nginx-site с проверкой `nginx -t`, никаких `apt upgrade`, `docker prune`, перезапусков чужих контейнеров, правок Apache/PHP/Moodle и файрвола.
Остановить можно в любой момент до «y». Подробности и этапы — раздел 2.

## 1. GitHub: публикация, релизы и доступ сервера (для владельца репозитория)

Репозиторий публичный: `https://github.com/calleograph/peregovorka` — серверу достаточно обычного `git clone` по HTTPS, deploy key не нужен. Ниже — как выпускать релизы; если репозиторий приватный, используйте deploy key (последний пункт).

Секреты (`.env`), данные и `node_modules` в репозиторий **не попадают** (`.gitignore`). Если вы ведёте собственную копию проекта, не кладите в неё реальные адреса, учётные записи и пароли.

1. На github.com → **New repository** → имя, например `peregovorka`, без README/.gitignore (репозиторий уже готов локально).
2. В каталоге проекта (локальный коммит уже создан):
   ```bash
   git remote add origin git@github.com:<организация-или-логин>/peregovorka.git      # или https://github.com/.../peregovorka.git
   git push -u origin main
   ```
   Релизы выпускаются только скриптом `./scripts/release.sh` (он обновляет `VERSION`, CHANGELOG, `package.json`, ставит тег; затем `./scripts/release.sh push`) — см. [VERSIONING.md](VERSIONING.md).
   (SSH-ключ или токен доступа GitHub настраивается в вашем аккаунте; при HTTPS на вопрос пароля вводится **personal access token**.)
3. Вкладка **Actions** покажет прогон CI (тесты backend, ASR, frontend, проверка скриптов и compose). Зелёный CI — условие для релиза.
4. **Доступ сервера на чтение** (рекомендуется deploy key):
   ```bash
   # на сервере, от пользователя, который будет делать деплой
   ssh-keygen -t ed25519 -N "" -f ~/.ssh/peregovorka_deploy -C "peregovorka-deploy@$(hostname)"
   cat ~/.ssh/peregovorka_deploy.pub
   ```
   GitHub → репозиторий → **Settings → Deploy keys → Add deploy key** → вставить ключ, **без** права записи. Затем:
   ```bash
   printf 'Host github-peregovorka\n  HostName github.com\n  User git\n  IdentityFile ~/.ssh/peregovorka_deploy\n  IdentitiesOnly yes\n' >> ~/.ssh/config
   chmod 600 ~/.ssh/config
   ```
   Адрес для клонирования: `git@github-peregovorka:<организация-или-логин>/peregovorka.git`.

> Релизы: версия — тег `vX.Y.Z` (+ файл `VERSION`). На сервер выкатывайте **тег или SHA**, а не «что там сейчас в main».

## 2. Первичное развёртывание (shared-host / ручной путь)

Для обычного сервера этот раздел читать не нужно — достаточно трёх команд из начала документа. Здесь — то, что делает мастер `scripts/setup.sh`, и ручные шаги экспертного пути.

### 2.1 Общие шаги (оба профиля)

```bash
# 1) код: конкретная версия (тег последнего релиза), а не «что сейчас в main»
git clone --depth 1 --branch <версия> https://github.com/calleograph/peregovorka.git /var/www/projects/peregovorka
cd /var/www/projects/peregovorka

# 2) конфигурация: мастер задаёт вопросы, подбирает порты и ГЕНЕРИРУЕТ секреты; .env получает права 600
scripts/setup.sh --profile shared-host --env-only
```

Что в `.env` создаёт мастер (вручную секреты не вводятся и не копируются; править файл стоит только ради необязательных параметров из `.env.example`):

- `COMPOSE_PROJECT_NAME` — **уникальное** имя экземпляра (например `peregovorka-prod`); от него зависят имена контейнеров/сетей/томов.
- `INSTALL_PROFILE` — `shared-host` или `standalone`; `APP_PUBLIC_URL=https://meet.<домен>`; `LIVEKIT_PUBLIC_URL=wss://meet.<домен>/livekit`.
- `DATA_ROOT` — каталог постоянных данных **вне** checkout (например `/srv/peregovorka-data`).
- Порты: `WEB_PORT`, `LIVEKIT_HTTP_PORT`, `LIVEKIT_TCP_PORT`, `LIVEKIT_UDP_PORT`, `NGINX_LISTEN_PORT` — свободные; `LIVEKIT_NODE_IP` — IP сервера, по которому до него доходят клиенты.
- Ключи: `LIVEKIT_API_KEY/SECRET`, `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `APP_MASTER_KEY`, `INTERNAL_API_TOKEN` — случайные, создаёт мастер. **Сохраните копию `APP_MASTER_KEY` отдельно** — без него зашифрованные настройки (пароль SMB, токены, ключ LLM, пароль LDAP) невосстановимы.
- Каталог (LDAP), сертификаты CA и группы администраторов настраиваются в браузере; прежние `LDAP_*` в `.env` (если они есть) продолжают работать и переносятся в управляемые настройки кнопкой «Перенести настройки».
- `TRUSTED_PROXY_HOPS` — сколько прокси перед контейнером web (host-nginx = 1; внешний reverse proxy + host-nginx = 2).
- `ALLOWED_ORIGINS` — необязательно: дополнительные адреса, с которых пользователи открывают приложение (внешний reverse proxy под другим именем или IP), через запятую: `https://meet.example.org,https://192.0.2.10`. Адрес из `APP_PUBLIC_URL` разрешён всегда, проверка Origin остаётся включённой. Если вход даёт «Недопустимый Origin» — см. [DEPLOYMENT.md](../DEPLOYMENT.md) §3.2.

```bash
# 3) модель распознавания (в Git её нет)
scripts/models.sh                         # с интернетом; в закрытой сети: scripts/models.sh --from-dir /путь/к/gigaam

# 4) проверка — ничего не меняет; исправьте все FAIL
scripts/preflight.sh

# 5) план установки — тоже ничего не меняет; прочитайте
scripts/install.sh --profile shared-host --dry-run       # или --profile standalone

# 6) установка (повторный запуск безопасен)
scripts/install.sh --profile shared-host                 # standalone: добавьте --configure-firewall, если хотите правила ufw

# 7) проверка работы
scripts/status.sh
scripts/smoke-test.sh
```

### Что важно знать о вопросах мастера
- **Каталог данных (`DATA_ROOT`)** — только локальный Linux-путь (`/srv/peregovorka-data`). Сетевой путь (`\сервер\ресурс`, `smb://…`) мастер не примет и объяснит почему. SMB-ресурс для готовых протоколов настраивается **после** установки: админка → «Хранилище».
- **LDAPS** вводится как `ldaps://dc.corp.local:636`; завершающий `/` допускается (мастер его уберёт). Значения с пробелами и кириллицей (DN групп) записываются в `.env` безопасно; после записи мастер сам проверяет, что `.env` читается теми же значениями.
- **Порты** подбираются свободные и проверяются; в конце мастер печатает **сетевую схему**: куда должен вести внешний прокси (порт host nginx) и какие порты LiveKit (ICE/TCP, ICE/UDP) нужны клиентам напрямую. HTTP-прокси (в т.ч. Nginx Proxy Manager) доступ к ICE-портам **не заменяет**.
- **Оперативная память**: требование 8 ГиБ «по паспорту» ВМ; сравнение идёт в КиБ с допуском на накладные расходы (ВМ на 8 ГиБ показывает ~7.8): ≥90% — ок, 75–90% — предупреждение, меньше — отказ.
- **Модель ASR**: скачивается с CDN (`GIGAAM_MODEL_BASE_URL`); контрольные суммы не проверяются (файлы upstream могут обновляться), проверяется только полнота (не пустой файл). При неудаче частичный файл сохраняется (`.part` / `.failed`) для разбора.

### Сервер, где нужный порт уже зарезервирован другим сайтом
Установщик создаёт **свой** listener (`NGINX_LISTEN_PORT`, например 18400) и существующие site-файлы **не меняет**. Связку делает администратор отдельно, например:
внешний прокси → `сервер:<зарезервированный порт>` → (ваш существующий site) `proxy_pass http://127.0.0.1:<NGINX_LISTEN_PORT>;` — либо направьте внешний прокси сразу на `сервер:<NGINX_LISTEN_PORT>`. Для WebSocket (`/api/v1/ws`, `/livekit/`) нужны заголовки `Upgrade`/`Connection`.

### 2.2 Shared-host (сервер с Moodle/другими приложениями)

- Docker должен быть уже установлен — иначе установка остановится (это намеренно).
- Установщик создаёт **только**: каталоги в `DATA_ROOT`, **один** новый site-файл nginx `NGINX_SITE_NAME` + симлинк, проект docker-compose. Перед включением выполняется `nginx -t`; при ошибке свои изменения откатываются и nginx **не перезагружается**. `sites-available/projects`, Apache, PHP-FPM, Moodle, файрвол не затрагиваются.
- Внешний reverse proxy должен направлять `meet.<домен>` на `NGINX_LISTEN_PORT` сервера, передавать `X-Forwarded-Proto: https` и пропускать WebSocket (`Upgrade`) для `/api/v1/ws` и `/livekit/`.
- **SIP-телефония** (необязательна, выключена по умолчанию) использует отдельные порты SIP signalling (`SIP_SIGNALING_PORT`, 5060) и RTP (`SIP_RTP_START`–`SIP_RTP_END`) только для вашей АТС; установщик их не открывает и файрвол не меняет. Включение, порты и правила — [SIP.md](SIP.md).
- **Откройте для клиентов** (напрямую, без HTTP-прокси) `LIVEKIT_TCP_PORT/tcp` и `LIVEKIT_UDP_PORT/udp` сервера. Файрвол сервера установщик не меняет.

### 2.3 Standalone (новый сервер)

Вручную ничего делать не нужно: см. начало документа («Обычная установка на чистый сервер»). `install.sh --profile standalone` сам ставит Docker, Compose, Buildx, nginx и утилиты (`apt install`, без `upgrade`/`reboot`) и применяет параметры ядра.
Свой сертификат HTTPS вместо самоподписанного: задайте `NGINX_TLS_CERT`/`NGINX_TLS_KEY` и выполните `scripts/install.sh --profile standalone --from nginx`.

### 2.4 Первая настройка в интерфейсе

1. Откройте `https://meet.<домен>`, войдите доменной учёткой из группы администраторов. В шапке появится «Администрирование».
2. **Система** — все пять проверок (PostgreSQL, Redis, LiveKit, ASR, Active Directory) должны быть зелёными. ASR становится зелёным после загрузки модели (1–2 мин после старта).
3. **Переговорки → Создать комнату**: название, идентификатор, доступ (кнопка «Найти» ищет группы/пользователей в AD), транскрибация/запись/камера/экран, сроки хранения. Без записей доступа комната видна только администраторам.
4. **Хранилище** — локальный каталог (`/data/exports`) или SMB (сервер, ресурс, учётка, пароль) → «Проверить подключение».
5. **Обезличивание** и **LLM и протокол** — адрес/токен/ключ → «Проверить подключение»; инструкции для протокола; при желании автосоздание.
6. **Экран** — профиль трансляции (по умолчанию «Чёткость» для слайдов и текста).
7. **Система → Общие настройки** — часовой пояс (для имён папок и времени в протоколах).
8. **Проверка с двумя браузерами/компьютерами**: оба входят в комнату, говорят — в панели справа появляются реплики с именами; «Показать экран» — второй видит экран на большой сцене; завершите встречу — в хранилище появилась папка `комната / дата, день недели / время / protocol.txt`.

### 2.5 Этапы установщика, сбои и повторный запуск

`install.sh` работает этапами (проверенная на реальном сервере последовательность): `prerequisites → preflight → dirs → kernel → models → pull → build → database → migrations → services → healthcheck → nginx → firewall → verify → report`, то есть: скачать/собрать образы → поднять **только** PostgreSQL+Redis и дождаться healthy → миграция Alembic → **проверка, что ревизия БД = head** → остальные сервисы → healthcheck → nginx → итоговая проверка.
Каждый этап печатает `[ok]/[warn]/[FAIL]`, сбой — одной строкой вида `FAIL stage=build service=backend subsystem=docker-buildkit` (по `subsystem` видно, что сломалось: Docker/хост или сам проект).

- **host nginx включается последним** — когда приложение уже запущено и здорово. Если что-то упало раньше, nginx и его порты остаются как до установки. При ошибке `nginx -t` свои изменения откатываются, reload не выполняется.
- **Повторный запуск безопасен** — просто выполните ту же команду. Готовое пропускается: образы не пересобираются, если исходники не менялись; собственный nginx-site (marker `managed-by: peregovorka:<проект>`, `listen`, symlink) распознаётся и не считается конфликтом порта; занятые **своими** контейнерами порты допустимы. `--from ЭТАП` начинает с указанного этапа; `--force-build` — пересобрать образы; `--adopt-images` — принять образы, собранные вручную, как актуальные (ваше явное решение).
- **Сбой прикладных сервисов** (не стали healthy): установщик останавливает только прикладные контейнеры проекта (`web backend asr livekit`), данные БД не трогает, nginx не включает.

**Сборка и BuildKit.** `preflight` показывает версии Docker/Compose/`buildx`, storage driver, режим сборки и устаревшие mount'ы containerd. Установщик перед сборкой реально проверяет builder (`FROM scratch`-образ):
- BuildKit работает → используется он (`COMPOSE_BAKE=false` — Bake отключён ради предсказуемости);
- BuildKit падает характерной ошибкой Docker/containerd (`exporting to image`, `mount callback failed`, `failed to open writer … locked`) → в логе явный **FALLBACK** на legacy builder (`DOCKER_BUILDKIT=0`), пока ваш Docker его поддерживает; ошибка помечается как проблема **Docker**, а не проекта;
- упал `RUN`/`COPY` в Dockerfile → `subsystem=dockerfile/project`, fallback не применяется.
Режим можно задать явно: `BUILD_MODE=auto|buildkit|legacy` в `.env`. Установщик **никогда** не делает `docker system prune`, не удаляет `/var/lib/docker|containerd`, не размонтирует чужие mount'ы и не перезапускает Docker/containerd. При обнаружении зависших `containerd-mount` он лишь выводит диагностику — решение за администратором сервера.

**Сетевые сбои скачивания.** `docker pull`/сборка при тайм-ауте registry/CDN/зеркала пакетов повторяются до 3 раз (пауза ~10 с, номер попытки в логе), уже скачанные слои не удаляются; итог при полном отказе — `FAIL subsystem=registry-network` (это не ошибка приложения и не Dockerfile).

### 2.6 Итоговая проверка («доказательство работоспособности»), параметры хоста, управление

Этап `verify` (и отдельно `scripts/verify.sh`, только чтение) проверяет: состояние и Docker healthcheck всех контейнеров; PostgreSQL; Redis; backend (ready); ASR и **загрузку модели GigaAM**; LiveKit (HTTP и сигналинг через web); web; фактическую ревизию Alembic (`current == head`); HTTP-цепочку (web, host nginx → web, `/internal/` закрыт); слушающие порты LiveKit; версию сборки (`version`, `commit`, `built_at`). Затем — `[ok] Peregovorka deployment completed` и памятка администратору (URL, каталоги, модель, порты, оставшиеся WARN, команды, путь к nginx-конфигу). Любая ошибка проверки — `FAIL stage=verify`, установка не считается успешной.

Типичные WARN. На **standalone** установщик сам применяет параметры ядра (этап `kernel`), а «Исправить автоматически» вернёт их при расхождении. На **shared-host** это глобальные настройки сервера, их меняет только администратор:
- `vm.overcommit_memory != 1` (Redis): `sudo sysctl -w vm.overcommit_memory=1`, постоянно — `echo 'vm.overcommit_memory = 1' | sudo tee /etc/sysctl.d/99-peregovorka.conf`. Последствие: при фоновом сохранении Redis возможна ошибка fork «Cannot allocate memory». Параметр влияет на все приложения сервера.
- `net.core.rmem_max` < 5000000 (LiveKit предупреждает «UDP receive buffer is too small»): `sudo sysctl -w net.core.rmem_max=5000000 net.core.wmem_max=5000000` и запись в `/etc/sysctl.d/`. Последствие: под нагрузкой потери UDP-пакетов и ухудшение звука/видео; для пробного запуска не критично.
- RTC-порты LiveKit: HTTP-прокси (в т.ч. Nginx Proxy Manager) **не заменяет** доступность `ICE/TCP` и `ICE/UDP` для клиентов — проверяйте порты с клиентского компьютера.

Управление: `scripts/status.sh`, `scripts/logs.sh [сервис] -f`, `scripts/ctl.sh restart|stop|start [сервис]` (только своего compose-проекта, данные не удаляются). Глубокий тест: `scripts/smoke-test.sh [--login ЛОГИН]` — LDAP bind, сигналинг, модель и тестовый инференс ASR, внутренняя сессия; с `--login` — реальная аутентификация (пароль запрашивается без эха, не сохраняется и не логируется).

**Версия работающего кода.** `version`, `commit` и `built_at` «запекаются» в образы при сборке (не переопределяются при запуске) и доступны на `/api/v1/version`, в «Система» админки и в итоговой проверке: `commit=unknown` помечается предупреждением.

**Зачем три порта на shared-host** (внешний порт → `NGINX_LISTEN_PORT` → `WEB_PORT`): внешний прокси (HTTPS, зарезервированный общий порт) → **host nginx :NGINX_LISTEN_PORT** — управляемый Peregovorka ingress (свой site-файл, WebSocket, закрытый `/internal`, `nginx -t` до reload; его конфигурацию установщик ведёт сам и не требует правки общих файлов) → **web 127.0.0.1:WEB_PORT** — контейнер (интерфейс, `/api`, `/livekit`). Упрощать до «NPM → приложение» автоматически нельзя без пересмотра WebSocket-заголовков, границы безопасности и автономности конфигурации; при желании существующий site можно направить прямо на `127.0.0.1:<WEB_PORT>` вручную (тогда `/internal/` нужно закрыть самостоятельно). **Общие nginx-файлы установщик не редактирует**: только собственный site (или готовый фрагмент `location`, который печатает сводка). Если вы правите общий файл вручную — используйте резервную копию, временный файл, `nginx -t` и только затем reload.

## 3. Обновление существующей установки

> **Памятка администратора** (всё остальное скрипты делают сами):
> ```bash
> ./scripts/check-updates.sh     # проверить наличие обновлений (ничего не меняет)
> ./scripts/update.sh            # обновить существующую установку
> ./scripts/verify.sh            # проверить состояние
> ./scripts/smoke-test.sh        # сквозная проверка
> ./scripts/diag.sh              # диагностический пакет (секреты маскируются)
> ./scripts/ctl.sh status        # состояние контейнеров
> ```
> `scripts/update.sh` — **единственный рекомендуемый способ** обычного обновления. `scripts/install.sh` — для первой установки и явно предусмотренных
> repair/reconfigure этапов (`--from ЭТАП`), а не для каждого обновления. `scripts/deploy.sh` оставлен как обёртка над `update.sh`.

### 3.1 First installation

См. разделы 0–2 выше (`scripts/setup.sh` → `scripts/install.sh`). После установки длинные команды git/docker/alembic вручную больше не нужны.

### 3.2 Check for updates

```bash
./scripts/check-updates.sh
```
Покажет: сколько новых commit'ов на `origin` и их список, новые параметры `.env.example` (только имена), наличие миграций БД, а также справочно —
какие новые версии LiveKit/SDK вышли. Ничего не меняет.

### 3.3 Normal update

```bash
./scripts/update.sh --dry-run    # что будет сделано (без изменений)
./scripts/update.sh              # обновление (спросит подтверждение; для автоматического запуска: --yes)
```

Что делает `update.sh` (по порядку, каждый этап печатает `[n/18] …`):

1. определяет каталог проекта, `COMPOSE_PROJECT_NAME`, текущий commit;
2. `git fetch` (с повтором при сетевых сбоях), показывает **список новых commit'ов** и наличие миграций;
3. **сохраняет локальные изменения** (патч, новые файлы и `git stash` — в каталог резервных копий, с инструкцией возврата) и продолжает; затем проверяет **источники сборки из среды сборки** — до переключения кода (см. 3.6);
4. сравнивает `.env` с новым `.env.example` **по именам** (значения секретов никогда не печатаются);
5. делает резервную копию `.env.backup-ГГГГММДД-ЧЧММСС` (права 600) и запоминает состояние для отката (предыдущий commit, образы `prev-<sha>`);
6. переходит на целевую версию — `git merge --ff-only` (установка на ветке) или `git checkout --detach <тег>` (установка на релизном теге; см. «Канал обновления» ниже) — после чего **продолжает уже новая версия скрипта**;
7. дописывает в `.env` только **безопасные новые параметры** со значениями по умолчанию (ASR-потоки, таймауты LiveKit и т. п.); всё, что зависит от сервера
   (порты, адреса, пути, `NGINX_*`, `LDAP_*`) или похоже на секрет, **выводится списком «требуют решения»** и не добавляется; закрепляет LiveKit на проверенной версии;
8. `preflight`; 9. проверяет модели (**ничего не скачивает повторно**);
10. собирает образы (ограниченные повторы при сетевых сбоях, при характерной ошибке BuildKit/containerd — автоматический повтор через legacy builder с записью `FALLBACK` в лог)
    и проверяет, что все они собраны из устанавливаемого кода; в образы «запекаются» **commit и время сборки**; 11. **backup БД** (при миграциях — с остановленным приложением, 3.7);
12. `alembic upgrade head` и проверка `current == head`;
13. `docker compose up -d` и **ожидание healthcheck** (`Waiting for web... 12/180 sec`); 14. миграция собственного nginx-site;
15. `verify`; 16. `smoke-test`; затем короткий итог из **четырёх раздельных частей**:

```text
Update:       SUCCESS      код получен, образы собраны, миграции применены
Deployment:   SUCCESS      сервисы запущены и здоровы
Health:       SUCCESS      verify и проверка работы системы (БД, ASR, звонки, веб)
Integrations: WARNING (LDAP/LDAPS)   подключения к внешним системам (каталог и т. п.)
```

Проблема интеграции (например, нет связи с каталогом) **не делает обновление неудачным**: версия установлена, сервисы работают. Код возврата `update.sh`: `0` — всё в порядке; `3` — обновление выполнено, но интеграции требуют внимания (в браузере рядом появляется кнопка «Исправить LDAP / открыть диагностику LDAP»); `1` — остановка или сбой работоспособности.
После обновления помощник сразу ищет известные проблемы (права на каталоги, устаревшая настройка nginx и т. п.) — см. 3.12.

**Никогда:** `git reset --hard`, удаление `DATA_ROOT` и моделей, пересоздание тома PostgreSQL, перезапись `.env`, повторный destructive install.

Параметры: `--ref SHA|TAG` (конкретная версия), `--pull` (обновить базовые образы и зависимости при сборке), `--force-build` (пересобрать образы на том же commit —
например, если `verify` сообщил `commit=unknown`), `--no-backup`, `--skip-models`, `--no-nginx`, `--skip-smoke`, `--wait СЕК`, `--stash`.

Обновлять лучше вне рабочих часов: на время пересоздания контейнеров активные встречи прерываются (клиенты переподключаются сами).

#### Канал обновления: релизный тег или ветка

Установщик ставит проект клоном **релизного тега** (`git clone --branch vX.Y.Z`), поэтому у обычной установки HEAD **отсоединён** (`git status` пишет «HEAD detached at vX.Y.Z»). Это штатное состояние, а не повреждение. `update.sh`, `check-updates.sh`, помощник обновлений и страница «Обновления и версии» определяют канал одинаково:

| Что стоит на сервере | С чем сравнивается | Как обновляется |
| --- | --- | --- |
| HEAD точно на релизном теге `vX.Y.Z` (обычная установка) | самый новый тег `vX.Y.Z` на origin | `git checkout --detach <тег>`; ветка не переключается, `main` не используется |
| ветка с upstream (установка из `main`, разработка) | upstream ветки | `git merge --ff-only` |
| HEAD на обычном commit (после отката на SHA, установка по `--ref <SHA>`) | не определяется | обновление **останавливается, ничего не меняя**, и подсказывает: `./scripts/update.sh --ref <тег|SHA>` или `git switch <ветка>` |

Правила, которые скрипты не нарушают: установка на релизном теге **никогда не переводится на `main` автоматически**; локальные изменения не стираются (`git reset --hard` не используется — изменения и собственные коммиты сохраняются, см. ниже); обновление выполняется только вперёд (установленная версия новее целевой — откат обновлением не выполняется).

Узнать канал: `git describe --tags --exact-match` (печатает тег — канал релизный) и `git symbolic-ref -q HEAD` (печатает ветку — канал ветки). Вернуть сервер, который когда-то вручную переключили на `main`, на релизы: `./scripts/update.sh --ref vX.Y.Z` (нужный тег) — дальше обновления пойдут по тегам.

**Сервер, установленный прежней версией (до исправления канала).** Старый `update.sh` на отсоединённом HEAD останавливается («Detached HEAD: укажите --ref…»), а при остановке до выбора цели может завершиться ошибкой `TARGET: unbound variable`. Обойти один раз, не переключаясь на `main`, можно явной версией — она не требует ветки:

```bash
cd /opt/peregovorka
sudo ./scripts/update.sh --ref vX.Y.Z --dry-run     # что будет сделано; ничего не меняет
sudo ./scripts/update.sh --ref vX.Y.Z               # сам переход; X.Y.Z — тег исправленного релиза
```
После этого установка уже содержит исправленные скрипты, и дальше работает обычное `./scripts/update.sh` и кнопка «Обновить» в браузере. Перед обновлением боевого сервера прогоните тот же сценарий на отдельном стенде.

#### Локальные изменения

Обновление из-за правок в рабочей копии **не останавливается**. Изменённые файлы сохраняются в `DATA_ROOT/backups/local-changes-ГГГГММДД-ЧЧММСС/` (`changes.patch`, новые файлы в `untracked.tar.gz`, `README.txt` с командой возврата) и в `git stash` под именем `peregovorka-update-…`; собственные коммиты на сервере (история разошлась с репозиторием) — в bundle и отдельную ссылку git. Затем устанавливается версия из репозитория.
Сохранённое **не применяется автоматически**: вернуть правки — по `README.txt` в каталоге копии; решает администратор. На сервере ничего не правят вручную — настройки задаются в `.env` и в интерфейсе.

#### Файл `.env`

`.env` не заменяется никогда. Резервные копии `.env.backup-*` лежат рядом (содержат секреты — храните с правами 600). Новые параметры:
безопасные добавляются в конец файла блоком `# --- добавлено scripts/update.sh …`, остальные перечислены в итоге — внесите их вручную по `.env.example`.

#### Версия проекта и образов

**Автоматическое обновление.** «Администрирование → Обновления и версии → Автоматическое обновление»: переключатель, время запуска (по умолчанию 00:00, часовой пояс из «Общих настроек») и «ждать окна без встреч» (по умолчанию 6 часов, допустимо 1–23). В назначенное время сервис просит помощника обновлений проверить версию; если новой нет — ничего не делает; если есть — запускает то же обновление, что и кнопка «Обновить проект» (запрос помощнику, `by=auto-update`). **Идущие встречи не прерываются**: пока они есть (или помощник занят), обновление откладывается и проверяется каждые 30 секунд; если окна нет в пределах заданных часов, цикл завершается записью «отложено» и повторяется на следующие сутки. Итог (версии «было → стало», длительность, причина ошибки) виден в разделе и записывается в историю попыток (метка «автоматически»). Требуется установленный помощник обновлений; без него цикл пропускается с пояснением. «Выполнить сейчас» запускает цикл вне расписания по тем же правилам.

**«Что нового» перед обновлением.** В «Обновления и версии» рядом с «Обновить проект» есть кнопка «Что нового»: установленная и доступная версии и изменения между ними, разобранные из `CHANGELOG.md` (тот же текст, что в описании релиза на GitHub; помощник обновлений берёт разделы новее установленной версии из опубликованной редакции, поэтому интернет у браузера не нужен). Пункты разложены по смыслу: заголовки `### Новое`, `### Исправления`, `### Интерфейс`, `### Конфигурация`, `### База данных`, `### Что потребуется от администратора`, `### Известные ограничения` внутри раздела версии задают группу явно; без подзаголовков группа определяется по тексту пункта. Отдельным блоком «Обратите внимание» выделяются пункты про схему БД и миграции, порты, перезапуск LiveKit, ручные действия, загрузки, удаление прежнего поведения, а также факты репозитория (изменились файлы миграций или `.env.example`). Описание перехода версий сохраняется при запуске обновления из веб-интерфейса (`$DATA_ROOT/updater/changes/<от>__<до>.json`) и открывается из истории («что изменилось»); у обновлений из терминала описания нет.

Версия проекта — файл `VERSION` (схема `MAJOR.MINOR.PATCH`), история — `CHANGELOG.md`; в интерфейсе она показана как «`версия · commit`». `update.sh` и веб-обновление собирают образы с версией из `VERSION`
и commit из git; итог обновления печатает `Version: <было> → <стало>`, а на странице «Обновления и версии» видно, что нового в опубликованной версии. Подробности и выпуск версии — [VERSIONING.md](VERSIONING.md).
Строки `APP_VERSION`/`APP_GIT_COMMIT` в `.env` больше не нужны и игнорируются.

#### Версии образов и LiveKit

Образы собираются с `APP_VERSION`, `APP_GIT_COMMIT`, `APP_BUILT_AT` (`APP_BUILD_TIME` тоже понимается) — `verify.sh` сравнивает git HEAD с commit в образах backend, asr и web
(`/version.json`) и предупреждает при несовпадении или `commit=unknown` (так бывает после ручной `docker compose build`: пересоберите `./scripts/rebuild.sh` или `./scripts/update.sh --force-build`).

**Не собирайте образы командой `docker compose build` напрямую.** Она не передаёт `APP_GIT_COMMIT`/`APP_BUILT_AT` (образ получит «commit unknown» и в интерфейсе будет помечен как «собран вне штатного обновления»), не умеет автоматически
переходить с BuildKit на legacy builder (нет `buildx`, блокировка containerd при экспорте образа) и не повторяет сборку при сетевых сбоях. Для ручной пересборки есть помощник:

```bash
./scripts/rebuild.sh                 # backend, asr и web: тот же путь сборки, что у update.sh (commit и время в образе, BuildKit → legacy, повторы)
./scripts/rebuild.sh backend         # только backend; затем он пересоздаётся и проверяется на healthcheck
./scripts/rebuild.sh --if-changed    # только то, у чего изменились исходники
```

Веб-обновление («Обновления и версии») тоже идёт через `update.sh`, то есть тем же путём сборки.

**Пути резервных копий.** `BACKUP_DIR` (как и `DATA_ROOT`) — только локальный абсолютный Linux-путь вне репозитория; UNC-путь (`\\сервер\папка`), `smb://` и относительные пути отвергаются сразу, до записи на диск
(`backup.sh`, `update.sh`, `preflight.sh`). Копию дампа на сетевой ресурс делайте отдельно: примонтируйте ресурс на сервере и укажите точку монтирования в `BACKUP_COPY_DIR` — дамп копируется туда после успешного локального `pg_dump`
(сбой копирования только предупреждает, локальная копия остаётся).

**TLS в smoke-test.** Если сам сервер не доверяет цепочке публичного сертификата (нет корневого/промежуточного сертификата в его хранилище или отдаётся неполная цепочка), а в браузере адрес открывается нормально, это **предупреждение**, а не ошибка.
Ошибкой остаются истёкший сертификат и несовпадение имени хоста — их увидят и браузеры.
**LiveKit в production не `latest`**: `update.sh` выставляет проверенный набор из `deployment/compat.env` (LiveKit Server v1.13.10, JS SDK 2.23.0, Python SDK 1.1.21, livekit-api 1.2.2, SIP-служба v1.20.0):
устаревший или `latest` тег заменяется (одна строка `.env`, копия сохранена), более новый конкретный тег остаётся с предупреждением. Smoke-test обязательно проверяет настоящий WebSocket на
`/rtc/v1` (без отката `/rtc/v1 → 404 → /rtc`).

### 3.4 Updating models

Модели — не одноразовые артефакты сборки: `update.sh` **только проверяет** `DATA_ROOT/models/gigaam` и ничего не скачивает повторно и не удаляет. Файлы:
`v3_e2e_rnnt.ckpt` + `v3_e2e_rnnt_tokenizer.model` (полная GigaAM v3 e2e RNNT, PyTorch; квантованная модель снята с вооружения). Проверяется наличие и размер
(контрольные суммы не сверяются — решение владельца: файлы upstream могут меняться). Если Full отсутствует, запускается `scripts/models.sh` (он пропускает уже имеющееся).

**Автоматическая подготовка при установке (0.39.1).** Этап `models` у `scripts/install.sh` сам запускает `scripts/models.sh`: готовой считается только пара «чекпойнт + токенайзер»; загрузка идёт с докачкой (`curl -C -`, до 4 попыток, тайм-аут соединения 20 с, обрыв при скорости ниже 10 КБ/с в течение минуты), размер сверяется с `Content-Length` сервера, HTML-страницы вместо файла (вход через прокси) отвергаются и сохраняются как `*.failed`, неполный `*.part` остаётся для докачки. Причина сбоя печатается словами (DNS, соединение, TLS, HTTP, тайм-аут). Хеши можно задать в `.env`: `GIGAAM_CKPT_SHA256`, `GIGAAM_TOKENIZER_SHA256` (по умолчанию не требуются — upstream может обновлять файлы). После загрузки или копирования права внутри `DATA_ROOT/models` приводятся к «читается всеми» (каталоги 755, файлы 644; владелец не меняется, остальные каталоги данных не затрагиваются), а перед запуском служб файлы читаются от имени пользователя ASR (uid 10001) в одноразовом контейнере. Закрытая сеть: `scripts/install.sh --profile … --models-from КАТАЛОГ`.

**Если служба не запустилась.** Установщик показывает последние строки её журнала (секреты маскируются), вероятную первопричину и действие. Ошибка прав на модель исправляется автоматически (перезапускается только `asr`); PostgreSQL, тома и образы не пересоздаются, внешний nginx включается только после того, как все службы стали healthy.
Добавить/обновить модель вручную: `scripts/models.sh [--from-dir КАТАЛОГ]`; выбор активной модели — в админке «Интеграции → Распознавание речи».

### 3.5 Update failures

При любой ошибке скрипт останавливается и печатает этап и что делать, например: `Обновление остановлено на этапе «Сборка образов»`. Данные, `.env` и модели не затрагиваются; уже работающие контейнеры
не останавливаются до этапа запуска. Состояние сохраняется в `DATA_ROOT/state/last-update.state` (этап, commit'ы, резервные копии). Типичные причины:

| Этап | Причина | Что делать |
| --- | --- | --- |
| git fetch | нет доступа к GitHub | сеть/прокси; повторить |
| локальные изменения | правки в рабочей копии | `--stash` или убрать правки |
| сборка | сеть/registry/зеркала; Docker/containerd; ошибка в коде | см. 3.6; лог `DATA_ROOT/state/build-<сервис>.log` |
| источники сборки | npm/PyPI/GitHub/зеркала недоступны из среды сборки | остановка **до** переключения кода; в отчёте — источник, этап (DNS/TCP/прокси/TLS/передача данных) и рекомендация (см. 3.6) |
| миграции | ошибка Alembic | приложение было остановлено до копии БД; база **точно** возвращается к копии (текущая сохраняется как `<имя>_failed_<время>`), затем откат кода и образов (3.7) |
| healthcheck | сервис не стал healthy | автоматически: возврат базы к копии (если схема менялась) и `rollback.sh`; итог — в отчёте (3.13) |
| verify/smoke | FAIL-проверки | итоговая таблица `smoke-test.sh`; `scripts/diag.sh` |

### 3.6 Build retry / network problems

Сетевые операции повторяются автоматически: `apt-get` (`Acquire::Retries=5`), `pip` (`PIP_RETRIES`, повтор до 4 раз с растущей паузой для torch/зависимостей/GigaAM с GitHub), `npm ci`
(повтор), `docker pull` (3 попытки), `git fetch` (4 попытки), сборка сервиса (3 попытки при сетевой ошибке registry/CDN). Повторяется **только упавший сервис**; Docker-кэш слоёв сохраняется,
а commit/время сборки объявлены в конце Dockerfile, поэтому их смена **не сбрасывает** слои с torch и зависимостями.
**Долгая сборка ASR — не зависание.** Установка `torch`, `pip install "gigaam @ git+https://github.com/…"` может идти 15+ минут; пока лог растёт и есть сетевая активность (ESTAB :443), процесс работает.
`update.sh` не убивает сборку по таймауту и раз в минуту печатает `сборка asr идёт N мин (лог +N КБ …)` и последнюю строку лога. Если BuildKit падает на уровне Docker/containerd
(`mount callback failed`, `failed to open writer`), `update.sh` сам повторяет сборку legacy builder'ом (`DOCKER_BUILDKIT=0`) и пишет `FALLBACK`; обычная ошибка исходников так не «лечится».

**Проверка источников сборки (до переключения кода).** Сеть хоста и сеть контейнера сборки могут вести себя по-разному: например, на хосте загрузка с CDN «зависает» на сотнях килобайт, а из контейнера проходит, или наоборот.
Поэтому `update.sh` проверяет источники **из тех же базовых образов, в которых идёт сборка** (node, python), и с **настоящей передачей данных** (до 4 МБ реального пакета: npm-пакеты из `package-lock.json`, колёса PyPI из `constraints.txt`, индекс PyTorch, GitHub, зеркала apt):
DNS → TCP → прокси (`HTTPS_PROXY`, если задан) → TLS → ответ → передача. Итог по каждому источнику — `OK`, `WARN` (медленно) или `FAIL` с этапом. Решение:

* источник недоступен из сети сборки и **не прошёл повторные проверки** (по умолчанию ещё 2 с паузой 5 с: `NETCHECK_BRIDGE_RETRIES`, `NETCHECK_RETRY_PAUSE`), но доступен из сети хоста — сборка этого обновления идёт в сети хоста (`BUILD_NETWORK=host` для `docker compose build`); системные DNS, маршруты, MTU, прокси и настройки Docker **не меняются**. Единичный тайм-аут моста сеть хоста не включает: если повторная проверка прошла, сборка идёт в обычной сети Docker, а отчёт называет это временным сбоем;
* **сборка в сети хоста сначала проверяется**: BuildKit с плагином `buildx` и отдельным builder'ом требует для `network: host` отдельного разрешения (`network.host`), иначе сборка падает с «additional privileges requested: pass "--allow=network.host"». Перед такой сборкой `update.sh` собирает крошечный образ в сети хоста тем же путём, что и настоящая сборка (`docker compose build`): разрешает BuildKit — собирает BuildKit; не разрешает — шаги в сети хоста собирает классический builder (`DOCKER_BUILDKIT=0`, ему разрешение не нужно; в журнале строка `FALLBACK`); не работает ни то ни другое — обновление останавливается **до сборки** с причиной `subsystem=build-network-host` и рекомендацией (разрешить `network.host` отдельному builder'у: `docker buildx create --use --buildkitd-flags '--allow-insecure-entitlement network.host'`, либо `BUILD_MODE=legacy`, либо устранить причину недоступности из моста). Настройки Docker, builder'ы и сеть сервера проект сам не меняет;
* недоступен совсем, а зависимости компонента **изменились** — обновление останавливается **до переключения кода** (сервер остаётся на прежней версии) с причиной и рекомендацией; если зависимости не менялись — предупреждение (слои возьмутся из кэша Docker);
* проверку выполнить нельзя (нет базового образа локально) — `SKIP`, решение принимает сама сборка. Пропустить проверку: `--skip-netcheck`.

**Повторы ограничены.** Сетевой сбой npm/pip/apt/git внутри сборки распознаётся как сетевой (в том числе `ETIMEDOUT`, `ECONNRESET`, `socket hang up`, `Could not resolve host`), а не как ошибка проекта. Перед повтором источники компонента проверяются снова:
доступны — повтор (не более `BUILD_ATTEMPTS`, по умолчанию 3, и в пределах `BUILD_BUDGET_S`, по умолчанию 90 мин); доступны только из сети хоста — повтор в сети хоста; недоступны — остановка без бесполезных повторов.
Уже собранные компоненты при повторном запуске **не пересобираются** (по отпечатку исходников), поэтому после сбоя последнего компонента повтор собирает только его. Для Node в образе сборки включено `--dns-result-order=ipv4first` и увеличенный таймаут выбора IPv4/IPv6 —
без этого `npm ci` в сетях без IPv6 падает с `ETIMEDOUT`. Перед переключением проверяется, что все образы собраны **из устанавливаемого кода** (commit внутри образа и отпечаток исходников); образ не из этого кода пересобирается один раз, иначе переключение не выполняется.

### 3.7 Database migrations

Перед миграцией `update.sh` показывает текущую ревизию и целевую (`head`), убеждается, что PostgreSQL healthy, **останавливает приложение** (web, backend, asr; базы работают), **делает backup БД** (`DATA_ROOT/backups/<проект>-db-…-pre-<sha>.dump`),
выполняет `alembic upgrade head` и требует `current == head` (например, `0003 = head`). Миграции делаются «расширяющими» ([docs/MIGRATIONS.md](MIGRATIONS.md)). Если миграций нет, приложение не останавливается до этапа запуска.

Обновление транзакционное: после копии в базу никто не пишет, поэтому при сбое миграции или новой версии база возвращается к копии **без потери данных** — текущая база не удаляется, а переименовывается в `<имя>_failed_<время>` (для разбора; удалить вручную),
создаётся новая и восстанавливается из копии; затем код и образы возвращаются на прежнюю версию. Если миграция нужна, а копия отключена (`--no-backup`), обновление **останавливается до изменения схемы** (код возвращается, прежние контейнеры не тронуты).

### 3.8 Verification

`./scripts/verify.sh` (только чтение): контейнеры и healthcheck, PostgreSQL, Redis, Alembic, backend ready, ASR и модель, **commit образов = git HEAD**, HTTP-цепочка, LiveKit, порты, параметры хоста.
Собственный nginx-site проверяется по той схеме, на которую он настроен: сначала HTTPS с именем сайта (SNI и `Host`, проверка сертификата не отключается), затем HTTP. Ответ `400 The plain HTTP request was sent to HTTPS port` — признак HTTPS-порта, а не неисправности;
если сам сервер не доверяет сертификату сайта, это предупреждение (доверие к сертификату оценивает отдельная проверка TLS). Маршрут LiveKit `/rtc/v1` считается рабочим при `101`, при `400 «join_request is required»` и при `400` с другим текстом, если тот же адрес с заведомо неверным токеном
отвечает `401 «invalid authorization token»` (запрос дошёл до LiveKit); `404`, `5xx`, страницы прокси и ошибки соединения остаются ошибками.
Код возврата: **FAIL → 1; WARN → 0; PASS → 0.** Предупреждения хоста (`vm.overcommit_memory`, `net.core.rmem_max/wmem_max/netdev_max_backlog`, потоки ASR × параллелизм > ядер, старый nginx-site) —
только рекомендации: установщик/`update.sh` sysctl не меняет, ASR-параметры не меняет (оценить: `scripts/asr-bench.sh --concurrency 1,2`). `./scripts/smoke-test.sh` заканчивается строкой `Smoke test: PASS`.

### 3.9 Rollback

> **Git rollback ≠ database rollback.**

```bash
./scripts/rollback.sh                  # к версии, стоявшей до последнего update.sh
./scripts/rollback.sh --to <SHA>       # к конкретному commit
```
`update.sh` перед изменениями сохраняет: предыдущий commit, копию `.env`, путь к backup БД и ссылки на работающие образы (теги `prev-<sha>`). Откат возвращает **код и образы без пересборки**,
но не схему БД. Перед откатом проверяется, что текущая ревизия БД **известна коду целевой версии**; если после обновления применена новая миграция — `rollback.sh` **останавливается**
(код возврата 3) и предупреждает: старый образ поверх новой схемы может не запуститься или портить данные. Варианты: восстановить БД из backup, сделанного перед обновлением
(`scripts/restore.sh <файл>`; потеряются данные, записанные после backup), затем откатывать код; либо остаться на новой версии и исправить проблему обновлением.
`.env` при откате автоматически не восстанавливается (путь к копии выводится). После отката рабочая копия в detached HEAD. Если откат пришёл на релизный тег (обычная установка), следующий `./scripts/update.sh` снова пойдёт по релизным тегам к самому новому — чтобы остаться на старой версии, обновление не запускайте. Если откат пришёл на произвольный commit, `update.sh` остановится, ничего не меняя, и подскажет `--ref <тег|SHA>` либо `git switch main` (для установки на ветке).

### 3.10 Recovery after interrupted update

Если `update.sh` прервали (Ctrl+C, обрыв SSH, перезагрузка): ничего не восстанавливайте вручную — **повторите `./scripts/update.sh`**. Обновление помечено маркером `DATA_ROOT/state/update-in-progress`;
если код уже обновлён, скрипт напишет «Найдено прерванное обновление» и продолжит со сборки/миграций (все этапы идемпотентны: уже собранные образы пропускаются, миграции применяются только недостающие).
Если backup БД уже сделан, повторный запуск сделает ещё один — это безопасно. Состояние и копии: `DATA_ROOT/state/last-update.state`, `.env.backup-*`, `DATA_ROOT/backups/`.

**Код новый, а контейнеры или схема БД — прежние** (обновление прервали после переключения кода, маркер потерян): «Обновления и версии» не показывает «актуально», а пишет «Обновление установлено не полностью» и что именно расходится
(сравниваются код на сервере, версия работающего backend и ревизия схемы БД). Повторный `./scripts/update.sh` (или кнопка «Обновить проект») при отсутствии новых коммитов **доводит развёртывание** той же версии — сборка недостающих образов, копия БД и миграции, перезапуск, проверка — а не ограничивается `verify`.
То же делает исправление «Обновление установлено не полностью» (3.12).

### 3.11 Для разработчика: выпуск

```bash
# внести изменения, прогнать тесты локально/в CI
git add -A && git commit -m "Что изменено" && git push origin main
# выпуск релиза (необязательно)
./scripts/release.sh patch        # (или minor / major) — VERSION, CHANGELOG, package.json и тег одним действием
./scripts/release.sh push
```
Дождитесь зелёного CI. Версии LiveKit/SDK меняются только вместе с `deployment/compat.env` после проверки (`docs/COMPATIBILITY.md`).

### 3.12 Обновление из браузера, помощник обновлений и «Исправить автоматически»

Администрирование → «Обновления и версии» показывает установленную редакцию, опубликованную на GitHub, список новых изменений и версии компонентов, а кнопка «Обновить проект» запускает тот же `scripts/update.sh` и показывает ход построчно.
Контейнеры не имеют доступа к Docker и git сервера, поэтому на хосте работает небольшой **помощник** (`scripts/updater.sh`, служба systemd **от root**). При обычной установке он ставится сам.

Помощник выполняет **только фиксированный набор действий**: сверка с GitHub, `scripts/update.sh --yes` (флаги из белого списка), поиск проблем и одно исправление из белого списка. Произвольных команд, путей и `sudo` из браузера нет: запрос — несколько проверяемых строк
(формат, возраст до 10 минут, идентификатор исправления из списка), в аудит попадает кто и что запросил. Все дочерние команды запускаются в **стерильном окружении** (`env -i`): настройки берутся только из `.env` экземпляра, посторонние `ASR_*`, `NGINX_*`, `LIVEKIT_*` из окружения службы или пользователя не подмешиваются.

**Итог обновления (0.46.0).** После запуска `verify` и `smoke-test.sh` дают четыре независимых итога. Ошибка самой системы (сервисы, БД, ASR, LiveKit напрямую и через web, тестовая комната) — «проверка нашла ошибки»; перед этим безопасно исправимое (права на каталоги данных, не запущенные сервисы — только `up -d --no-build`, без прокси, сертификатов, сети и `.env`) исправляется само, даётся время на прогрев и проверка повторяется ОДИН раз: итог определяет повторная проверка, первая и действия остаются в отчёте. Проблемы внешнего окружения (каталог LDAP, публичный адрес LiveKit, TLS публичного URL) — код 3: обновление «успешно», а причина показана отдельно. После ошибки в «Обзоре» и «Обновлениях» появляется пункт «Проверить заново» (`reverify`): пройденная проверка исправляет статус, отчёт и пометки, а запись о первой неудачной попытке в истории остаётся. `/rtc/v1` проверяется запросом с `join_request`, как у браузера; при отказе причину уточняет `/rtc/v1/validate` (200 — Upgrade режет прокси/WAF; 404 — устаревший LiveKit или путь не передаётся; 401 — ключи; 400 без признаков LiveKit — WAF/прокси).

**«Исправить автоматически»** (Состояние системы и Обновления и версии). Известные проблемы показываются как «Проблема → Что это значит → Что будет сделано» с кнопкой; команд Linux администратор не видит. Исправление идёт по шагам, и каждый виден в журнале:
1) **диагностика** — проблема проверяется заново (если она уже не подтверждается, ничего не меняется); 2) **подтверждённая причина**; 3) **безопасное исправление**; 4) **повторная проверка**. Если исправить не удалось или проблема осталась — сообщение об этом и что сделать вручную.
Перезапускается только затронутый сервис (например, исправили права на сертификаты — перезапустится backend, а не весь стек):

| Проблема | Что исправляется |
| --- | --- |
| неверный владелец/режим каталогов данных (сертификаты, вложения чата, записи, обмен с помощником) или сервис не может в них писать | каталоги создаются/приводятся к нужным владельцу и правам, перезапускается backend |
| устаревший или отсутствующий собственный nginx-site | обновление по шаблону с `nginx -t`, reload и откатом при ошибке (чужие файлы не трогаются) |
| параметры ядра ниже рекомендаций (только standalone) | рекомендованные значения в `/etc/sysctl.d/99-peregovorka.conf` |
| не хватает программ или Docker Buildx (только standalone) | установка из репозиториев |
| обновление установлено не полностью: сервисы работают из образов другой версии, чем код на сервере | штатное обновление на ту же версию (`update.sh --ref <текущий commit>`): сборка, копия БД и миграции, перезапуск, проверка |
| образы собраны без сведений о версии (`commit unknown`) | пересборка и перезапуск |
| база данных отстаёт от программы | резервная копия и миграции |
| полная проверка давно не выполнялась | запуск `verify` и `smoke-test` |

Проверка выполняется при запуске помощника, раз в 5 минут и после каждого обновления/исправления. «Перенести настройки» для старой конфигурации LDAP — отдельный пункт, он виден, пока `LDAP_*` в `.env` используются (см. [ADMIN_SETUP.md](ADMIN_SETUP.md)).

**Если помощника нет или он работает без прав** (сервер установлен прежней версией, служба создавалась от обычного пользователя), в браузере будет единственная подсказка с командой — выполнить её один раз на сервере:

```bash
cd /opt/peregovorka && sudo ./scripts/updater.sh install --yes
```

Тот же результат даёт обычное ручное обновление от администратора (`sudo ./scripts/update.sh`): оно само переустановит службу помощника. Управление: `./scripts/updater.sh status | print-unit | uninstall`.

**Как проверяется обновление.** Каждая версия проверяется не только на чистой установке, но и как *обновление предыдущего релиза* с существующими данными, правами, `.env`, прежним LDAP и файлами: тест `backend/tests/test_upgrade_path.py`
(схема БД релиза 0.2.x с данными → миграции → прежний `LDAP_*` в `.env` и недоступный каталог CA → вход по домену работает → перенос настроек → данные на месте). Ограничение: полный сквозной прогон на настоящем сервере (Docker, реальный каталог AD) в автоматических тестах не выполняется.

**Действия с дополнительными компонентами (с 0.52.0).** Тот же помощник выполняет действия со службами из разделов «Видеозапись», «Трансляции» и «SIP-телефония»: `video_enable|video_disable|video_restart`, `sip_enable|sip_disable|sip_restart`, `livekit_restart`, `web_restart` и `state` (только опрос). Веб-интерфейс кладёт запрос `action=component op=<ID>`; ID проверяется по белому списку в backend (`services/server_components.py`) и ещё раз на хосте (`COMPONENT_OPS` в `scripts/lib/complib.sh`; совпадение проверяет тест). Каждое действие — фиксированная последовательность над контейнерами этого compose-проекта (`video.sh`/`sip.sh enable|disable` или пересоздание одного сервиса), затем ожидание `healthy` и итог в `status.json`/`update.log`. Перед запуском интерфейс показывает последствия (перезапуск LiveKit прерывает звонки), без `confirm=true` backend запрос не принимает; при идущем обновлении, исправлении или другом действии — 409. Каждое действие пишется в аудит (`system.component`) и журнал событий. Фактическое состояние (что включено в `.env`, контейнеры, их health и время запуска, наличие образов) помощник пишет в `components.json` при каждой проверке (раз в 5 минут) и после действия; backend считает его истиной вместо переменных окружения своего контейнера. Новый компонент добавляется в оба списка и в `COMPONENTS`.

### 3.13 Отчёт об обновлении

Каждый запуск `update.sh` (из терминала или браузера) заканчивается единым отчётом `DATA_ROOT/updater/report.txt` (и `report.json` для интерфейса); в «Обновления и версии» он показан карточкой «Отчёт о последнем обновлении» с кнопкой «Скачать отчёт».
В отчёте: версия до обновления и целевая, что работает сейчас, ревизия схемы БД, итог и **этап остановки с причиной**, **автоматические действия** (сохранение локальных изменений, выбор сети сборки, повторы с номерами попыток, остановка приложения, восстановление БД, возврат кода, откат),
**состояние сборки каждого компонента** (собран / использован без пересборки / ошибка с классом и попытками), результат проверки источников сборки, состояние сервисов и рекомендация. Пароли, ключи и токены в отчёте и в журнале окна обновления скрываются.

### 5.1. Внутреннее зеркало установщика — возможный механизм (не реализовано)

**Не реализовано и не проверялось.** Раздел описывает, как можно устроить установку и обновление без прямого доступа сервера в интернет, чтобы владелец мог решить, нужен ли такой механизм. Сейчас из этого работают только `PEREGOVORKA_REPO` (адрес git-репозитория для `install.sh`) и `install.sh --models-from` (готовый каталог моделей).

Что установщик и `update.sh` берут из интернета и чем это можно заменить:

| Источник | Для чего | Возможная замена внутри сети |
| --- | --- | --- |
| GitHub (`git clone`, теги) | код выбранной версии | внутренний git-сервер с зеркалом репозитория; `PEREGOVORKA_REPO=https://git.example.org/peregovorka.git` (уже поддерживается в `install.sh`; `update.sh` берёт `origin` установленного каталога) |
| Docker Hub и другие registry | базовые образы (python, node, nginx, postgres, redis, livekit, egress) | registry-прокси (Harbor, Nexus, `registry:2` в режиме pull-through) и `registry-mirrors` в `/etc/docker/daemon.json` — средство Docker, проекту менять ничего не нужно |
| PyPI | зависимости backend и asr при сборке | прокси PyPI (Nexus, devpi); понадобится передавать `PIP_INDEX_URL` в сборку как build-arg — **в Dockerfile этого нет** |
| npm | зависимости frontend | прокси npm (Nexus, Verdaccio); понадобится `NPM_CONFIG_REGISTRY` как build-arg — **в Dockerfile этого нет** |
| источник моделей | GigaAM, Silero VAD, Qwen3 | каталог на внутреннем ресурсе; `install.sh --models-from` и `scripts/models.sh --from-dir` (уже поддерживается) |

Чего не хватает для полного механизма:

1. Build-args `PIP_INDEX_URL`, `PIP_TRUSTED_HOST`, `NPM_CONFIG_REGISTRY` в `backend`, `asr` и `frontend` Dockerfile и их передача из `.env` через `deployment/compose.yml`. Без значений поведение остаётся прежним.
2. Проверка источников сборки в `update.sh`, которая сейчас обращается к публичным npm и PyPI, должна брать те же адреса из `.env`.
3. Доверие к корпоративному УЦ внутри сборочных образов (сертификат зеркала), иначе pip и npm откажут по TLS.
4. Документированный порядок обновления зеркала: новый тег в git-зеркале, предварительная загрузка образов и пакетов новой версии.

Другой вариант — офлайн-комплект: архив с кодом, `docker save` всех образов и каталогом моделей, который `install.sh` разворачивает без сети. Он проще в эксплуатации, но каждый выпуск весит несколько гигабайт и требует отдельной сборки.

## 6. Типовые проблемы

| Симптом | Что делать |
| --- | --- |
| `preflight` ругается на порт | выберите другой порт в `.env`; автоматически порты не занимаются |
| «Не удалось подключиться к серверу звонков» | страница не по HTTPS; не доходит `LIVEKIT_PUBLIC_URL` (`/livekit/` не проксируется с Upgrade); `scripts/logs.sh livekit` |
| Подключились, но нет звука | закрыты `LIVEKIT_UDP_PORT/udp` и `LIVEKIT_TCP_PORT/tcp` на пути клиент → сервер; неверный `LIVEKIT_NODE_IP` |
| Не входит доменная учётка | `scripts/logs.sh backend` (коды `invalid_credentials`, `tls_error`, `service_account_error`); проверьте CA и имена в `LDAP_URIS`; блокировка нашей защитой от перебора снимается через 15 мин |
| Текста нет | вкладка «Система»: ASR красный → `scripts/models.sh`, `scripts/logs.sh asr`; в комнате выключена транскрибация или остановлена запись |
| Краткий протокол «failed» | в строке протокола — причина: не настроено обезличивание/LLM, сервис вернул `verification.clean=false`, таймаут |
| В хранилище нет файлов | «Хранилище → Проверить подключение»; для SMB — права учётки на запись, доступность `445/tcp` с сервера |
| `update.sh`: «Обнаружены локальные изменения» | на сервере ничего не правят вручную: уберите правки либо `./scripts/update.sh --stash` (stash не применяется автоматически) |
