# Аудит производительности реального времени

Дата: 2026-10-06. Область: вход в комнату, жизненный цикл Room (LiveKit), показ экрана, ASR, запись, прокси.
Исходный факт (владелец): после расширения ВМ до 8 vCPU / 16 ГБ существенного ускорения нет; во время встречи ASR — единицы процентов CPU
(пики 20–40 %), LiveKit 1–3 %, backend < 1 %, RAM с запасом, swap не используется. Значит узкое место — **не железо**, а задержки и последовательность
в realtime-пайплайне. Добавление CPU/RAM методом оптимизации не считается.

## Как читать статусы

| Статус | Значение |
| --- | --- |
| **confirmed** | подтверждено измерением владельца, журналом или прочитанным исходным кодом (источник указан) |
| **hypothesis** | правдоподобная причина, измерением не подтверждена |
| **fixed** | исправление внесено в код и проверено тестами; **не** означает, что эффект измерен на сервере |
| **measured** | эффект измерен на реальном стенде (после исправления) — таких записей пока **нет**, см. раздел «Что остаётся измерить» |

Чего здесь нет: замеров на реальном LiveKit/клиентах после исправлений. Всё, что помечено `fixed`, ждёт замера.

## F1. Пятисекундная пауза между `/join` и RTC-сессией

| | |
| --- | --- |
| **Симптом** | Пользователь нажимает «Войти» — и видит комнату через 5–7 с |
| **Подтверждённые измерения** | confirmed: backend 19–40 мс, ASR < 1 с, браузер начинает RTC через ≈5 с; confirmed: 404 на `/rtc/v1` + откат на `/rtc` |
| **Текущая реализация (до исправления)** | confirmed (код): `setJoin(info)` вызывался **после** `room.connect` и `setMicrophoneEnabled(true)`; так как `getUserMedia` с запросом разрешения шёл последовательно, комната и WebSocket событий появлялись только после него; `await room.startAudio()` стоял в критическом пути перед публикацией микрофона |
| **Референс** | Jitsi: сигналинг (XMPP over WebSocket `/xmpp-websocket`) и медиа — независимые соединения; JVB использует один UDP-порт ICE (10000) и принимает ICE restart как make-before-break (`reference.conf`). LiveKit-эквивалент: `/rtc/v1` + UDP-mux порт + `reconnectPolicy`/resume. Мы их используем, но против **устаревшего** сервера |
| **Найденная причина** | (a) **confirmed**: сервер 1.9.0 не знает `/rtc/v1` — это видно в логах; (b) **hypothesis**: именно откат на `/rtc` даёт основную часть 5 с (связь «404 → секунды» логами показана, но интервал откат-времени не измерен); (c) **confirmed (код)**: последовательные независимые операции во frontend |
| **Исправление** | **fixed**: LiveKit по умолчанию `latest` (проверена v1.13.7); проба настоящего WebSocket Upgrade на `/rtc/v1` в `smoke-test.sh` и в диагностическом отчёте (404 → FAIL с объяснением); `getUserMedia` стартует сразу после `/join` параллельно с `Room.connect`; `startAudio()` вынесен из критического пути; комната и WebSocket событий открываются сразу после `/join`; этапы входа с секундомером; preflight предупреждает о LiveKit старее проверенной версии |
| **Ожидаемый эффект** | hypothesis: вход ≤ 1–2 с в LAN/VPN при `/rtc/v1` без 404 |
| **Результат после исправления** | **не измерен**. Измерение: админка → «Состояние системы» → «Время входа» (`total_join_ms`, `livekit_connect_ms`, `signaling_connect_ms`, `ice_connect_ms`), в комнате «⚙ Диагностика», `performance.measure("pg:total_join")` во вкладке Performance |

## F2. Пересоздаётся ли LiveKit Room

| | |
| --- | --- |
| **Симптом** | В логах LiveKit один и тот же пользователь через несколько секунд создаёт «новую RTC session» |
| **Подтверждённые измерения** | confirmed (логи владельца): повторная сессия того же пользователя |
| **Текущая реализация** | confirmed (аудит кода `RoomPage.tsx`): `Room` создаётся только в `connectLivekit`; эффекты имеют пустые/стабильные зависимости (`teardown` — `useCallback([])`), состояние микрофона/камеры/экрана/транскрипции/WebSocket/списка участников Room не затрагивает; пересоздание возможно **только** при явном повторном входе после потери связи. `React.StrictMode` в dev вызывает двойной эффект, но до `join` Room ещё нет |
| **Референс** | Jitsi: при ICE failed ждёт возврата сети (`xmpp.ping`, до 65 с), +2 с на восстановление ICE и только затем перезапускает медиасессию (`IceFailedHandling.ts`) — т. е. пересоздание сессии осознанное и редкое. LiveKit: сначала resume (ICE restart), затем полный reconnect — внутри одного объекта Room |
| **Найденная причина** | **hypothesis**: вторая «сессия» в логах — это откат SDK с `/rtc/v1` на `/rtc` (каждая попытка видна серверу как отдельное подключение); пересоздания Room в нашем коде не найдено |
| **Исправление** | **fixed** (наблюдаемость): `client_instance_id` у каждого Room; фазы `ROOM_CREATE, CONNECT_START, SIGNALING_CONNECTED, ICE_CONNECTED, CONNECT_OK, RECONNECTING, RECONNECTED, DISCONNECTED, ROOM_DISPOSE` — в журнал комнаты и на сервер; админка «Диагностика клиентов» показывает фазы с `instance`, а «Состояние системы» — **объектов Room на один вход** (норма 1.0) и счётчики reconnect/rejoin |
| **Ожидаемый эффект** | различимость «нормальный reconnect» (тот же `instance`) и «создан новый Room» (новый `instance`, `reason=rejoin`) |
| **Результат** | не измерен |

## F4. ASR: параллелизм и потоки

| | |
| --- | --- |
| **Симптом** | `ASR_CPU_THREADS=6`, `ASR_MAX_CONCURRENT_INFERENCE=2` на 8 vCPU; нагрузка CPU низкая; скорости не прибавилось |
| **Текущая реализация** | confirmed (код до исправления): `GigaAmProvider` создавал `threading.Lock`, но **нигде его не использовал** — вызовы не сериализовались; confirmed (исходники GigaAM): `RNNTGreedyDecoding.decode` и `GigaAM.forward` не меняют состояние объекта (скрытые состояния — локальные переменные, `SentencePiece` только читает), поэтому одна общая копия модели из нескольких потоков безопасна |
| **Референс** | Jitsi/JVB: очереди пакетов на участника ограничены по размеру (`queue-size = 1024`) и разделены на вход/выход; тяжёлая обработка не блокирует приём (hypothesis — по конфигурации, код JVB не читался) |
| **Найденная причина** | arithmetic confirmed: 6 потоков × 2 одновременных = **12 потоков на 8 ядер** (переподписка); **hypothesis**: параллельные распознавания мешают друг другу. Выгода от 2 одновременных распознаваний **не измерена** |
| **Исправление** | **fixed**: мёртвый замок удалён, обоснование потокобезопасности — в коде; предупреждение при старте и в `preflight`/`verify` (`потоки × параллелизм > ядер`); `asr-bench.sh --concurrency 1,2` печатает задержку одного вызова и **пропускную способность** — по ним видно, даёт ли параллелизм выгоду; `ASR_INTEROP_THREADS` и журнал реальных `os.cpu_count`, `torch.get_num_threads`, `get_num_interop_threads` из рабочего процесса |
| **Ожидаемый эффект** | hypothesis: `ASR_CPU_THREADS=6, ASR_MAX_CONCURRENT_INFERENCE=1` не хуже (CPU и так простаивает); окончательно — по бенчмарку |
| **Результат** | не измерен (нет модели в этой среде) |

## F5. Метрики по сегментам ASR

**fixed.** В журнале на каждый сегмент: `speech_duration_ms, vad_wait_ms, queue_wait_ms, preprocessing_ms, inference_ms (модель), decoding_ms, total_latency_ms, end_to_end_ms, realtime_factor, participant, meeting_id, model_id, runtime`. `vad_wait_ms` — ожидание паузы-конца реплики (≈ `end_silence + pad`), поэтому **основной вклад в задержку до текста даёт не модель, а VAD**: при `ASR_VAD_END_SILENCE_MS=700` каждая реплика ждёт ≥ 0,7 с — confirmed арифметикой; влияние на качество не измерено. Параметры VAD вынесены в админку (применяются к новым трекам без перезапуска): пауза, минимальная речь, запас, максимальная реплика, порог. Подбирать по реальным разговорам: задержка, обрезание концов слов, короткие реплики, длинная речь, пунктуация.

## F7. ASR и WebSocket приложения не влияют на звонок

confirmed (код): `/join` не ждёт ASR (в ответе только флаг `asr_ready`); воркер ASR входит в комнату сам; WebSocket событий (`LiveSocket`) — отдельный объект с независимым backoff и не связан с `Room` ни в одну сторону. **fixed**: при пропаже ASR во время встречи показывается «Транскрибация временно недоступна» (звонок продолжается); готовность опрашивается всегда, а не только до первого успеха.

## F9. Прочее (решения «не менять»)

| Пункт | Решение и причина |
| --- | --- |
| Параметры ядра | **не менять дальше.** Для сравнения: пакет JVB ставит `rmem_max=10485760`, `netdev_max_backlog=100000`; у нас 5 000 000 / 5 000, предупреждение LiveKit исчезло. Менять наугад нет оснований |
| Лимиты Docker | отсутствуют; JVB в systemd задаёт `LimitNOFILE=65000`, `TasksMax=65000`. Для 3–20 участников не актуально; при росте проверить `ulimit -n` в контейнере LiveKit |
| `uvicorn --workers` у backend | **не увеличивать.** Нагрузка < 1 %. Безопасность multi-worker не доказана: фоновые задачи (`segment-consumer`, `reaper`, `retention`, `asr-model-sync`) запускаются в `lifespan` и продублировались бы в каждом worker'е без выбора лидера; фоновые генерации протоколов живут в процессе. Состояние сессий, throttle и pub/sub уже в Redis. Сначала — лидер-выбор для фоновых задач |
| Железо | 8 vCPU / 16 ГБ — запас для пилота, а не исправление; ресурсного узкого места не найдено |

## Сравнение с современным Jitsi Meet / JVB

Колонки по запросу владельца. «Изучено» — что реально прочитано; остальное — `hypothesis` (общая архитектура, не код).

| Тема | Какую проблему решает Jitsi и как (изучено) | Эквивалент в LiveKit | Используем / правильно ли | Что перенести как принцип |
| --- | --- | --- | --- | --- |
| Conference join lifecycle | Сигналинг по WebSocket отделён от медиасессии JVB; Jicofo выделяет мост | `/rtc/v1` + SFU-сессия в одном соединении Room | Да; но сервер был старый (404) → исправлено | Каждый этап входа измеряется отдельно (сделано: 10 меток) |
| Reconnect / resume | `IceFailedHandling`: ждать сеть (ping до 65 с) → +2 с на возврат ICE → только затем перезапуск сессии | `reconnectPolicy`, resume (ICE restart), затем full reconnect | Да, поверх добавлен свой rejoin с backoff | Не пересоздавать сессию сразу; различать resume и новый Room (сделано: `instance`) |
| ICE | Один UDP-порт (10000), `keep-alive-strategy=selected_only`, make-before-break при ICE restart | UDP-mux порт, TCP-fallback, `node_ip` | Да (mux-порт, TCP 17881) | Проверять тип выбранного кандидата (host/srflx/relay) — сделано |
| WebSocket lifecycle | `tcp_nodelay on`, HTTP/1.1, Upgrade; WebSocket сигналинга и колибри отдельно | WebSocket `/rtc/v1`; наш `/api/v1/ws` — отдельно | Да; добавлен `tcp_nodelay`/no-buffering | Независимые lifecycle сигналинга и событий приложения (подтверждено) |
| Media track lifecycle | Треки добавляются/удаляются через Jingle source-add/remove без пересоздания PeerConnection | publish/unpublish в Room | Да | Фазы `SCREEN_*` и проверка, что Room не пересоздаётся |
| Simulcast | `disableSimulcast`, слои 1:2:4; для экрана HD-слой всегда, нижние — при высоком FPS | `simulcast`, `videoSimulcastLayers`, `screenShareSimulcastLayers` | Да, явные слои для камеры (360p/180p) и экрана (720p5) | Низкие слои экрана нужны не всегда |
| Adaptive bitrate | Таблицы `maxBitratesVideo` по кодеку и уровню; адаптивный режим только при CPU-перегрузке | `adaptiveStream`, `dynacast`, `videoEncoding` | Да | Реагировать на `qualityLimitationReason` (cpu/bandwidth) — выводим в статистику |
| Bandwidth estimation | JVB: send-side BWE (`jmt.bwe`, `max-bw=20 Mbps`, пороги потерь 2 %/10 %), `trust-bwe`, `allow-oversend-onstage` для экрана ≤ 500 кбит/с, `padding-period=15ms` | Stream allocator + transport-wide CC на сервере (по документации; не проверялось) | Используем умолчания LiveKit, не трогаем | Для демонстрации экрана допустим «oversend» нижнего слоя — смотреть настройки LiveKit только по данным |
| Screen sharing | 5 к/с по умолчанию, `ssHigh` 2,5 Мбит/с, `contentHint`, кодек экрана отдельно (`screenshareCodec`) | `screenShareEncoding`, `contentHint`, `degradationPreference` | Да; у нас 15 к/с, до 4 Мбит/с в «Чёткости» | Приоритет разрешения над FPS; значения FPS/битрейта подбирать по замерам |
| RTP/RTCP, packet loss, jitter | `RTPStatsCollector`: потери, jitter, RTT, битрейт, кодек по SSRC | `getStats()`, `getSenderStats/getReceiverStats` | Да (панель + сервер) | Собирать те же поля — сделано |
| NACK / PLI | JVB ограничивает запросы ключевых кадров: ≤ 3 от получателя за 10 с, не чаще 1 на источник за 2 с («1,2 Мбит/с деградирует при ключевом кадре раз в секунду») | PLI throttle в LiveKit (по документации; не проверялось) | Умолчания; считаем NACK/PLI/FIR на клиенте | Лавина PLI на экране — признак проблемы; мониторится |
| Jitter handling / media queues | Очереди пакетов на участника: вход и выход по 1024 пакета (≈1,5 с при 650 пп/с) | Буферы пакетов в SFU (по документации) | Умолчания | Ограниченные очереди + явный учёт потерь — перенесено в запись аудио ASR |
| Thread separation | Конфигурация: отдельные очереди, `load-management` по CPU (порог 0,9, учёт CPU steal) | Горутины SFU | Н/д (код JVB не читался — hypothesis) | Отдельный поток для медленного ввода-вывода — перенесено (писатель записи) |
| Device switching | Смена устройств без пересоздания сессии | `switchActiveDevice` | Да | Ошибку показывать у списка устройств — сделано |
| Graceful degradation | `load-management`: уменьшение `last-n` при перегрузке (×0,75, восстановление ×1,25, не чаще раза в минуту) | dynacast/adaptiveStream, ограничение слоёв | Да | Деградировать качеством, а не соединением |
