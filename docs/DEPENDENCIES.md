# Сторонние компоненты: ревизия версий при каждом релизе

Peregovorka собрана из чужих компонентов (LiveKit, PyTorch, FastAPI, PostgreSQL, React и десятков других). Правило проекта: **при каждом релизе — в том числе исправлении вида 0.24.1 — каждая вышедшая новая версия каждого компонента получает решение**: либо она включена в релиз после проверки, либо отложена с конкретной причиной, номером задачи и датой повторной проверки. Устаревшие зависимости не должны переходить из релиза в релиз «по умолчанию».

## Откуда берутся версии

| Что | Где закреплено | Кто меняет |
| --- | --- | --- |
| Манифест релиза: версия, проверенная версия, решение по каждому компоненту | `backend/app/components.json` | `scripts/deps.py` и разработчик (решения) |
| Python-зависимости **всех** уровней (прямые и транзитивные) | `backend/constraints.txt`, `asr-service/constraints.txt` | `scripts/deps.py freeze` (в контейнере Python 3.12 — как в образе) |
| Диапазоны допустимых версий Python | `requirements.txt` | разработчик |
| npm-зависимости | `frontend/package.json` + `package-lock.json` | `npm install`/`npm update` |
| Базовые образы (Python, Node, nginx, Alpine, PostgreSQL, Redis) | тег **и digest** в `ARG …_IMAGE` Dockerfile и в `deployment/compose.yml` | `scripts/deps.py pin-images` + `apply` |
| LiveKit Server, SIP-служба, llama.cpp | тег в `.env.example`, Dockerfile, `compose.yml`, `scripts/lib/*.sh`, `deployment/compat.env` | `scripts/deps.py apply` |
| PyTorch, torchaudio, GigaAM | `TORCH_VERSION`/`TORCHAUDIO_VERSION` в `asr-service/Dockerfile`, `GIGAAM_GIT_COMMIT` в `.env.example` | `scripts/deps.py apply` |
| draw.io | `ARG DRAWIO_VERSION` в `frontend/Dockerfile` | `scripts/deps.py apply` |
| Приложение для Windows (Electron, electron-builder, esbuild, WiX) | точные версии в `desktop/package.json` + `desktop/package-lock.json`, WiX — в `.github/workflows/desktop.yml` | разработчик при выпуске клиента (`desktop-vX.Y.Z`): `npm outdated` в `desktop/`, Electron — последний патч поддерживаемой ветки (исправления безопасности Chromium), запись в `desktop/CHANGELOG.md`. В манифест сервера (`components.json`) не входит: это отдельный продукт со своей версией |

Сборка образа ставит **ровно** версии из constraints и lock-файлов, а не «самые новые в диапазоне», поэтому «Полная пересборка» воспроизводит тот комплект, который проверен в релизе. Новые версии приходят **только** через ревизию релиза (или PR от Dependabot/еженедельного контроля), а не при пересборке на сервере.

## Как готовить релиз (обязательный порядок)

```bash
python3 scripts/deps.py review          # сеть: обновляет «что вышло» и дату ревизии, проверяет уязвимости (OSV)
python3 scripts/deps.py check           # таблица: закреплено · проверено · доступно · решение
# по каждой строке «НОВАЯ…»: обновить версию (и проверить) ИЛИ оформить отсрочку (ниже)
#   обновление: поправьте pinned/tested в манифесте (или requirements/package.json), затем
python3 scripts/deps.py apply           # версии и digest — в файлы проекта
python3 scripts/deps.py freeze          # constraints Python (Docker)
(cd frontend && npm install)            # lock npm
python3 scripts/deps.py sync            # pinned/tested из constraints и lock — в манифест
python3 scripts/deps.py pin-images      # digest образов (если обновляли базовые образы)
python3 scripts/deps.py verify --online --max-age 3   # итог: код 0
python3 scripts/deps.py report          # «Было → Стало» для отчёта о релизе
```

`scripts/release.sh minor|patch` **не выпустит версию**, пока `deps.py verify --online --max-age 3` не пройдёт (ревизия не старше трёх дней, нет версий без решения, нет известных уязвимостей без записи в `security_ack`). Без сети проверка пропускается только явным `PEREGOVORKA_SKIP_DEPS_ONLINE=1` с записью в отчёт о релизе. CI на каждый push выполняет `verify` без сети (закрепления в файлах совпадают с манифестом, constraints покрывают requirements, у каждой отсрочки есть причина, задача и непросроченная дата).

### Отсрочка обновления

В манифесте у компонента:

```json
"deferred": {"version": "<какая версия отложена>", "reason": "<конкретная техническая причина>", "issue": "DEP-N или https://…", "recheck": "ГГГГ-ММ-ДД", "plan": "<что и когда будет сделано>"}
```

Правила: `version` равна новейшей доступной; `issue` — раздел `### DEP-N` в этом файле (или ссылка); `recheck` — не позднее чем через 120 дней и не в прошлом (иначе `verify` падает). Фраза «дождитесь следующего релиза» без плана недопустима. Обновление минорной/патч-версии откладывать без причины нельзя.

### Что значит «проверено»

* **Patch** — предлагается и проверяется при каждом релизе; после зелёных тестов входит в релиз.
* **Minor** — читается changelog, проверяется совместимость (для 0.x минор считается мажором), обновляется после профильных проверок.
* **Major** — отдельная оценка совместимости, миграций и API; для PostgreSQL и Redis — отдельная процедура (ниже).
* **Комплект LiveKit** (сервер, SIP, `livekit-client`, Python SDK `livekit` и `livekit-api`) проверяется **вместе**: поле `bundle: livekit` в манифесте, `deployment/compat.env` повторяет эти версии (совпадение проверяет `verify`).

Профильные проверки: LiveKit — вход участников, звук, видео, показ экрана, переподключение, адаптивное качество, E2EE (`tests/live/`); SIP — запуск службы с LiveKit и Redis, транки, правила, вызов, `OPTIONS`; ASR — тесты, импорт, прогрев и **настоящая** расшифровка тестового аудио моделью GigaAM; backend — полный набор тестов и миграции; frontend — типы, тесты, сборка, живые сценарии; PostgreSQL/Redis — запуск и сохранность данных; Outlook — манифест и серверные API. Что нельзя проверить без внешней инфраструктуры (реальная АТС, Exchange), помечается в отчёте как не проверенное.

### Что ловит проверка помимо версий (урок 0.24.1)
Совпадение версий не доказывает, что компоненты работают вместе: в 0.24.1 образ ASR остался без `onnxruntime`, и Silero VAD не запускался. Поэтому образ ASR собирается с `RUN python -m app.selfcheck` (`pip check` + создание Silero VAD и один прогон), то же выполняется в CI (job `asr-image`) и в `deps.py postcheck` после обновления; сквозную проверку «LiveKit → VAD → GigaAM → текст» даёт `tests/live/asr_e2e.py <образ> <каталог весов>` — её выполняют при каждой ревизии релиза. Зависимости GigaAM (onnx 1.19.*, onnxruntime 1.23.*) ставятся вместе с ним под constraints; уязвимости onnx 1.19 учтены в `security_ack`.

## Раздел «Версии компонентов» в интерфейсе

«Администрирование → Обзор → Версии компонентов»: **Работает** (версия из запущенного контейнера: библиотеки backend — из самого процесса, ASR — из его «пульса», PostgreSQL и Redis — запросом к серверу, frontend — из собранного приложения `/version.json`, `/nginx-version.txt`, `/drawio/VERSION`), **Проверено с релизом**, **Доступно**, **Статус**, дата ревизии, причина и задача отсрочки, ссылка на changelog, статус безопасности (OSV). Статусы: «Актуально», «Доступно обновление», «Обновление отложено», «Требуется проверка» (работает не та версия, что проверена в релизе — например, образ не пересобран), «Ошибка определения версии». Полная пересборка воспроизводит комплект текущего релиза; новые версии приходят с релизом.

## Проверка после обновления сервера

`scripts/update.sh` после перезапуска сервисов запускает `scripts/deps.py postcheck`: версии **работающих** контейнеров (Python-пакеты backend и ASR, LiveKit, PostgreSQL, Redis, nginx, draw.io, digest образов) сверяются с манифестом релиза. Итог пишется в журнал обновления и `components-report.json` (виден в интерфейсе). Расхождение критичных компонентов (LiveKit, SDK, PostgreSQL, Redis) считается ошибкой обновления: update.sh останавливается с понятным сообщением и предлагает `./scripts/rollback.sh`; остальные расхождения — предупреждение.

## Автоматический контроль между релизами

* `.github/dependabot.yml` — еженедельные PR для pip (backend, ASR), npm, Docker (все Dockerfile), GitHub Actions.
* `.github/workflows/deps-watch.yml` — по понедельникам и вручную: `deps.py check`; при появлении версий без решения или уязвимостей создаётся (обновляется) задача «Ревизия зависимостей» с таблицей: компонент, было, стало, ссылка на changelog, сведения об уязвимостях.
* Что Dependabot не видит (LiveKit-образы по `.env`, llama.cpp, draw.io, GigaAM, torch, digest) — контролирует `deps.py`.

## Отложенные обновления

### DEP-1 — llama.cpp: server-b11371 → новее
Образ локальной LLM (Qwen3 1.7B Q4_K_M). Новый образ не проверен с моделью на CPU: ответы протоколов и скорость на целевом железе не измерялись. План: поднять образ с моделью (1,2 ГБ), прогнать структурированное извлечение на эталонной стенограмме, сравнить время и результат с b11371; при совпадении — включить. Повторная проверка — в ближайшем релизе.

### DEP-2 — Python 3.12 → 3.15 (образы backend и ASR)
Для torch 2.14.1 в PyPI есть колёса только до cp314 — на Python 3.15 ASR не соберётся. Образы остаются на 3.12 (поддержка до 2028), переход на 3.13/3.14 обсуждается отдельно. План: после выхода колёс torch для 3.15 проверить сборку ASR и backend, обновить `PYTHON_IMAGE`, `freeze`, CI.

### DEP-3 — Node.js 24 → 26 (сборка frontend)
Node 26 по графику проекта Node.js переходит в LTS осенью 2026. Сборка остаётся на LTS-версии 24. План: после перехода 26 в LTS собрать frontend, прогнать типы, тесты и живые сценарии, обновить `NODE_IMAGE` и CI.

### DEP-4 — PostgreSQL 16 → 18 (мажорная)
Каталог данных PostgreSQL не совместим между мажорными версиями: нужна отдельная процедура. Процедура обновления существующего сервера: (1) `scripts/backup.sh` и проверка копии; (2) остановка сервисов; (3) `pg_dumpall` из старого контейнера; (4) новый каталог данных, запуск `postgres:18-alpine`, восстановление; (5) `alembic upgrade head`, `scripts/verify.sh`; (6) старый каталог хранится до подтверждения. Автоматизация в `update.sh` пока не сделана — до неё мажорная смена на серверах не выполняется. PostgreSQL 16 получает исправления безопасности в линии 16.x (digest образа обновляется ревизией).

### DEP-5 — Redis 7 → 8 (мажорная)
В Redis хранятся очереди, сессии, ключи встреч и E2EE-ключи; данные временные, но потеря ключей идущей встречи прерывает её. Нужна оценка: совместимость сервера Redis 8 с клиентом redis-py 8.1 (используется) на настоящем сервере, поведение при обновлении «на месте» (RDB/AOF) и условия лицензии. План: проверка на стенде с настоящим Redis 8 (очередь ASR, сессии, E2EE-ключ, LiveKit SIP), затем обновление образа.

*DEP-6 (FastAPI) закрыта в 0.29.0: версия 0.149.0 включена после полного набора backend-тестов, тестов ASR-службы (70) и сборки образа ASR с самопроверкой в CI; настоящая расшифровка (`tests/live/asr_e2e.py`) для этой версии отдельно не выполнялась — FastAPI в ASR отвечает только за служебный HTTP-интерфейс, путь модели не затрагивает.*

### DEP-6 — FastAPI 0.149.0 → 0.162.x
В 0.29.0 FastAPI обновлён до 0.149.0 (предыдущая отсрочка DEP-6 закрыта). К ревизии 0.30.0 (2026-10-23) вышло ещё 12 выпусков 0.x за четыре дня; для 0.x каждый минор считается мажором. Релиз 0.30.0 — исправление надстройки Outlook, смешивать его с крупным обновлением веб-фреймворка нельзя. К ревизии 0.34.0 вышла 0.162.0 — отсрочка продлена с той же причиной (обновление веб-фреймворка — отдельным выпуском с полным регрессом). План: разобрать release notes 0.150–0.162, обновить constraints backend и ASR, полный набор тестов, живые сценарии, `tests/perf`, включить в ближайшем релизе.

### DEP-7 — LiveKit SIP v1.20.0 → 1.21.0
Комплект LiveKit (сервер, SIP, SDK) проверяется вместе, а служба SIP — только с настоящей АТС: транк, входящий и исходящий вызов, `OPTIONS` (docs/SIP.md). Тестовой АТС у разработчика нет, поэтому непроверенная минорная версия в релиз не включается. План: поднять `livekit/sip:1.21.0` вместе с LiveKit и Redis на стенде с АТС, пройти проверки SIP, обновить `deployment/compat.env` и образ.

### DEP-8 — draw.io v32.5.5 → v32.6.x
Вышла 21–23.10.2026, в день ревизии 0.34.0. По списку изменений — новые функции и ускорения редактора, исправлений безопасности нет. Доска встраивается в страницу встречи и проверяется живым сценарием с настоящим draw.io, а выпуск 0.34.0 посвящён главной странице — смешивать их не стоит. План: собрать статику v32.6.x (`frontend/drawio/prune.sh`), пройти живые сценарии доски и её выгрузки, сборку образа web (CI `web-image`), обновить `DRAWIO_VERSION`; повторная проверка — до 2026-11-06.

### DEP-9 — LiveKit Server v1.13.10 → v1.13.11
Вышла 25.10.2026, в день ревизии 0.39.0. Изменения касаются медиасервера (FlexFEC, лимит повторных передач на трек, каналы данных в режиме одного соединения), исправлений безопасности в списке нет. Комплект LiveKit проверяется вместе; выпуск 0.39.0 посвящён интерфейсу. План: поднять версию на стенде, пройти живые сценарии звука, видео, показа экрана, переподключения и E2EE, обновить `deployment/compat.env` и образ; повторная проверка — до 2026-11-01.

### DEP-10 — LiveKit Python SDK 1.1.21 → 1.2.0
Вышла к ревизии 0.41.2 (2026-10-27). Это клиент, через который ASR-служба слушает комнаты; приём звука и переподключение с новой версией не проверялись, а выпуск 0.41.2 меняет только вид главной страницы. Версию лучше поднимать вместе с LiveKit Server (DEP-9). План: поднять на стенде, пройти живые сценарии звука, записи и стенограммы, обновить constraints, `asr-service/requirements.txt` и `deployment/compat.env`; повторная проверка — до 2026-11-10.

### DEP-11 — React Router 7.18.4 → 7.18.5
Вышла за день до ревизии 0.42.0 (2026-10-27), патч без новых возможностей. Выпуск 0.42.0 меняет защитный слой запросов и разделы администрирования безопасности, маршрутизацию клиента не трогает; обновление отложено до следующей ревизии, когда можно прочитать список изменений и прогнать vitest и живые сценарии интерфейса. Повторная проверка — 2026-11-10.
