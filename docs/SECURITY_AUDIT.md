# Аудит безопасности, производительности и надёжности — этапы 1 (0.8.5) и 2 (0.9.0)

Документ описывает **что реально проверено** (и как), что найдено, что исправлено, что сознательно оставлено. Чего не проверяли — сказано отдельно: «проверено» здесь означает «просмотрено и/или запущено», а не «безопасно».

Принцип: надёжность → скорость → безопасность. Любое исправление не должно ухудшать вход в комнату, звонок, стенограмму, запись.

## Метод и ограничения
* **Специальных security-skills в рабочем окружении не оказалось** (установлены только плагины для разработки Claude Code), поэтому использован собственный чек-лист по OWASP Top 10 / API Security Top 10 и архитектуре проекта.
* Проверялось: чтение кода, конфигурации compose/nginx/скриптов, запуск тестов, `npm audit`, `pip-audit`, скан репозитория на частные данные. Стенд LiveKit/ASR/LDAP здесь не поднимался: замеров реального входа в комнату, задержки стенограммы и нагрузочных сценариев **нет** (см. «Не проверено»).

## Сетевая поверхность (по `deployment/compose.yml`)
| Сервис | Публикуется на хост | Зачем | Вывод |
|---|---|---|---|
| web (nginx) | `${WEB_BIND_ADDR}:${WEB_PORT}` (по умолчанию 127.0.0.1) | единственная HTTP-точка; снаружи — через TLS-прокси хоста | верно: по умолчанию только loopback |
| backend, postgres, redis, asr, llm-local | **нет** (только внутренняя сеть compose) | доступ только из соседних контейнеров | верно; Redis с паролем, LLM — в отдельной сети `llm_internal` |
| livekit HTTP/сигналинг | `127.0.0.1:${LIVEKIT_HTTP_PORT}` | проксируется nginx (`/livekit/`) | верно |
| livekit RTC TCP/UDP | `${LIVEKIT_BIND_ADDR}` (по умолчанию 0.0.0.0) | медиа должно приходить напрямую; иначе звонок невозможен | нужно, оставлено; ограничивается только сетевым экраном хоста |
| livekit-sip | `${SIP_BIND_ADDR}` (0.0.0.0, только при включённой телефонии) | SIP/RTP | нужно только при `SIP_ENABLED`; ограничение — `SIP_ALLOWED_CIDRS` (рекомендуется задавать) |

Контейнерам backend/web/redis добавлено `no-new-privileges` (процесс не получает дополнительных прав). `cap_drop`/`read_only` **не** включались: без проверки на реальном Docker они могут сломать запуск сервисов (приоритет надёжности).

## Находки и решения
| № | Область | Находка | Серьёзность | Решение |
|---|---|---|---|---|
| S1 | Конфигурация | `docs_enabled` в коде по умолчанию `True` (в compose — `false`): схема внутреннего API открыта, если приложение запущено не через compose | низкая | исправлено: по умолчанию `False` |
| S2 | Файлы | Проверка относительного пути отсекала `..` и абсолютные пути, но не обратную косую и `:`; на **SMB-сервере** (Windows) `\` — разделитель, `..\..\x` вышел бы из каталога хранилища. Сейчас все компоненты проходят `safe_component`, то есть эксплуатации нет, но защита держалась на одном слое | низкая (глубина защиты) | исправлено: `_check_rel` отклоняет `\`, `:` и NUL; тесты (в том числе символьные ссылки на Linux) |
| S3 | Updater (root) | Каталог обмена открыт на запись всем (1777: контейнер пишет от uid 10001). На общем сервере **любой локальный пользователь** мог положить `request.txt` и запустить разрешённое действие (проверка / обновление / исправление из белого списка). Произвольные команды выполнить нельзя (проверено: белый список действий и исправлений, значения проверяются regexp, окружение дочерних команд стерильно, запрос одноразовый и живёт ≤10 минут, временные файлы со случайными именами) | средняя (только общий сервер) | исправлено: запрос принимается, если это не символьная ссылка и владелец — root, сам исполнитель или uid контейнера backend; тест на символьную ссылку |
| S4 | TLS-прокси хоста | В шаблоне `site.tls.conf.tpl` нет `Strict-Transport-Security` | низкая | **не применено по решению владельца**: сначала проверка цепочки HTTPS на реальном сервере; требования и поэтапное включение — [HTTPS_AND_HSTS.md](HTTPS_AND_HSTS.md) |
| S5 | nginx | Нет ограничения частоты на уровне nginx (есть в backend: вход, чат, карты) | низкая | оставлено: за общим NAT `limit_req` на `/api/v1/auth/login` блокировал бы честных пользователей; защита — блокировка в backend по логину и IP |
| S6 | Зависимости | `npm audit`: 0 уязвимостей (с dev-зависимостями тоже). `pip-audit` окружения разработчика: только сам `pip` (инструмент сборки, не часть образа). `requirements.txt` содержит диапазоны версий, а не точные закрепления; образ собирается при каждом обновлении, поэтому состав может меняться | низкая | оставлено: перевод на lock-файл с хэшами — отдельная задача (риск несовместимости), CVE-проверка образа при сборке |
| S7 | Репозиторий | Сканер `scripts/check_private_data.py` по текущему дереву — находок нет. В **ранних коммитах** остаются частные значения (см. HISTORY.md, 0.8.1) | средняя (раскрытие) | требует решения владельца (`git filter-repo` с force-push и перевыпуском тегов); без явного разрешения не выполнялось |

## Проверено без находок (по коду/конфигурации)
* Cookie сессии: `HttpOnly`, `SameSite=Lax`, `Secure` по настройке; CSRF — токен на изменяющих запросах + проверка Origin.
* Просмотр Markdown и HTML-выгрузки: HTML от модели не принимается (LLM → проверенный JSON → отрисовка нашим кодом); в выгрузках CSP; карта разговора и Draw.io — в `iframe sandbox` без доступа к cookie.
* CSP/заголовки в nginx заданы для SPA, `/drawio/`, `/mapview/`; изменений не вносилось (чтобы не сломать LiveKit WebSocket и Draw.io).
* Пути записей/вложений/аватарок: имена файлов формируются из UUID/`safe_component`, не из пользовательских имён; удаление записей проверяет принадлежность каталогу.
* Секреты: в БД шифруются мастер-ключом, во frontend не передаются; в журнал попадают через `scrub`.

## Этап 2 (0.9.0): публичный API и Bitrix24
Проверено **живой «атакой» на стенд** (`tests/live/probe_public_api.py`, 26 проверок, все прошли) и тестами (`backend/tests/test_public_api.py`, `test_profile_sources.py`). Соответствие OWASP API Security Top 10 (2023):

| Риск | Что сделано и как проверено |
|---|---|
| API1 BOLA | Каждый объект проверяется на принадлежность области комнат ключа; чужая и несуществующая встреча дают **одинаковый** ответ (код и текст) на всех вложенных адресах — проверено попарно на 6 чужих встречах × 7 адресов. Идентификаторы типизированы (`mtg_…`), чужой префикс и голый UUID — 404 |
| API2 Auth | Один и тот же 401 на неверный секрет, неизвестный ключ и мусор; детали (отозван, истёк, адрес) — только при верном секрете; сравнение за постоянное время; при неизвестном `key_id` выполняется такое же сравнение (замер: 8,7 мс против 9,7 мс — задержка не раскрывает существование ключа). Ключ только в заголовке; в адресе, `X-API-Key`, Basic, другой регистр — 401; огромный заголовок — 400 |
| API3 Лишние данные | Участники без e-mail и телефона; HTML-вид документа с `sandbox` |
| API4 Ресурсы | Лимиты по классам и интеграциям с заголовками; `limit` вне диапазона — 422, иначе ужимается до `max_page_size`; текстовая выгрузка стенограммы ≤ 20 000 реплик; запись журнала — пачками с ограниченной очередью |
| API5 BFLA | Права проверяются на каждом маршруте (тест «каждое объявленное право используется маршрутом»); без `meetings:end` — 403 с названием права; PUT/PATCH/DELETE не определены |
| API7 SSRF | В API этапа 1 исходящих запросов нет. Bitrix24: фото только с узла портала, без редиректов, ≤ 5 МБ, `image/*`, адреса loopback/link-local запрещены, webhook обязан принадлежать порталу |
| API8 Конфигурация | `Cache-Control: no-store`; CORS не включён (интеграции «сервер — сервер»), preflight чужого сайта не разрешается; API выключен по умолчанию; документация без скриптов и внешних ресурсов |
| API9 Инвентарь | Единственная версия `/api/public/v1`; OpenAPI публикуется и содержит только публичные методы (тест: внутренний API в описание не попадает) |
| API10 Небезопасное потребление | Ответы Bitrix24 ограничены по размеру (2 МБ JSON), ошибки не содержат секрет webhook (тест), сопоставление неоднозначных записей отвергается |
| Инъекции | `room_id`, `state`, `after`, `started_after` с SQL-строками — 4xx в формате API, таблицы целы |
| Изоляция | Ключ не открывает внутренний API (401); cookie-сессия не открывает публичный (тест) |

**Найдено и исправлено при проверке:** (1) `datetime` в `details` аудита ломал обработку запроса (JSON-колонка) — значения приводятся к строкам; (2) кэш настроек API мог до 5 с держать старое значение — сбрасывается при сохранении; (3) при неизвестном `key_id` время ответа отличалось от случая «верный ключ, неверный секрет» — выровнено.

**Производительность публичного API** (`tests/live/bench_api.py`, стенд: SQLite + fakeredis, одна машина, 130 участников в встрече; цифры относительные, не продуктивные): `/me` p50 9,5 мс; список встреч (50) p50 41 мс / p95 48 мс; стенограмма SRT 30 мс; неверный ключ 8,7 мс. Замер «новое соединение на каждый запрос» даёт ~800 мс — это стоимость соединения на машине замеров (системный прокси), не сервера.

## Не проверено / отложено (честно)
* **Публичный API, этап 2** (webhooks, задачи генерации, скачивание записей) не написан — его аудит впереди. Этап 1 не проверялся под нагрузкой и за реальным обратным прокси со списком разрешённых адресов (определение адреса клиента общее с входом, но на сервере владельца не проверялось).
* Bitrix24 проверен на подставном портале (`httpx.MockTransport` и локальный HTTP-сервер); реальный портал владельца — нет.
* **Производительность:** реальные p50/p95 для «вход в комнату» (page → token → WebSocket → RTC), задержка стенограммы, нагрузка при 5/20+ участниках, влияние записи/LLM на звонок, планы запросов БД — **не измерялись** (нужен стенд с LiveKit/ASR). В приложении уже есть замеры входа в комнату у клиентов (Администрирование → Обзор → Технические показатели) — по ним и надо снимать цифры на рабочем сервере. Из проверенного: начальный JS основной страницы 447 КБ (137 КБ gzip); LiveKit (519 КБ), админка (334 КБ), Draw.io, карты и просмотр изображений загружаются отдельно, только когда нужны; хэшированные ресурсы кэшируются на 30 дней (`immutable`), Draw.io — на сутки, шрифты — на неделю.
* **Надёжность (отказы компонентов, обрыв сети, перезапуски):** автоматических сценариев нет; по архитектуре LLM, карты, SMTP и Draw.io — фоновые и со своим учётом ошибок, но это не подтверждено нагрузочным прогоном.
* Приоритет CPU «звонок + ASR выше LLM» не проверялся и не менялся.

**Найдено и исправлено проверкой:** (1) сбой именно соединения на первом проверенном адресе (IPv6) не давал попробовать следующий — найдено **живым стендом** (`localhost` → `::1`), теперь пробуются до трёх проверенных адресов, ответ получателя повторно не отправляется; (2) ключ идемпотентности «сгорал» после ошибки запроса (атрибут объекта устаревал после отката) — исправлено, тест.

**Нагрузка и размеры (тестами):** обход 1200 встреч страницами по 500 за доли секунды; стенограмма из 20 001 реплики — курсором полностью, текстовая выгрузка ограничена 20 000 (`413`); 40 параллельных запросов одной интеграции — ровно по лимиту (10 прошли, 30 — `429`), другая интеграция не затронута.

**Остаётся / не проверено:** нагрузка на настоящем PostgreSQL и за обратным прокси; реальный получатель за корпоративным УЦ (флаг `webhook_use_corporate_ca` проверен только логикой); скачивание очень больших записей (файл читается целиком в память — как и в интерфейсе; для гигабайтных записей нужна потоковая отдача, не сделана).
