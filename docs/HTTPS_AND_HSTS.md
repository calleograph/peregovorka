# HTTPS и HSTS: проверка цепочки и безопасное включение

**Статус: HSTS в приложении и в шаблонах НЕ включён — намеренно.** HSTS запоминается браузером на месяцы: если после включения сертификат окажется недействительным (истёк, не тот корневой УЦ, смена домена), пользователи **не смогут обойти предупреждение**, и вход, комната и страница с инструкцией станут недоступны до исправления. Поэтому включать его нужно только после того, как цепочка HTTPS проверена на вашем сервере.

Адреса в примерах условные (`meet.example.com`).

## 1. Что нужно проверить на сервере до включения

| Проверка | Как | Должно быть |
|---|---|---|
| Кто завершает TLS | схема вашего сервера: обратный прокси хоста (шаблон `deployment/nginx/site.tls.conf.tpl`) или внешний балансировщик | один узел, который вы контролируете; HSTS добавляется **только на нём** (не в контейнере `web`, иначе при доступе по HTTP во внутренней сети он бесполезен или вреден) |
| Сертификат действителен и доверен всеми клиентами | `openssl s_client -connect meet.example.com:443 -servername meet.example.com </dev/null \| openssl x509 -noout -dates -issuer` | срок не истекает в ближайшие месяцы; корневой УЦ установлен на **всех** рабочих местах (для внутреннего УЦ — групповой политикой) |
| Автопродление | ваш процесс (ACME, внутренний УЦ) | проверено, что продление отрабатывает и перезагружает nginx; есть оповещение о сроке |
| Нет доступа по HTTP, кроме редиректа | `curl -sI http://meet.example.com/` | `301` на `https://…`, без отдачи содержимого |
| Прокси передаёт схему | в шаблоне `X-Forwarded-Proto https` | cookie сессии с `Secure` (в приложении `COOKIE_SECURE=true`), адрес клиента берётся верно (`TRUSTED_PROXY_CIDRS`, `TRUSTED_PROXY_HOPS`) |
| WebSocket и LiveKit по защищённому каналу | в браузере: комната подключается, в консоли нет mixed content; `wss://…/livekit/` | всё через HTTPS/WSS на том же имени |
| Все поддомены под контролем | список имён вашей зоны | только если планируете `includeSubDomains` (см. ниже) |
| Нет «http-only» сервисов на том же имени | другие сайты на этом домене | иначе после HSTS они перестанут открываться |
| Клиентские устройства | пользователи с мобильных сетей, VPN, терминальные серверы | сертификат доверен и там (иначе после HSTS обхода не будет) |

Проверить текущее состояние заголовков: `curl -sI https://meet.example.com/ | grep -i -E "strict-transport|x-content-type|content-security"` (HSTS пока отсутствует — это ожидаемо).

## 2. Как включать (поэтапно, с откатом)

Заголовок добавляется на TLS-прокси хоста в блок `server` с `ssl` (в шаблоне это `site.tls.conf.tpl`):

```nginx
add_header Strict-Transport-Security "max-age=300" always;
```

1. **`max-age=300`** (5 минут) — проверка на всех рабочих местах в течение рабочего дня. Если что-то не так, браузеры «забудут» политику за 5 минут.
2. **`max-age=86400`** (сутки) — неделя наблюдения: нет жалоб на сертификат, продление сертификата прошло (если оно попадало на этот срок).
3. **`max-age=604800`** (неделя) → **`max-age=15552000`** (6 месяцев) — рабочее значение; больше не нужно.
4. **`includeSubDomains`** — только если каждый поддомен зоны отдаёт HTTPS с действительным сертификатом. Для одного сервера переговорки он обычно **не нужен**.
5. **`preload`** — **не использовать**: попадание в список браузеров практически необратимо и рассчитано на публичные сервисы.

Важно: директива `add_header` в `location` отменяет унаследованные из `server` — повторите её в каждом `location`, где вы задаёте свои заголовки (так устроены и остальные заголовки безопасности в шаблоне).

**Откат:** замените значение на `max-age=0` и оставьте так на срок прежнего `max-age`; сертификат при этом должен оставаться рабочим, пока политика не истечёт у клиентов.

## 3. Требования к безопасному включению (чек-лист решения)

- [ ] Сертификат выдан УЦ, которому доверяют все клиентские устройства, срок ≥ 3 месяцев, автопродление проверено.
- [ ] Редирект HTTP → HTTPS работает; обращения по IP-адресу и «чужому» имени не обслуживаются как основной сайт.
- [ ] Приложение работает по HTTPS без mixed content: комната, показ экрана, доска, чат, вложения, публичный API.
- [ ] `COOKIE_SECURE=true`, `X-Forwarded-Proto https` на прокси, доверенные прокси настроены.
- [ ] Есть оповещение об истечении сертификата не позже, чем за 21 день.
- [ ] Выбран ответственный за первое включение и проверку на каждом этапе (п. 2) и план отката.
- [ ] Для внутреннего УЦ: корневой сертификат установлен в хранилищах ОС и браузеров (Firefox — отдельное хранилище или политика предприятия).

## 4. Что проверить уже после включения

- `curl -sI https://meet.example.com/ | grep -i strict-transport` — значение и `always` (заголовок есть и в ответах с ошибками).
- Открыть сайт в окне без сохранённых данных: вход, комната, API (`/api/public/v1/docs`).
- Через сутки — повторить с рабочего места под VPN и с мобильной сети.
- Календарь: дата истечения сертификата минус 21 день → проверка продления до повышения `max-age`.
