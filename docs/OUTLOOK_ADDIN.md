# Microsoft Outlook: конференция Peregovorka в приглашении

Организатор создаёт встречу в календаре Outlook, нажимает **«Добавить конференцию»** (группа «Peregovorka» на ленте окна встречи), и в приглашение автоматически попадают ссылка и краткая инструкция. Затем — обычная кнопка **«Отправить»**: все приглашённые получают стандартное приглашение Outlook со ссылкой Peregovorka.

Интеграция выключена по умолчанию: **«Администрирование → Интеграции → Microsoft Outlook»**. Там же — состояние и проверки, пакет установки, настройки, серверная сверка календаря, история созданных конференций и журнал ошибок надстройки. Все настройки хранятся в базе и входят в резервную копию конфигурации (секреты — зашифрованно).

## Как это устроено

Обычная надстройка Outlook на Office.js (манифест только для надстроек, `AppointmentOrganizerCommandSurface`, Mailbox 1.3, разрешение `ReadWriteItem` — минимально нужное, чтобы записать ссылку в текст, «Место» и пользовательское свойство встречи). Надстройка — это только веб-страницы и API **вашего** сервера (`/outlook/…`, `/api/v1/outlook/…`): администратор один раз устанавливает манифест, логика обновляется вместе с сервером.

**Кнопка «Добавить конференцию» (с 0.30.0) открывает боковую панель Peregovorka** (`ShowTaskpane` → `/outlook/taskpane.html`). В ней — тема и время встречи, состояние входа, одна основная кнопка и результат. Весь сценарий проходит в панели:

1. Панель читает встречу (тема, начало, окончание, серия) и проверяет время теми же правилами, что сервер (прошедшая, неверный интервал, нет времени).
2. Вход: если действующего входа нет — форма **«Логин / Пароль / Войти»** прямо в панели (`POST /api/v1/outlook/login`: проверка пароля, правил допуска, ограничения попыток, CAPTCHA и аудит — как у обычного входа, но **без сеанса браузера** и без места в лимите сеансов). Отдельное окно (`/outlook/auth.html`, Office Dialog API) открывается только по кнопке «Войти через окно» или когда нужен дополнительный шаг: код 2FA, его настройка, смена пароля, проверка «не робот». После входа в окне панель продолжает сама.
3. Если вход действует и конференции ещё нет — она создаётся сразу при открытии панели (пользователь уже нажал «Добавить конференцию»), иначе — кнопка «Создать конференцию» / «Обновить конференцию».
4. Ключ события (`pg_key`, пользовательское свойство встречи) сохраняется **до** запроса к серверу: сбой сети между созданием комнаты и ответом не даёт дубля — повтор вернёт ту же комнату.
5. В текст встречи вставляется блок между маркерами `<!--pg-conf-->…<!--/pg-conf-->` (повтор заменяет блок; остальной текст не трогается), в «Место» — ссылка, если клиент позволяет.
6. Результат: «Конференция в приглашении», ссылка (скопировать, «Открыть конференцию»), отметки «в тексте» и «в поле «Место»». Если комната создана, а вставить ссылку не удалось, панель так и говорит, показывает ссылку и предлагает «Вставить ссылку ещё раз» — новая комната не создаётся.

У каждого шага свой предел ожидания (Office.js — 15 с, ответ Outlook — 10 с, открытие окна входа — 15 с, вход человека в окне — 5 мин, запрос к серверу — 20 с, журнал — 5 с): ни один шаг не ждёт бесконечно, любая ошибка заканчивается понятным сообщением и кнопкой повтора. Пользователь не видит HTTP-кодов, JSON и внутренних кодов — они есть только в свёрнутом блоке «Подробности для администратора».

**Вход и его сохранение.** Токен надстройки хранится в хранилище браузера надстройки (`localStorage` источника вашего сервера) на срок «Срок действия входа надстройки» (по умолчанию **7 суток**, настраивается от 1 часа до 30 суток). Закрытие панели, новая встреча и перезапуск Outlook вход не сбрасывают. Когда прошла половина срока, панель продлевает вход (`POST /api/v1/outlook/token/refresh`: права проверяются заново, прежний токен отзывается), но не дольше **30 дней** от ввода пароля. «Выйти» в панели отзывает токен на сервере сразу; отключение учётной записи в Peregovorka или выключение интеграции действуют на следующем запросе. Токен даёт доступ только к `/api/v1/outlook/*`; в Redis хранится лишь его SHA-256.

**Единый вход (SSO).** Не реализован: вход в Outlook не даёт токена Peregovorka, а универсального и официально поддерживаемого способа для локального Exchange нет (Nested App Authentication и `getAccessToken` требуют Microsoft Entra ID). Пароль Outlook надстройка не получает и не извлекает. Повторно вводить пароль не нужно, пока действует вход надстройки.

**Скрытые команды** (`commands.html` + `commands.js`, FunctionFile манифеста) остаются: `insertPeregovorkaMeeting` — кнопка манифестов до 0.30.0 (работает и после обновления сервера без переустановки манифеста; сообщает администратору о необходимости обновить манифест, событие «кнопка старого манифеста»), `onAppointmentSendHandler` — передача изменений при отправке (Smart Alerts, только Microsoft 365). Обе завершаются `event.completed()` ровно один раз — по успеху, по ошибке или по общему пределу времени, и не ждут отправки журнала; `allowEvent` передаётся только обработчику отправки.

### Почему зависала прежняя кнопка (до 0.30.0)

Прежняя кнопка была скрытой командой `ExecuteFunction`. Сам механизм поддерживается Microsoft и ошибкой не является; по коду прежней версии найдены три дефекта, каждый из которых даёт наблюдавшуюся картину («выполняется запрос…», окна входа нет, ссылки нет):

1. **Страница функций не вызывала `Office.onReady()`** (и не задавала `Office.initialize`). По документации Microsoft страница функций обязана сообщить Office о готовности; без этого клиент может не вызвать функцию вовсе и показывать «выполняется» до своего тайм-аута — окно входа при этом не появляется.
2. **Функция регистрировалась только через `Office.actions.associate`**, без глобального имени. Клиенты со старыми наборами Mailbox API (в том числе локальный Exchange 2016/2019, Mailbox ≤ 1.5) ищут функцию команды по имени в `window`.
3. **`event.completed()` в ветке ошибки ждал отправки события в журнал** (запрос без тайм-аута), а у окна входа и запросов к серверу не было предела ожидания. Любое зависание сети или окна оставляло команду незавершённой.

Какой из пунктов срабатывал у конкретного клиента, в настоящем Outlook не установлено (нет доступа к стенду): исправлены все три, а основная кнопка переведена на боковую панель, где ход операции виден пользователю. Ошибки загрузки MicrosoftAjax и ресурсов Exchange в Outlook в браузере относятся к самому Exchange и устанавливать исправления на сервер Exchange для работы Peregovorka не требуется.

### Значок

Кнопка на ленте — яркий цветной значок (оранжевая плитка с камерой и «+»), размеры 16, 20, 24, 32, 40, 48, 64, 80 и 128 px для разных масштабов Windows и клиентов.

## Что нужно

* Публичный адрес Peregovorka **по HTTPS** с сертификатом, которому доверяют рабочие станции (Outlook не загружает надстройки по HTTP; самоподписанный сертификат не подойдёт без установки доверия).
* Клиентам Outlook доступен адрес сервера. Библиотека Microsoft Office.js лежит на самом сервере (раздел «Библиотеки Office.js» ниже), доступ компьютеров к CDN Microsoft нужен только на запасном пути, если локальной копии в образе нет.
* Права: создавать конференции может любой сотрудник либо члены выбранных групп (разделитель — `;` или перенос строки: DN групп содержат запятые). Вход в панели — пароль с теми же правилами допуска и ограничением попыток, что в браузере; **TOTP** и **CAPTCHA** — в окне входа на странице сервера; токен надстройки действует только для `/api/v1/outlook/*`.

## Пакет надстройки для вашего сервера

Кнопка **«Скачать надстройку для этого сервера»** формирует ZIP: `Peregovorka-Outlook.xml` (манифест с адресами этой установки), `README.txt` (установка, обновление, удаление), `Install-OutlookAddin.ps1` (Exchange Management Shell: `New-App -OrganizationApp`, ключи `-WhatIf`, `-Replace`, `-ProvidedTo`, `-UserList`), `Test-OutlookAddin.ps1` (манифест, доступность адресов, сертификат HTTPS, состояние в Exchange; ничего не меняет). Идентификатор надстройки (`Id`) вычисляется из адреса сервера и **не меняется** при повторном скачивании и обновлении версии — манифест заменяет предыдущий, а не добавляет второй. В пакете нет паролей, ключей API и секретов сверки; скачивание записывается в аудит (`outlook.package`).

### Установка
* **Локальный Exchange 2019 (основной сценарий):** распаковать, в Exchange Management Shell `.\Test-OutlookAddin.ps1`, затем `.\Install-OutlookAddin.ps1 -WhatIf` и `.\Install-OutlookAddin.ps1`; либо Exchange admin center → Organization → Add-ins → Add from file. Клиенты получают надстройку до нескольких часов.
* **Microsoft 365 / Exchange Online:** центр администрирования → Settings → Integrated apps → Upload custom apps (Office Add-in) → манифест → пользователи или группы (до 24 часов).
* **Проверка у одного пользователя:** Outlook в браузере → Get Add-ins → My add-ins → Custom add-ins → Add from file. Кнопка появится на ленте, но переключатель Teams/Skype не заменится (это только для установленных администратором).

### Обновление и удаление
Логика надстройки обновляется вместе с сервером. **При обновлении до 0.30.0 манифест нужно переустановить один раз** (кнопка теперь открывает боковую панель, у неё новые значки): до этого работает прежняя кнопка — исправленная, а журнал надстройки показывает «кнопка старого манифеста». Также переустановить манифест нужно при смене адреса сервера или настройки «Передавать изменения при отправке»: скачать пакет заново, `.\Install-OutlookAddin.ps1 -Replace` (или заменить файл в центре администрирования). Удаление: `Get-App -OrganizationApp | ? DisplayName -eq 'Peregovorka' | Remove-App -OrganizationApp` либо Integrated apps → Remove. Созданные комнаты и ссылки в отправленных приглашениях продолжают работать.

## Матрица совместимости (по документации Microsoft)

Основа — набор требований **Mailbox API** (Office.js). **Локальный Exchange 2016/2019 поддерживает Mailbox API не выше 1.5**, Exchange Online и современные клиенты — 1.12 и выше. Матрица выдаётся сервером (`services/outlook_compat.py`), одна и та же в админке и на публичной странице `/outlook`.

**Базовые функции (Mailbox 1.3, работают везде, где работает надстройка):** создать конференцию из окна встречи; добавить ссылку в приглашение; открыть конференцию; войти (пароль, 2FA, CAPTCHA); получить сведения о связанной конференции.

**Дополнительные (зависят от версии Mailbox API):** передача времени и темы при отправке приглашения (Smart Alerts, `OnAppointmentSend`, **Mailbox 1.12**); автоматическая обработка переноса и отмены. На локальном Exchange вместо них работает **серверная сверка календаря EWS** (минимальные права: роль «Рецензент» к календарям организаторов либо ApplicationImpersonation только на нужные ящики); для Microsoft 365 — Graph (только чтение календарей).

| Среда | Mailbox API | Базовые функции | Подписка на отправку | Серверная сверка |
| --- | --- | --- | --- | --- |
| Exchange 2016 + классический Outlook | до 1.5 | да | нет | EWS |
| Exchange 2019 + классический Outlook | до 1.5 | да | **нет** | EWS |
| Exchange Subscription Edition + классический Outlook | уточняйте у Microsoft | да | не включается до подтверждения | EWS |
| Exchange 2016/2019/SE + Outlook в браузере | до 1.5 | да | нет | EWS |
| Exchange (локальный) + новый Outlook | по клиенту | зависит от клиента и политики | нет | EWS |
| Microsoft 365 + Windows (классический и новый), Mac, браузер | 1.12 и выше | да | да | Graph, EWS |

Настройка «Передавать изменения при отправке» **применяется только при типе почтовой системы «Microsoft 365»**: на локальном Exchange манифест остаётся на Mailbox 1.3 (иначе кнопка не появилась бы вовсе), а администратору показывается пояснение и рекомендация включить сверку EWS. Ранее в документации и интерфейсе встречалось утверждение, что подписка на отправку работает на Exchange 2019 CU12+ — оно неверно для Mailbox API локального Exchange и исправлено.

**Всё в таблице взято из документации; в настоящем Outlook, Exchange и Microsoft 365 не проверялось.**

## Две ссылки в приглашении: для сотрудников и для внешних гостей

Если в «Администрирование → Microsoft Outlook» включено **«Пускать гостей без учётной записи»** (`guest_links`), надстройка вставляет в приглашение два блока:

* «Для сотрудников организации» — обычная ссылка `/m/…` со входом учётной записью организации;
* «Для внешних участников» — отдельная гостевая ссылка `/guest/…` с поясняющей строкой «Если у участника нет корпоративной учётной записи, передайте ему гостевую ссылку».

Принципы:

* **Один секрет на событие.** Гостевая ссылка выпускается вместе со встречей и хранится в комнате; повторное сохранение события, «Обновить конференцию» и перенос её **не меняют** и второй не создают (`outlook.ensure` идемпотентен по ключу события).
* **Отдельный механизм не вводился:** это обычная гостевая ссылка комнаты (`/guest/<токен>`): гость вводит имя, проверяет оборудование и входит только в идущую встречу; права минимальные — чат и звук, без показа экрана, без истории и материалов организации и без других встреч. Окно входа, закрытие, отмена и «слишком рано» работают так же, как у гостевых ссылок остальных комнат.
* **Срок жизни — жизнь встречи:** ссылка перестаёт работать, когда встречу отменили (в Outlook, через серверную сверку или кнопкой) или комната закрылась.
* **Отзыв и перевыпуск** — в боковой панели Outlook, блок «Для внешних участников»: «Выпустить гостевую ссылку» (если её нет), «Выпустить новую» (прежняя сразу перестаёт работать, гости встречи отключаются) и «Отозвать»; для двух последних нужно второе нажатие. После действия блок в тексте приглашения обновляется. В уже **отправленных** письмах остаётся прежняя ссылка: после перевыпуска отправьте обновление встречи.
* **Запрет администратора не обходится:** если «Пускать гостей» выключено, новые гостевые ссылки не выпускаются, блок в приглашении и в панели не показывается, а **уже выпущенные ссылки встреч Outlook перестают работать** (страница гостя отвечает как на недействительную ссылку).
* **Секрет не попадает в журналы:** в журнал событий, аудит и отчёты диагностики пишется только факт действия (`outlook.guest_link.issue|rotate|revoke`), токен — никогда.
* Серия встреч использует одну гостевую ссылку на всю серию; ссылка живёт, пока серию не закроют или не отменят.

API надстройки: `POST /api/v1/outlook/meetings/{id}/guest-link` с телом `{"action": "issue" | "rotate" | "revoke"}` (токен надстройки, только организатор встречи); ответ — та же встреча с полями `guest_url`, `guests_allowed` и обновлённым текстом приглашения.

Проверено: pytest `backend/tests/test_outlook_guest_links.py`, живой сценарий `tests/live/scenario_outlook_guest.py` (панель в настоящем браузере с подставным Office.js). **Не проверено:** настоящий Outlook и Exchange.

## Время, вход и комнаты

1. Первое нажатие открывает панель с формой входа (2FA и CAPTCHA — в окне `/outlook/auth.html`); вход хранится в браузерном хранилище надстройки на срок «Срок действия входа» (по умолчанию 7 суток), продлевается до 30 дней от ввода пароля и отзывается кнопкой «Выйти».
2. Надстройка отправляет тему, начало, окончание, признак серии и **шаблон повторения**, **организатора, часовой пояс, приглашённых (обязательных и необязательных: адрес и имя) и идентификаторы события** (если встреча сохранена). Ключом события служит случайная строка в пользовательских свойствах встречи: повторное нажатие, перенос, черновик и удалённая из текста ссылка дают **ту же** комнату, дубля нет (одна комната на событие у организатора — уникальный индекс).
3. Создаётся временная **равноправная** запланированная комната `ol-<код>`: участники равны в звуке, камере и показе экрана; организатор управляет комнатой и может её закрыть; администратор сервера сохраняет свои права. Войти может любой вошедший сотрудник, а при включённой настройке — гость по той же ссылке (гость получает права гостя, без показа экрана).
4. **Вход открывается за N минут до начала** (настройка «Открывать вход за», по умолчанию 10). До этого `/m/<код>` показывает название, дату и время в часовом поясе читателя, обратный отсчёт и статус; сервер не пускает в комнату раньше (HTTP 425). Серия событий — постоянная ссылка без календарных ограничений.
5. Комната конференции закрывается **по расписанию** — через «Держать открытой после окончания» после планового окончания — или при отмене. Окончание отдельного сеанса (все вышли) её не закрывает: до планового окончания в неё можно вернуться, а у серии каждая следующая встреча проходит в той же комнате и попадает в «Историю» отдельной встречей со своими материалами. Материалы хранятся по настройкам хранения. Завершённые комнаты, в которых встреч не было, удаляются через «Хранить завершённые комнаты».

| Создана встреча, нажата кнопка | надстройка | создаётся комната |
| Повторное нажатие | надстройка (тот же ключ) | возвращается та же комната, время и тема обновляются |
| Изменены дата, время, тема и нажато «Отправить обновление» | надстройка при отправке (`OnAppointmentSend`, включается настройкой, Mailbox 1.12) | время, тема и окно входа обновляются, **ссылка прежняя** |
| Изменено на другом устройстве/клиенте, встреча удалена, отменена | серверная сверка календаря (Graph или EWS) | расписание обновляется; удалённая и отменённая — комната «отменена» |
| Изменён список приглашённых | надстройка при нажатии кнопки и отправке; серверная сверка (Graph, EWS) | обновляется список для «Предстоящих встреч» (кто видит встречу на главной). Доступ к входу по-прежнему определяет политика Peregovorka (сотрудники по учётной записи, гости — настройкой), а не список приглашённых |
| Серия | признак серии и шаблон повторения (надстройка; сверка — `recurrence` в Graph, `Recurrence` в EWS) | постоянная ссылка без календарных ограничений, все занятия серии — одна комната; на главной — ближайшее занятие по шаблону с учётом перенесённых и отменённых занятий (сверка читает их у мастер-события: Graph `exceptionOccurrences`/`cancelledOccurrences`, EWS `ModifiedOccurrences`/`DeletedOccurrences`); удаление или отмена **всей** серии отменяет комнату, отмена или перенос **одного** занятия — нет. Изменение одного занятия в Outlook (надстройка получает `seriesId`) серию не переносит и не перепривязывает; комната серии, которую прежняя надстройка привязала к одному занятию, при сверке переводится на мастер-событие |

**Передача при отправке** никогда не блокирует отправку приглашения (обработчик всегда разрешает отправку), не открывает окон (в обработчиках событий окна входа запрещены): если действующего токена нет, ничего не делает — токен появится при следующем нажатии кнопки.

### Серверная сверка календаря (необязательна)

Раз в «Как часто сверять» (по умолчанию 10 минут) сервер читает **одно событие по идентификатору** (тема, начало, окончание, признак отмены, приглашённые; тело письма не запрашивается) и приводит комнату в соответствие. Правила безопасности: **ошибка связи или нехватка прав комнату не отменяет** — записывается состояние `error` с причиной (видно в истории конференций и журнале), отмена — только по явному ответу «события нет» или признаку отмены. Если встреча не сохранена в Outlook и у события нет идентификатора, оно не отслеживается (в истории помечено «не отслеживается»); идентификаторы приходят при отправке приглашения или повторном нажатии кнопки в сохранённой встрече.

* **Microsoft 365 — Graph.** Приложение в Entra ID с правом **приложения** `Calendars.ReadBasic.All` (минимально необходимое: чтение сведений о событии без тела, в том числе приглашённых; нужно согласие администратора; новых прав для списка приглашённых не нужно). Настройки: каталог (tenant), приложение, секрет (хранится зашифрованно).
* **Локальный Exchange — EWS.** Учётная запись с ролью `ApplicationImpersonation` (`New-ManagementRoleAssignment -Name PeregovorkaSync -Role ApplicationImpersonation -User svc-peregovorka`) либо с доступом «Рецензент» к календарям организаторов. Способы входа (Basic, NTLM, Negotiate/Kerberos) — в разделе «Серверная сверка через EWS» ниже. Права минимальные: чтение элемента по идентификатору (приглашённые — поля `RequiredAttendees` и `OptionalAttendees` того же элемента).
* Кнопка «Проверить доступ» проверяет вход и чтение календаря указанного ящика; «Сверить сейчас» запускает проход вне очереди.

Восстановление после недоступности Exchange: сверка по расписанию продолжится сама; состояние `error` заменится на `ok` при первой успешной сверке. Пока календарь недоступен, на главной показывается **последнее подтверждённое** время и состав приглашённых с пометкой «Сверено с календарём в ЧЧ:ММ»; список приглашённых при ошибке не меняется, а адреса, которые календарь вернул не в SMTP-виде, прежних приглашённых не удаляют.

## «Предстоящие встречи» на главной странице

Конференции из Outlook и временные комнаты показываются отдельным блоком **над** каталогом постоянных переговорок (в каталоге их больше нет): название из события, дата и время в часовом поясе пользователя, организатор, состояние («Запланирована», «Скоро начнётся» — за 15 минут или после открытия входа, «Идёт» — только когда кто-то действительно вошёл, «Завершена», «Отменена»), обратный отсчёт и приглашённые (первые имена и «+N», полный список — по нажатию или наведению). Ближайшие — первыми. У серии показывается **ближайшее занятие** по шаблону повторения (ежедневно, по дням недели, по числу или «последний четверг» месяца, ежегодно; окончание по дате или числу занятий). Время занятий считается в **часовом поясе самой серии** из календаря (Office.js `recurrenceTimeZone`, Graph `recurrenceTimeZone` или `originalStartTimeZone`, EWS `StartTimeZone`; имена поясов Windows переводятся в IANA по таблице CLDR), поэтому переходы на летнее и зимнее время учитываются по правилам пояса серии; показывается время — в поясе пользователя. Пояс браузера организатора — только запасной вариант, если календарь пояса не сообщил (например, собственный пояс Outlook `tzone://Microsoft/Custom`). **Перенесённое занятие** показывается в новое время, **отменённое** — пропускается (следующее занятие идёт по шаблону; в счёт «N занятий» отменённое входит, как в Outlook). Исключения серии берутся только из серверной сверки: Outlook не сообщает надстройке исходное время перенесённого занятия и не вызывает её при отмене занятия, поэтому без сверки (Graph или EWS) серия показывается по шаблону. Каждая сверка заменяет исключения целиком — повторная сверка дублей не создаёт; если календарь не отдал исключения (ошибка или непонятный ответ), остаются прежние, а причина видна в состоянии сверки. Прошедшие встречи серии и их материалы остаются в «Истории» при любых изменениях занятий. Серия без известного шаблона (надстройка старой версии, сверка не настроена) показывается без даты занятия, после остальных встреч.

* **Кто видит встречу:** организатор, приглашённые (сотрудник найден по адресу почты — сразу или при первом входе), руководители комнаты, те, кому доступ к комнате выдан отдельно, и администратор — у него по умолчанию только свои встречи, остальные — по переключателю «Все встречи организации». Видимость в списке **доступа не даёт**: вход решают правила комнаты.
* **Список приглашённых** видят организатор, руководители, администратор и сами приглашённые; **адреса почты** — только организатор, руководители и администратор. Остальным — только число. Проверки — на сервере (`GET /api/v1/rooms/upcoming`, `GET /api/v1/rooms/{id}/invitees`; чужая встреча — 404, без права на список — 403).
* **Отсчёт** считает браузер по времени сервера; сверка со списком — раз в 30 секунд и при возврате на вкладку, без частых запросов. Отменённая встреча видна со статусом «Отменена», пока не прошло её время; завершённая уходит из блока после закрытия комнаты и остаётся в «Истории» по её правилам.

## Безопасность

* Токены надстройки — случайные, в Redis хранится только их SHA-256; действуют лишь для `/api/v1/outlook/*`, ограничены по частоте (30 запросов/мин на пользователя). Пароль из панели уходит только на `POST /api/v1/outlook/login` вашего сервера (по HTTPS), нигде не сохраняется; TOTP и CAPTCHA проверяются в окне входа на странице самого сервера. Отключённая учётная запись теряет доступ сразу.
* **Хранение токена.** `localStorage` источника вашего сервера внутри надстройки (другие сайты к нему доступа не имеют; `OfficeRuntime.storage` есть только у общей среды выполнения, которую локальный Exchange не поддерживает). Риск — доступ к профилю пользователя на рабочей станции; ограничен сроком токена, его узкой областью (только `/outlook/*`) и мгновенным отзывом кнопкой «Выйти».
* **CSP страниц надстройки** (только `location /outlook/` в `frontend/nginx.conf`, общая политика продукта не ослаблена): `script-src 'self' https://officeapis.public.onecdn.static.microsoft https://appsforoffice.microsoft.com https://*.cdn.office.net` (свои файлы, включая Office.js с `/outlook/assets/`; адреса Microsoft — запасной путь и режимы «CDN»; `unsafe-eval` не разрешён), `connect-src` — те же плюс свой сервер, `frame-ancestors *` (панель встраивается Outlook в браузере и классическим Outlook), `style-src 'self'`, `img-src 'self' data:`, `form-action 'none'`, `object-src 'none'`, `base-uri 'none'`. Без `unsafe-inline` и `unsafe-eval`. Если внешний обратный прокси добавляет свою CSP или `X-Frame-Options`, для `/outlook/` они не должны запрещать встраивание и загрузку Office.js — проверка «Проверки» в разделе администрирования это показывает; нарушения CSP панель отправляет в журнал (`csp_blocked`).
* Запросы надстройки идут с источника вашего же сервера (манифест перечисляет только его домен), CSRF-токен не нужен — используется заголовок `Authorization` (куки не используются). Чужие комнаты недоступны: изменять и отменять комнату может её создатель или администратор; ключ события уникален в пределах организатора.
* Страница обратного отсчёта публична и отдаёт только название, время и состояние; неверный код и чужая комната отвечают одинаково (404), число запросов ограничено по IP.
* Секреты сверки хранятся зашифрованно, в ответы API, пакет и резервную копию без пароля не попадают.
* Журнал надстройки (раздел администрирования): итог каждой операции («конференция добавлена»), ошибки с этапом и кодом (`[meeting/in_past]`, `[api/network]`, `[invite/invite_failed]`…), тип и версия клиента Outlook и поддерживаемые наборы API, неудачные входы в панели. Без токенов, паролей и текста встречи; отправка журнала никогда не задерживает основную операцию.
* Все действия попадают в аудит: `outlook.token` (с пометкой, вход в панели или в окне), `outlook.create`, `outlook.sync`, `outlook.reschedule`, `outlook.cancel`, `outlook.package`, `outlook.sync_test`, `outlook.sync_run`.

## «Ошибка надстройки» в классическом Outlook (0.32.1): причина, исправление, проверка на месте

**Симптом.** После обновления до 0.30.0–0.32.0 классический Outlook для Windows с локальным Exchange 2019 при нажатии кнопки открывает боковую панель, но вместо неё — «Ошибка надстройки. Возникла какая-то ошибка, и нам не удалось запустить эту надстройку». В 0.29.0 в той же среде было «Peregovorka работает над вашим запросом» без конца.

**Что установлено (по коду, файлам и официальным требованиям; в настоящем Outlook не воспроизводилось — его нет на стенде):**
1. Классический Outlook 2016/2019 (сборки без подписки Microsoft 365) показывает надстройки во встроенном **Internet Explorer 11**. Официальный валидатор Microsoft для нашего манифеста перечисляет «Outlook 2016/2019 or later on Windows» — значит, страницы надстройки обязаны работать в IE 11.
2. В страницах надстройки не было `X-UA-Compatible: IE=edge`. Сайт во **внутренней сети** IE по умолчанию открывает в **режиме совместимости (документ IE 7)**, в котором Office.js не запускается. Это объясняет **оба** симптома одной средой: в 0.29.0 не запускалась страница функций (`ExecuteFunction` — «работает над запросом» без конца), в 0.30.0+ не запускается боковая панель (Outlook показывает «Ошибка надстройки» по истечении времени инициализации).
3. Даже в нормальном режиме IE 11 панель 0.30.0+ не смогла бы работать: в IE 11 нет `Promise` и `fetch`, на которых построены вход и создание конференции (панель показала бы «Устаревший Outlook»).
Рабочий прототип в той же среде (`ShowTaskpane`, отдельные файлы) по устройству совпадает со штатной панелью: тот же тип кнопки, та же точка расширения, те же API. Отличие, которое объясняет результат, — совместимость страницы с этим встроенным браузером (типовой шаблон надстроек Microsoft содержит `X-UA-Compatible`). Исходников прототипа у разработки нет, поэтому сравнение сделано по описанию.

**Исправлено:** `X-UA-Compatible: IE=edge` — в каждой странице надстройки (первым после `charset`) и заголовком сервера на `/outlook/`; свой полифил `Promise` (только если его нет); запросы через `XMLHttpRequest`, если нет `fetch` (вход в панели, создание, продление, журнал), `msCrypto` для ключа; запасные значения стилей для браузеров без CSS-переменных и `xlink:href` у значков. Синтаксис скриптов проверяется тестом как ES5.

**Самодиагностика (чтобы причина была видна, а не угадывалась).** Каждая страница надстройки первым делом загружает `boot.js` (работает даже в режиме совместимости IE 7) и отправляет серверу маячок: режим документа IE, есть ли `Promise`/`fetch`, загрузился ли Office.js. Если Office не запустил панель за 10 с, панель пишет причину на странице и сообщает её серверу. Всё видно в **«Администрирование → Интеграции → Microsoft Outlook → журнал»**: «панель открыта (среда клиента)», «панель запущена Office», «Office не запустил панель (причина в сообщении)». Сведения технические, без токенов, почты и содержимого встречи; без входа принимаются только известные события, с ограничением частоты.

**Приёмка на месте (классический Outlook + Exchange 2019; затем остальные поддерживаемые клиенты).** Обновление сервера — штатное, файлы надстройки обновятся сами (манифест в Exchange менять не нужно: его содержимое не изменилось).
1. Закройте Outlook полностью и откройте снова (Outlook перечитает страницы надстройки).
2. Создайте собрание на будущее время → «Добавить конференцию». Ожидается панель Peregovorka со статусом входа.
3. Если вместо панели «Ошибка надстройки» — откройте журнал Outlook в администрировании: строка «Office не запустил панель» назовёт причину (режим IE, Office.js не загрузилась и из какого источника — `local`, `cdn`, `local:cdn_fallback`, есть ли глобальный `Sys` (MicrosoftAjax), нет контекста Office); пришлите её текст.
4. Войдите в панели (логин/пароль) → «Создать конференцию». Ожидается ссылка в тексте приглашения и поле «Место»; в журнале — «панель запущена Office» и «конференция добавлена».
5. Сохраните/отправьте приглашение. Откройте его снова и нажмите кнопку ещё раз: та же конференция («Обновить конференцию»), без повторного входа.
6. Создайте второе собрание: вход не запрашивается (действующий вход сохраняется на срок из настроек, по умолчанию 7 суток).
Ограничение IE 11: окно дополнительного шага входа (2FA, CAPTCHA, смена пароля) открывает основное приложение, которое IE 11 не поддерживает; учётным записям без этих шагов оно не нужно — вход идёт в самой панели.

**Не проверено (нужна инфраструктура, которой нет):** установка и работа в настоящем Outlook (классический, новый, Web) и Exchange 2019/2016/Online — в том числе панель, окно входа, сохранение `localStorage` между перезапусками Outlook и обновление манифеста у клиентов; поэтому матрица совместимости выше остаётся документальной; запуск `Install-OutlookAddin.ps1` на Exchange; обработчик отправки в настоящем Outlook; ответы настоящих Graph и EWS (разбор сделан по документированным форматам); поведение при совпадении идентификаторов серии; настоящие ответы `exceptionOccurrences`/`cancelledOccurrences` (Graph) и `ModifiedOccurrences`/`DeletedOccurrences` (EWS) и передача `seriesId`/`recurrenceTimeZone` настоящим Outlook; доставка приглашений получателям (делает сам Outlook).

**Не реализовано:** единый вход (SSO, см. выше); Smart Alerts блокирующего режима (не нужен); мобильный Outlook (в манифесте не заявлен); NTLM/Kerberos для EWS; автоматическое добавление/удаление гостей по списку приглашённых; запись в календарь итогов встречи (Graph `Calendars.ReadWrite`) — в синхронизации только чтение.

## HTTPS: сам сервер или внешний обратный прокси

Источник истины — **публичный HTTPS-адрес**, который видят клиенты Outlook. Администрирование → Интеграции → Microsoft Outlook → «Состояние и проверки» подключается к этому адресу и проверяет реальный сертификат: цепочка по системному хранилищу доверия, **обязательное совпадение имени сервера**, срок действия (предупреждение за 14 дней), затем доступность `/api/v1/outlook/config` и файлов надстройки. Локальный сертификат в приложение загружать не нужно: при HTTPS на внешнем прокси проверка успешна, если успешен внешний адрес. Режим (`tls_mode`): `auto` — по заголовку `X-Forwarded-Proto` запроса администратора, `proxy`, `direct` (меняет только пояснение в проверке). Сертификат без доверия никогда не принимается; режим без проверки используется только для показа издателя и срока непрошедшего проверку сертификата.

Если сервер приложения не имеет маршрута к собственному публичному адресу, статус — «Внешняя проверка с сервера недоступна» (не ошибка): нажмите «Проверить с этого компьютера» (проверяет браузер) или запустите `Test-OutlookAddin.ps1` из пакета на рабочей станции.

Подпись самого манифеста или установочного пакета (если её требует политика организации) — отдельный вопрос и сертификатом HTTPS не решается; эти проверки не смешиваются.

## Публичный центр установки, сертификаты и схемы HTTPS

**Страница `https://<публичный-адрес>/outlook`** открывается без входа сразу после включения интеграции: манифест, инструкции для классического Outlook для Windows, нового Outlook и Outlook в браузере; проверка доступности «с этого компьютера» (браузер сам проверяет HTTPS, API, манифест — прямой ответ без перенаправлений, корректный тип, постоянный идентификатор, отсутствие внутренних и не-HTTPS адресов — и все ресурсы из манифеста); для администратора Exchange — полный пакет, отдельный манифест, сценарии PowerShell, инструкции для Exchange 2016/2019, Subscription Edition и Microsoft 365; сведения о публичном TLS и скачивание цепочки и сертификатов. Секретов, паролей, закрытых ключей и внутренних настроек на странице нет.

**Публичные ресурсы** (без входа): `/api/v1/outlook/manifest.xml`, `/api/v1/outlook/package`, `/api/v1/outlook/scripts/<имя>.ps1`, `/api/v1/outlook/center`, `/api/v1/outlook/tls/…`. Защищённый административный маршрут пакета (`/api/v1/admin/outlook/package`) сохранён. Публичная документация API — `/api/docs` и `/api/docs/openapi.json`: документация открыта, **выполнение** запросов по-прежнему требует ключа или входа; админские и пользовательские методы не публикуются. Для Exchange 2019 используйте прямую ссылку на манифест: перенаправлений нет (проверяется и тестами, и страницей).

**Диагностика TLS** (Администрирование → Интеграции → Microsoft Outlook) разбирает цепочку, которую реально отдаёт публичный адрес: сертификат сайта, промежуточные, корневой, имя в SAN, срок, доверие **этого сервера** (системное хранилище контейнера) и полноту цепочки, и называет, **где исправлять**:

| Причина | Что показано | Где исправлять |
| --- | --- | --- |
| Неполная цепочка (нет промежуточного) | «Цепочка неполная»; недостающие общедоступные сертификаты найдены в AIA и проверены до системного корня; можно скачать `fullchain.pem` | на reverse proxy / WAF / балансировщике — устройстве, где установлен сертификат сайта |
| Внутренний центр сертификации | «Сервер не доверяет цепочке; станции организации могут доверять» (не ошибка надстройки) | развёртывание корня штатными средствами организации (групповая политика, MDM); для проверок с сервера — явно подключённый файл корня организации (`<DATA_ROOT>/ca/outlook-ca.pem` или `OUTLOOK_CHECK_CA_FILE`) |
| Самоподписанный, чужое имя, просрочен | ошибка | заменить сертификат на устройстве, где завершается HTTPS |
| Публичный адрес не виден с сервера (DNS, hairpin NAT) | «Внешняя проверка с сервера недоступна» (не ошибка) | проверка с рабочей станции: кнопка на странице, `Test-OutlookAddin.ps1` |

Безопасность: проверка TLS никогда не отключается; сертификат сайта не добавляется в доверенные; соединение без проверки читает цепочку только для разбора и «успехом» не считается; AIA-ссылки берутся только из самого сертификата, по http(s), только на публичные адреса (внутренние и loopback отклоняются), ограниченного размера, и принимаются лишь если подписали предыдущий сертификат и цепочка доходит до системного корня; внешний прокси сервис не изменяет. Копирование сертификата сайта в Peregovorka исправлением не является.

**Схема HTTPS** определяется по признакам установки и доверенным proxy-заголовкам, а не по исходу TLS-соединения: собственный сертификат установщика (`NGINX_TLS_CERT`) → «на самом сервере»; `X-Forwarded-Proto: https`/цепочка `X-Forwarded-For`/`Via` → «на внешнем узле (reverse proxy, WAF или балансировщик)»; признаков нет → **«Требуется уточнение»** и ручной выбор (`tls_mode`: auto / local / proxy / gateway). Поддержаны HTTP и HTTPS между прокси и приложением, разные внутренние и внешние имена.

**Проверка API** различает причины (вместо общего `ConnectError`): API внутри приложения (в процессе) · через контейнер web · через публичный адрес; ответы 200 (успешно), 401 (маршрут работает, нужен вход), 403 (доступ ограничен политикой), 404 (маршрута нет), 502/503/504 (ошибка прокси или сервиса); сбой DNS/маршрутизации/доверия TLS из контейнера — «особенность внутренней маршрутизации» / «ошибка доверия TLS», а не недоступность надстройки: достоверно клиентскую доступность показывает проверка из браузера.

**Сценарии PowerShell** (`Install/Uninstall/Test-OutlookAddin.ps1`): проверка Exchange Management Shell и прав, чтение манифеста (файл или прямая ссылка), поиск существующей установки по идентификатору, установка (`New-App`), назначение пользователей, проверка результата (`Get-App`), обновление (`-Replace`), удаление, `-WhatIf`, журнал; повторный запуск не создаёт дубликатов; адреса и идентификаторы — только из манифеста и аргументов. Проверено: разбор парсером PowerShell и прогон на подставном Exchange (`tests/ps/run.sh`, CI-задача `outlook-scripts`); **не проверено на настоящем Exchange**.

## Серверная сверка через EWS: способы входа, серверы, права

**Способ входа** (Администрирование → Интеграции → Microsoft Outlook → «Способ входа в EWS»): `auto` · `basic` · `ntlm` · `negotiate` · `kerberos`.
* `auto` (по умолчанию, существующие установки продолжают работать как раньше): сначала Basic; если сервер Basic не предлагает — берётся то, что предложено в ответе 401 (NTLM, затем Negotiate), и найденный способ запоминается на 10 минут. Если Basic предложен и пароль неверен, других способов с теми же данными **не пробуется** (чтобы не блокировать учётную запись).
* `ntlm` — чистый Python (pyspnego), системных библиотек не требует; `negotiate` — SPNEGO: Kerberos, при отказе NTLM; `kerberos` — только Kerberos (библиотеки MIT krb5 в образе есть).
* Кнопка **«Определить способы входа»** опрашивает адреса без учётных данных и показывает, что предлагает каждый сервер, с рекомендацией и кнопкой «Применить».
* Kerberos: имя сервера в адресе должно совпадать с зарегистрированным именем службы `HTTP/<имя>` (за балансировщиком — имя балансировщика); область и KDC находятся по DNS, при необходимости их можно указать в настройках. Без KDC билет получить нельзя — сообщение называет область, KDC и имя службы.
* Логин: `ДОМЕН\пользователь` или `пользователь@домен`; отдельное поле «Домен» дописывается, если в логине его нет.

**Адреса и серверы.** Поле принимает несколько адресов (по одному в строке): имя сервера или балансировщика (`mail.example.org` → `https://mail.example.org/EWS/Exchange.asmx`) либо полный адрес; только HTTPS; ничего не зашито. При недоступности сервера (соединение, 502/503/504) пробуется следующий; ошибка входа (401) на другой сервер **не переносится**. Сертификаты серверов EWS проверяются по системному хранилищу доверия, внутренний центр сертификации — `<DATA_ROOT>/ca/outlook-ca.pem` (см. выше).

**Права на календари.** Успешный вход в EWS прав на чужие календари **не даёт**. Нужно одно из двух: роль `ApplicationImpersonation` (имперсонация; в `auto` пробуется первой) либо право «Рецензент» на календарь каждого организатора (делегированный доступ; запрос идёт без заголовка имперсонации). Режим задаётся полем «Доступ к календарям организаторов»; в `auto` при отказе имперсонации сверка переходит на делегированный доступ и запоминает, что сработало. Кнопка «Проверить доступ» показывает **два шага отдельно**: «Вход выполнен (способ, сервер)» и «Права на календарь ящика: есть (способ) / нет».

**Ошибки и журнал.** Сообщения называют причину и место: нет связи (с каким сервером и почему: DNS, отказ, таймаут), сервер не предлагает выбранный способ, учётная запись отклонена, HTTP 403/404, нет прав на календарь. Пароль и заголовки `Authorization` в сообщения и журнал не попадают (замена на `***`). Сбой связи или входа **никогда не отменяет комнату**; отмена — только по явному ответу «события нет». В журнале (категория `outlook`) записи сверки содержат способ входа и сервер.

**Проверено:** настоящее NTLM-рукопожатие между клиентом и серверным контекстом pyspnego (в тестах), перенос времени и темы, отмена, потеря связи, неверный пароль, переключение серверов, имперсонация → «Рецензент», пароль отсутствует в ошибках; Kerberos — загрузка библиотек в образе и попытка получения билета (без KDC ожидаемо «Cannot find KDC»). **Не проверено:** настоящий Exchange с NTLM/Kerberos, настоящий KDC и SPN, балансировщик с «липкими» сессиями для NTLM (рекомендуется привязка соединения), Exchange Subscription Edition.

## Библиотеки Office.js на сервере (0.40.1)

**Зачем.** В Outlook Web App локального Exchange панель могла не запускаться («Ошибка настройки»). Что установлено по коду библиотеки Microsoft и в браузере (на подставном узле Outlook, под CSP из `frontend/nginx.conf`): прежняя сборка `office.js` с `appsforoffice.microsoft.com` в узле Outlook Web требует MicrosoftAjax.js и загружает его с CDN, а MicrosoftAjax разбирает JSON через `eval` — этого запрещает CSP страниц надстройки (нарушение `script-src eval`, затем `Sys.ArgumentNullException`/`argumentNull` в `outlook-web-16.01.js`). Сборка с `officeapis.public.onecdn.static.microsoft/1/` помечена `osfLoadMsAjax = false` и MicrosoftAjax не требует: под той же CSP нарушений нет. Поэтому страницы теперь подключают `/outlook/assets/office-js/office.js` с вашего же сервера (общий загрузчик — `frontend/public/outlook/ms-loader.js`), и компьютерам с Outlook больше не нужен доступ к CDN Microsoft. **MicrosoftAjax.js не поставляется и не подключается намеренно:** в этой CSP он не работает, а при заранее загруженном «битом» `Sys` узел Outlook считает, что MicrosoftAjax есть, и падает позже. Разрешать для этого `unsafe-eval` на страницах надстройки не потребовалось.

**Откуда файлы.** Образ web при сборке (`frontend/Dockerfile`, шаг `scripts/vendor-officejs.mjs`) скачивает набор с `officeapis.public.onecdn.static.microsoft/1/`. Состав выводится из самого `office.js`: файлы узла Outlook (web, win32, mac, iOS, Android), строки всех поддерживаемых им языков, файлы старых форматов (Exchange 2013), телеметрия; около 135 файлов, 5 МБ. Сборка без флага `osfLoadMsAjax = false` отвергается. Файлы не изменяются; рядом лежат `SOURCE.json` (источник, дата, число файлов, SHA-256 `office.js`) и лицензия Microsoft. В репозиторий файлы Microsoft не входят: лицензия Office.js разрешает распространять их только в составе приложения, а не публиковать отдельно.

**Сбой при сборке не ломает установку.** Нет доступа к CDN при сборке — каталог `assets` не создаётся (частичных наборов не бывает), в журнале сборки предупреждение, а страницы надстройки сами берут Office.js с CDN Microsoft (`local:cdn_fallback` в журнале Outlook). «Администрирование → Интеграции → Microsoft Outlook → Проверки → Библиотека Microsoft Office.js» показывает, есть ли локальная копия, откуда и когда она получена. Нет копии — пересоберите web с доступом к CDN: `scripts/update.sh --force-build`. Обновление Peregovorka заменяет файлы вместе с образом; копировать их в контейнеры вручную не нужно и не следует.

**Настройка «Источник библиотеки Office.js»** (Почтовая инфраструктура):
* `local` (по умолчанию) — с сервера; запасной путь — CDN, если файла нет;
* `cdn` — с CDN `officeapis.public.onecdn.static.microsoft`;
* `cdn_only` — с прежнего CDN `appsforoffice.microsoft.com`, как до 0.40.1 (запасной вариант откатить поведение в классическом Outlook; в Outlook Web App этот вариант воспроизводит ошибку).
Значение, кроме `local`, добавляется к адресам страниц в манифесте (`taskpane.html?officejs=cdn`), поэтому после смены скачайте манифест заново и обновите надстройку в Exchange. При `local` манифест не меняется: ранее установленная надстройка получает локальные файлы сама после обновления сервера. Окно входа получает тот же источник, что и открывшая его панель.

**Проверка доверия к узлу Outlook Web App (0.40.4, AgaveErrorUX).** Office.js не запускает надстройку, пока не убедится, что её открыл доверенный узел Microsoft. Домены Microsoft известны ему заранее; домен локального OWA (ваш почтовый адрес) — нет. Для такого узла `OSF.InitializationHelper.checkWellKnownOrigins` не находит домен в списке, и `performUserTrustCheck` открывает скрытый фрейм `<каталог office.js>/AgaveErrorUX/index.html`, который хранит решение пользователя в `localStorage` (ключ `OfficeJSTrustKeyV2_https_<домен>`) и при первом запуске спрашивает «Доверять домену …?». Пока Office.js брался с CDN, эта страница лежала на CDN; с локальным `office.js` каталог стал нашим, а страницы там не было (404) — доверие не подтверждалось, и панель показывала «Ошибка настройки». Теперь `vendor-officejs.mjs` кладёт `AgaveErrorUX/` (страница, скрипт, стили, значки; имена с тем же регистром, что на CDN) рядом с `office.js`, а CSP `/outlook/` дополнена `frame-src` для своих страниц и адресов Microsoft (чтобы режим `cdn` тоже мог открыть эту страницу). Проверки доверия Microsoft не отключаются и не подменяются: **при первом запуске панели в Outlook Web App браузер покажет вопрос о доверии к домену OWA — нужно ответить «ОК», затем открыть панель заново** (вопрос появляется один раз для домена и браузера; «Отмена» запоминается как «не доверяю» — тогда очистите данные сайта Peregovorka в браузере). Страницы надстройки по-прежнему идут под CSP без `unsafe-eval`; общая политика приложения не менялась.

**Ограничения.** Локальная копия — снимок на день сборки: Microsoft обновляет библиотеки на CDN независимо, поэтому копия обновляется только пересборкой образа (каждое обновление Peregovorka). Если Outlook однажды запросит файл узла, которого в снимке нет, вернётся 404 — переключите источник на `cdn` и сообщите разработчикам. Microsoft документирует CDN как основной способ подключения Office.js; локальная поставка выбрана ради снятия зависимости от интернета у клиентов и по результатам сравнения с работающей сторонней надстройкой.

**Проверено запуском.** Скрипт поставки (тесты vitest на подставном CDN и запуск против настоящего CDN: 121 файл, в образе web — тот же набор), загрузчик и порядок подключения (vitest), проверка и манифест (pytest), раздача файлов настоящим образом web с настоящим nginx и CSP (200, `application/javascript`, 404 для отсутствующих), загрузка Office.js под этой CSP в настоящем браузере на подставном узле Outlook без нарушений. **Не проверено:** настоящий Outlook Web App и классический Outlook — запуск панели, вход, создание конференции и вставка ссылки в них не выполнялись; поведение при настоящем узле (обмен с родительским окном Outlook) подставной узел не воспроизводит.
