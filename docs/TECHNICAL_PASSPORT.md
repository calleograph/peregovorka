## 1. Назначение

Корпоративная система видеоконференций с распознаванием речи и подготовкой материалов встреч, разворачиваемая на сервере организации:

* видео- и аудиовстречи в браузере и в приложениях (Windows, Linux, Android), показ экрана, общая доска, чат встречи;
* распознавание речи на сервере (русский язык), стенограмма в реальном времени;
* протокол, резюме и «карта разговора» с помощью подключаемой языковой модели по API: своего сервера в сети организации или внешнего сервиса;
* аудио- и видеозапись встреч, плеер с субтитрами;
* вход по учётным записям Active Directory (LDAPS), роли и права на переговорные;
* корпоративные чаты; массовые трансляции (HLS, внешние площадки RTMP/RTMPS, собственные узлы раздачи CDN);
* интеграции: календари Exchange (EWS) и Microsoft 365 (Graph), надстройка Outlook, SIP-телефония, SMTP, SMB, Bitrix24, публичный API и webhooks.

Не является: системой хранения документов, сервисом для публичных конференций без администрирования, заменой АТС. Ограничения применимости —
вики «Когда продукт не подходит».

## 3. Архитектура и взаимодействие

```
браузер / приложения ──HTTPS 443──► внешний reverse proxy (TLS) ──► [nginx хоста, необязательно] ──► web:8080 ──► backend:8000
         │                                                                                        └── /livekit ──► livekit:7880 (сигнализация WebSocket)
         └──UDP LIVEKIT_UDP_PORT, TCP LIVEKIT_TCP_PORT (напрямую, не через HTTP-прокси)──► livekit (медиа WebRTC)
backend ──► postgres, redis, livekit API, asr; по настройке: LDAPS, SMTP, SMB, EWS/Graph, LLM, Bitrix24, webhooks
asr ──► livekit (подписка на звук участников) ──► backend (сегменты стенограммы)
```

Подробная схема и пояснения — вики «Как устроена Peregovorka», [ARCHITECTURE.md](../ARCHITECTURE.md), [INTERNALS.md](INTERNALS.md).

Ключевые решения:
* Медиа идёт напрямую к LiveKit (UDP, запасной путь TCP); HTTP-прокси медиа не передаёт. TURN не используется. STUN нужен только для определения публичного адреса за NAT (`LIVEKIT_STUN_SERVERS`); адреса ICE готовит `scripts/medianet.py` (**К**).
* Один экземпляр = один compose-проект (`COMPOSE_PROJECT_NAME`); на одном сервере могут работать несколько экземпляров с разными портами (**И**, стенд разработчика).
* Фоновые задачи с единственным исполнителем выполняет «ведущий» процесс (аренда в Redis); `BACKEND_WORKERS` > 1 — несколько процессов (**Т**, **И** нагрузочный стенд).

## 5. Требования к серверу

| Ресурс | Порог установщика | Примечание |
| --- | --- | --- |
| CPU | 4 vCPU | меньше — только предупреждение `preflight.sh` |
| ОЗУ | 8 ГиБ | от 7,2 ГиБ норма, от 6 до 7,2 ГиБ предупреждение, меньше 6 ГиБ установка не начнётся |
| Диск | 30 ГБ свободно в `DATA_ROOT` | меньше — отказ. Полный расход диска установкой не измерялся; модель ASR до ≈ 2 ГБ по сообщению установщика; образ Egress ≈ 3,8 ГБ; запись эфира 1080p ≈ 2,2 ГБ/час на локальном диске и столько же на копию |
| Swap | не обязателен | при отсутствии swap нехватка памяти приводит к OOM-остановке контейнера (виден в `diag.sh`, раздел resources) |
| Сеть | DNS-имя и доверенный сертификат HTTPS; UDP и TCP порты медиа доступны клиентам напрямую | без HTTPS браузер не даёт микрофон и экран |

Это пороги проверки, а не подтверждённая рабочая конфигурация: система целиком на них не испытывалась, запись и эфир в них не входят (статус: требует дополнительного тестирования). Предварительная рекомендация для пилота 8 vCPU и 16 ГБ тоже не проверялась сквозным испытанием. Расчёт под нагрузку — раздел 11. Пороговые значения проверок — `scripts/preflight.sh` и вики «Системные требования».

## 6. Программные зависимости хоста

* Docker Engine с Compose plugin v2; Buildx желателен (без него сборка автоматически идёт классическим сборщиком — **И** 2026-10-29).
* git, curl, openssl, bash 4+; nginx — только если установщику поручено управлять сайтом nginx (`NGINX_MANAGE=yes`).
* Профиль `standalone` ставит недостающее сам (`apt install`, без `upgrade`); профиль `shared-host` ничего системного не меняет.
* При сборке нужен доступ к GitHub, Docker Hub, PyPI, npm, индексу PyTorch и источнику модели GigaAM; закрытый контур — модели переносятся `scripts/install.sh --models-from`, остальное — заранее собранными образами (**Н**: полностью офлайн-установка не испытывалась).

## 8. Хранение данных

| Данные | Где | Резервирование |
| --- | --- | --- |
| Пользователи, встречи, стенограммы, чаты, протоколы, настройки, журнал аудита | PostgreSQL, `DATA_ROOT/postgres` | `scripts/backup.sh` (дамп `pg_dump`) |

| Протоколы, стенограммы, доски, журнал в файловом виде | профиль хранилища (`Transcripts/`, `Protocols/`, `Boards/`, `Logs/`) | копия ресурса; в базе — основная копия |

| Выгрузки и паспорт встречи `manifest.json` | `DATA_ROOT/exports` | копия каталога |

Поддерживаемые внешние хранилища: SMB (SMB 2/3, протокол реализован в приложении) и локальный каталог (в том числе примонтированный администратором
ресурс NFS/iSCSI на уровне ОС). S3 и NFS-клиент внутри приложения не реализованы. Подробно — вики «Резервное копирование и аварийное восстановление».

## 9. Безопасность

Механизмы и границы — вики «Безопасность и приватность», «Справочник для проверки ИБ», «Шифрование», [SECURITY_AUDIT.md](SECURITY_AUDIT.md). Кратко:
* TLS на reverse proxy; LDAPS с обязательной проверкой цепочки; CSRF и проверка `Origin` (отключить нельзя).
* Серверные сессии в Redis (HttpOnly, SameSite=Lax), TOTP, CAPTCHA и блокировки при переборе, доверенные подсети, встроенный WAF.
* Шифрование чата и стенограмм в базе AES-256-GCM (ключ `APP_MASTER_KEY`), сквозное шифрование звука и видео (по настройке комнаты).
* Журнал аудита с HMAC-подписью; журналы и диагностика маскируют секреты.
* Граница доверия: администратор сервера и процесс backend видят данные в памяти; шифрование в базе не защищает от владельца сервера.
* Нагрузочные испытания безопасности и внешний тест на проникновение не проводились (**Н**).

## 11. Производительность и масштабирование

### 11.1. Различаемые величины

| Величина | Что это | От чего зависит |
| --- | --- | --- |
| Зарегистрированные пользователи | учётные записи в базе (вход из AD создаёт запись) | объём базы; наибольший каталог в испытании 2100 записей, предел не определялся |
| Одновременно авторизованные пользователи | открыт интерфейс, идут запросы и WebSocket событий, медиа нет | процессор backend, пул PostgreSQL, `BACKEND_WORKERS` |
| Активные участники одной конференции | подключены к одной комнате LiveKit | один узел LiveKit: процессор и сеть; настройка комнаты «Максимум участников» 1–2000 — это предел, а не гарантия |
| Одновременные конференции | число активных комнат | LiveKit (медиа), ASR (по одновременно говорящим, конвейер на участника), запись, фоновые задачи |

## 13. Ограничения и известные проблемы

* Масштаб медиа выше одного узла LiveKit не испытан; кластер LiveKit (несколько узлов) не настраивается установщиком.
* Высокая доступность: один экземпляр приложения на одном сервере; резервный сервер и автоматическое переключение не реализованы — восстановление из копии.
* PostgreSQL и Redis работают в контейнерах на том же сервере. Адреса заданы в `deployment/compose.yml` жёстко (`POSTGRES_HOST: postgres`, `REDIS_HOST: redis`), внешняя база в поставке не поддерживается и не испытана (**Н**).
* Приложение для Windows: установщики не подписаны сертификатом издателя (предупреждение SmartScreen); стабильность микрофона по сравнению с Edge не установлена (открытый вопрос, вики «Известные проблемы»).
* Приложение для Android: предварительный выпуск; установить поверх версий до постоянной подписи нельзя, нужна однократная переустановка.
* HSTS не включается автоматически; ограничения частоты на уровне nginx нет (защита в backend).
* Публичный API отдаёт очень большие записи, читая файл целиком в память.
* Полный перечень — вики «Известные проблемы» и «Границы проверки».
