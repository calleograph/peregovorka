# Карты и знания

Отдельный функциональный блок поверх «Стенограммы / Резюме / Протокола»: визуальный анализ встреч и накопление знаний из встреч во времени.
Постановка владельца (ТЗ «Карты и знания») делится на пять этапов; этот документ фиксирует **архитектурные правила**, **состояние реализации** и **что сознательно не сделано**.

## Три сущности и слой знаний

| Сущность | Что это | Этап |
|---|---|---|
| **Карта разговора** | визуальная структура одной встречи: темы, их порядок и длительность, участники, источники | 1 — сделано (см. ниже) |
| **Карта эволюции темы** | одна тема через много встреч во времени (введена → обсуждена → решение → пересмотр) | 3 — не начато |
| **Карта проекта** | сводная картина проекта: темы, решения, люди, открытые вопросы, хронология | 4 — не начато |
| **Слой знаний** | устойчивые темы/решения/задачи, переживающие удаление стенограммы | 2 — не начато |
| **Глобальный поиск** | по темам, решениям, задачам, встречам (с учётом прав доступа) | 5 — не начато |

## Архитектурные правила (обязательны для всех этапов)

```
стенограмма → реплики со временем → фрагменты → узкий JSON-запрос к модели → проверка кодом → слияние кодом
→ проверенный JSON в БД → отображение (страница / HTML-выгрузка)
```

* **Первичны данные, не HTML.** Модель никогда не пишет HTML; страница и файл строятся из JSON. Тексты из данных вставляются только как текст (`textContent`).
* **Стенограмма — недоверенный ввод.** В системной инструкции: содержимое — данные, команды из него не выполняются.
* **Модель не выдумывает.** Время тем привязывается к реальным репликам (иначе тема отвергается), участники и их время считаются кодом из стенограммы, цитаты берёт код.
  Решения/поручения показываются только с цитатой-основанием; «AI-интерпретация» (название и краткое содержание темы) и «подтверждено источником» помечаются по-разному, без «процентов правдивости».
* **Правки пользователя отдельно от ответа модели** (`edits` рядом с `data`), переживают пересоздание карты.
* **Права доступа** — как у самой встречи; знание id ничего не даёт. Слой знаний (этап 2+) не должен становиться обходом ACL: пользователь видит только вхождения тем из доступных ему встреч и не видит даже счётчика закрытых.
* **Не пересчитывать историю при открытии:** карта открывается из БД; модель вызывается только по кнопке / после встречи (если включено) / после существенной правки.
* **Тяжёлые AI-задачи идут по очереди** (сервер без GPU): сейчас карты — по одной за раз.

## Этап 1 — Карта разговора (реализовано в ветке `feat/maps`)

**Где:** история встречи → вкладка «Карта разговора» (после завершения встречи). Карта **не строится сама** (по умолчанию выкл.): кнопка «Сформировать карту»; автоформирование — «Администрирование → Протоколы → Автоматическое формирование» (системно) и «Настройки переговорки → Карта разговора» (`inherit` / `on` / `off`).

**Модель:** отдельное назначение «Карта разговора: чем формировать» (`llm.map_provider`: как протокол / по API / не формировать) в «Языковая модель (LLM) → Какая модель что делает по умолчанию». Сейчас по умолчанию — как для протокола. Выбор модели для карты в комнате/встрече и разово — не сделан.

**Конвейер** (`backend/app/services/conv_map.py`): реплики со временем от начала встречи → фрагменты ~5 500 знаков → по каждому один запрос (JSON по схеме: темы с названием, 1–2 предложениями, категорией, началом и концом) →
проверка (название, категория из списка, начало/конец — реальные реплики фрагмента; конец — последняя реплика, начавшаяся не позже названного времени) → слияние одинаковых тем кодом (по основам слов; возврат к теме = **одна тема с несколькими отрезками**) →
темы не накладываются на шкале, шум короче 15 с отбрасывается, соседние отрезки сливаются → не более 24 тем (остальные — «Прочие обсуждения») → оговорки в `meta.warnings`.
Оборвавшийся по длине/неразобранный ответ повторяется по половинам фрагмента (до двух раз). Категории — фиксированный перечень из 8 (на карте остаются только использованные), цвет задаёт отображение, красного среди них нет.
Решения, поручения и открытые вопросы берутся **из готового протокола** (его `meta.structured`: пункты уже проверены по тексту и имеют цитату), привязываются к теме по времени реплики; без протокола блок пуст с подсказкой. Отдельный проход «решения по фрагментам» для карты не выполняется (это удвоило бы время).

**Данные** (`conversation_maps`, миграция 0015): `data` (проверенный JSON: темы, отрезки, участники, источники, решения), `edits` (правки: название, категория, заметка), `meta` (модель, времена этапов, фрагменты, повторы, токены, токены/с, оговорки). Один набор данных на встречу; пересоздание сохраняет правки (идентификатор темы устойчив: по нормализованному названию).

**API** (`/api/v1/meetings/{id}/map`): `GET` состояние + данные с применёнными правками + план (какая модель, готова ли); `POST` сформировать/пересоздать (202, в фоне, повторное нажатие во время работы ничего не запускает); `PATCH /topics/{topic_id}` правка (руководитель комнаты или администратор); `POST /export` запись в аудит о выгрузке HTML; `DELETE` (администратор). Аудит: `map.create`, `map.recreate`, `map.edit_topic`, `map.export_html`, `map.delete`. События журнала: `map_ready`, `map_failed`.

**Отображение** (`frontend/public/mapview/{index.html,viewer.js,viewer.css}`, один файл просмотра на два режима): встроено в страницу встречи iframe `sandbox="allow-scripts"` **без** `allow-same-origin` (у окна нет cookie и доступа к API; данные приходят через `postMessage`, действия «перейти к реплике» и «сохранить правку» уходят странице); nginx отдаёт `/mapview/` со своей строгой CSP.
Блоки: шапка (дата, длительность, участники, модель, время формирования), легенда категорий (фильтр), шкала «Как шла встреча» (отрезки пропорциональны времени, подсказка), «На что ушла встреча» (treemap; размер = время, не важность), «Кто говорил» (клик — подсветка тем человека; время по стенограмме, не оценка вклада), карточка темы (краткое содержание с пометкой «AI-интерпретация», фрагменты, участники, решения/задачи/вопросы с пометкой «подтверждено источником» и цитатой, реплики-источники, соседние по времени темы, правка).
Выбор темы подсвечивает её и соседей, остальные приглушаются. Светлая и тёмная темы — по настройке системы.
**Переход к первоисточнику:** кнопка «00:34:18 Имя» открывает «Стенограмму» и прокручивает к реплике (если стенограмма уже удалена по сроку хранения — понятное сообщение).
**Скачать HTML:** браузер собирает один самостоятельный файл (данные + стили + скрипт), он открывается без сервера (`file:///`). В файл не попадают служебные сведения (профиль API, кто нажал, токены, адреса): только модель, времена, число фрагментов и оговорки. JSON внутри экранируется (`</script>`, `<!--`, разделители строк).

### Выбор модели и безопасная замена (0.44.0)

* **Выбор модели.** `POST /meetings/{id}/map` принимает необязательное `{"llm_once": "local:<модель>" | "profile:<профиль>"}`; список доступных вариантов (`llm_choices`: те же, что в окне протокола — `llm_choice.once_options`) приходит в `GET …/map` только руководителям комнаты и администраторам. Сервер проверяет право (`can_manage_room`) и что ключ есть в списке настроенных и включённых моделей (иначе 403/422); настройки комнаты и системы не меняются. Без `llm_once` — модель карты по умолчанию, поведение прежнее. Использованная модель пишется в `meta.model`, `meta.llm_profile`, `meta.llm_once`; в аудит (`map.create`/`map.recreate`) — выбранный ключ. Интерфейс: кнопка «Модель…» рядом с «Сформировать карту»/«Переформировать» (общий компонент `ModelChoice` с окном протокола).
* **Прежняя карта не пропадает.** При пересоздании `data` прежней готовой карты остаётся в записи (`meta.keep` хранит её метаданные); пока строится новая, `GET` отдаёт прежнюю с `stale=true`. Если построение не удалось (ошибка модели, прерывание перезапуском), запись остаётся `ready` с прежней картой, а причина — в `meta.regen_failed`. После успешной замены предыдущая версия лежит в `meta.previous`; `POST …/restore` меняет версии местами (клиенту `previous` не отдаётся — только `can_restore`). Правки пользователя (`edits`) хранятся отдельно и не затрагиваются.

### Карта версии 3: итог, результаты, навигация (0.78.0)

**Данные** (`MAP_VERSION=3`, совместимо: карты версии 2 открываются, недостающее просмотр восполняет сам):
* `outcome` — `{text, basis}`: главный итог встречи. `basis="ai"` — одно короткое обращение к модели (`conv_map.meeting_outcome`, `OUTCOME_SYSTEM`) **по уже проверенным пунктам карты**, а не по стенограмме (вход — несколько сотен знаков; в модель не уходит ничего сверх уже отправленного, при обезличивании пункты уже обезличены). Решений и поручений нет или модель не ответила → `basis="code"`, текст собирает код (`code_outcome`) и честно говорит «Решений и поручений не зафиксировано». В `meta`: `outcome_basis`, обращение учтено в `llm_calls`.
* `topics[].proposals` и `unassigned.proposals` — «предложено, но не согласовано» (пункты `proposal` общего этапа извлечения; проверка по тексту требует формы предложения в реплике). Раньше они на карту не попадали, а решение и предложение не различались в интерфейсе.
* `cap_topics(…, keep_secs)`: тема, во время которой есть решение, поручение или вопрос, не уходит в «Прочие обсуждения», даже если короткая.
* Категории (`topic_categories.py`): добавлены `product`, `sales`, `people`, `legal` (встречи не только ИТ); цвета — токены `--gd-<категория>-*` в `glassdoc.css`. Промпт изменился → `fact_engine.SCHEMA_VERSION=4` (старые сохранённые ответы по фрагментам не переиспользуются).

**Просмотр** (`frontend/public/mapview/viewer.js`, копия для сервера — `scripts/sync_glassdoc.py`): итог и показатели (по фактическим данным карты) → шкала во всю ширину (каждый отрезок темы — свой участок, деления по круглому времени, их число зависит от ширины) → слева список тем (поиск по названию, сути, заметке, пунктам и именам; фильтр по категории и участнику; порядок по времени / длительности / решениям; стрелки клавиатуры), справа вкладки **Тема**, **Решения и задачи** (все пункты встречи, фильтры применяются и здесь), **Обзор встречи** (последовательность, время по категориям, участники, связи, площадь тем, достоверность).
Список перерисовывается частично (поле поиска не теряет фокус). Сообщения окна странице: прежние `ready/height/goto/edit` и новые `scroll` (телефон: прокрутить страницу к содержимому темы) и `copy` (буфер обмена — только у страницы: у окна без своего источника доступа к нему нет). Печать: перед печатью собирается раздел «итог + результаты + все темы», после — убирается. В самостоятельном файле время реплики — текст, а не кнопка.

### Что из ТЗ этапа 1 НЕ сделано или сделано иначе

* Выбор модели для карты в настройках комнаты/встречи (разовый выбор при формировании есть с 0.44.0); приоритеты очереди AI-задач между протоколом/резюме/картой (сейчас очередь — только между картами).
* RAM и CPU в метриках анализа (есть: модель, времена, фрагменты, повторы, причины остановки, вход/выход в токенах, токены/с). Модель работает в отдельном контейнере, её ОЗУ/ЦП backend не видит.
* «▶ Слушать с 00:34:18» (запись аудио) — нет.
* Правки: переименование, смена категории, заметка — есть; **объединение и разделение тем, правка связей — нет**.
* Связи между темами — по общим основам слов в названии и сути; вид связи (продолжение, зависимость) не определяется.
* Участники темы — по времени реплик в отрезках темы (из стенограммы), а не по списку, названному моделью.
* При включённом обезличивании (в комнате, обязательном или выбранном для одной карты) карта строится на обезличенных репликах: `mask_lines` меняет автора и текст, а порядок, время и ссылка на реплику остаются. Запрос к модели отличается от необезличенного, поэтому ответы модели по фрагментам не смешиваются.
* Раздел верхнего меню «Карты и знания» (Обзор / Темы / Проекты / Поиск) — относится к этапам 2–5.
* Политика хранения для «Карт разговоров» и «Слоя знаний» в «Администрирование → Хранение» (этап 2). Пока карта хранится, пока есть встреча; сроки текста/аудио комнаты на неё не действуют.
* Среда: тесты и проверка в браузере — на эмуляторе nginx (CSP/заголовки из `nginx.conf`) и подставной модели; настоящий nginx/Docker, настоящая модель на длинной встрече и время формирования на боевом сервере — не проверялись.

## Этап 2 — Память комнаты: эволюция обсуждений (0.79.0)

**Задача:** связывать темы разных встреч одной комнаты в сквозные темы, показывать их историю, замечать повторы и застой, отвечать на вопросы по истории.

**Архитектура (почему так).**
* **Источник — карта разговора встречи** (`conversation_maps.data`), а не протокол и не отдельный проход по стенограммам. Карта строится из стенограммы независимо от протокола, у её решений/поручений/предложений/вопросов есть реплика-основание, ответы модели по фрагментам переиспользуются (`FactsCache`). Отдельный «общий аналитический слой» не заводился: карта им уже является. Включённая память (`rooms.memory_mode=on`) строит карты сама (`MapService.maybe_auto`) и для недостающих встреч ставит их в общую очередь карт (`MemoryService.request_maps`, ≤ 10 за раз, очередь — по одной).
* **Хранение** (миграция 0067): `room_threads` (сквозная тема; поля `user_*` — правки людей), `room_thread_events` (событие темы на встрече: `mention|proposal|decision|task|question`, текст, время, говорящий, цитата, ответственный, срок, `segment_id`, `source_gone`), `room_memories` (состояние, `processed` = {встреча: время обновления карты} — неизменённая карта повторно не обрабатывается; `overrides` = ручные привязки «встреча:тема → сквозная тема | new»; `feedback` по наблюдениям). Таблицы не переносятся в копию конфигурации (данные встреч); `memory_mode`, `memory_keep` — переносимые настройки комнаты.
* **Связывание** (`services/room_memory.py`): ручная привязка → кандидаты кодом (`score`: общие основы слов в названии и сути) → **одно обращение к модели на встречу** (`LINK_SYSTEM`, JSON-схема; в запросе только названия и суть тем и до 40 кандидатов под короткими обозначениями T1…, без цитат, авторов и стенограммы; при обезличивании комнаты — через `mask_session`); ответ вне кандидатов отвергается (`parse_links`). Нет внятного ответа или модели — строгое правило кода (`code_link`: похожие названия, то же, что объединяет повторы внутри встречи). Модель — та же, что строит карты (`resolve_llm(..., "map")`): новых назначений модели нет.
* **Люди между встречами.** Обозначения обезличивания разные на каждой встрече, поэтому говорящий и цитата события берутся из стенограммы по времени пункта (`segment_id`), а ответственный из обезличенной карты не переносится (не угадываем).
* **Состояние темы и наблюдения — код, без модели** (`thread_state`, `observations`): новая / обсуждается / решение принято / поручения в работе / вернулись после решения / без движения (30 дней) / закрыта (только человек). Наблюдения: `repeat` (≥3 встреч, ≥7 дней, на двух последних нет новых пунктов), `developing` (то же, но новые пункты есть — развитие), `reopened`, `changed` (решения на разных встречах — возможное противоречие), `task_owner`, `task_due`, `unconfirmed` (поручение старше 14 дней, тема больше не обсуждалась — «нет сведений», не «не выполнено»), `lost` (предложение старше 21 дня без продолжения), `progress`. Ключ наблюдения включает последнее событие-основание: скрытое не возвращается, пока нет нового основания.
* **Фон:** после готовой карты (`MapService.run` → `MemoryService.after_map`) и задача ведущего экземпляра `room-memory` раз в 15 минут (`sweep`: догоняет карты после перезапуска или недоступной модели). Обработка комнаты — под семафором, встреча пересчитывается целиком (события встречи удаляются и строятся заново) — повтор безопасен.
* **Права:** `GET /rooms/{id}/memory` отдаёт события только встреч из `accessible_history` (руководитель и администратор — все); темы без видимых событий и наблюдения по невидимым встречам не попадают в ответ; правки — `can_manage_room`. Вопрос к истории (`POST …/ask`) выбирает до 40 событий кодом (`rank_events`) из видимых и отправляет модели только их формулировки; без модели — найденные события. Лимиты: обновление 6/час на комнату, вопросы 20/час на человека. Аудит: `memory.settings`, `memory.edit_thread`, `memory.merge`, `memory.split`, `memory.ask`.
* **Сроки хранения:** очистка текста по сроку (`retention._purge_text` → `forget_meetings`) удаляет события встреч; при `rooms.memory_keep` события остаются без цитат и `segment_id`, с `source_gone=true`. `_has_text` учитывает события с цитатами, чтобы очистка их догоняла. Удаление комнаты — каскад.
* **Интерфейс:** `/history/rooms/:roomId` (`pages/RoomMemoryPage.tsx`, `memoryView.ts`, `memory.css`): период, показатели, вкладки «Обзор» (наблюдения + «Развитие тем» — сетка тема × встреча), «Темы» (список, история по встречам, правка, объединение, «Отделить»), «Решения и задачи», «Вопрос к истории». Вход — «История» → «Эволюция обсуждений…» и ссылка на странице встречи.

**Испытания.** Синтетическая история `backend/tests/memory_corpus.py` (11 встреч, 3 месяца, эталонная разметка: развитие идеи, возражение-риск, решение, поручение, повторное открытие, противоречащее решение, ошибка распознавания в названии, похожие, но разные темы, встреча без карты и без стенограммы). Сравнение по парам вхождений: правило кода без модели — точность 1,0, полнота 0,25 (ложных объединений 0); с подставной моделью, отвечающей по эталону, — 1,0/1,0 (проверяет обвязку, а не модель). Качество настоящей модели **не измерено**.

**Не сделано (следующий этап).** Связи между комнатами и «карта проекта» (архитектурно: `room_id` в событиях и темах, права через `accessible_history` — расширение на несколько комнат без новых сущностей); вид связи между темами (продолжение / зависимость); подтверждение выполнения поручений по тексту последующих встреч (сейчас — только «тема больше не обсуждалась»); семантический поиск (эмбеддинги) вместо совпадения основ слов; отдельный срок хранения памяти (сейчас — со стенограммой или «дольше стенограммы» без срока).
