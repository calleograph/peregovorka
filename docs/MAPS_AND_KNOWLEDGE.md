# Карты и знания

Отдельный функциональный блок поверх «Стенограммы / Резюме / Протокола»: визуальный анализ встреч и накопление знаний из встреч во времени.
Постановка владельца (ТЗ «Карты и знания») делится на пять этапов; этот документ фиксирует **архитектурные правила**, **состояние реализации** и **что сознательно не сделано**.

## Три сущности и слой знаний

| Сущность | Что это | Этап |
|---|---|---|
| **Карта разговора** | визуальная структура одной встречи: темы, их порядок и длительность, участники, источники | 1 — сделано (см. ниже) |
| **Карта эволюции темы** | одна тема через много встреч во времени (введена → обсуждена → решение → пересмотр) | 3 — не начато |
| **Карта проекта** | сводная картина проекта: темы, решения, люди, открытые вопросы, хронология | 4 — не начато |
| **Слой знаний** | устойчивые темы/решения/задачи, переживающие удаление стенограммы | 2 — не начато |
| **Глобальный поиск** | по темам, решениям, задачам, встречам (с учётом прав доступа) | 5 — не начато |

## Архитектурные правила (обязательны для всех этапов)

```
стенограмма → реплики со временем → фрагменты → узкий JSON-запрос к модели → проверка кодом → слияние кодом
→ проверенный JSON в БД → отображение (страница / HTML-выгрузка)
```

* **Первичны данные, не HTML.** Модель никогда не пишет HTML; страница и файл строятся из JSON. Тексты из данных вставляются только как текст (`textContent`).
* **Стенограмма — недоверенный ввод.** В системной инструкции: содержимое — данные, команды из него не выполняются.
* **Модель не выдумывает.** Время тем привязывается к реальным репликам (иначе тема отвергается), участники и их время считаются кодом из стенограммы, цитаты берёт код.
  Решения/поручения показываются только с цитатой-основанием; «AI-интерпретация» (название и краткое содержание темы) и «подтверждено источником» помечаются по-разному, без «процентов правдивости».
* **Правки пользователя отдельно от ответа модели** (`edits` рядом с `data`), переживают пересоздание карты.
* **Права доступа** — как у самой встречи; знание id ничего не даёт. Слой знаний (этап 2+) не должен становиться обходом ACL: пользователь видит только вхождения тем из доступных ему встреч и не видит даже счётчика закрытых.
* **Не пересчитывать историю при открытии:** карта открывается из БД; модель вызывается только по кнопке / после встречи (если включено) / после существенной правки.
* **Тяжёлые AI-задачи идут по очереди** (сервер без GPU): сейчас карты — по одной за раз.

## Этап 1 — Карта разговора (реализовано в ветке `feat/maps`)

**Где:** история встречи → вкладка «Карта разговора» (после завершения встречи). Карта **не строится сама** (по умолчанию выкл.): кнопка «Сформировать карту»; автоформирование — «Администрирование → Протоколы → Автоматическое формирование» (системно) и «Настройки переговорки → Карта разговора» (`inherit` / `on` / `off`).

**Модель:** отдельное назначение «Карта разговора: чем формировать» (`llm.map_provider`: как протокол / локальная / внешняя / не формировать) в «Языковая модель (LLM) → Какая модель что делает по умолчанию». Сейчас по умолчанию — как для протокола (локальная Qwen3 1.7B). Выбор модели для карты в комнате/встрече и разово — не сделан.

**Конвейер** (`backend/app/services/conv_map.py`): реплики со временем от начала встречи → фрагменты ~5 500 знаков → по каждому один запрос (JSON по схеме: темы с названием, 1–2 предложениями, категорией, началом и концом) →
проверка (название, категория из списка, начало/конец — реальные реплики фрагмента; конец — последняя реплика, начавшаяся не позже названного времени) → слияние одинаковых тем кодом (по основам слов; возврат к теме = **одна тема с несколькими отрезками**) →
темы не накладываются на шкале, шум короче 15 с отбрасывается, соседние отрезки сливаются → не более 24 тем (остальные — «Прочие обсуждения») → оговорки в `meta.warnings`.
Оборвавшийся по длине/неразобранный ответ повторяется по половинам фрагмента (до двух раз). Категории — фиксированный перечень из 8 (на карте остаются только использованные), цвет задаёт отображение, красного среди них нет.
Решения, поручения и открытые вопросы берутся **из готового протокола** (его `meta.structured`: пункты уже проверены по тексту и имеют цитату), привязываются к теме по времени реплики; без протокола блок пуст с подсказкой. Отдельный проход «решения по фрагментам» для карты не выполняется (это удвоило бы время).

**Данные** (`conversation_maps`, миграция 0015): `data` (проверенный JSON: темы, отрезки, участники, источники, решения), `edits` (правки: название, категория, заметка), `meta` (модель, времена этапов, фрагменты, повторы, токены, токены/с, оговорки). Один набор данных на встречу; пересоздание сохраняет правки (идентификатор темы устойчив: по нормализованному названию).

**API** (`/api/v1/meetings/{id}/map`): `GET` состояние + данные с применёнными правками + план (какая модель, готова ли); `POST` сформировать/пересоздать (202, в фоне, повторное нажатие во время работы ничего не запускает); `PATCH /topics/{topic_id}` правка (руководитель комнаты или администратор); `POST /export` запись в аудит о выгрузке HTML; `DELETE` (администратор). Аудит: `map.create`, `map.recreate`, `map.edit_topic`, `map.export_html`, `map.delete`. События журнала: `map_ready`, `map_failed`.

**Отображение** (`frontend/public/mapview/{index.html,viewer.js,viewer.css}`, один файл просмотра на два режима): встроено в страницу встречи iframe `sandbox="allow-scripts"` **без** `allow-same-origin` (у окна нет cookie и доступа к API; данные приходят через `postMessage`, действия «перейти к реплике» и «сохранить правку» уходят странице); nginx отдаёт `/mapview/` со своей строгой CSP.
Блоки: шапка (дата, длительность, участники, модель, время формирования), легенда категорий (фильтр), шкала «Как шла встреча» (отрезки пропорциональны времени, подсказка), «На что ушла встреча» (treemap; размер = время, не важность), «Кто говорил» (клик — подсветка тем человека; время по стенограмме, не оценка вклада), карточка темы (краткое содержание с пометкой «AI-интерпретация», фрагменты, участники, решения/задачи/вопросы с пометкой «подтверждено источником» и цитатой, реплики-источники, соседние по времени темы, правка).
Выбор темы подсвечивает её и соседей, остальные приглушаются. Светлая и тёмная темы — по настройке системы.
**Переход к первоисточнику:** кнопка «00:34:18 Имя» открывает «Стенограмму» и прокручивает к реплике (если стенограмма уже удалена по сроку хранения — понятное сообщение).
**Скачать HTML:** браузер собирает один самостоятельный файл (данные + стили + скрипт), он открывается без сервера (`file:///`). В файл не попадают служебные сведения (профиль API, кто нажал, токены, адреса): только модель, времена, число фрагментов и оговорки. JSON внутри экранируется (`</script>`, `<!--`, разделители строк).

### Что из ТЗ этапа 1 НЕ сделано или сделано иначе

* Выбор модели для карты в настройках комнаты/встречи и разовый выбор; приоритеты очереди AI-задач между протоколом/резюме/картой (сейчас очередь — только между картами).
* RAM и CPU в метриках анализа (есть: модель, времена, фрагменты, повторы, причины остановки, вход/выход в токенах, токены/с). Модель работает в отдельном контейнере, её ОЗУ/ЦП backend не видит.
* «▶ Слушать с 00:34:18» (запись аудио) — нет.
* Правки: переименование, смена категории, заметка — есть; **объединение и разделение тем, правка связей — нет**.
* Решения/задачи/вопросы по фрагментам самой модели (п. 7 ТЗ) — берутся из протокола, а не из отдельного прохода.
* Участники темы — по времени реплик в отрезках темы (из стенограммы), а не по списку, названному моделью.
* Внешняя модель при включённом обезличивании: карта **не строится** (fail closed): имена участников нужны карте, а обезличенный текст их заменяет.
* Раздел верхнего меню «Карты и знания» (Обзор / Темы / Проекты / Поиск) — относится к этапам 2–5.
* Политика хранения для «Карт разговоров» и «Слоя знаний» в «Администрирование → Хранение» (этап 2). Пока карта хранится, пока есть встреча; сроки текста/аудио комнаты на неё не действуют.
* Среда: тесты и проверка в браузере — на эмуляторе nginx (CSP/заголовки из `nginx.conf`) и подставной модели; настоящий nginx/Docker, реальная Qwen3 на длинной встрече и время формирования на боевом сервере — не проверялись.

## Дальше (по ТЗ)

2. **Слой знаний:** `knowledge_topics / occurrences / decisions / tasks / questions / links / sources / projects`; устойчивые id тем; `source_status = deleted_by_retention`; режимы «сохранять доказательные цитаты» / «не сохранять исходный текст»; политика хранения по видам данных; ручные правки.
3. **Эволюция темы:** сопоставление тем между встречами (уверенность < 0.70 — новая; 0.70–0.90 — предложить; > 0.90 — автосвязь только при включённой политике, по умолчанию выключена), типы событий (`introduced … closed`), ручное подтверждение; события не придумываются, при сомнении — `discussed`.
4. **Проекты:** сущность «Проект» (владельцы, группы доступа, комнаты, встречи), привязка встреч, карта проекта (размер блока: встречи / время / события), хронология, решения (с «заменено решением от …»), задачи, открытые вопросы, участники (без «рейтингов людей»), граф связей с источником и уверенностью.
5. **Глобальный поиск** с фильтрами; после удаления стенограммы находит темы/решения/задачи, но не делает вид, что исходный текст существует; не раскрывает закрытое (ни названий, ни факта встречи, ни «скрыто N»).
