# Совместимость версий и политика обновлений

## Главное правило

Браузерный клиент (`livekit-client`) и ASR (`livekit`, Python SDK) при подключении **сначала пробуют путь `/rtc/v1`**,
а если сервер отвечает 404 — переходят на старый `/rtc`. LiveKit Server **v1.9.0** `/rtc/v1` не знает: 404 → запасной путь →
вход в комнату затягивался на 5–7 секунд (backend при этом отвечал за 40 мс, ASR входил за секунду). Поэтому:

- **старый сервер опасен**, новый — нет: клиенты обратно совместимы с более новыми серверами;
- совместимость проверяется не по номеру версии, а **практикой** (`scripts/smoke-test.sh`, а также админка → «Состояние системы» → «Скачать диагностический отчёт»). Проверок две, и их нельзя путать:
  1. **Маршрут `/rtc/v1` существует.** Запрос без параметров SDK (`join_request`) LiveKit 1.13 отклоняет ответом **`400` «join_request is required»** — это и значит «маршрут есть» (норма, OK).
     Устаревший сервер ответил бы `404` — тогда SDK тратит секунды на запасной путь `/rtc`.
  2. **Настоящий WebSocket Upgrade на `/rtc` с токеном → `101`.** Проверяется напрямую у LiveKit, через web-контейнер и через публичный адрес.
  Диагностика сравнивает ответ «напрямую» и «через прокси»: виноват прокси только если напрямую `101`, а через него — нет (нужны `proxy_http_version 1.1`, `Upgrade`, `Connection upgrade`, путь `/livekit/`).
  Если и напрямую ответ не `101` (например, `400`), это ответ самого LiveKit (токен, ключи, версия), а не прокси.

## Политика: проверенный и закреплённый комплект, новые версии — только через ревизию релиза

| Что | Как задано | Почему |
| --- | --- | --- |
| Python-зависимости (все, включая транзитивные) | `requirements.txt` — допустимые диапазоны; **точные версии — `constraints.txt`** (`scripts/deps.py freeze`), образ ставится `pip install -c constraints.txt` | сборка и «Полная пересборка» воспроизводят проверенный комплект релиза, а не «самые новые в диапазоне» |
| npm-зависимости | `package.json` + `package-lock.json` (`npm ci`) | воспроизводимая сборка |
| Базовые образы (Python, Node, nginx, Alpine, PostgreSQL, Redis) | тег **и digest** (`ARG *_IMAGE`, `compose.yml`) | исправления безопасности образов приходят ревизией релиза (`deps.py pin-images`) и Dependabot |
| LiveKit Server, SIP-служба, SDK | закреплены на проверенном комплекте (`deployment/compat.env`) | воспроизводимость и защита от несовместимости: старый сервер даёт 404 на `/rtc/v1` |
| PostgreSQL 16, Redis 7 | **мажорная версия закреплена намеренно** (отсрочка DEP-4, DEP-5) | смена мажорной версии PostgreSQL требует миграции каталога данных |
| GigaAM | закреплённый коммит (`GIGAAM_GIT_COMMIT`), ставится **без** зависимостей (нужные — в `requirements.txt`) | API модели не стабилен; onnx из его зависимостей имеет известные уязвимости и проекту не нужен |

Каждый релиз начинается с ревизии: `scripts/deps.py review` показывает всё, что вышло нового; по каждой версии принимается решение «включить после проверки» или «отложить с причиной, задачей и датой» (см. [DEPENDENCIES.md](DEPENDENCIES.md)). `release.sh` без этого не выпускает версию.

## Как обновлять

```bash
scripts/check-updates.sh        # что вышло нового (ничего не меняет)
scripts/update.sh               # установить проверенный комплект следующего релиза (образы пересобираются, если изменились исходники или зависимости)
scripts/update.sh --force-build # полная пересборка: воспроизводит комплект ТЕКУЩЕГО релиза (точные версии, digest образов), новые версии не ищет
scripts/smoke-test.sh           # убедиться: маршрут /rtc/v1 есть, WebSocket /rtc → 101, ASR, LDAP, TLS, порты
```

Новые версии компонентов приходят **только с релизом** после ревизии (см. выше и [DEPENDENCIES.md](DEPENDENCIES.md)): пересборка на сервере их не подтягивает. После обновления `update.sh`
сверяет версии **работающих** контейнеров с манифестом релиза (`scripts/deps.py postcheck`); расхождение критичных компонентов — ошибка обновления. Если новая версия что-то сломала,
сообщите разработчикам: решение — отложить её в манифесте с причиной (`deferred`) или откатить (`scripts/rollback.sh`).
