# Записи встреч

## Что сохраняется

| Запись | Для чего | Кому доступна | Формат |
| --- | --- | --- | --- |
| **Общая аудиозапись встречи** | прослушать встречу целиком | всем, кто видит встречу в «Истории» | M4A (AAC 56 кбит/с, моно) |
| Файлы участников | расшифровка речи, разбор спорных мест | только администратору | WAV 16 кГц, моно |
| **Общая видеозапись** (с 0.48.0) | посмотреть встречу целиком: участники и показ экрана | всем, кто видит встречу в «Истории»; скачивание — по правам | MP4 (H.264 + AAC), пишет LiveKit Egress — [VIDEO_RECORDING.md](VIDEO_RECORDING.md) |

Общая аудиозапись собирается **один раз**, в фоне, после завершения встречи: завершение и формирование протокола её не ждут. В «Истории» запись
появляется со статусом «формируется…» и обновляется сама. Если сведение не удалось (нет `ffmpeg`, не хватило места), встреча не страдает: файлы участников
остаются, в журнале событий появляется `meeting_mix_failed`, в блоке «Записи» видна причина.

### Как сохраняется время

ASR-сервис пишет сырой звук каждого участника непрерывной дорожкой: паузы заполняются тишиной, начало дорожки фиксируется отметкой времени (`<identity>.t0`).
Сведение (`backend/app/services/mixdown.py`) сдвигает каждую дорожку на её отметку и складывает в одну (`ffmpeg`: `adelay` + `amix` без нормализации + `alimiter`):
паузы сохраняются, одновременная речь звучит одновременно, обрезаний нет (мягкое ограничение пиков, а не срезание). Дорожка без отметки времени (записана
версией до 0.14.0) ставится в начало встречи — сдвиг, которого мы не знаем, не выдумывается.

### Режим записи комнаты

«Настройки комнаты → Режим → Запись и транскрибация → Общая запись встречи»:

* **Только аудио** (по умолчанию) — общая аудиозапись;
* **Аудио и видео** — зарезервировано и по-прежнему отклоняется (409): видеозапись включается отдельным режимом комнаты «Видеозапись встречи»
  (выключена / вручную / автоматически), см. [VIDEO_RECORDING.md](VIDEO_RECORDING.md);
* **Без общей записи** — общая запись не формируется. Файлы участников для расшифровки сохраняются в любом случае.

Аварийный выключатель для всей установки: переменная `MEETING_MIX_ENABLED=false`.

## Воспроизведение

Страница завершённой встречи → блок «Записи» → «Слушать». Плеер открывается поверх страницы: пауза, перемотка по шкале, время, громкость, скорость
0,75×–2×, клавиатура (пробел, ←/→, ↑/↓, M, «,» «.», Esc), закрытие крестиком или Esc, «Скачать» — только тем, кто может редактировать протокол встречи
(администратор, руководитель комнаты, организатор). При закрытии воспроизведение останавливается.

API (`backend/app/api/media.py`):

* `GET /api/v1/meetings/{id}/media` — список записей; файлы участников возвращаются только администратору;
* `GET /api/v1/meetings/{id}/media/{rid}/stream` — поток файла с поддержкой `Range` (206, 416, `Accept-Ranges`); `?download=true` — скачивание;
* права проверяются на сервере для каждого запроса (как для истории встречи); запись другой встречи по чужому идентификатору не открывается (404);
* ответы: `409` — запись ещё формируется или не удалась, `410` — файл удалён из хранилища, `503` — хранилище недоступно;
* физические пути и адреса SMB наружу не выдаются; файл читается кусками по 1 МиБ — целиком в память сервера не попадает ни при воспроизведении, ни при выгрузке.

## Плеер: волна, субтитры, стенограмма, мини-плеер

**Окно.** `frontend/src/player/PlayerHost.tsx` живёт в оболочке приложения (рядом со страницами, а не внутри страницы истории), поэтому единственный медиа-элемент не пересоздаётся при смене раздела, режима
(полный ↔ мини) и перетаскивании. Окно не затемняет страницу (`z-index` ниже модальных окон: диалоги и меню перекрывают плеер, а не наоборот), перетаскивается за заголовок, не уходит за экран целиком,
меняет размер, положение и размер запоминаются (`localStorage`: `pg:player:rect:*`, настройки — `pg:player:prefs`). Открытие другой записи заменяет текущую (ключ окна — id записи). Клавиши и Esc
обрабатываются только при фокусе внутри плеера. При входе в комнату встречи запись ставится на паузу и плеер сворачивается (иначе звук записи попал бы в микрофон).

**Волна.** `services/waveforms.py`: ffmpeg (`astats` по окнам 100 мс на 8 кГц) → один байт на 100 мс, логарифмическая шкала (0 — ≤ −60 дБ). Считается один раз при готовности записи (после сборки общей
записи и регистрации файлов участников, пока файлы на локальном диске), для старых записей — по первому запросу в фоне. Хранится в таблице `recording_waveforms` (по записи, а не по файлу — перенос
между хранилищами её не затрагивает). 3 часа ≈ 108 000 байт, расчёт ≈ 20 с. API: `GET /meetings/{id}/media/{rid}/waveform` → `{status, bucket_ms, peaks (base64)}` или 202 `processing`;
права те же, что у воспроизведения.

**Субтитры.** `GET /meetings/{id}/media/{rid}/subtitles` — реплики стенограммы, пересчитанные на шкалу записи: `start = реплика.started_at − запись.started_at`. У общей записи `started_at` — время самого
раннего файла участника; у файла участника — время начала этого файла (записывается с 0.14.0). Для общей записи — все участники с именами, для записи участника — только реплики этого участника
(`participant_identity`). Нет `started_at`, нет реплик или реплики вне записи — `available=false` с причиной (`no_timeline`, `no_transcript`, `no_overlap`), приблизительный текст не подставляется.
Один и тот же слой показывает субтитры поверх волны (аудио) и поверх видео (когда появится видеозапись).

## Хранение и очистка

* Общая запись — такая же запись (`recordings`), как и файлы участников: выгружается во внешнее хранилище, удаляется вместе с ними («Удалить записи», срок
  хранения аудио в комнате), видна в сверке хранилища.
* Пока общая запись собирается, очистка по срокам не удаляет файлы участников этой встречи. Сведение, прерванное перезапуском сервера (старше 6 часов),
  помечается неудавшимся и очистку не блокирует.
* Публичный API (`/api/public/v1`) по-прежнему отдаёт только файлы участников; общая запись в него не включена. Список «Файлы участников» на странице встречи
  и прежний админский список тоже показывают только их; общая запись — в блоке «Записи» и в общем списке администратора (`kind = mix_audio`).

## Требования

* `ffmpeg` в образе backend (ставится `backend/Dockerfile`); при запуске без образа укажите путь в `FFMPEG_BIN`.
* Миграция базы данных 0022 (поля записи: вид, тип, статус, отметка начала, контрольная сумма).

## Видеозапись

Реализована в 0.48.0 службой **LiveKit Egress** (запрос `StartEgress` с `TemplateSource`, раскладка `speaker`: экран — основное место, участники — миниатюры).
Режимы комнаты, установка службы, пределы, диагностика и список непроверенного — в [VIDEO_RECORDING.md](VIDEO_RECORDING.md). Видео — обычная запись встречи
(`recordings.kind = mix_video`, `has_video`, `egress_id`): тот же плеер, скачивание, выгрузка, перенос и копия. Для встреч, прошедших до 0.48.0, видео не создаётся.

## Как это проверено

* Автотесты backend и ASR — см. HISTORY.md.
* Живой сценарий `tests/live/scenario_recordings.py` — плеер, Range, права (синтетические дорожки, настоящие ffmpeg и браузер).
* Живой сценарий `tests/live/scenario_recordings_real.py` — **настоящий звук через LiveKit**: два браузера «говорят» русской речью (SAPI, голоса Pavel и Irina) в
  микрофон через WebRTC (Opus, шумоподавление, DTX), реплики частично накладываются, между ними пауза; запись ведёт настоящий код ASR-воркера (без модели
  распознавания); затем встреча завершается обычным путём, собирается общая запись и `analyze_mix.py` сверяет её с дорожками. Ограничение: физические
  микрофоны и их эхоподавление так не проверяются — только тракт «браузер → LiveKit → запись → общая запись».
