# Миграции БД и резервное копирование

## Правила

1. Схема БД меняется **только** через Alembic (`backend/migrations/versions`).
   Ручные `CREATE/ALTER` в рабочей БД — ошибка процесса.
2. Тест `backend/tests/test_migrations.py` проверяет, что `alembic upgrade head`
   даёт схему, совпадающую с моделями SQLAlchemy (нет «дрейфа»), и что цепочка
   миграций линейна (одна голова).
3. Миграции пишем «расширяющими» (expand/contract): сначала добавляем
   колонки/таблицы (совместимо со старым кодом), удаляем/переименовываем
   только в более позднем релизе, когда ни один работающий код их не использует.
   Это даёт возможность откатить код без отката БД.
4. Деструктивные миграции (DROP, смена типа с потерей данных) требуют
   отдельной пометки в сообщении коммита и обязательного backup.
5. `downgrade()` пишется, где это возможно, но **автоматический откат БД
   не выполняется** ни одним скриптом.

## Поведение скриптов

- `update.sh` (и обёртка `deploy.sh`): если между версиями есть изменения в `backend/migrations/versions`
  — делает `backup.sh --label pre-<sha>` до `alembic upgrade head`.
- `rollback.sh`: возвращает код/образы без пересборки. **Git rollback ≠ database rollback:** если текущая ревизия БД неизвестна коду целевой версии
  (после обновления была применена миграция), откат ОСТАНАВЛИВАЕТСЯ (код 3) — старый образ поверх новой схемы небезопасен. Полноценный возврат данных —
  `restore.sh` из дампа `pre-<sha>`, затем откат кода.

## Резервное копирование

- `scripts/backup.sh` — `pg_dump -Fc`, ротация `--keep N` (только файлы этого проекта).
- Записи аудио и экспорты протоколов — отдельно (`--with-recordings`) или
  системным резервным копированием `DATA_ROOT`.
- `APP_MASTER_KEY` хранить отдельно от дампов: без него зашифрованные
  настройки в восстановленной БД не расшифровываются.
- Регулярность: cron/systemd timer на сервере — вне репозитория (пример в
  DEPLOYMENT.md не навязывается).
