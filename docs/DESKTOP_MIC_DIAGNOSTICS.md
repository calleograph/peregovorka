# Микрофон в приложении для Windows: разбор причин и методика проверки

Документ для разработчиков и второй линии поддержки. Описывает, почему микрофон в приложении для Windows (Electron) может открываться хуже, чем в Edge, что уже сделано в сервере 0.51.0 и приложении 1.4.0, и как проверить это на настоящем компьютере с Windows.

**Состояние на 2026-10-29.** Анализ исходников Chromium и Electron выполнен. Классификация ошибок, повтор коротких отказов, журнал звука движка и сбор сведений Windows реализованы и проверены автотестами. Под Linux/Xvfb проверено, что Electron пишет журнал звука в файл. **На Windows ничего из этого не проверялось**: коды WASAPI, поведение Kaspersky и влияние повтора нужно подтвердить по методике ниже. Дефект не считается устранённым, пока нет сравнения Edge и приложения на одном компьютере.

## 1. Что выяснено

### 1.1. Повтор `WasapiInputDeviceInUseRetry` не объясняет разницу с Edge

Гипотеза была такая: в Chromium появился повтор открытия устройства при `AUDCLNT_E_DEVICE_IN_USE`, Edge его получил, а наш Electron нет.

- Изменение `ae2917f2` добавило в `media/audio/win/audio_low_latency_input_win.cc` повтор `IAudioClient::Initialize` (2 повтора по 50 мс) под флагом `kWasapiInputDeviceInUseRetry`.
- Флаг объявлен как `FEATURE_DISABLED_BY_DEFAULT`. Включался он только экспериментом Finch, а Finch в Electron не работает. Значит, даже в Chromium 152 (Electron 44.10) повтор выключен, пока его не включить ключом `--enable-features`.
- 2026-08-19 изменение откатили (`5b50c26e08`). В Chromium 156, на котором собраны Electron 45.x и текущий Edge, кода повтора нет.

Вывод: в текущих Edge и Electron этого повтора нет, поэтому разница не в нём. Включать флаг в приложении бессмысленно: в версиях после отката его нет.

### 1.2. Монопольная блокировка — реже, чем кажется

Chromium всегда открывает микрофон в режиме `AUDCLNT_SHAREMODE_SHARED`. Поэтому `AUDCLNT_E_DEVICE_IN_USE` (0x8889000A) возникает, только когда другая программа держит устройство монопольно, либо в короткое окно, пока Windows ещё не освободила устройство после нашего же закрытия. Монопольный захват чужой программой одинаково мешает Edge и приложению. Значит, если Edge работает, а приложение нет, причина, скорее всего, другая.

Blink (Chromium 152, `user_media_processor.cc`) передаёт причину отказа в тексте ошибки:

| Ошибка `getUserMedia` | Причина в WASAPI |
| --- | --- |
| `NotReadableError: Device in use` | `AUDCLNT_E_DEVICE_IN_USE` |
| `NotAllowedError: Permission denied by system` | `E_ACCESSDENIED` (конфиденциальность Windows или защитная программа) |
| `NotReadableError: Device was removed` | устройство пропало |
| `NotReadableError: Could not start audio source` | любой другой отказ |

До 0.51.0 интерфейс показывал любую `NotReadableError` как «микрофон занят другой программой» и отправлял человека к монопольному режиму, даже когда Windows сообщала совсем другое.

### 1.3. Защитные программы

В electron/electron#43524 Kaspersky блокировал микрофон приложению на Electron. Ошибка была `Could not start audio source`, а приложение не появлялось в списке программ, использующих микрофон. В Kaspersky Endpoint Security 12.x за это отвечает компонент «Предотвращение вторжений» (HIPS): по умолчанию аудиопоток получают только программы из группы «Доверенные». Edge подписан Microsoft и обычно попадает в доверенные. Приложение Peregovorka пока не подписано сертификатом издателя ([DESKTOP_SIGNING.md](DESKTOP_SIGNING.md)), поэтому KES может отнести его к ограниченным группам. Сейчас это самая вероятная причина того, что в Edge микрофон работает, а в приложении нет.

### 1.4. Наши собственные гонки

Страница встречи закрывает и сразу снова открывает микрофон в нескольких местах:

- проверка оборудования перед входом → вход;
- смена режима шумоподавления (поток пересоздаётся);
- смена микрофона;
- восстановление после пропажи устройства;
- «Подробная проверка микрофона».

Запросы `getUserMedia` могли идти одновременно, например проверка уровня и публикация LiveKit. Короткое окно, пока Windows освобождает устройство, даёт `Device in use` или `Could not start audio source` без какой-либо чужой программы.

## 2. Что сделано

| Где | Что |
| --- | --- |
| `frontend/src/micCapture.ts` | `micErrorKind` различает отказы по имени и тексту ошибки; `installMicCaptureGuard` выполняет запросы микрофона по одному и повторяет короткие отказы (`in_use`, `start_failed`, `aborted`) через 120, 350 и 800 мс. Отказы `NotAllowedError`, `NotFoundError` и другие не повторяются. Обёртка ставится один раз и покрывает и наши вызовы, и вызовы LiveKit |
| `frontend/src/mediaErrors.ts` | отдельный текст для каждой причины: «занят», «не запустился (защитная программа, драйвер)», «отключён», «запрещено системой» |
| `frontend/src/main.tsx`, `backend/app/api/client.py`, «Микрофон по клиентам» | события `mic_retry_recovered` (открылся со 2–4 попытки — признак гонки освобождения) и `mic_retry_failed` (повтор не помог) |
| `desktop/src/main/audiolog.ts` | журнал звука движка `chromium-audio.log` (`--enable-logging=file --vmodule=media_stream_manager=1`, ротация 4 МБ); раздел `audio` отчёта «Диагностика»: коды HRESULT из строк WASAPI с расшифровкой, последние 60 строк журнала (маскированы), защитные программы из Центра безопасности Windows, журнал доступа к микрофону `CapabilityAccessManager\ConsentStore\microphone\NonPackaged` |
| `desktop/src/common/media.ts` | причины `security_product`, `start_failed`, `removed`; при найденном Kaspersky — шаги для администратора KES |

## 3. Методика проверки на Windows

Нужны компьютер с Windows 10 или 11, Edge, приложение 1.4.0 или новее и сервер 0.51.0 или новее. На каждом шаге записывайте, что показала страница, и сохраняйте отчёты.

### 3.1. Что собирать

1. В Edge и в приложении: «Устройства…» → «Подробная проверка микрофона» → «Скопировать полный отчёт».
2. В приложении: «Настройки» → «Диагностика» → «Сохранить отчёт». Нужен раздел `audio`.
3. Текст ошибки на странице встречи, имя ошибки и сообщение (есть в отчёте подробной проверки).
4. Если стоит KES: журнал событий «Предотвращение вторжений» и группу доверия, в которую попал `Peregovorka.exe`.
5. Администратору: «Администрирование → Диагностика клиентов → Микрофон по клиентам», столбцы «открылся со 2–4 попытки» и «повтор не помог».

### 3.2. Сценарии

| № | Сценарий | Edge | Приложение |
| --- | --- | --- | --- |
| 1 | Микрофон свободен, вход во встречу | | |
| 2 | Микрофон занят другой программой в общем режиме (звонок в Teams или «Запись голоса») | | |
| 3 | Монопольный захват (программа записи с флажком монопольного режима, например Audacity с WASAPI exclusive) | | |
| 4 | Сразу после выхода из другой конференции | | |
| 5 | Смена микрофона во встрече; смена шумоподавления | | |
| 6 | Отключение и подключение USB-гарнитуры во время встречи | | |
| 7 | Повтор 1–6 с включённым KES; затем с `Peregovorka.exe` в группе «Доверенные» | | |

### 3.3. Как читать результат

| Признак | Что это значит |
| --- | --- |
| В `audio.wasapi` код `0x8889000A`, в Edge при том же сценарии тоже отказ | настоящая монопольная блокировка чужой программой |
| В статистике растёт «открылся со 2–4 попытки», пользователь отказа не видит | гонка освобождения устройства; повтор её закрывает |
| `Could not start audio source`, в `audio.wasapi` нет кода или код `0x80070005`; в `microphone_use` у приложения нет свежего `lastStart`, а у Edge есть; в `security_products` есть Kaspersky | запрос не дошёл до устройства: блокирует защитная программа |
| После перевода приложения в «Доверенные» сценарий 7 проходит | подтверждена блокировка KES; лечится политикой KES или подписью приложения |
| `Permission denied by system` | конфиденциальность Windows (Микрофон → доступ для классических приложений) или защитная программа |
| `Device was removed` или код `0x88890004` | устройство пропало: драйвер, USB, Bluetooth |
| В `audio.native_log` значение `false` | журнал звука не пишется (запуск со старым ярлыком или нет прав на каталог журналов) — сначала исправить это |

Повтор открытия не обходит настоящую блокировку. Если после повтора отказ остаётся, пользователь видит причину, а статистика увеличивает «повтор не помог».

## 4. Что осталось

- Подтвердить на Windows, что строки `WAIS … HRESULT` действительно попадают в `chromium-audio.log` при отказе (под Linux проверено только, что пишутся строки `MediaStreamManager`).
- Проверить сценарии 1–7, особенно с KES.
- Если подтвердится KES: подписать приложение сертификатом издателя ([DESKTOP_SIGNING.md](DESKTOP_SIGNING.md)) и описать правило KES для администраторов.
