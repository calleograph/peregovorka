# Как ИИ формирует протокол, резюме и карту разговора

Документ для разработчика и администратора: что и сколько раз спрашивается у модели, почему, какие бывают сбои и что видно в диагностике. Пользователю достаточно CHANGELOG.

## Принципы контракта с моделью

1. **Модель отдаёт содержание, оформление — наше.** Ни HTML, ни CSS, ни разметка страницы в ответе модели не нужны и не принимаются: Markdown или небольшой JSON по схеме превращаются в страницу детерминированным шаблоном (`services/glass_html.py`, `frontend/public/glassdoc.css`, одна копия стилей на сервере и в приложении, проверяет `test_glass_html.py`). Текст модели экранируется, ссылки — только http/https/mailto, страница отдаётся с политикой `default-src 'none'` и хешем единственного собственного скрипта.
2. **Один формат — без новых запросов к модели.** HTML, Word, PDF, Markdown, текст, письмо и публичный API берут один сохранённый результат (`protocols.content`, для карты — `conversation_maps.data`); смена формата модель не вызывает.
3. **Один запрос — один полный ответ там, где встреча помещается в контекст; на длинных — один запрос на фрагмент и никаких повторов целого.** Дефектный фрагмент повторяется отдельно (хвост или половины), всё остальное сохраняется.
4. **Протокол и карта независимы.** Ни один документ не требует другого. Повторное использование допускается только для уже проверенных промежуточных ответов (`meta.facts`) и только при побайтном совпадении запроса (тот же текст фрагмента, участники, схема, модель); нет совпадения — извлечение выполняется заново.
5. **Неполный результат не выдаётся за полный.** Ответ, оборванный по лимиту длины, помечается (`meta.truncated`, предупреждения, метка «обрезано», красная плашка в интерфейсе) и несёт пометку «Документ может быть неполным» во всех выгрузках, письмах и в публичном API (`incomplete: true`).

## Какой вариант контракта где используется

| Вариант | Где | Почему |
| --- | --- | --- |
| **A. Текст/Markdown на входе и выходе** | протокол и резюме внешней моделью (`protocol.external_mode = free`, по умолчанию) | Пользовательские и специализированные шаблоны (медицинские и т. п.) задают собственную структуру — её нельзя подменять универсальной схемой. Короткая встреча — ровно **один** запрос и один ответ. Длинная — заметки по фрагментам и один итоговый документ (N+1). Сбои: пустой ответ и обрыв диагностируются (ниже). |
| **B. Минимальная схема JSON (4 списка: темы, решения/предложения, поручения, вопросы)** | карта разговора; протокол и резюме в режиме `structured`; встроенная локальная модель | Нужны точные связи с репликами (время), участники, ответственные и сроки, которые код проверяет по тексту (`extraction.verify_pass`): ответственный — подтверждённое имя, срок — из реплики, решение — только если сказано «решили», предложение остаётся предложением. Один запрос на фрагмент вместо 4–5 проходов (было: темы, решения, поручения, вопросы, итог). Ограничения схемы (`maxItems`, `maxLength`) делают ответ заведомо короче потолка — обрывов практически нет; обрыв всё равно разбирается (`salvage_json`) и повторяется только неразобранный хвост. |
| **Гибрид** | структурный протокол: итоговый абзац — отдельный короткий запрос по уже проверенным пунктам | Итог не должен выдумывать: он пишется по проверенным пунктам, а не по сырой стенограмме. Не удался — документ остаётся без итога, но полным. |

Решение принято по структуре задачи и по замерам обращений (см. таблицу), а не по числу токенов: Markdown не гарантирует меньшего расхода, чем JSON.

## Измерения «до» и ограничения «после»

«До» — прежний выпуск 0.41.x, локальная Qwen3 1.7B (llama.cpp, процессор без AVX), синтетическая стенограмма «короткая» (8 минут, 6 770 знаков с заложенными фактами, `tests/perf/llm_pipeline_bench.py`, итог в `~/pg-work/bench`):

| Конвейер | Обращений | Оборвано по длине | Токены вход+выход | Время | Найдено заложенных фактов |
| --- | --- | --- | --- | --- | --- |
| протокол (структурный, прежний) | 2 (по одному на каждый из двух фрагментов) | 2 из 2 | 3 795 + 570 | 647,7 с | решения 2/2, поручения 0/2, вопросы 0/2 |
| карта (прежняя) | 2 | 0 | 3 431 + 748 | 625,9 с | тем 2/2, покрытие шкалы 0,73 |

Реальная карта пользователя (48 мин 38 с): 561,9 с, 12 частей, **34 повторных запроса**, 11 неразобранных фрагментов, 1 072 с не отнесены к темам, описание темы обрезано на полуслове (`[:520]`).

**«После» на тех же корпусах получить не удалось.** Процессор стенда без AVX даёт около 0,9 токена в секунду: один ответ в 450 токенов занимал 523 с, ответ до потолка 2 200 токенов — около 40 минут, и сервер модели обрывал соединение (`RemoteProtocolError`). Сравнение скорости и полноты на этой машине невалидно и на реальное оборудование не переносится. Что подтверждено запуском на подставной модели (количество обращений зависит только от структуры конвейера): внешний структурный протокол — **2** обращения вместо 5 (`test_doc_render`), на каждый фрагмент карты — 1 обращение, обрыв повторяет только хвост, неразобранный участок попадает на шкалу как «не разобрано», а не пропадает. Ускорение не заявляется: для него нужны замеры на настоящей модели и сервере.

## Пустой ответ модели

Причина разбирается по ответу провайдера (`integrations/llm.py`, `_parse_answer`, `_empty`), см. [LOCAL_LLM.md](LOCAL_LLM.md) — таблица кодов `empty_length`, `empty_refusal`, `empty_filtered`, `empty` и единственный ограниченный повтор. Самая частая причина у «рассуждающих» моделей — лимит ответа целиком уходит на мысли: `finish_reason=length`, `content` пуст. Бесконечных повторов нет.

## Карта: полнота и честность

* Описание темы — только целые предложения (`conv_map.whole_sentences`); не уместилось целое — сокращение с «…», видимое как сокращение.
* Число тем зависит от длительности встречи; сверх предела короткие темы собираются в «Прочие обсуждения» с полным перечнем (`members`) — важные не теряются.
* «Связанные обсуждения» — по смыслу (общие основы слов названия и описания), а не по соседству во времени; хронологию показывает шкала «Ход встречи».
* Не разобранные участки стенограммы отмечены штриховкой на шкале и названы текстом (`data.unprocessed`).
* Модель, число обращений, повторы и токены — только в «Диагностика формирования» для администратора; в файле карты и в письме их нет.
