# Паспорт встречи и восстановление материалов после переноса

Материалы встреч (записи, стенограммы, протоколы, схемы доски) лежат в файловых хранилищах, а их связи со встречами, комнатами, участниками и правами — в базе. Если хранилище перенесено на другой сервер или диск, а база восстановлена не полностью (или это новая база), файлы остаются на диске, но приложение их не показывает. Для таких случаев есть два механизма: **паспорт встречи** (метаданные рядом с файлами, пишутся сейчас) и **восстановление материалов** (поиск и возврат в приложение).

**Основной надёжный способ переноса остаётся прежним:** база данных и файловое хранилище переносятся вместе как согласованный комплект ([MIGRATIONS.md](MIGRATIONS.md), «Как сделать резервную копию и перенести сервер» в вики). Повторное сканирование — дополнение для исправления связей, а не гарантия восстановления всей истории по одним файлам.

## Паспорт встречи (`manifest.json`)

С выпуска 0.40.0 для каждой завершённой встречи в каждой папке хранилища, где у неё есть файлы (Audio, Transcripts, Protocols, Chat, Boards; при «плоской» раскладке без профиля — в общем каталоге встречи), создаётся и обновляется файл `manifest.json`. Он пишется в фоне после завершения встречи, формирования протокола и выгрузки записей; ошибка записи паспорта встречу, протокол и выгрузку не отменяет (событие `manifest_failed` в журнале хранилища). Для встреч, завершённых **до** 0.40.0, паспортов нет.

Содержимое (версия формата 1):

| Поле | Что это |
| --- | --- |
| `format`, `version` | `peregovorka-meeting-manifest`, `1` |
| `instance` | постоянный идентификатор установки (из APP_MASTER_KEY; ключ по нему не восстановить) |
| `created_at`, `folder`, `dir` | когда записан, папка хранилища, каталог встречи внутри неё |
| `meeting` | идентификатор встречи, начало, окончание, причина завершения, признаки транскрибации и записи |
| `room` | идентификатор, адрес (slug), название, постоянная или временная, политика доступа к истории (`history_access`) |
| `access` | права комнаты: списки доступа и руководителей (только ссылки: DN группы или GUID сотрудника), явные разрешения на встречу (идентификатор и GUID) |
| `participants` | идентификатор сотрудника, GUID каталога (если он из AD), время входа и выхода — без ФИО |
| `retention` | сроки хранения текста и аудио комнаты |
| `files` | для каждого файла папки: имя (относительно `dir`), вид (`audio_participant`, `audio_mix`, `transcript`, `protocol`, `summary`, `chat`, `board`), формат, размер и SHA-256 |
| `signature` | HMAC-SHA256 по каноническому JSON паспорта |

Паспорт **не содержит** паролей, токенов, ключей, адресов почты, ФИО, текстов встречи и содержимого файлов. Подпись — не шифрование: файл можно прочитать, но нельзя изменить незаметно.

**Подлинность.** Подпись вычисляется ключом, выведенным (HKDF) из `APP_MASTER_KEY`: поэтому ключ нужно хранить в резервной копии отдельно от данных (это уже требуется для расшифровки секретов). Простой JSON не доказывает права: содержимое каталога можно изменить руками. Состояния проверки: `valid` — подпись верна ключом этой установки; `unsigned` — подписи нет; `foreign` — подписан другим ключом (чужая установка или утраченный ключ); `invalid` — не паспорт или изменён после подписи. Доверяются **только** паспорта в состоянии `valid`.

## Восстановление (Администрирование → Хранение и журналы → «Восстановление материалов»)

Кнопка **«Найти и восстановить материалы встреч»** запускает фоновое сканирование хранилищ, настроенных в «Хранилище документов встреч» и «Хранилище аудиозаписей» (можно ограничить подкаталогом и включить проверку контрольных сумм). Затем администратор просматривает отчёт, отмечает нужное и подтверждает восстановление.

Сценарий после переноса: подключить диск или хранилище → создать (или проверить) профиль хранилища и выбрать его в разделах хранилищ → запустить поиск → просмотреть отчёт → выбрать встречи → подтвердить → прочитать отчёт о восстановлении.

### Два режима

* **Достоверно (паспорт `valid`).** Восстанавливаются встреча (со своим идентификатором), её связь с комнатой, участники и явные разрешения — **только для существующих учётных записей**, найденных по GUID каталога либо внутреннему идентификатору (не по ФИО; отключённые и удалённые не получают доступ). Права комнаты не меняются, если комната найдена по идентификатору. Если комнаты нет, она создаётся **выключенной** с правами из подписанного паспорта (принимаются только записи, похожие на настоящие: группа — DN, сотрудник — GUID). Права просмотра встречи затем определяет обычная политика: участники по `history_access`, руководители комнаты, администратор, явные разрешения.
* **Предположительно (нет паспорта, чужая подпись, подпись нарушена, паспорт без подписи).** Материалы попадают в изолированную комнату «Восстановленные материалы (проверьте права)»: она выключена, видна только администратору (`history_access = admin`), без участников, разрешений и прав. Встреча создаётся под **новым** идентификатором: идентификатор из неподтверждённого файла не доверяется. Время начала берётся из пути (`Комната/ГГГГ-ММ-ДД, день/ЧЧ-ММ`) и помечено в отчёте как предположение. Администратор переносит встречу в нужную комнату сам, и это его решение фиксируется обычным аудитом изменения комнаты.

Права **не создаются по догадке и не переносятся между независимыми организациями**: паспорт чужой установки всегда восстанавливается как «предположительно».

### Что восстанавливается

| Материал | Как |
| --- | --- |
| Записи участников и общая запись | строки записей со ссылкой на файл в хранилище, размер и SHA-256; воспроизведение и скачивание — как у обычных записей (общая запись видна всем, у кого есть доступ к встрече, файлы участников — администратору) |
| Протокол, резюме | документ с текстом из файла |
| Стенограмма | документ с текстом из файла; **реплики с привязкой ко времени записи не воссоздаются** (по текстовому файлу это ненадёжно) |
| Схема доски | восстанавливается, если файл — разметка draw.io |
| Переписка встречи (`chat.txt`) | в чат **не восстанавливается**, остаётся файлом; в отчёте это сказано |
| Карта разговора | не восстанавливается |

### Безопасность и устойчивость

* **Источник только читается:** файлы не изменяются, не переименовываются и не удаляются даже при ошибках; проверено автотестом (снимок дерева файлов до и после).
* Чтение идёт через общий слой хранения: выход за каталог по `..` и символьным ссылкам невозможен, «ссылка» на чужой каталог пропускается.
* Контрольные суммы паспорта проверяются при восстановлении по каждому файлу; расходящийся (повреждённый) файл пропускается и попадает в отчёт. При сканировании по умолчанию сверяются наличие и размер; полная проверка сумм — по галочке.
* Фоновая работа: запрос только запускает задание; один обход ограничен по глубине (7) и числу каталогов (30 000); между каталогами и порциями чтения — паузы; перед каждым каталогом проверяется отмена. Одновременно выполняется одно задание на весь кластер; оборванное перезапуском сервера помечается как прерванное, и его можно запустить заново.
* **Идемпотентность:** повторный запуск не создаёт дублей встреч, записей и документов; изолированная область повторно по той же папке второй встречи не создаёт.
* Все действия пишутся в аудит (`restore.scan`, `restore.apply`, `restore.item`, `restore.finish`, `restore.cancel`) с идентификаторами и счётчиками, без содержимого.

### Совместимость со старыми версиями

Встречи, записанные до 0.40.0, паспортов не имеют: их можно найти по структуре каталогов (режим «предположительно»), но сведений об участниках и правах в файлах нет, поэтому они попадают только в изолированную область. Это ограничение по существу, а не недоработка: данных в файлах нет.

Проверено: pytest `backend/tests/test_manifest.py`, `test_restore.py` (подпись и подделка, чужой ключ, достоверное и изолированное восстановление, права, повтор, повреждённый файл, символьные ссылки, неизменность источника, права администратора, блокировка и отмена); `frontend/src/restoreView.test.ts`; страница в настоящем браузере на стенде. **Не проверено:** SMB-хранилище с большими архивами (только локальный профиль и общий слой хранения), нагрузка на сотни тысяч файлов, перенос между серверами с разными PostgreSQL.
