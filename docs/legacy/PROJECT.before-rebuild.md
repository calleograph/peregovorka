# PROJECT.md — Корпоративный AI-чат с доменной авторизацией

Этот файл — текущее состояние проекта. Читай его и HISTORY.md перед началом
любой работы. Обновляй этот файл после каждого изменения, которое меняет
архитектуру, файлы, зависимости или поведение. Не удаляй и не переписывай
HISTORY.md — только дописывай.

## 1. Назначение проекта

Внутренний PHP-сервис для безопасной работы сотрудников с внешними LLM
(OpenAI, Anthropic, OpenAI-совместимые API, в т. ч. polza.ai). Вход только
доменной учётной записью через LDAPS; доступ к каждой нейросети определяется
членством пользователя в доменных группах AD. Весь пользовательский текст и
содержимое файлов по умолчанию обязательно обезличивается внутренним
сервисом (DocClean или совместимый JSON API) перед отправкой во внешний LLM
— запрос с необезличенными данными наружу не уходит (fail closed).
Единственное осознанное исключение — явная галочка «не обезличивать» в
композере чата (см. «Пользовательский чат» ниже): доступна только тем
группам/пользователям, кому администратор точечно включил право
`allow_unanonymized`, требует подтверждения на каждое сообщение и
журналируется отдельным событием.

Исходный проект был сервисом штатной смены пароля Active Directory
(«Norbit»). Функциональность смены пароля и связанная с ней диагностика
Kerberos-only (kpasswd, Protected Users, C-хелпер) **полностью удалены**
23.09.2026 — см. HISTORY.md. LDAPS-инфраструктура, локальный аварийный
администратор, сертификаты, сессии, CSRF, rate limiting и журналы от
исходного проекта унаследованы и используются модулем LLM-чата напрямую.

## 2. Основная архитектура

```text
Пользователь
    │ HTTPS
    ▼
nginx / reverse proxy ──► PHP-FPM (www-data)
                              │
                              ▼
                     LDAPS bind + проверка
                     членства в разрешённых
                     группах AD (ChatAuthenticator)
                              │
                              ▼
                     AccessPolicy: группа → нейросети
                     (backend-проверка при каждом запросе)
                              │
                              ▼
                     AnonymizationGateway (fail closed)
                     DocClean api_text/api_file/api_download
                     ИЛИ произвольный JSON API
                              │
                              ▼
                     LlmGateway → адаптер провайдера
                     (OpenAI / Anthropic / OpenAI-compatible)
                     → внешний LLM API
```

Точки входа:

- `public/index.php` — доменный вход + пользовательский чат (главная страница `/`).
- `public/api.php` — JSON API чата (bootstrap, send, проекты, диалоги).
  Отдельно определяет реальное превышение `post_max_size` (PHP молча
  обрезает такое тело, `$_POST`/`$_FILES` остаются пустыми) — сравнивает
  `Content-Length` именно с настроенным пределом (`parseIniSize()`), а
  не просто с нулём: пустой POST-запрос без полей (например
  `delete_all_conversations`) — это нормальный, ожидаемый случай, а не
  усечённое тело, и не должен получать ответ 413.
- `public/admin/index.php` — административная панель (`/admin/`).
- `public/healthz.php` — health-check (только для localhost/доверенных адресов).
- `index.php`, `api.php`, `admin/index.php`, `admin/setup.php`, `healthz.php` в
  корне проекта — тонкие шлюзы в `public/` для развёртывания с document root
  в корне (см. README, раздел «Развёртывание»).

Модуль LLM-чата целиком лежит в `src/Llm/` и использует общие сервисы
исходного проекта (БД, сертификаты, сессии, CSRF, журналы) — отдельной
инфраструктуры не создаёт.

## 4. Используемые технологии

- PHP 8.2+, без фреймворка, PSR-4 автозагрузка (`App\` → `src/`).
- SQLite (`var/data/app.sqlite`) через PDO, WAL-режим.
- ext-ldap (LDAPS), ext-curl (обезличивание + внешние LLM), ext-zip/ext-dom
  (разбор DOCX/XLSX), ext-openssl, ext-mbstring, ext-session.
- Опционально на сервере: `poppler-utils` (pdftotext/pdftoppm),
  `tesseract-ocr` (+ языковые пакеты rus/eng) — для локальной обработки PDF
  и сканов, если файлы не передаются целиком в DocClean.
- PHPUnit 11 для тестов (composer dev-зависимость; проект может работать и
  без composer install — см. `vendor_autoload.php`).
- Фронтенд — vanilla JS (без сборки/фреймворков), IBM Plex Sans локально.

## 5. Важные настройки и зависимости

- Секреты (API-ключи LLM, пароль read-only сервисной учётки домена, токен
  сервиса обезличивания) — только в зашифрованном виде через `SecretBox`,
  ключ шифрования в `var/data/master.key` (0600) или `APP_MASTER_KEY`.
- `var/data`, `var/certs`, `var/logs`, `var/sessions`, `var/tmp` — вне
  document root, создаются автоматически при первом запуске.
- CA bundle (`var/certs/ca-bundle.pem`) собирается администратором из
  загруженных сертификатов, используется и для LDAPS, и опционально для
  HTTPS до сервиса обезличивания/внутренних LLM-шлюзов.
- CSP: `default-src 'self'`, без `unsafe-inline` — весь JS только во
  внешних файлах, инлайн-обработчиков событий нет.
- Профиль обезличивания по умолчанию — DocClean (`api_text`/`api_file`/
  `api_download`/`openapi`), альтернатива — произвольный JSON API с
  настраиваемыми именами полей.

## 6. Реализованные функции

### Пользовательский чат (`/`)
- Доменный вход (LDAPS bind + проверка членства в разрешённых группах),
  несколько доменов одновременно.
- Интерфейс в стиле ChatGPT: новый чат, поиск по чатам (названия +
  обезличенный текст), закреплённые чаты, история по дате последнего
  использования, проекты (инструкции + источники), светлая/тёмная тема,
  сворачиваемая боковая панель.
- Вид открытого проекта — три вкладки («Чаты» открыта по умолчанию,
  «Инструкции», «Источники»; переключение чисто визуальное —
  `switchProjectTab()`, все три панели уже загружены разом при открытии
  проекта, новых запросов при переключении нет). Раньше «Инструкции» и
  «Источники» были развёрнуты бок о бок одновременно, а список чатов
  проекта уезжал вниз за пределы видимой без прокрутки области —
  теперь на экране сразу то, что нужно чаще всего. И вид проекта, и
  «Управление данными» (ниже) закрываются явной кнопкой «×» в
  заголовке (`#projectViewClose`/`#dataManagerClose`) — возвращает на
  обычный пустой экран чата; раньше выйти можно было только кликнув
  на другой чат в сайдбаре.
- Список чатов проекта в сайдбаре реально скрывается в свёрнутом
  состоянии (`grid-template-rows: 0fr`) — чаты обёрнуты в
  `.gpt-project-sub-inner` (`min-height: 0`) внутри `.gpt-project-sub`,
  иначе высота грид-строки не схлопывалась до нуля и чат оставался
  видимым даже при свёрнутой папке проекта.
- Источники проекта — клик по источнику разворачивает его реально
  сохранённый (уже обезличенный) текст прямо в интерфейсе
  (`GET project_source_text`, `ProjectRepository::sourceText()`,
  моноширинный превью-блок со своей прокруткой) — способ убедиться, что
  обезличивание действительно произошло, без слепого доверия. Текст
  подтягивается лениво при первом раскрытии, не вместе со списком
  источников. Перетаскивание сразу нескольких файлов на панель
  источников добавляет каждый отдельным источником последовательными
  запросами (до 5 за раз, `MAX_FILES`, как и в композере чата) —
  раньше принимался только `files[0]`, остальные перетащенные файлы
  молча игнорировались. Пункт меню проекта переименован из «Открыть» в
  «Открыть проект» — точнее передаёт действие.
- Ограничения источников проекта: `project_sources_max_files`
  (по умолчанию 3) — новый лимит числа источников на проект, проверяется
  ДО обработки/обезличивания файла в `ChatService::addProjectSource()`
  (`ProjectRepository::sourceCount()`); `project_sources_max_chars`
  снижен с 100000 до 30000 по умолчанию. Оба лимита защищают от одной и
  той же проблемы: `ProjectRepository::contextFor()` добавляет ВЕСЬ
  текст источников целиком в системный промпт КАЖДОГО запроса в этом
  проекте (`LlmGateway::complete()`), без учёта реального контекстного
  окна конкретной модели — компактные модели легко получали `bad_request`
  от внешнего API при нескольких/крупных источниках. Ограничение числа
  файлов само по себе не решает проблему (несколько крупных файлов
  всё ещё могут превысить контекст) — отсюда именно снижение суммарного
  символьного лимита как основная защита, а лимит числа файлов — более
  понятный пользователю ориентир поверх неё. UI показывает оба лимита
  в счётчике («2 / 3 файла · 12000 / 30000 симв.») и явно предупреждает
  в подсказке, что стоит использовать короткие текстовые источники, а
  не тяжёлые многостраничные файлы.
- Инструкции проекта — именованные блоки коротких правил поведения
  модели (вкладка «Инструкции», кнопка «+ Добавить блок инструкций»)
  вместо одного текстового поля. Каждый блок — самостоятельная запись в
  `llm_project_sources` (`source_type = 'instruction'`, тот же
  просмотр/удаление, что и у источников-документов), со своими
  независимыми лимитами: `project_instructions_max_blocks` (по
  умолчанию 5 блоков) и `project_instruction_max_chars` (по умолчанию
  2000 символов на ОДИН блок — не суммарно, блок задуман коротким
  правилом, а не документом). `ProjectRepository::contextFor()`
  собирает блоки инструкций отдельно от источников: без нумерации
  (`[Инструкция: Название]`) — это правила, а не документы;
  источники по-прежнему нумеруются (`[Источник N: Название]`).
  Устаревшее единое поле `llm_projects.instructions_z`
  (`setProjectInstructions()`, ещё используется как API-эндпоинт
  `project_update` с полем `instructions`, для обратной совместимости)
  автоматически переносится в первый именованный блок «Основные
  инструкции» при первом чтении проекта или сборке контекста
  (`ProjectRepository::migrateLegacyInstructions()`, идемпотентна) —
  ничего не теряется молча. Явно рассмотрен и отклонён вариант
  автоматического сжатия загруженных файлов через саму LLM в контекст
  («источники контекста») — риск непредсказуемой потери данных при
  суммаризации, дополнительная стоимость/задержка на каждый файл и
  необходимость выбора отдельной модели для сжатия перевесили выгоду
  по сравнению с уже реализованными явными лимитами.
- Автовыбор единственной доступной нейросети, выбор при нескольких. Если
  администратор пометил одну из нейросетей «по умолчанию»
  (`llm_providers.is_default`, кнопка в разделе «Подключения LLM API») —
  именно она выбрана в выпадающем списке при открытии чата (если она
  доступна конкретному пользователю); иначе, как и раньше, первая по
  алфавиту. Ровно одна нейросеть может быть «по умолчанию»
  (`ProviderRepository::setDefault()` сбрасывает флаг у остальных).
- Загрузка файлов: TXT, CSV, TSV, MD, LOG, DOCX, XLSX, PDF, изображения
  (PNG/JPG/TIFF/BMP) — с OCR для сканов. В композере чата можно приложить
  до 5 файлов разом (`ChatService::MAX_UPLOADS`) — перетаскиванием сразу
  нескольких файлов или по одному; при превышении лимита принимаются
  первые 5, об остальных показывается предупреждение (заявка не
  блокируется). Панель «Источники» проекта остаётся одно-файловой.
  Перетаскивание (drag-and-drop) в окно ввода сообщения и в панель
  «Источники» проекта; подсвечивается только сама зона ввода/панели
  (`.gpt-composer-wrap`/`.gpt-panel`), а не весь экран — события
  перетаскивания слушаются на широкой области (`.gpt-main`), подсветка
  ограничена узким целевым элементом.
- Кнопка копирования текста под каждым ответом ассистента (как в
  ChatGPT) — появляется по наведению на сообщение, копирует через
  `navigator.clipboard` с фоллбэком на `execCommand('copy')`, кратко
  показывает галочку после успешного копирования. Копируется исходный
  markdown-текст (не отрендеренный HTML) — так вставка сохраняет
  разметку там, где она поддерживается.
- Ответы нейросети рендерятся из markdown в разметку (не как сырой
  текст): заголовки, **жирный**/*курсив*, `инлайн-код`, ссылки
  (`target="_blank" rel="noopener noreferrer nofollow"`), нумерованные/
  маркированные списки, цитаты (`>`), таблицы, горизонтальная линия —
  поверх уже существующих блоков кода (```). Свой минимальный
  парсер (`renderInline()`/`renderMarkdownBlock()` в `chat.js`), а не
  внешняя библиотека — CSP (`script-src 'self'`) не пускает сторонние
  CDN, а вся сборка DOM идёт через `createElement`/`textContent`
  (никогда `innerHTML`), поэтому контент нейросети остаётся безопасным
  по построению, без отдельной санитизации.
- Отправка сообщения без обезличивания — только для групп/пользователей
  с явным правом `llm_domain_groups.allow_unanonymized` (настраивается в
  админке, раздел «Доступ к чату», таблицы групп/отдельных пользователей)
  ЛИБО с личным правом `llm_users.allow_unanonymized` (та же таблица,
  колонка «Без обезличивания» в матрице «Индивидуальный доступ вошедших
  пользователей» — только для уже входивших в чат; `AccessPolicy::
  canSkipAnonymization()` объединяет оба источника, как и права на
  нейросети). В композере рядом с кнопкой
  «Отправить» появляется компактная красная галочка «не обезличивать»
  (`#skipAnonToggle`, виден только тем, у кого есть право — атрибут
  `data-can-skip-anonymization`/`can_skip_anonymization` из bootstrap);
  сбрасывается автоматически после каждой отправки — решение принимается
  заново на каждое сообщение, не залипает. При включённой галочке текст
  сообщения и вложения уходят в LLM Gateway напрямую, минуя
  `AnonymizationGateway` целиком (файлы — только локальное извлечение
  текста, `FileProcessor::process()`, без похода в сервис обезличивания
  даже целиком через `api_file`); сообщение сохраняется в истории в
  открытом виде (`llm_messages.unanonymized = 1`) и помечается в
  интерфейсе («Отправлено без обезличивания», красным). Каждая такая
  отправка — отдельное событие аудит-лога `LLM_SEND_UNANONYMIZED`;
  попытка без права — `LLM_UNANONYMIZED_DENIED` и отказ `403` (проверка
  дублируется на backend в `ChatService::send()`, не только в UI).
- Индикатор расхода лимита токенов.
- Плавающая кнопка «к последнему сообщению» и боковые точки быстрого
  перехода к своим последним вопросам (с превью текста по наведению) —
  появляются при прокрутке истории чата вверх.
- Меню «⋯» у проектов в боковой панели (переименовать, открыть, закрепить/
  открепить, удалить) — проекты с закреплением сортируются наверху списка,
  аналогично уже существующему закреплению чатов.
- Клик по названию проекта в боковой панели разворачивает/сворачивает
  список его чатов прямо в сайдбаре (аккордеон с плавной CSS-анимацией
  высоты через `grid-template-rows`; переключение класса точечное, без
  пересоздания DOM-узла — иначе анимировать нечего) — открытие самого
  проекта (окно с инструкциями/источниками) доступно только через «⋯» →
  «Открыть».
- При ответе сервера с кодом ошибки `csrf` (устаревший CSRF-токен —
  например, вкладка была открыта очень долго) показывается один явный
  баннер с кнопкой «Обновить страницу», а не только текст ошибки.

### Backend-логика
- `ChatAuthenticator` — LDAPS-вход + рекурсивная проверка членства в группах
  (тот же механизм `LDAP_MATCHING_RULE_IN_CHAIN`, что для группы админов).
- `AccessPolicy` — права «группа → нейросети» проверяются на backend при
  каждом запросе; подмена `provider_id` в запросе доступа не даёт.
  `AccessPolicy::canSkipAnonymization()` — тем же принципом (объединение
  прав всех групп пользователя) проверяет право отправлять без
  обезличивания; `ChatService::send()` перепроверяет его на backend
  независимо от того, что показал/скрыл фронтенд.
- `AnonymizationGateway` — fail closed; DocClean или произвольный JSON API;
  файл целиком в `api_file` либо локальное извлечение + `api_text`.
- `LlmGateway` — адаптеры OpenAI/Anthropic/OpenAI-compatible; повторная
  проверка прав перед каждым внешним запросом.
- Роутинг у мультипровайдерных шлюзов (тип OpenAI-compatible, например
  polza.ai) — два взаимоисключающих режима, задаются в форме нейросети:
  - `llm_providers.routing_provider` — жёстко фиксирует конкретный бэкенд
    (например `DeepInfra`/`dekallm/fp8` у polza.ai). Подставляется как
    `provider: {"only": [...]}`.
  - `llm_providers.sort_by_price` (+ необязательный
    `max_price_per_mtoken`, ₽ за млн токенов, + `allow_fallbacks`,
    по умолчанию включён) — автовыбор самого дешёвого доступного
    маршрута. Подставляется как `provider: {"sort": "price",
    "allow_fallbacks": bool, "max_price": {"prompt": X, "completion": X}}`
    — формат подтверждён документацией Polza (`POST
    /v1/chat/completions`, объект `provider`). `max_price` — жёсткий
    фильтр: если ни один маршрут не укладывается в потолок цены, шлюз без
    `allow_fallbacks` отклоняет весь запрос (выглядит как обычная ошибка
    «внешний сервис отклонил запрос», а не как «цена не найдена») — при
    включённом `allow_fallbacks` в этом случае берётся любой доступный
    маршрут вместо отказа. `sort: "price"` — это подсказка шлюзу, а не
    гарантия: в моменте может быть выбран не абсолютно самый дешёвый
    маршрут (доступность/задержка конкретных бэкендов у Polza тоже
    влияют на выбор).
  Все три поля реализованы в `ChatCompletionsAdapter::buildRequest()`.
  Для типов OpenAI/Anthropic не показываются (собственные API
  поставщика, не шлюз).
- `FileProcessor` — сигнатуры файлов проверяются по содержимому (не по
  расширению), OOXML разбирается с лимитами против zip-бомб, временные
  файлы удаляются в `finally` при любом исходе.
- `ConversationRepository`/`ProjectRepository` — изоляция истории по
  `owner_key`, сжатие длинных записей (DEFLATE) перед сохранением в SQLite.
- `UsageLimiter` — лимиты токенов по приоритету: ручной override пользователя
  (обратная совместимость) → персональная категория лимита → самая щедрая
  категория среди групп пользователя → категория лимита по умолчанию →
  устаревшие общие настройки чата (`ChatSettings`, если категорий вообще не
  заведено). Расход не переносится на следующий период (сгорает).
- `LimitCategoryRepository` (`llm_limit_categories`) — именованные категории
  лимита («Базовый», «Расширенный»...), ровно одна помечена как категория по
  умолчанию для новых пользователей чата; удалить категорию по умолчанию
  нельзя, пока не назначена другая. При обновлении существующего стенда
  миграция один раз создаёт категорию «Базовый» из прежних общих настроек
  лимита, чтобы поведение не менялось скачком.
- `UserProviderRepository` (`llm_user_providers`) — индивидуальный доступ
  пользователя чата к нейросети, второй тип «субъекта прав» в дополнение к
  доменным группам (`llm_group_providers`). Не расширяет круг тех, кто может
  войти в чат (для входа по-прежнему нужно членство в разрешённой группе
  домена) — только список нейросетей, доступных уже вошедшему пользователю.
  `AccessPolicy::allowedProviders()` объединяет права групп и персональные.
- `StorageQuotaService` — квота хранения (МБ) на пользователя, задаётся тем
  же механизмом категорий лимита, что и токены (`llm_limit_categories.storage_mb`,
  приоритет идентичен `UsageLimiter`: персональная категория → групповая →
  по умолчанию → без ограничения). Единица учёта — фактический размер
  обезличенного текста в SQLite (`LENGTH(content)+LENGTH(content_z)` по
  сообщениям + `LENGTH(content_z)` по источникам проектов), а не файлы:
  исходные загруженные файлы на диске не хранятся вообще — `FileProcessor`
  обрабатывает их во временном каталоге и удаляет в `finally` сразу после
  извлечения текста/обезличивания (это архитектурное решение существовало
  и раньше, до появления квоты). При превышении квоты `ChatService::send()`/
  `addProjectSource()` отклоняют НОВОЕ содержимое с кодом
  `storage_quota_exceeded` (HTTP 507) и ссылкой на самостоятельную очистку —
  уже сохранённые данные не блокируются и не трогаются автоматически.
- Раздел «Управление данными» в чате (клик по индикатору хранилища в
  сайдбаре) — пользователь сам видит статус квоты и список своих чатов с
  чекбоксами, может удалить выбранные или всю историю целиком
  (`POST bulk_delete_conversations` / `POST delete_all_conversations`).
  Список чатов и панель хранилища — в карточках с явной рамкой/тенью
  (`.gpt-panel`), список чатов ограничен собственной прокруткой
  (340px), а не панелью в 50% высоты экрана. Кнопки удаления после
  подтверждения автоматически возвращаются в обычное состояние через
  4 секунды, если не кликнуть второй раз (иначе состояние
  «точно удалить?» оставалось навсегда, и следующий несвязанный клик
  удалял бы без предупреждения). Успех/ошибка операции показывается
  независимым от текущего экрана всплывающим уведомлением
  (`showStatusToast()`, крепится к `document.body`) — обычный `toast()`
  пишет в ленту `#chatMessages`, невидимую, пока открыта любая другая
  панель (управление данными, вид проекта).
- `InactivityCleanupService` — фоновая (запускается лениво, как и
  `UsageLimiter::purgeOldUsage`, со случайной вероятностью при чьём-либо
  входе) зачистка содержимого пользователей, не заходивших дольше порога
  (`ChatSettings.inactivity_content_purge_days`, по умолчанию 90 дней, 0 —
  отключено): текст сообщений и источников проектов обнуляется, сами
  диалоги/проекты (заголовки, структура истории) остаются видны.

### Административная панель (`/admin/`)
Меню сгруппировано по смыслу (`templates/admin/layout_top.php`, `$sectionGroups`):

- **Обзор**: Состояние, Состояние сервисов.
- **LDAP**: LDAP-подключения, Доступ к админ-панели.
- **Доступ к чату**: Доступ к чату.
- **Нейросети**: Подключения LLM API, Категории лимитов.
- **Пользователи**: Пользователи чата.
- **Система**: API обезличивания, Журналы, Настройки.

Локальный аварийный администратор и вход доменной учётной записью из
группы администраторов — без изменений от исходного проекта.

**Поиск по глобальным настройкам** (как в Moodle) — в шапке каждой
страницы админки (`templates/admin/layout_top.php`) есть поле поиска
(`#settingsSearchInput`), которое ищет по короткому латинскому коду
настройки, её названию и разделу; результат ведёт по ссылке
`{url раздела}#{id поля}`, после перехода поле на 2.2 с подсвечивается
пульсацией (`initSettingsSearch()`/`highlightSettingsAnchor()` в
`app.js`, CSS `[data-settings-highlight]`). Индекс — единственный файл
`templates/admin/settings_index.php` (массив `{section, label, anchor,
code}`), рендерится в шапку как JSON. Каждое проиндексированное поле
также несёт рядом со своим заголовком короткий код настройки
(`View::settingCode()`, класс `.field-code`) — тот же код, что найдёт
поиск. Индекс сознательно ограничен ДЕЙСТВИТЕЛЬНО глобальными
настройками (одна запись на всё приложение: «Настройки»,
«API обезличивания», общие параметры чата в конце «Подключения LLM
API», блок «Хранение» в «Пользователях чата», DN группы администраторов
в «Доступе к админ-панели») — поля динамических записей (нейросети,
LDAP-подключения, категории лимитов) НЕ индексируются, у них нет
постоянного id вне контекста конкретной записи; такие ищут по
имени/списком внутри своего раздела, как и раньше.

**«LDAP-подключения»** (`public/admin/sections/ldap.php`) — объединяет
бывшие разделы «Подключения» (`connections.php`) и «Сертификаты»
(`certificates.php`), которые редактировали одну и ту же таблицу
`ldap_configs` в двух разных местах. Одна карточка на LDAPS-подключение
содержит и сам коннект (host/base DN/протокол), и параметры для чата
(включение, сервисная учётка), «Сделать активным для входа
администраторов» и тест подключения (ручной bind или сервисной учёткой).
Сертификаты (общий CA bundle для всех подключений) — отдельным блоком
на той же странице.

**«Доступ к чату»** (`public/admin/sections/chat_access.php`) — кому
разрешён доступ к LLM-чату: доменные группы **и отдельные пользователи
домена** (виртуальная «группа из одного» — запись в `llm_domain_groups`
с `subject_type = 'user'`, `group_ref` = sAMAccountName вместо CN/DN;
`ChatAuthenticator`/`DomainGroupRepository::validateSamAccountName()`
резолвят её прямым сравнением имени, без обращения к группам AD, но
пользователь всё равно обязан пройти обычный вход по логину/паролю —
это право не заменяет аутентификацию). Категория лимита — у каждой
группы/пользователя. Ниже — единая матрица «домен × (группа или
пользователь) × нейросеть», включающая и обычные группы, и виртуальных
пользователей-групп, и индивидуальный доступ уже вошедших пользователей
чата (`UserProviderRepository`) — раньше это были три отдельных места
(`domains.php`, `llm_access.php`, матрица в `llm_users.php`). В таблицах
групп/отдельных пользователей есть колонка «Без обезличивания»
(`llm_domain_groups.allow_unanonymized`, `DomainGroupRepository::
setAllowUnanonymized()`) — выключена по умолчанию у всех; включение
разрешает членам этой группы/учётной записи ставить в чате галочку
«не обезличивать» (см. «Пользовательский чат» выше). Изменение права
пишется в аудит-лог отдельным действием `chat_access_unanonymized_change`.
Единая матрица прав на нейросети ниже дополнена последней колонкой «Без
обезличивания» — но только для строк «Индивидуальный доступ вошедших
пользователей»: это личное разрешение (`llm_users.allow_unanonymized`,
`UsageLimiter::setAllowUnanonymized()`), которое действует в дополнение
к групповому; для строк групп/отдельных пользователей ячейка неактивна
(«—»), так как их право задаётся в таблицах субъектов выше. Изменение
пишется как `llm_user_unanonymized_change`.

**«Категории лимитов»** — у каждой категории, помимо периода и токенов,
есть квота хранения в МБ (или «без ограничения»). **«Пользователи
чата»** — блок «Хранение» (retention/зачистка при неактивности) всегда
виден; устаревший способ задания лимита по умолчанию (период+токены
без категорий) свёрнут в `<details>`; таблица пользователей — выбор
лимита, столбец «Хранилище» (занято/квота), блокировка, кнопка
«Очистить историю» для полной очистки конкретного пользователя
администратором. Матрица индивидуального доступа к нейросетям отсюда
перенесена в «Доступ к чату» (устранено дублирование).

**«Настройки»** (бывшая «Система») — таймаут бездействия администратора
теперь настраиваемый (`admin_idle_timeout_minutes` в `app_settings`,
5–1440 минут, по умолчанию 240 = `SessionManager::DEFAULT_ADMIN_IDLE_TIMEOUT_SECONDS`);
доверенные reverse proxy; резервное копирование конфигурации LLM-чата.

Раздел «Настройки» → «Резервное копирование»: `ConfigBackupService`
(`src/Llm/Backup/`) экспортирует конфигурацию LLM-чата (домены и LDAPS-
подключения, разрешённые группы/пользователи, нейросети, права
«группа/пользователь → нейросеть», общие параметры чата) в один
ZIP-архив (`config.json` внутри) и восстанавливает её из загруженного
архива. Секреты (API-ключи нейросетей, пароли служебных учёток LDAP) в
архив не попадают ни в открытом, ни в шифрованном виде — после
восстановления администратор вводит их заново вручную. Импорт — upsert
по бизнес-ключам (имя домена/провайдера, group_ref + domain fqdn), а не
по числовым id: работает и на пустой БД, и поверх уже настроенного
стенда, повторный импорт того же архива не создаёт дублей.

### Журналы
Расширены существующие `app_log` (события `LLM_*`), `audit_log`
(административные действия `llm_*`, `anonymization_*`), `diagnostic_log`
(источники `chat_auth`, `anonymization`, `llm_gateway`, `file_processing`).
Пароли, API-ключи и содержимое запросов/файлов никогда не журналируются —
проверено юнит- и живыми smoke-тестами.

Раздел «Журналы» (`log.php`): фильтр категорий вкладки «Все события»
детализирован по точным значениям `LlmEventLog::OP_*` (`UnifiedEventLog::query()`),
а не по общему префиксу `LLM_%` — раздельно «вход в чат», «переписка и
лимиты», «обезличивание», «файлы», плюс «Прочие операции»/«Административные
действия»/«Диагностика». Фильтрующие формы и панель вкладок — на CSS-классах
(`.log-tabs`, `.log-tab-links`, `.log-filter-row`), без инлайн-стилей.

## 7. Известные ограничения

- Логин-форма (`templates/chat/login.php`) показывает подсказку только для
  формата `DOMAIN\ivanov`, хотя backend (`ChatAuthenticator::parseLogin`)
  также принимает `ivanov@domain.local`. Не исправлено — не мешает работе,
  при нескольких доменах используется явный выпадающий список.
- Категория журнала `password_change` в `UnifiedEventLog`/`log.php`
  (отображается как «Прочие операции») — историческая ветка для чтения
  записей, сделанных до перехода на LLM-чат на уже развёрнутых экземплярах;
  для новых установок всегда пуста.
- Локальная OCR-обработка (`tesseract`, `poppler-utils`) не была проверена
  на реальных файлах в этой среде — только через юнит-тесты с фейковыми
  инструментами и живой smoke-тест fail-closed поведения без обезличивания.
- Ни разу не проверялось против настоящего Active Directory и настоящего
  внешнего LLM API — только против фейковых HTTP-транспортов в тестах и
  живого smoke-теста с локальным SQLite (без реального LDAPS/LLM).
- Проект не является git-репозиторием (`git status` → not a git repository).
  История версий не отслеживается системой контроля версий — только этим
  файлом и HISTORY.md.
