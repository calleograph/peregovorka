## 2026-09-23 — Диагностика ложного отказа при загрузке файлов (второй проход обезличивания)

**Контекст.** Пользователь сообщил, что текстовые сообщения обезличиваются
и уходят в LLM нормально, а загрузка файла (.txt) стабильно отклоняется с
`ANONYMIZATION_FAILED: purpose=file_api; reason=not_clean`, хотя тот же
файл в веб-интерфейсе DocClean с режимом `full` и всеми группами категорий
проходит проверку («✓ Проверено»). В логах видно, что `api_file` в первый
проход и повторная проверка (`purpose=file_recheck`) обе завершались
`verification.clean !== true`.

**Разбор.** В админке «Обезличивание» был включён тумблер «Повторно
проверять текст, извлечённый из обезличенного файла, через api_text»
(`second_pass`). Логика `AnonymizationGateway::anonymizeFile()`: после
успешного `api_file` (сам файл уже обезличен и прошёл проверку DocClean)
результат скачивается, из него локально извлекается текст, и при
включённом `second_pass` этот уже обезличенный текст прогоняется через
`api_text` ещё раз. Именно на этом избыточном втором проходе DocClean
возвращал `verification.clean = false` — по всей видимости, из-за меток-
заменителей или артефактов извлечения текста, которые он трактует как
неочищенные данные, хотя сам файл уже прошёл проверку на первом шаге.

**Решение.** Пользователь отключил тумблер `second_pass` в админке —
загрузка файлов заработала. Правка кода не потребовалась: это ложное
срабатывание избыточной проверки на конкретном стенде DocClean, а не
дефект `AnonymizationGateway`/`FileProcessor`. `api_file` сам по себе уже
требует `verification.clean = true` перед тем, как отдать результат
дальше — то есть безопасность (fail-closed) не пострадала при отключении
второго прохода.

**Изменённые файлы.** Нет (изменена только настройка в БД через админку,
не код).

**Результат.** Загрузка файлов через DocClean (`api_file`) работает при
`docclean_mode = full`, всех группах категорий включённых и выключенном
`second_pass`.

**Известные проблемы/незавершённые части.** Причина, по которой конкретно
у этого DocClean-стенда второй проход даёт ложный `not_clean` на
уже-обезличенном тексте, не выяснена (не воспроизводилась целенаправленным
тестом сырого ответа api_text на извлечённый текст — пользователь решил
вопрос отключением тумблера до начала такой диагностики). Если в будущем
`second_pass` понадобится (например, для форматов, где локальное
извлечение текста может задеть неочищенные метаданные), стоит сначала
проверить сырой ответ DocClean на конкретный извлечённый текст.

## 2026-09-24 — Резервное копирование конфигурации LLM-чата (экспорт/импорт ZIP)

**Контекст.** У пользователя накопилось много настроенных конфигов
(домены, нейросети, права), и он попросил пункт меню в админке для
бэкапа с автоскачиванием архива и восстановлением через веб-интерфейс
(загрузка архива), по аналогии с бэкапом конфигов в другом инструменте.
Уточнением определили состав (домены/группы + нейросети + права доступа
+ общие параметры чата, включая сам LDAPS-коннект) и то, что секреты
(API-ключи, пароли служебных учёток) в архив не попадают — после
восстановления администратор вводит их заново вручную.

**Что сделано.**
1. `src/Llm/Backup/ConfigBackupService.php` (новый) — `exportZip()`
   собирает JSON (домены с LDAPS-параметрами и LLM-полями без пароля,
   их группы, нейросети без API-ключей/доп. заголовков, матрицу прав
   «домен+группа → нейросеть» по именам, общие параметры чата) и
   упаковывает в ZIP (`ext-zip`, как в `ZipPackage` для DOCX/XLSX).
   `importZip()` разбирает архив и делает upsert по бизнес-ключам (имя
   домена/провайдера, group_ref+domain fqdn) — работает и на пустой БД,
   и поверх настроенного стенда; ничего не удаляет; при ошибке валидации
   отдельной записи (домен/группа/провайдер) — пропускает её с
   предупреждением, а не прерывает весь импорт. Переиспользует
   существующие валидаторы (`LdapConfigValidator`, `DomainGroupRepository`,
   `ProviderValidator`, `ChatSettings::validate`).
2. `src/Llm/Backup/ConfigBackupException.php` (новый).
3. `src/Llm/LlmModule.php` — метод `backup(LdapConfigRepository $ldapConfigs)`
   собирает сервис (LdapConfigRepository передаётся параметром, так как
   принадлежит основному AD-модулю, а не LLM).
4. `public/admin/sections/system.php` — раздел «Система» → «Резервное
   копирование» дополнен блоком «Конфигурация LLM-чата»: кнопка-ссылка
   скачивания архива (`action=export_llm_config`, GET с CSRF в query) и
   форма восстановления (`action=import_llm_config`, POST, загрузка
   .zip) с модальным подтверждением и выводом статистики/предупреждений
   после восстановления. Оба действия пишутся в `audit_log`.

**Изменённые файлы.**
- `src/Llm/Backup/ConfigBackupService.php` (новый)
- `src/Llm/Backup/ConfigBackupException.php` (новый)
- `src/Llm/LlmModule.php`
- `public/admin/sections/system.php`
- `PROJECT.md`

**Результат.** `php -l` без ошибок. Полный набор тестов (156, 372
assertions) проходит без регрессий. Отдельным сквозным скриптом (вне
PHPUnit) проверено: экспорт не содержит секретов ни в каком виде;
восстановление на пустой БД поднимает домен/группу/провайдера
(`routing_provider` включая)/права/настройку чата корректно;
API-ключ после восстановления отсутствует (`has_api_key=0`), как и

**Известные проблемы/незавершённые части.** Импорт не оборачивается в

но это безопасно, так как повторный запуск того же архива идемпотентен

## 2026-09-24 — Доработка интерфейса чата: точный drag-and-drop, кнопка "вниз", точки быстрого перехода

**Контекст.** Пользователь пожаловался, что при перетаскивании файла в
окно чата подсвечивается («белым») весь экран целиком, а не только зона
ввода — «это не нормально», должна выделяться только зона, куда файл
реально попадёт. Также попросил: иконки скрепки/отправки в композере
(уже были реализованы ранее), плавающую кнопку «в самый низ чата»,
появляющуюся при прокрутке истории вверх, и боковое мини-меню из точек
для быстрого перехода к своим последним вопросам (по образцу интерфейса
DeepSeek, приложенного как чисто визуальный референс). Отдельно попросил
добавить в админку бэкап конфигурации LLM-провайдера — эта часть работы
описана отдельной записью выше.

**Что сделано.**
1. `templates/chat/app.php` — композер обёрнут в `.gpt-composer-wrap`
   (узкая зона, именно она подсвечивается при drag-and-drop, а не весь
   `.gpt-main`); область сообщений обёрнута в `.gpt-messages-wrap` с
   новыми элементами: `#scrollToBottom` (плавающая кнопка возврата к
   последнему сообщению) и `#jumpDots` (боковые точки-переходы к своим
   вопросам).
2. `public/assets/js/chat.js`:
   - `initDropzone()` теперь принимает раздельно «зону прослушивания
     drag-событий» (широкую, `.gpt-main`) и «зону подсветки» (узкую,
     `.gpt-composer-wrap` для чата, сам `.gpt-panel` для источников
     проекта) — событие ловится широко, класс `.drag-over` навешивается
     только на целевой элемент.
   - `renderJumpDots()` — строит до 12 точек по последним сообщениям
     пользователя текущего чата, с превью текста (первые 120 символов)
     во всплывающей подсказке при наведении; клик — плавный скролл к
     этому сообщению.
   - `updateScrollButton()`/`scrollMessagesToBottom()` — кнопка «вниз»
     показывается, когда есть переполнение и пользователь не рядом с
     низом списка (`isNearBottom()`), скрывается иначе; клик — плавная
     прокрутка вниз.
3. `public/assets/css/app.css` — новые стили `.gpt-dropzone` (теперь
   позиционируется относительно `.gpt-composer-wrap`, а не всего окна),
   `.gpt-scroll-bottom`, `.gpt-jumpdots`/`.gpt-jumpdot` (с тултипом через
   `::after` и `data-label`), лёгкие hover-эффекты (масштабирование,
   переход тени/цвета) на кнопке отправки и иконке скрепки.
4. Визуальная проверка в реальном браузере (Playwright/Chromium,
   headless), так как это чисто UI-фича: отрендерен реальный шаблон
   `templates/chat/app.php` через отдельный PHP built-in server с
   мок-API (`bootstrap`/`send`), отправлено 14 сообщений через настоящий
   `send()`-путь JS (не прямая правка DOM) и сделаны скриншоты. В процессе
   найдены и исправлены два реальных бага, не видных при чтении кода:
   - `.gpt-jumpdots` имел `opacity: 0` по умолчанию и переключался на
     видимый только классом `.visible`, который JS никогда не
     проставлял — точки существовали в DOM, но были невидимы всегда.
     Исправлено: базовая видимость `opacity: .45`, `1` по hover.
   - `#scrollToBottom` имел статический HTML-атрибут `hidden` в разметке,
     который `classList.toggle('visible', ...)` не снимает — кнопка
     оставалась в `display:none` независимо от класса. Исправлено:
     `updateScrollButton()` явно снимает `hidden`, видимость дальше
     полностью на CSS (`opacity`/`pointer-events` через `.visible`).
   После обеих правок повторной проверкой в браузере подтверждено: при
   drag-over подсвечивается только `composerWrap` (`gptMain.drag-over`
   остаётся `false`), кнопка «вниз» появляется/скрывается по прокрутке и
   возвращает к низу по клику, точки видны и показывают текст вопроса по
   наведению.

## 2026-09-24 — Квота хранения на пользователя, самостоятельная очистка данных, автоочистка неактивных

**Контекст.** Пользователь поднял вопрос роста нагрузки на диск с числом
пользователей чата и попросил: (1) ограничение места на пользователя,

больше (базово 50 МБ, у особых групп — 100/500 МБ/1 ГБ); (2) возможность
для пользователя самому удалять свои чаты (выборочно чекбоксами или все
разом) и файлы; (3) автоочистку данных при неактивности (3 месяца).
Важный технический факт, уточнённый в начале работы: исходные загруженные
файлы на сервере физически не хранятся — они обрабатываются во временном
каталоге (`FileProcessor::withStagedFile`) и удаляются в `finally` сразу
после извлечения текста/OCR/обезличивания; на диске остаётся только
обезличенный текст (сжатый, в SQLite) вместе с историей чата/источниками
проекта. Это сместило постановку: квота считается по объёму текста в БД,
а не по файлам; «удаление файлов» — это удаление чатов/источников
(текста), а не расчистка файловой системы. Автоочистку неактивности
решили ограничить только зачисткой содержимого сообщений/источников
(заголовки чатов остаются), не удалением самих диалогов.

Отдельно уточнили механизм задания квоты: вместо нового параллельного
понятия квота встроена в уже существующий механизм именованных категорий
лимита токенов (`llm_limit_categories`) — та же категория, что отвечает
за лимит токенов, получила второе поле (МБ). Также обсудили поведение при
превышении: явно решили не блокировать пользователя жёстко — превышение
не мешает читать/использовать уже сохранённое, только отклоняет попытку
добавить новое содержимое, с понятным сообщением и прямым переходом в
раздел самостоятельной очистки.

## 2026-09-24 — allow_fallbacks для сортировки по цене: потолок цены без него отклонял весь запрос

**Контекст.** После добавления сортировки по цене (см. запись выше)
пользователь на реальном сервере обнаружил два эффекта: 1) при
включённой сортировке (без потолка цены) в качестве провайдера иногда
выбирался не самый дешёвый вариант (в конкретном случае — Io Net вместо
более дешёвого DekaLLM); 2) при попытке задать потолок цены `3` (₽ за
млн токенов) сервис стал возвращать «Запрос не выполнен. Внешний сервис
отклонил запрос (возможно, слишком длинный диалог)» — притом что диалог
был коротким.

**Разбор.** Код, отправляющий `provider.sort`/`provider.max_price`,
работал ровно так, как задумано и как описано в документации Polza —
это не баг интеграции. Оба эффекта объясняются природой самого
параметра `provider.max_price` у Polza:
- `sort: "price"` — это подсказка шлюзу для ранжирования кандидатов, а
  не жёсткая гарантия «всегда самый дешёвый прямо сейчас»: реальный
  выбор конкретного бэкенда у мультипровайдерного шлюза дополнительно
  зависит от текущей доступности/задержки этого бэкенда в момент
  запроса — отсюда Io Net вместо DekaLLM в одном конкретном вызове.
- `max_price` — это жёсткий фильтр, а не приоритет: если ни один
  доступный в моменте маршрут не укладывается в указанный потолок цены,
  Polza должна либо отклонить запрос, либо (если явно разрешено) взять
  маршрут вне фильтра. Разрешение на второй вариант — отдельный флаг
  `provider.allow_fallbacks`, который в реализации до этой правки в
  запрос не отправлялся вовсе. Значение `3` ₽/млн токенов, судя по всему,
  оказалось ниже цены всех доступных в тот момент маршрутов — без
  `allow_fallbacks` шлюз отклонил весь запрос целиком, а обобщённая
  обработка HTTP-ошибок в `LlmException::fromHttpStatus()` (любой
  4xx, кроме 401/403/429, помечается как `bad_request`) показала
  пользователю неточную типовую формулировку про «слишком длинный
  диалог» вместо настоящей причины.

**Что сделано.**
1. `src/Llm/LlmSchema.php` — новая колонка `llm_providers.allow_fallbacks`
   (INTEGER, по умолчанию 1/включено).
2. `ProviderValidator::normalize()` — читает `allow_fallbacks` из формы
   (чекбокс, как `is_enabled`/`use_corporate_ca`).
3. `ProviderRepository`/`ProviderConfig` — поле проведено через `all()`,
   `create()`, `update()`, `bind()`, `loadForGateway()`; по умолчанию
   `true`, если колонка ещё не заполнена (обратная совместимость).
4. `ChatCompletionsAdapter::buildRequest()` — в ветке `sortByPrice`
   теперь всегда добавляется `provider.allow_fallbacks` (bool из
   конфигурации), независимо от того, задан ли потолок цены.
5. `public/admin/sections/llm_providers.php` — рядом с полем «Потолок
   цены» добавлен переключатель «Если по потолку цены не осталось ни
   одного маршрута — не отклонять запрос, а взять любой доступный»,
   включён по умолчанию (в форме и для новых, и для уже существующих
   записей — `$val($row, 'allow_fallbacks', '1')`); подсказка у поля
   «Потолок цены» дополнена предупреждением о риске слишком низкого
   значения.
6. `src/Llm/Gateway/LlmException.php` — типовое сообщение пользователю
   при `bad_request` дополнено упоминанием возможной причины
   («настройки маршрутизации нейросети слишком строгие — сообщите
   администратору»), чтобы не указывать только на длину диалога. Полная
   техническая причина (включая реальный текст ошибки Polza) уже и
   раньше показывалась администратору через «Проверить подключение»
   (`LlmGateway::describeForAdmin()`) — это осталось без изменений и
   остаётся основным способом диагностики подобных случаев.
7. `src/Llm/Backup/ConfigBackupService.php`, `tests/LlmTestKit.php` —
   новое поле добавлено в экспорт конфигурации и в тестовую фабрику
   провайдера (иначе `ProviderRepository::bind()` обращался бы к
   несуществующему ключу массива).
8. Прямая проверка через PHP REPL (`ChatCompletionsAdapter::buildRequest()`
   напрямую, без HTTP): при `sortByPrice=true, maxPricePerMtoken=3.0,
   allowFallbacks=true` тело запроса содержит
   `"provider":{"sort":"price","allow_fallbacks":true,"max_price":
   {"prompt":3,"completion":3}}`; при `allowFallbacks=false` без потолка
   цены — `"provider":{"sort":"price","allow_fallbacks":false}`.

## 2026-09-24 — Рендеринг markdown в ответах нейросети (заголовки, таблицы, списки, ссылки, цитаты)

**Контекст.** Пользователь прислал скриншот реального ответа модели:
`###`-заголовки, `**жирный**`, таблицы через `|` и нумерованные списки
выводились в чате буквально как текст, без визуального форматирования
— выглядело «плохо без обработки». До этого `renderText()` в
`chat.js` умел выделять только тройные code-block (```) — весь
остальной markdown, включая инлайн-разметку, шёл через `textContent`
как обычный абзац.

**Решение.** Внешнюю библиотеку подключить нельзя — CSP проекта
(`script-src 'self'`) разрешает скрипты только с того же источника, а
проект принципиально without-framework/vanilla JS без сборки. Поэтому
написан собственный минимальный markdown-парсер прямо в `chat.js`:
- `renderInline()` — построчный инлайн-парсер одним регэкспом с
  альтернативами (`[текст](url)`, `**жирный**`/`__жирный__`,
  `` `код` `` в любом количестве бэктиков, `*курсив*`/`_курсив_`),
  рекурсивно вызывает себя для содержимого `**bold**`/`*italic*`
  (чтобы `**_вложенное_**` тоже работало). Ссылки — только `http(s)://`,
  открываются в новой вкладке с `rel="noopener noreferrer nofollow"`.
- `renderMarkdownBlock()` — построчный блочный парсер поверх уже
  выделенных (не-код) фрагментов: заголовки `#`..`######`,
  горизонтальная линия (`---`/`***`/`___`), таблицы (GFM-стиль, строка
  `|...|` + строка-разделитель `---|---`), цитаты `>` (рекурсивно, для
  вложенной разметки внутри цитаты), списки — маркированные и
  нумерованные (пока без верной вложенности по отступу — только плоский
  список), обычные абзацы — остаток.
- Весь DOM строится через `createElement`/`textContent`/`el()`, ни
  разу `innerHTML` — контент нейросети остаётся небезопасным по
  происхождению ровно как раньше (проектное правило «данные с сервера
  выводятся только через textContent»), но теперь ещё и отформатирован;
  синтаксис markdown-разметки в тексте не может превратиться в
  исполняемый HTML, потому что разметка строится программно, а не
  через парсинг строки браузером.
- `renderText()` (точка входа) не изменилась по контракту — по-прежнему
  сперва режет текст по тройным бэктикам на код/не-код фрагменты,
  просто не-код фрагмент теперь идёт в `renderMarkdownBlock()` вместо
  плоского `textContent`.
- Кнопка копирования (`buildMessageActions()`) не изменилась — копирует
  исходный markdown-текст сообщения, а не отрендеренный HTML: так
  вставка в другой markdown-редактор (или в сам чат) сохраняет разметку.
- `public/assets/css/app.css` — новые стили: `.gpt-heading` (+ размеры
  по уровню `h1`..`h6`), `.gpt-hr`, `.gpt-inline-code`, `.gpt-list`,
  `.gpt-quote`, `.gpt-table-wrap`/`.gpt-table` (с горизонтальным
  скроллом на переполнении), ссылки внутри `.gpt-msg-body`. Убраны
  лишние вертикальные отступы у первого/последнего дочернего элемента
  тела сообщения (`.gpt-msg-body > :first-child/:last-child`).
- Визуальная проверка (Playwright, застабленный `api.php` с реальным
  текстом из присланного скриншота — заголовки, GFM-таблица, списки,
  цитата, инлайн-код, ссылка, `---`): всё отрендерилось корректно и
  визуально аккуратно; ссылка получила `target="_blank"` и правильные
  `rel`; кнопка копирования продолжает работать поверх новой разметки.

**Изменённые файлы.**
- `public/assets/js/chat.js` (+ синхронизированная корневая копия)
- `public/assets/css/app.css` (+ синхронизированная корневая копия)
- `PROJECT.md`

**Результат.** `node -c` без ошибок. Полный набор тестов (156, 372
assertions) проходит без регрессий (эта правка не затрагивает backend).
Визуальная проверка в браузере подтвердила корректный рендеринг всех

**Известные проблемы/незавершённые части.** Списки не поддерживают
настоящую вложенность по отступу (маркер второго уровня внутри пункта

## 2026-09-25 — Отправка сообщения без обезличивания (по праву группы, с явной галочкой пользователя и аудит-событием)

**Контекст.** Пользователь попросил: для файлов/сообщений, в которых
заведомо нет конфиденциальных данных (например техническая документация
для анализа), дать возможность пропустить обезличивание — галочка
рядом с кнопкой «Отправить», компактная, мелким шрифтом, с красным
восклицательным знаком, чтобы не мешать интерфейсу, но быть заметной.
При включении сообщение и вложения должны уходить в LLM API напрямую,
минуя сервис обезличивания целиком. Уточняющие вопросы решили: 1)
такие сообщения хранятся в истории в открытом виде (не обезличенными)
для консистентности UI, а не скрываются из истории вовсе; 2) право
ограничивается группой/пользователем через новую настройку в админке
(не доступно всем без исключения); 3) каждый такой случай — отдельное
событие в аудит-логе.

Это первое осознанное исключение из принципа fail closed, на котором
построен весь проект («запрос с необезличенными данными наружу никогда
не уходит») — реализовано как явный, редко включаемый администратором
флаг на уровне группы/пользователя, а не общая настройка чата.

**Что сделано.**
1. `src/Llm/LlmSchema.php` — новые колонки: `llm_domain_groups.
   allow_unanonymized` (по умолчанию 0 — выключено у всех существующих
   субъектов при миграции) и `llm_messages.unanonymized` (0 — обычное
   сообщение хранится обезличенным, как и раньше; 1 — сообщение
   отправлено без обезличивания и хранится в открытом виде).
2. `src/Llm/Domain/DomainGroupRepository::setAllowUnanonymized()` —
   точечное обновление флага у одного субъекта (группы или виртуального
   пользователя).
3. `src/Llm/Access/AccessPolicy::canSkipAnonymization(array $groupIds)`
   — тем же принципом объединения прав, что и `allowedProviders()`:
   разрешено, если хотя бы одна из групп пользователя (включённая,
   `is_enabled = 1`) имеет `allow_unanonymized = 1`.
4. `src/Llm/Chat/ChatService::send()` — новый параметр `bool
   $skipAnonymization = false`. При `true`: сначала проверяется право
   через `AccessPolicy::canSkipAnonymization()` — при отказе событие
   `LLM_UNANONYMIZED_DENIED` и `ChatException('access_denied', ...,
   403)`, ничего не отправляется. При наличии права: текст сообщения
   оборачивается в `AnonymizedText::fromStorage()` вместо прогона через

## 2026-09-25 — Уточнено сообщение об ошибке «пустой файл» при отправке без обезличивания

**Контекст.** Пользователь попытался отправить .txt-файл с включённой
галочкой «не обезличивать» и получил «Запрос не выполнен. Не удалось
извлечь текст из файла — запрос не отправлен», ожидая, что раз файл не
обезличивается, то и «потрошить» его (парсить/проверять) не должны —
казалось, что это ошибка в реализации режима skipAnonymization.

**Разбор.** Логика сработала верно — файл действительно оказался
пустым (подтвердил пользователь), и `FileProcessor::extractText()`
закономерно отклоняет пустой текст (`empty_content`) что при обычной
отправке, что при отправке без обезличивания — отправлять в LLM
буквально нечего в обоих случаях. Реального бага нет:
`handleUploadRaw()` (добавлен в предыдущей сессии для skipAnonymization)
и так уже не отправляет файл в сервис обезличивания, использует только
локальное извлечение текста — само извлечение (чтение файла + проверка
сигнатуры/расширения через `FileProcessor`) остаётся нужным независимо
от режима обезличивания, так как для DOCX/XLSX/PDF/изображений это
единственный способ вообще получить текст из бинарного формата.
Единственная реальная проблема — формулировка сообщения об ошибке:
`empty_content` показывал общее «не удалось извлечь текст», что вводило
в заблуждение при по-настоящему пустом файле, наводя на мысль о сбое
парсинга, а не о том, что отправлять просто нечего.

## 2026-09-26 — Источники проекта переполняли контекст модели («bad_request» при 6 файлах): лимит числа файлов + снижен лимит символов + подсказки в UI

**Контекст.** Пользователь добавил 6 файлов в источники проекта и
получил «Запрос не выполнен. Внешний сервис отклонил запрос (возможно,
слишком длинный диалог или настройки маршрутизации нейросети слишком
строгие)» — то же типовое сообщение `bad_request`, что фигурировало в
прошлых сессиях по другим причинам. Заподозрил лимит в 5 файлов
(с композера чата) или переполнение контекста, попросил продумать
разумный лимит источников (предложил не более 3, явно текстовых) с

**Разбор.** Подтверждено чтением кода: `ProjectRepository::
contextFor()` собирает ВЕСЬ текст всех источников проекта целиком и
добавляет его в системный промпт (через `LlmGateway::complete()`)
КАЖДОГО запроса к модели в этом проекте — независимо от того, к какому
конкретно сообщению относится вопрос. До этой правки единственным
ограничителем был `project_sources_max_chars` (по умолчанию 100000
символов, ≈25000 токенов) — общий на весь проект, без всякого учёта
реального контекстного окна конкретной подключённой модели (оно
сильно разнится: у компактных моделей вроде qwen3.5-9b оно заметно
меньше, чем у крупных). При 6 файлах суммарный объём легко приближался
или превышал этот предел и/или реальный лимит модели — внешний API
в ответ на слишком длинный запрос отклонял его с `HTTP 4xx`, что
`LlmException::fromHttpStatus()` показывает пользователю как общий
`bad_request`, никак не поясняя настоящую причину (не связанную с
диалогом чата — источники добавляются в системный промпт, а не в
историю переписки).

**Что сделано.**
1. `src/Llm/Chat/ChatSettings.php` — снижен дефолт
   `project_sources_max_chars` со 100000 до 30000 (оставляет запас под
   историю переписки, системный промпт и ответ модели даже для
   компактных моделей); добавлена новая настройка
   `project_sources_max_files` (по умолчанию 3, диапазон 1–50) —
   ограничивает типичный сценарий «нахватал десяток файлов», хотя сама
   по себе не гарантирует непревышение контекста (несколько крупных
   файлов всё ещё могут это сделать) — оба лимита работают вместе, не
   взаимоисключающе.
2. `src/Llm/Chat/ProjectRepository::sourceCount(int $projectId): int`
   — подсчёт источников проекта (новый метод, по аналогии с уже
   существующим `totalSourceChars()`).
3. `src/Llm/Chat/ChatService::addProjectSource()` — проверка лимита
   числа источников выполняется ДО обработки/обезличивания
   загружаемого файла (не после), чтобы не тратить время на файл,
   который всё равно будет отклонён; при превышении —
   `ChatException('sources_limit', ...)` с понятным текстом.
4. `public/api.php` — `GET project` дополнительно отдаёт

## 2026-09-26 — Именованные блоки инструкций проекта вместо одного текстового поля (вместо автосуммаризации через LLM)

**Контекст.** Пользователь предложил идею: при загрузке файла в
источники автоматически прогонять его через текущую нейросеть, сжимать
в компактный контекст и добавлять как один из нескольких именованных
блоков в разделе «Инструкции» (с кнопкой «+» для ручного добавления
новых блоков, каждый со своим лимитом символов). Попросил критически
оценить идею и предложить, что реализовывать, а что оптимизировать
иначе.

**Разбор идеи.** Автоматическое сжатие через LLM признано более
рискованным, чем то, что уже сделано в предыдущей сессии (чёткие
лимиты числа/размера источников): 1) суммаризация LLM непредсказуемо
теряет данные — модель сама решает, что «неважно», и может выбросить
точные цифры/даты, которые пользователю были нужны; 2) требует ещё
одного внешнего запроса на каждый файл — деньги, время, ещё одна точка
отказа; 3) требует выбора «какой моделью сжимать» — отдельная
конфигурация. Признана здравой и полезной только часть идеи —
структурные именованные блоки инструкций с ручным наполнением, без
автоматической LLM-суммаризации.

**Что сделано.**
1. `src/Llm/Chat/ProjectRepository.php` — именованные блоки инструкций
   хранятся в уже существующей таблице `llm_project_sources` с новым
   значением `source_type = self::TYPE_INSTRUCTION = 'instruction'`
   (переиспользует весь уже отработанный код: `addSource()`,
   `deleteSource()`, `sourceText()` — просмотр обезличенного текста
   блока работает точно так же, как у источников-документов). Новые
   методы: `instructions()` (список блоков, аналог `sources()`, но
   фильтрует по типу `instruction`), `instructionCount()`/
   `totalInstructionChars()` (аналоги `sourceCount()`/
   `totalSourceChars()`). Существующие `sources()`/`sourceCount()`/
   `totalSourceChars()` обновлены — исключают строки типа `instruction`
   через `WHERE source_type != :instr`, чтобы не путать блоки инструкций
   со списком источников-документов в UI.
   - `contextFor()` переписан: собирает блоки инструкций отдельно от
     источников — БЕЗ нумерации (`[Инструкция: Название]`, это правила

2. `src/Llm/Chat/ChatSettings.php` — две новые настройки:

   блока, не суммарный: блок задуман коротким правилом, в отличие от
   источников-документов с их суммарным лимитом побольше).
