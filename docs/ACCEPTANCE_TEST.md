# Приёмочный тест перед фиксацией системных требований

Системные требования (CPU/RAM/сеть) фиксируются **только после** этого сценария на реальном стенде. До его выполнения
рекомендации (4 vCPU / 8 ГБ — рабочий минимум; 8 vCPU / 16 ГБ — запас для пилота) считаются предварительными.
Добавление CPU/RAM **не заменяет** исправление конфигурации и несовместимых компонентов: сначала — LiveKit Server с `/rtc/v1`,
параметры ядра, потоки ASR (`.env.example`, `docs/COMPATIBILITY.md`).

## Подготовка

1. `scripts/smoke-test.sh` — все строки OK (допустимы WARNING с объяснением). Особое внимание: «LiveKit /rtc/v1» = 101,
   «LiveKit WebSocket (публичный URL)» = OK, «Параметры ядра» без WARNING.
2. `scripts/asr-bench.sh --wav <реальная речь 5–15 с> --threads 2,4` → выбрать `ASR_CPU_THREADS` **по задержке (RTF)**, а не по
   загрузке CPU; при малой разнице брать меньшее число потоков.
3. Участники: 3 пользователя на разных компьютерах (с разными сетями, если возможно), админ.
4. Сбор нагрузки: `scripts/collect-metrics.sh --minutes 35` (CPU/RAM контейнеров и хоста, max/avg).

## Сценарий

| № | Действие | Что зафиксировать |
| --- | --- | --- |
| 1 | 3 пользователя входят в одну комнату | время «Войти → в комнате» (админка → «Состояние системы» → «Время входа»; цель 1–2 с); `join_backend_ms`, `signaling_connect_ms`, `ice_connect_ms` |
| 2 | Одна камера, три микрофона, все говорят по очереди | транскрипция по каждому; ASR: задержка, RTF, очередь, отброшено |
| 3 | Один участник показывает экран | FPS, битрейт, потеря кадров/пакетов (⚙ Диагностика в комнате), причина ограничения качества |
| 4 | Остановить показ (кнопкой и кнопкой браузера «Остановить доступ»), запустить снова | в «Диагностике клиентов» — причины остановки; повторный запуск работает |
| 5 | Разорвать сеть одному участнику на 5–15 с | автоматическое восстановление; комната и встреча не закрылись |
| 6 | Непрерывная работа 20–30 минут | стабильность показа экрана, рост памяти, задержка ASR |
| 7 | Завершить встречу | участники попадают на страницу встречи |
| 8 | Сформировать протокол (окно инструкции, шаблон, правка, скачивание DOCX/PDF/MD/TXT, копирование) | время формирования |
| 9 | Проверить сохранение записи и стенограммы во внешнее хранилище | статус выгрузки «выгружена» |
| 10 | Админ удаляет запись (только аудио), затем встречу целиком | подтверждения, записи в журнале аудита |
| 11 | Обычный участник вышел со страницы встречи → доступ закрыт; прямая ссылка не открывает | 404 |
| 12 | Админ повторно открывает историю и протокол | доступ есть |

## Что занести в отчёт

- CPU: max/avg хоста и по контейнерам (`collect-metrics.sh`); RAM: max; пропускная способность LiveKit; потери пакетов;
- задержка ASR (среднее / p95), RTF; время входа пользователей (среднее / p95 из админки);
- стабильность показа экрана (число обрывов за тест и их причины);
- время формирования протокола; размер записи на час разговора.

Диагностический отчёт (админка → «Скачать диагностический отчёт» или `scripts/diag.sh`) приложить к результатам: секреты в нём
замаскированы автоматически.
