# Bitrix24 как источник профиля

Каталог (Active Directory) остаётся **основой входа и идентичности**. Bitrix24 — необязательный **дополнительный источник** карточки сотрудника: должность, подразделение, рабочий телефон, фото. Интеграция только читает данные портала.

> **Главное правило надёжности:** вход, пре-джойн и комната не зависят от доступности портала. Обновление идёт в фоне после входа; при любом сбое остаются прежние значения и последняя аватарка, а событие попадает в журнал.

Адреса в этом документе условные (`portal.example.com`).

## Что нужно на стороне Bitrix24

1. В портале: **Разработчикам → Другое → Входящий вебхук**.
2. Права вебхука — только чтение:
   * **Пользователи** (`user_brief` — минимум; `user_basic` — если нужны телефон и e-mail);
   * **Подразделения** (`department`) — чтобы показывать название подразделения (без права поле просто останется пустым, остальное работает).
3. Скопировать адрес вида `https://portal.example.com/rest/<номер>/<секрет>/`. **Секрет внутри адреса** — храните как пароль.

## Настройка

Администрирование → **Интеграции → Bitrix24 (профили)**:

1. Указать адрес портала и входящий webhook (адрес webhook обязан принадлежать тому же узлу, что и портал).
2. Выбрать, что подтягивать (должность, подразделение, телефон, фото) и приоритеты полей.
3. **Сохранить**, затем **«Проверить подключение»** — покажет, от чьего имени создан вебхук.
4. **«Показать, что вернёт портал»** — пробный поиск по e-mail сотрудника, ничего не сохраняет.
5. Включить интеграцию. Данные подтянутся при следующем входе каждого человека; **«Обновить профили сейчас»** запускает ручную синхронизацию (до 200 человек за запуск, самые недавние по входу).

Секрет webhook хранится зашифрованно (как другие секреты настроек), не возвращается API и не попадает в журнал и сообщения об ошибках.

## Как сопоставляются люди

* По **e-mail** из каталога (или по сохранённому номеру сотрудника Bitrix после первого совпадения).
* Если на портале **несколько** совпадений, неактивный сотрудник или совпадений нет — данные портала **не используются** (угадывание исключено). Учётная запись при этом работает как обычно.

## Приоритеты полей

Для каждого поля — список источников по порядку: `ad` (каталог), `bitrix`, `local` (то, что человек указал сам). Берётся первый источник, у которого поле заполнено. Пустое значение никогда не стирает прежнее.

| Поле | По умолчанию |
|---|---|
| ФИО, e-mail | `ad, bitrix, local` |
| Должность, подразделение, телефон | `bitrix, ad, local` |
| Фото | `local, bitrix, ad` |

**Фото:** загруженное самим человеком (`manual`) портал не заменяет, пока `local` стоит в приоритете раньше `bitrix`. Если фото нет вообще, берётся фото портала. Фото портала приводится к квадрату 256×256 (WebP) и хранится у нас; при смене фото на портале обновляется.

## Что и когда обновляется

* При входе пересчёт карточки по уже сохранённым источникам — **без сети**.
* Запрос к порталу — в **фоне**, один человек одновременно, не чаще срока «Обновлять не чаще, чем раз в N часов» (по умолчанию 24).
* После сбоя портала повтор не раньше чем через 10 минут (портал не «долбится» при каждом входе).
* Одновременно к порталу идёт не более 3 запросов.

## Безопасность

* Только чтение; запись в Bitrix24 не выполняется.
* Фото скачивается **только с того же узла**, что указан в настройках, без переходов по редиректам, не больше 5 МБ, только `image/*`; картинка перекодируется (метаданные и активное содержимое не сохраняются).
* Адреса loopback/link-local (в том числе метаданные облака) не допускаются; `http://` — только по явному разрешению для тестов.
* Проверка сертификата портала включена; для внутреннего удостоверяющего центра — «Доверять корпоративному УЦ».
* Операции администратора (проверка, поиск, синхронизация) доступны только администраторам; синхронизация пишется в журнал аудита.

## Диагностика

| Симптом | Причина / действие |
|---|---|
| «нет соединения с порталом» | Сетевой доступ сервера приложения до портала; для внутреннего УЦ — включить «Доверять корпоративному УЦ». |
| «портал отклонил запрос: …» | Проверьте права вебхука (пользователи, подразделения) и что вебхук не отозван. |
| «Сотрудник не найден или найдено несколько совпадений» | В Bitrix24 нет такого e-mail либо он у двух сотрудников. Исправьте данные на портале. |
| Должность есть, подразделения нет | Нет права `department` у вебхука. |
| Фото не меняется | У человека своё фото (`local` выше `bitrix` в приоритете) или фото на портале не изменилось. |
| События | Журнал → источник «profile»: `bitrix_profile_refresh_failed`, `bitrix_photo_rejected`, `bitrix_sync_done`. |

## Для разработчиков

Код — `backend/app/profiles/`: `base.py` (поля и ошибки), `merge.py` (чистые функции слияния по приоритетам), `bitrix.py` (клиент REST, без записи), `service.py` (`ProfileEnrichment`: вход, фон, кэш, ручная синхронизация). Снимки источников хранятся в `users.profile_sources` (`ad`, `bitrix`), идентификатор портала — в `users.external_ids`, происхождение фото — в `users.avatar_source` (`manual` | `bitrix`). Тесты — `backend/tests/test_profile_sources.py` (портал подменяется `httpx.MockTransport`, сеть не нужна). Новый источник (например, другой HR-каталог) добавляется как ещё один провайдер с теми же правилами изоляции сбоев.
