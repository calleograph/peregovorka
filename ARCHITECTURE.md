# ARCHITECTURE.md — архитектура голосовой переговорки

Документ описывает **целевую** архитектуру и принятые решения. Что из этого
уже реализовано — в `PROJECT.md` (единственный источник фактического
состояния). Здесь записано «как устроено и почему», чтобы все этапы
разработки опирались на одну схему.

## 1. Назначение и границы

Полностью локальная корпоративная веб-система голосовых переговорок:

- вход только доменной учёткой Active Directory (LDAPS), локальных
  пользователей и самостоятельной регистрации нет;
- голос/видео/экран — WebRTC через локальный LiveKit (SFU);
- микрофон каждого участника — **отдельный WebRTC-трек**; ASR-worker
  подписывается на треки по отдельности, поэтому «кто говорит» определяется
  identity трека, а не диаризацией общего микса;
- транскрибация локальная (GigaAM v3 E2E RNNT + Silero VAD), без облаков;
- итог встречи — полный протокол по времени и участникам; позже — краткий
  протокол/решения/поручения через локальную LLM (архитектура к ней
  подготовлена, но с конкретной LLM не связана).

Внешние облачные сервисы для авторизации, медиа и распознавания не
используются. Единственные необязательные внешние обращения: загрузка весов
модели (один раз, `scripts/models.sh`; в закрытой сети — из локального
каталога) и, на этапе протоколов, обращение к LLM через обезличиватель.

## 2. Компоненты

```
 Браузер (Chromium) ──HTTPS──► [host nginx / внешний reverse proxy]
        │                                  │
        │ WSS /livekit  ┐                  ▼
        │ HTTPS /api    ├────────────►  web (nginx + React SPA)
        │ WSS /api/v1/ws┘                  │         │
        │                                  ▼         ▼
        │                              backend    livekit ◄─────┐
        │  ICE: UDP mux + TCP (напрямую) (FastAPI)  (SFU)        │ подписка на
        └──────────────────────────────────┼─────────▲──────────┘ микрофонные
                                           │         │            треки
                                  ┌────────┴───┐     │
                                  ▼            ▼     │
                              postgres       redis ◄─┴──── asr (worker + GigaAM)
                                              ▲   streams: asr:control → / ← asr:segments
```

| Сервис (compose) | Технология | Ответственность |
| --- | --- | --- |
| `web` | nginx + собранный React/TS | статика SPA; прокси `/api/` → backend, `/livekit/` → livekit (WS) |
| `backend` | Python, FastAPI, SQLAlchemy, Alembic | AD-вход, сессии, права, комнаты, встречи, выдача LiveKit-токенов, REST/WS API, аудит, настройки, хранение транскриптов, фоновая очистка |
| `livekit` | LiveKit Server | только WebRTC/SFU; медиа через backend **не проксируется** |
| `asr` | Python, livekit rtc SDK, Silero VAD, GigaAM | служебный скрытый участник комнаты, VAD, подготовка аудио, инференс, публикация реплик |
| `postgres` | PostgreSQL | постоянные данные |
| `redis` | Redis | сессии, rate limit, очереди (streams), pub/sub живых событий, временное состояние |

Все сервисы — только в внутренней сети compose-проекта. Наружу публикуются
заранее заданные порты: `web` (по умолчанию loopback), `livekit` ICE/UDP
(один mux-порт) и ICE/TCP, опционально `livekit` HTTP/WS на loopback.
PostgreSQL и Redis на интерфейсы хоста **не публикуются никогда**.

## 3. Ключевые решения

### 3.1 Аутентификация и сессии
- LDAPS, `ldap3`, `ssl.CERT_REQUIRED` + CA-файл из конфигурации; «мягкого»
  режима нет — без CA backend не стартует.
- Алгоритм входа: (1) сервисная read-only учётка ищет пользователя по
  `LDAP_LOGIN_ATTRIBUTE`; (2) bind от имени **найденного DN** с введённым
  паролем (так не нужны UPN/NetBIOS-догадки); (3) читаются `objectGUID`,
  `sAMAccountName`, `displayName`, `userPrincipalName`, `mail`, статус
  учётки; (4) все группы пользователя, включая вложенные, одним запросом
  `member:1.2.840.113556.1.4.1941:=<userDN>`; (5) проверка
  `LDAP_ACCESS_GROUP_DN` (если задана) и определение админа по
  `LDAP_ADMIN_GROUP_DN`.
- Пароль нигде не сохраняется и не логируется.
- Стабильный внешний идентификатор — `objectGUID` (не sAMAccountName:
  логины переименовываются). В БД — локальное представление пользователя.
- Сессия — **серверная, в Redis**; cookie `HttpOnly; Secure; SameSite=Lax`
  содержит только случайный id. Долгоживущих JWT и `localStorage` нет.
  CSRF: токен в сессии + заголовок `X-CSRF-Token` на небезопасных методах.
  Idle- и абсолютный таймауты. Группы фиксируются на момент входа и
  обновляются при следующем входе (ограничение, см. §9).
- Защита от перебора: счётчики в Redis по логину и по IP; после N неудач
  (по умолчанию **3**, ниже типичного порога блокировки AD) новые попытки
  для этого логина отклоняются **без обращения к AD** на время окна;
  единый «неверный логин или пароль» без раскрытия существования учётки.

### 3.2 Identity в LiveKit
- Identity = `u-<uuid пользователя без дефисов>`; никогда не берётся из
  пользовательского ввода. Имя передаётся отдельно (`name` в токене).
- Токен короткоживущий (по умолчанию 5 минут на подключение), выдаётся только
  после проверки ACL, привязан к одной LiveKit-комнате конкретной встречи,
  `can_publish_data=False`, источники публикации ограничены настройками
  комнаты (камера/экран). Права `room_admin`, `room_record`, `hidden` у
  пользовательского токена отсутствуют.
- LiveKit-комната = **встреча** (`m-<uuid встречи>`), а не постоянная
  переговорка: так нет «залипшего» состояния между сеансами.

### 3.3 Комната и встреча
- **Room** — постоянная сущность (настройки, ACL, пароль, инструкции).
- **Meeting** — конкретный сеанс: `started_at`, `ended_at`, состав
  участников, транскрипт. В одной комнате не более одной активной встречи
  (partial unique index `ended_at IS NULL`).
- Встреча стартует при входе первого участника (или кнопкой «начать запись»),
  завершается при выходе последнего (после grace-периода) либо кнопкой
  «завершить встречу». Источники факта входа/выхода: webhook LiveKit
  (`participant_joined/left`, `room_finished`) + явные вызовы API.

### 3.4 Транскрибация
```
LiveKit track (mic, один участник)
  → rtc.AudioStream(16 kHz, mono)
  → SpeechSegmenter (Silero VAD, гистерезис, пауза-конец реплики, пред-/пост-роллы,
                      максимальная длина сегмента)
  → InferenceQueue (ограниченная; N параллельных инференсов; общая модель)
  → AsrProvider.transcribe(pcm)  (GigaAM v3 E2E RNNT)
  → Redis stream asr:segments {segment_uid, meeting, participant_identity, t0, t1, text, model}
  → backend ingest: identity→user, запись в БД (идемпотентно по segment_uid),
                    publish в Redis pub/sub → WebSocket клиентам
```
- Одна копия модели на процесс; параллелизм ограничен семафором, очередь
  ограничена — при переполнении сегмент отбрасывается с метрикой/логом
  (защита памяти важнее одной реплики; политика конфигурируема позже).
- Подписка только на `TrackSource.MICROPHONE`; экранное аудио и прочее в ASR
  не уходит. Служебные идентичности (`asr-*`) игнорируются.
- Задержка = длина реплики + пауза + инференс. Пословный стриминг внутри
  незаконченной фразы не требуется.
- ASR не знает про БД и пользователей; backend не знает про GigaAM.
  Контракт — сообщения Redis streams (см. `docs/ASR_CONTRACT.md`).
- `AsrProvider` — интерфейс (`load`, `transcribe`, `health`, метаданные
  модели). Реализован `GigaAmProvider`; Whisper и др. добавляются новым
  классом без изменений в комнатах/БД.
- Диаризация общего микса не используется. Одновременно говорящие дают
  независимые записи.

### 3.5 Управление ASR-сессиями
Backend при старте встречи пишет в Redis hash `asr:sessions`
(`meeting_id → {room_name, …}`) и команду в stream `asr:control`
(`start`/`stop`). ASR при запуске поднимает все сессии из hash (самолечение
после рестарта), дальше читает stream. Команды идемпотентны.

### 3.6 Хранение данных
- PostgreSQL — пользователи, комнаты, ACL, встречи, участники, сегменты,
  аудит, настройки.
- `DATA_ROOT` (вне Git checkout): `postgres/`, `redis/`, `models/`,
  `recordings/`, `exports/`, `backups/`.
- **Запись аудио** — отдельная функция комнаты (`record_audio`). Пишет сам
  ASR-worker (он уже получает PCM каждого участника): отдельный файл на
  участника на встречу. LiveKit Egress не используется (не нужны Chrome-
  контейнеры). Транскрибация не означает хранения аудио.
- **Хранилище протоколов** (админка → «Хранилище»): локальный каталог либо
  сетевой ресурс SMB с сервисной учёткой. Структура:
  `<корень>/<комната>/<YYYY-MM-DD, день недели>/<HH-MM начало>/protocol.txt`
  с шапкой «участвовали: …» и далее реплики. SMB — через pure-python клиент
  (без монтирования CIFS в контейнер). Секреты — в `app_settings`,
  зашифрованы мастер-ключом (AES-GCM).
- Retention: отдельные сроки для текста и аудио на уровне комнаты; фоновая
  очистка в backend.

### 3.7 Протоколы встреч
- **Стенограмма** — полный протокол по времени и участникам: шапка («Переговорка», дата и день недели, начало/окончание,
  «Участвовали: …») и реплики `[ЧЧ:ММ:СС] Имя: текст`. Доступна в интерфейсе, как `.txt` через API
  (`/api/v1/meetings/{id}/transcript.txt`) и выгружается в хранилище.
- **Краткий протокол** (решения, поручения) — `ProtocolService`: стенограмма → **API обезличивания**
  (`integrations/anonymizer`, DocClean или произвольный JSON API, портировано из старого проекта) → LLM
  (`integrations/llm`: OpenAI, Anthropic, OpenAI-совместимые, в т.ч. шлюзы с фиксацией провайдера) → сохранение и выгрузка
  `summary.txt`. **Fail closed**: нет настройки/таймаут/не-2xx/`verification.clean != true` → в LLM не уходит ничего,
  протокол получает статус `failed` с понятной причиной. Длинные встречи обрабатываются по частям (заметки → итог).
- Инструкции: глобальные (админка → «LLM и протокол») + для комнаты (`rooms.protocol_instructions`).
- Запуск: вручную из истории встречи либо автоматически по завершении (`protocol.auto_generate`).

### 3.7.1 Хранилище и запись (факты реализации)
- По завершении встречи (`MeetingService.end` → `ProtocolService.finalize`, фоновая задача): запись аудио → WAV,
  выгрузка стенограммы в хранилище `<корень>/<комната>/<ГГГГ-ММ-ДД, день недели>/<ЧЧ-ММ>/protocol.txt`
  (при совпадении минуты — « (2)»), затем автопротокол.
- Хранилище: локальный каталог (внутри контейнера, по умолчанию `/data/exports`) или SMB (`smbprotocol`, без монтирования).
- Аудио: ASR-воркер пишет сырой PCM `/data/recordings/<m-…>/<u-…>.pcm` (устойчив к обрыву); backend превращает в WAV
  `recordings/<комната>/<дата, день>/<время>/<Имя>.wav` и регистрирует в `recordings`. Скачивание — только админ, в аудит.
- Кнопки «Начать/Остановить запись» (`POST /meetings/{id}/recording`) меняют флаги живой сессии ASR командой `config`;
  состояние рассылается всем по WebSocket (`recording_changed`) и видно индикатором «● Идёт запись».
- Сроки хранения (`workers/retention.py`, раз в час): текст/краткие протоколы и аудио — раздельно по комнате; `0` = после
  обработки; пусто = бессрочно. Уже выгруженное во внешнее хранилище приложение не удаляет.

### 3.7.2 Трансляция экрана
Одна кнопка «Показать экран». Профили (админка → «Экран»): *Чёткость* (текст/слайды: 1080p, 15 к/с, `contentHint=text`,
`maintain-resolution`), *Сбалансированный*, *Плавность* (видео: 1080p, 30 к/с, `maintain-framerate`). VP9 для экрана
(SDK добавляет резервный кодек), дополнительный низкий simulcast-слой, `adaptiveStream` и `dynacast` у зрителей;
у зрителей — большая «сцена» с полноэкранным режимом (двойной клик), «вписать/заполнить» и текущим разрешением.
Звук экрана — по настройке, в транскрибацию не попадает. Права публикации экрана — в LiveKit-токене по настройке комнаты.

### 3.8 Права
- Админ — членство в `LDAP_ADMIN_GROUP_DN`.
- Доступ к комнате — `room_acl` (subject = AD-группа или конкретный
  пользователь). Пустой ACL = никому, кроме админов. Пароль комнаты (если
  задан) — дополнительный фактор поверх ACL; хранится как argon2/bcrypt-хэш.
- Любая проверка выполняется на backend при каждом запросе и при выдаче токена.

### 3.9 Аудит и журналы
- Структурированные JSON-логи, `X-Request-ID` на каждый запрос.
- Аудит админ-действий — отдельная таблица `audit_log`, не смешивается с
  техническим логом. Пароли, токены, секреты, LDAP bind в логи не попадают
  (фильтр + отсутствие в коде).

## 4. Модель данных (первая миграция)

`users`, `rooms`, `room_acl`, `meetings`, `meeting_participants`,
`transcript_segments`, `audit_log`, `app_settings`.
Подробные поля — `backend/app/models/` и миграция `backend/migrations/versions/0001_initial.py`.
Заложены сразу: пароль комнаты, флаги камеры/экрана/записи/транскрибации,

(`recordings`, `protocols`) добавляются своими миграциями на соответствующих
этапах.

## 5. API

- REST `/api/v1/*` + OpenAPI (`/api/v1/docs`, отключаемо).
- WebSocket `/api/v1/ws`: аутентификация по cookie сессии, проверка Origin;
  клиент подписывается на встречу, сервер проверяет ACL и шлёт события
  `segment`, `participant_joined/left`, `meeting_ended`.
- Health: `/api/v1/health/live`, `/api/v1/health/ready` (БД + Redis + LiveKit
  + ASR heartbeat), `/api/v1/version`.
- Внутренние `/internal/v1/*` — только по сервисному токену и только из
  внутренней сети (nginx наружу `/internal` не пропускает).

## 6. Развёртывание

Два профиля: `shared-host` (консервативный, Docker внешняя зависимость,
отдельный nginx-site, никаких чужих изменений) и `standalone` (новый
сервер). Подробности и перечень файлов/команд — `DEPLOYMENT.md`.

## 9. Известные ограничения проекта (осознанные)

- Группы пользователя в сессии обновляются при входе, не «на лету».
- Отброшенные при перегрузке сегменты не восстанавливаются (в метриках).
- Один сервер LiveKit (SFU без кластера) — целевой масштаб «односерверный
  корпоративный разворот».
- Браузерный микрофон требует HTTPS (secure context) — TLS на внешнем
  reverse proxy/nginx обязателен.
