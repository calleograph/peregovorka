# PROJECT.md — Peregovorka: текущее состояние

Единственное актуальное описание проекта. Только факты; запланированное и непроверенное помечено явно. Целевая архитектура и
причины решений — `ARCHITECTURE.md`. Журнал изменений — `HISTORY.md` (только дописывается). Старый проект — `legacy/`, `docs/legacy/`.

## 1. Назначение

Локальная корпоративная система голосовых переговорок: вход доменной учёткой AD (LDAPS), звук/видео/экран через локальный
LiveKit, транскрибация каждого участника отдельным микрофонным треком (GigaAM v3 E2E RNNT + Silero VAD), история встреч,
протоколы и резюме по инструкции пользователя (после обезличивания по API, через LLM), выгрузка в локальное/SMB-хранилище.
Внешние облака для авторизации, медиа и распознавания не используются. Создан поверх старого PHP-проекта (`legacy/php/`,
локально, вне Git); новый код от него не зависит.

## 2. Фактическая архитектура

Сервисы compose (`deployment/compose.yml`): `postgres`, `redis`, `livekit`, `backend` (FastAPI), `asr` (воркер + health),
`web` (nginx + React SPA). Медиа — LiveKit ⇄ браузер напрямую (UDP mux + TCP). Backend ⇄ ASR — Redis (`asr:sessions`,
`asr:control`, `asr:segments`, `asr:heartbeat`; `docs/ASR_CONTRACT.md`); запись аудио — общий том.

Сквозной путь: логин AD → список комнат по ACL → `join` (встреча + команда ASR + токен LiveKit; **не ждёт готовности ASR**) →
браузер: LiveKit и канал событий (WebSocket) открываются параллельно, микрофон публикуется асинхронно → ASR (скрытый участник,
микрофонные треки) → VAD → очередь → GigaAM → `asr:segments` → реплика в БД → pub/sub → WebSocket → панель.

**Доступ к завершённой встрече** (`services/access.py`): админ; участник идущей встречи; «аренда» (lease) у тех, кто был в комнате при
завершении, пока открыта страница встречи (`/release` при уходе; срок — `post_meeting_access_minutes`); политика комнаты
`history_access=participants`; явные `meeting_grants`. Прямой URL/ID доступа не даёт. WebSocket подписка — те же правила.

**Протоколы** (`services/protocols.py`): `POST /meetings/{id}/protocols {kind: protocol|summary, instruction}` — инструкцию
подтверждает пользователь в окне; обезличивание → LLM (fail closed); просмотр/правка/удаление (удаление — админ, аудит); экспорт
md/txt/docx/pdf; шаблоны инструкций (общие — админ, личные). Выгрузка `official-protocol.md` / `summary.md` в хранилище.

**Модель распознавания** (`asr-service/app/{catalog,runtimes,model_manager,scoring}.py`, `backend/app/api/admin_asr.py`): каталог моделей —
данные (Full/PyTorch и Q5_K_M/GGUF + `catalog.json` для новых), runtime — регистрируемые фабрики; выбор хранится в настройках (`asr.active_model`) и
раздаётся через Redis (`asr:desired_model`, воркер `asr_sync` восстанавливает ключ); ASR переключает модель «загрузить → переключить → освободить», при
ошибке прежняя остаётся активной; отсутствие файлов — понятная ошибка. Админка: статус, размер, runtime, устройство CPU, «Протестировать модель» и
«Сравнить установленные модели» на встроенном WAV (скорость, RTF, CPU, RAM, WER/CER, пунктуация).

**Хранилища**: протоколы (`storage`) и записи (`audio_storage`) — раздельные настройки в БД, `local|smb`; недоступность
хранилища записей не теряет файл (статус `failed`, повторная выгрузка автоматически и кнопкой).

**Обновление** (`scripts/update.sh`, `lib/updatelib.sh`): fetch → список commit'ов → отказ при локальных изменениях (stash только по `--stash`, не применяется автоматически) → копия `.env` (600) и сравнение
с `.env.example` по именам (безопасные новые параметры дописываются, остальное — «требуют решения»; секреты не печатаются) → `git merge --ff-only` → перезапуск скрипта новой версией (фаза 2) →
закрепление LiveKit на проверенной версии (`deployment/compat.env`; `latest` в production не используется) → preflight → проверка моделей (ничего не скачивается повторно) → backup БД →
сборка (retry apt/pip/npm/git/docker pull, fallback BuildKit→legacy, commit и время сборки в образах и `/version.json`, индикатор долгой сборки) → Alembic (`current == head`) → up и ожидание healthcheck →
миграция собственного nginx-site (по marker) → verify (сравнивает git HEAD с commit образов) → smoke-test → итог. Состояние: `DATA_ROOT/state/last-update.state`; `rollback.sh` останавливается,
если ревизия БД неизвестна коду целевой версии (git rollback ≠ database rollback). Прерванное обновление повторяется той же командой.

**Правки по итогам обновления на реальном сервере** (HISTORY.md, 2026-10-08): `BACKUP_DIR`/`BACKUP_COPY_DIR` проверяются как `DATA_ROOT` (`validate_env_paths` в `backup.sh`, `update.sh`, `rebuild.sh`, `preflight.sh`); копия дампа на сетевой
ресурс — отдельным шагом (`BACKUP_COPY_DIR`, сбой только предупреждает). Проверка LiveKit разделена на «маршрут `/rtc/v1` существует» (ответ 400 «join_request is required» — норма) и «WebSocket Upgrade на `/rtc` → 101» (напрямую, через web, публичный URL);
вывод «виноват прокси» делается только если напрямую 101, а через прокси нет. TLS: цепочка, которой не доверяет сам сервер, — WARNING (истёкший срок и несовпадение имени — по-прежнему FAIL). `scripts/rebuild.sh` — ручная пересборка с правильным commit
(вместо `docker compose build`). Окно обновления: опции переименованы («Полная пересборка всех образов (обычно не требуется)», «Обновить базовые образы PostgreSQL/Redis (необязательно)»), заметное сообщение про однократную установку службы, подсветка образа с commit «unknown».

**Руководители комнат** (`api/moderation.py`, таблица `room_moderators`, миграция 0005): в настройках комнаты назначаются группы AD и люди с правом выключать микрофоны — у всех участников одной кнопкой («Выключить у всех», кроме себя) или у одного
(кнопка на плитке участника). Администраторы сервера — руководители всех комнат; руководителю вход разрешён и вне списка доступа. Выключение выполняется на стороне LiveKit (mute дорожки), участник может включить микрофон сам; он видит уведомление.
Действия пишутся в аудит и журнал. Новые параметры комнаты: «микрофон при входе выключен» и приветствие. Форма комнаты разбита на вкладки (основное, доступ и руководители, возможности, нейросети, хранение), доступ и руководители редактируются списками.

**Обновление из веб-интерфейса** (Администрирование → Обзор → «Обновления и версии»; `api/admin_updates.py`, `services/updates.py`, `scripts/updater.sh`): backend не имеет доступа к Docker/git и ничего не обновляет сам. Он кладёт запрос в `$DATA_ROOT/updater`
(монтируется в `/data/updater`), а «исполнитель» на хосте (`updater.sh run` / служба systemd `updater.sh install`) выполняет только `scripts/update.sh --yes` с флагами из списка и пишет `status.json`, `remote.json` (git fetch: новые commit'ы,
миграции, параметры `.env`), `update.log`. Окно показывает версии (установлено / GitHub), этапы и построчный вывод; оно переживает перезапуск backend. Без исполнителя кнопка недоступна, интерфейс объясняет, что сделать.
Таблица «Версии компонентов» (также на панели «Состояние системы»): установлено · проверено с проектом · актуально в интернете (GitHub/PyPI/npm, кэш 6 ч; без интернета — «нет данных») · статус · что делать;
закреплённые компоненты отдельно не обновляются. Запрос от веб-интерфейса проверяется исполнителем (формат, возраст, разрешённые флаги). **Не проверено на реальном сервере** (подставной `update.sh`, подставной стенд интерфейса).

**Журнал событий** (`services/journal.py`, `api/admin_journal.py`, таблица `event_log`, миграция 0004): запись неблокирующая (очередь → пакетная запись), сбой журнала не влияет на работу. Пишутся входы и отказы
(логин показывается только если он корректен — пароль, введённый в поле логина, не попадает), блокировки, вход/выход из комнат, события браузера (ICE, повторы подключения, медленный вход, занятый микрофон, отказ в разрешениях, список устройств
и сведения о сети и оборудовании клиента), создание протоколов (профиль API, было ли обезличивание), ошибки выгрузки записей, записи аудита администраторов (зеркало). Срок хранения — 30 дней (настраивается, `retention_days`), очистка раз в час,
в том числе во внешнем хранилище. Хранение: в базе (`keep_local`) и/или во внешнем каталоге/SMB файлами NDJSON `journal/ГГГГ-ММ-ДД/…ndjson` (`enabled`); оба выключены — журнал не ведётся. Админка: бесконечная лента (курсор по id, без страниц),
10 столбцов, фильтры с условиями «равно / не равно / содержит / не содержит / начинается / не ниже» (объединяются через «И»), быстрые наборы, щелчок по значению добавляет фильтр, выбор записей флажками (с Shift — диапазон) и удаление выбранных
или всех по фильтру (с подтверждением, пишется в аудит), статистика и размер журнала (также на панели «Состояние системы»), две кнопки выгрузки — за сутки и полный архив за 30 дней (ZIP: `journal.csv` для Excel с защитой от формул, `journal.ndjson`,
`audit.csv`). Журнал аудита (`audit_log`) остаётся неизменяемым: вручную не удаляется.

**Несколько API и обезличивание по желанию** (`services/api_profiles.py`, таблица `api_profiles`, поля комнаты `anonymize_mode`, `llm_profile_id`, `anonymizer_profile_id`): для LLM и для обезличивания можно завести несколько профилей, выбрать один «по умолчанию для всех»,
а комнате назначить свой. «Основной» профиль — прежние общие настройки (после обновления всё работает как раньше). Обезличивание: `inherit` (как в общих настройках: включено → fail closed, выключено → текст идёт в LLM как есть и ничему не мешает),
`on` (всегда; если сервис не настроен — протокол не создаётся), `off` (выключено для комнаты). В метаданных протокола — `anonymized`, `llm_profile`, `anonymizer_profile`; окно «Сформировать протокол» честно показывает, будет ли текст обезличен.

**Комната (браузер)**: круглые кнопки-пиктограммы (микрофон, камера, шумоподавление, показ экрана, запись, выход) с состояниями «включено / выключено / идёт процесс» и анимацией; шумоподавление, эхоподавление и автоусиление включаются и применяются «на лету»
(перезапуск захвата), есть режим «освобождать микрофон при выключении». Занятый другой программой микрофон не блокирует вход: пользователь остаётся в комнате без звука, видит причину (включая «монопольный режим» Windows) и кнопку «Повторить»; в журнал уходит
число и названия устройств, состояние разрешений. Первое подключение при сетевых/ICE-сбоях (`could not establish pc connection`, таймауты) автоматически повторяется до 3 раз со свежим токеном; итоговый отказ и медленное установление ICE (> 4 с) записываются
в журнал с данными о сети клиента (тип и задержка соединения, ядра, память, экран, браузер и ОС).

**Защита (быстрый аудит)**: логин принимается по белому списку (буквы, цифры, `. _ -`; `ДОМЕН\логин`, `логин@домен`; на клиенте и на сервере), пароль по символам не фильтруется (допустимы любые); блокировка входа после 20 неверных вводов на логин на 5 минут
(`LOGIN_MAX_FAILURES_PER_USER=20`, `LOGIN_LOCKOUT_SECONDS=300`, по IP — 60); события диагностики клиента ограничены 240 в минуту на пользователя; CSV-выгрузка экранирует ячейки, начинающиеся с `= + - @`; ответы API не кэшируются (`Cache-Control: no-store`);
изменение значений по умолчанию не затрагивает уже существующий `.env` — для действующих установок строки нужно поправить вручную. Небезопасное (http) подключение по-прежнему работает, если `COOKIE_SECURE=false`.

**Realtime-аудит** (`docs/realtime-performance-audit.md`, статусы hypothesis/confirmed/fixed/measured): критический путь входа — `Room.connect`; `getUserMedia`,
WebSocket событий и ASR идут параллельно/независимо; жизненный цикл Room и показа экрана логируется с `client_instance_id` (фазы `ROOM_CREATE … ROOM_DISPOSE`, `SCREEN_*`);
статистика WebRTC (кодек, FPS, битрейт, потери, jitter, RTT, NACK/PLI/FIR, кадры, путь ICE) + детектор заморозки по `framesDecoded`; запись аудио ASR — через ограниченную очередь
и поток-писатель; тайминги каждого сегмента (`vad_wait_ms … end_to_end_ms`); VAD-параметры меняются в админке на лету; realtime-директивы nginx (`proxy_buffering off`, `tcp_nodelay on`).

**Диагностика** (`services/diagnostics.py`, `timings.py`, `api/client.py`): отчёт (версии, ядро, WebSocket-проба `/rtc/v1`,
RTC TCP/UDP, зависимости, ASR, тайминги) с маскированием секретов; метрики времени входа по этапам (backend, браузер, ASR);
события и статистика WebRTC из браузера (screen share).

## 4. Технологии и версии

Python 3.12 (образы), FastAPI, SQLAlchemy 2 (async), Alembic, PostgreSQL 16 и Redis 7 (мажор закреплён намеренно), LiveKit Server
(`LIVEKIT_IMAGE_TAG`, **закреплён v1.13.7**), `livekit` 1.1.20 / `livekit-api` 1.2.1 (Python, `==`), GigaAM (закреплённый коммит),
silero-vad, torch; frontend: React 19, React Router 7, Vite 8, TypeScript 7, Vitest 5, `livekit-client` 2.22.3 (точно). Прочие Python-зависимости заданы диапазонами
(≥ проверенной, < следующего мажора), npm — `^` + lock; базовые образы — через ARG (`docs/COMPATIBILITY.md`).

## 5. Конфигурация

Инфраструктура — `.env` (`.env.example`). Бизнес-настройки — в админке (БД), секреты шифруются `APP_MASTER_KEY`. Админка сгруппирована:
Обзор · Встречи · Комнаты и люди · Протоколы · Интеграции · Система; у каждого поля название, пояснение и пример. Таймауты комнаты LiveKit
(`LIVEKIT_ROOM_DEPARTURE_TIMEOUT`, `LIVEKIT_ROOM_EMPTY_TIMEOUT`) и `MEETING_END_GRACE_SECONDS` (60) задают льготный период: webhook
`room_finished` встречу сразу не завершает.

## 7. Известные ограничения и непроверенное

- **Не проверялось на реальных LiveKit/GigaAM/SMB/клиентах:** живая комната, показ экрана (причины остановки, статистика, повторный запуск),
  автоматический повторный вход, ASR-инференс, реальный SMB, `smoke-test`/`diag.sh`/`tune-kernel.sh` на сервере (проверены функции и логика на подставных данных),
  синтаксис `room: {departure_timeout, empty_timeout}` в конфигурации LiveKit (написан по документации, не запускался).
- **Причина 5-секундной паузы входа не подтверждена измерением.** Подтверждено логами: 404 на `/rtc/v1` + откат на `/rtc`; подтверждено чтением кода: последовательные независимые операции во frontend (исправлены). Связь «404 → ~5 с» — гипотеза (docs/realtime-performance-audit.md §F1). **Замер времени входа после обновления LiveKit не выполнен.** Гипотеза (404 на `/rtc/v1` → запасной путь) подтверждена наблюдением владельца;
  устранение — новый сервер, проверка — `smoke-test.sh`. Второй вклад в задержку устранён в коде: комната и WebSocket открываются сразу после `/join`,
  микрофон публикуется асинхронно (раньше ждал ответа на запрос разрешения).
- **`Attempted to drop unknown FFI handle` (ASR):** причина не подтверждена. Вероятные: двойное отключение комнаты и закрытие потоков после
  освобождения комнаты — порядок исправлен (потоки дожидаются, уже отключённая комната не отключается повторно). Нужен повторный тест на сервере;
  пока warning не считать безобидным.
- **Runtime GGUF** (`asr-service/app/runtimes.py`, `GgufNativeProvider`): Python-привязки transcribe.cpp (`transcribe-cpp` 0.3.x), модель резидентна, пул сессий по `ASR_MAX_CONCURRENT_INFERENCE`.
  Проверен на реальной модели Q5_K_M (Windows, CPU): WER 4,5 % на тестовой записи, RTF ≈ 0,24; **в Docker-образе Linux ещё не собирался** (колёса manylinux есть на PyPI). Запасной вариант — внешний бинарник. Реальное сравнение Full ↔ Q5_K_M на серверных CPU не выполнялось.
