# PROJECT.md — Peregovorka: текущее состояние

Единственное актуальное описание проекта. Только факты; запланированное и непроверенное помечено явно. Целевая архитектура и
причины решений — `ARCHITECTURE.md`. Журнал изменений — `HISTORY.md` (только дописывается). Старый проект — `legacy/`, `docs/legacy/`.

## 1. Назначение

Локальная корпоративная система голосовых переговорок: вход доменной учёткой AD (LDAPS), звук/видео/экран через локальный
LiveKit, транскрибация каждого участника отдельным микрофонным треком (GigaAM v3 E2E RNNT + Silero VAD), история встреч,
протоколы и резюме по инструкции пользователя (после обезличивания по API, через LLM), выгрузка в локальное/SMB-хранилище.
Внешние облака для авторизации, медиа и распознавания не используются. Создан поверх старого PHP-проекта (`legacy/php/`,
локально, вне Git); новый код от него не зависит.

## 2. Фактическая архитектура

Сервисы compose (`deployment/compose.yml`): `postgres`, `redis`, `livekit`, `backend` (FastAPI), `asr` (воркер + health),
`web` (nginx + React SPA). Медиа — LiveKit ⇄ браузер напрямую (UDP mux + TCP). Backend ⇄ ASR — Redis (`asr:sessions`,
`asr:control`, `asr:segments`, `asr:heartbeat`; `docs/ASR_CONTRACT.md`); запись аудио — общий том.

Сквозной путь: логин AD → список комнат по ACL → `join` (встреча + команда ASR + токен LiveKit; **не ждёт готовности ASR**) →
браузер: LiveKit и канал событий (WebSocket) открываются параллельно, микрофон публикуется асинхронно → ASR (скрытый участник,
микрофонные треки) → VAD → очередь → GigaAM → `asr:segments` → реплика в БД → pub/sub → WebSocket → панель.

**Доступ к завершённой встрече** (`services/access.py`): админ; участник идущей встречи; «аренда» (lease) у тех, кто был в комнате при
завершении, пока открыта страница встречи (`/release` при уходе; срок — `post_meeting_access_minutes`); политика комнаты
`history_access=participants`; явные `meeting_grants`. Прямой URL/ID доступа не даёт. WebSocket подписка — те же правила.

**Протоколы** (`services/protocols.py`): `POST /meetings/{id}/protocols {kind: protocol|summary, instruction}` — инструкцию
подтверждает пользователь в окне; обезличивание → LLM (fail closed); просмотр/правка/удаление (удаление — админ, аудит); экспорт
md/txt/docx/pdf; шаблоны инструкций (общие — админ, личные). Выгрузка `official-protocol.md` / `summary.md` в хранилище.

**Модель распознавания** (`asr-service/app/{catalog,runtimes,model_manager,scoring}.py`, `backend/app/api/admin_asr.py`): каталог моделей —
данные (штатно только Full/PyTorch; Q5_K_M/GGUF снята с вооружения, `catalog.json` для новых), runtime — регистрируемые фабрики; выбор хранится в настройках (`asr.active_model`) и
раздаётся через Redis (`asr:desired_model`, воркер `asr_sync` восстанавливает ключ); ASR переключает модель «загрузить → переключить → освободить», при
ошибке прежняя остаётся активной; отсутствие файлов — понятная ошибка. Админка: статус, размер, runtime, устройство CPU, «Протестировать модель» и
«Сравнить установленные модели» на встроенном WAV (скорость, RTF, CPU, RAM, WER/CER, пунктуация).

**Хранилища**: протоколы (`storage`) и записи (`audio_storage`) — раздельные настройки в БД, `local|smb`; недоступность
хранилища записей не теряет файл (статус `failed`, повторная выгрузка автоматически и кнопкой).

**Обновление** (`scripts/update.sh`, `lib/updatelib.sh`): автопочинка git (`lib/autorepair.sh`) → fetch → список commit'ов → локальные изменения и свои коммиты сохраняются (патч/архив/stash/bundle) → проверка источников сборки из базовых образов сборки с реальной передачей (`lib/netcheck.sh`, `scripts/netprobe.py`; недоступен и зависимости менялись — остановка до переключения кода; доступен только из сети хоста — `BUILD_NETWORK=host`) → копия `.env` (600) и сравнение
с `.env.example` по именам (безопасные новые параметры дописываются, остальное — «требуют решения»; секреты не печатаются) → `git merge --ff-only` → перезапуск скрипта новой версией (фаза 2) →
закрепление LiveKit на проверенной версии (`deployment/compat.env`; `latest` в production не используется) → preflight → проверка моделей (ничего не скачивается повторно) →
сборка (retry apt/pip/npm/git/docker pull; сетевые сбои внутри RUN, включая npm `ETIMEDOUT`, — класс network; повторы ≤ `BUILD_ATTEMPTS` в пределах `BUILD_BUDGET_S` с перепроверкой источника; готовые компоненты не пересобираются; fallback BuildKit→legacy, commit и время сборки в образах и `/version.json`, индикатор долгой сборки) → сверка образов с устанавливаемым commit → при миграциях остановка приложения → backup БД → Alembic (`current == head`) → up и ожидание healthcheck →
миграция собственного nginx-site (по marker) → verify (сравнивает git HEAD с commit образов) → smoke-test → итог. Состояние: `DATA_ROOT/state/last-update.state`; `rollback.sh` останавливается,
если ревизия БД неизвестна коду целевой версии (git rollback ≠ database rollback). Прерванное обновление повторяется той же командой.

**Правки по итогам обновления на реальном сервере** (HISTORY.md, 2026-10-08): `BACKUP_DIR`/`BACKUP_COPY_DIR` проверяются как `DATA_ROOT` (`validate_env_paths` в `backup.sh`, `update.sh`, `rebuild.sh`, `preflight.sh`); копия дампа на сетевой
ресурс — отдельным шагом (`BACKUP_COPY_DIR`, сбой только предупреждает). Проверка LiveKit разделена на «маршрут `/rtc/v1` существует» (ответ 400 «join_request is required» — норма) и «WebSocket Upgrade на `/rtc` → 101» (напрямую, через web, публичный URL);
вывод «виноват прокси» делается только если напрямую 101, а через прокси нет. TLS: цепочка, которой не доверяет сам сервер, — WARNING (истёкший срок и несовпадение имени — по-прежнему FAIL). `scripts/rebuild.sh` — ручная пересборка с правильным commit
(вместо `docker compose build`). Окно обновления: опции переименованы («Полная пересборка всех образов (обычно не требуется)», «Обновить базовые образы PostgreSQL/Redis (необязательно)»), заметное сообщение про однократную установку службы, подсветка образа с commit «unknown».

**Руководители комнат** (`api/moderation.py`, таблица `room_moderators`, миграция 0005): в настройках комнаты назначаются группы AD и люди с правом выключать микрофоны — у всех участников одной кнопкой («Выключить у всех», кроме себя) или у одного
(кнопка на плитке участника). Администраторы сервера — руководители всех комнат; руководителю вход разрешён и вне списка доступа. Выключение выполняется на стороне LiveKit (mute дорожки), участник может включить микрофон сам; он видит уведомление.
Действия пишутся в аудит и журнал. Новые параметры комнаты: «микрофон при входе выключен» и приветствие. Форма комнаты разбита на вкладки (основное, доступ и руководители, возможности, нейросети, хранение), доступ и руководители редактируются списками.

**Обновление из веб-интерфейса** (Администрирование → Обзор → «Обновления и версии»; `api/admin_updates.py`, `services/updates.py`, `scripts/updater.sh`): backend не имеет доступа к Docker/git и ничего не обновляет сам. Он кладёт запрос в `$DATA_ROOT/updater`
(монтируется в `/data/updater`), а «исполнитель» на хосте (`updater.sh run` / служба systemd `updater.sh install`) выполняет только `scripts/update.sh --yes` с флагами из списка и пишет `status.json`, `remote.json` (git fetch: новые commit'ы,
миграции, параметры `.env`), `update.log`. Окно показывает версии (установлено / GitHub), этапы и построчный вывод; оно переживает перезапуск backend. Без исполнителя кнопка недоступна, интерфейс объясняет, что сделать.
Таблица «Версии компонентов» (также на панели «Состояние системы»): установлено · проверено с проектом · актуально в интернете (GitHub/PyPI/npm, кэш 6 ч; без интернета — «нет данных») · статус · что делать;
закреплённые компоненты отдельно не обновляются. Запрос от веб-интерфейса проверяется исполнителем (формат, возраст, разрешённые флаги). **Не проверено на реальном сервере** (подставной `update.sh`, подставной стенд интерфейса).

**Самопроверки и надёжность обновления** (после инцидента `default $xfp;` внутри `map … $xfp` в `frontend/nginx.conf`: «cycle while evaluating variable», 499 при X-Forwarded-Proto: https): `check_web_image_config` (`nginx -t` в собранном образе web ДО замены контейнера;
`update.sh`, `rebuild.sh`), `verify_deployment` — этапы PASS/FAIL (контейнеры, `nginx -t` в web, запрос через web со схемой https и цепочкой X-Forwarded-For, `/health/ready`, WebSocket LiveKit через web), итог печатают `verify.sh`, `update.sh`, `rebuild.sh` (rebuild сам запускает verify);
CI `web-image` (`tests/nginx/run.sh`: настоящая сборка образа web и запросы на живом nginx, **включая стадию draw.io**), статическая проверка map на самоссылку. История обновлений: `$DATA_ROOT/updater/history.ndjson` (пишет `update.sh` при любом запуске, источник cli/web); «Обновления и версии» показывают установленную версию,
последнее успешное обновление и историю, прежний неудачный запуск из веб-интерфейса помечается `stale`. **Диагностика подключения** (`frontend/src/lkDiag.ts`): этапы сигнал/ICE/медиа, `ERR_CONNECTION_RESET` объясняется как сетевая проблема (VPN/MTU/прокси/файрвол; на практике помог MTU=1250), HTTPS-проверка сервера звонков, событие `livekit_connection`
(транспорт, ICE, пара кандидатов, время сигнала; без токенов), `redactSecrets` на клиенте и `scrub` на сервере; библиотека звонков пишет в консоль только предупреждения (нативное сообщение браузера об ошибке WebSocket с адресом изменить нельзя). **IP клиента**: `pick_client_ip` — цепочка X-Forwarded-For справа налево,
пропуская `TRUSTED_PROXY_CIDRS` (по умолчанию loopback) и `TRUSTED_PROXY_HOPS-1` прокси. Автоматический протокол для пустой встречи не создаётся (`protocol_skipped`, info). README — короткий продуктовый, подробности — `docs/INTERNALS.md`.

**Версионирование** (`VERSION`, `CHANGELOG.md`, `scripts/release.sh`, `scripts/lib/versionlib.sh`, `.github/workflows/{ci,release}.yml`, `docs/VERSIONING.md`): схема `0.1.0 → 0.1.1 → …`, единственный источник — файл `VERSION`. Образы собираются с ним (`host_version_info`),
commit — из git (устойчиво к «dubious ownership» и отсутствию команды `git`); `update.sh`/`rebuild.sh` не собирают образ с commit «unknown». В интерфейсе — «версия · commit (7 символов)»; окно «Обновления и версии» показывает версию и commit установленной и
опубликованной редакции и разделы CHANGELOG новее установленной (`remote.json`: `current_version`, `remote_version`, `changelog`); итог `update.sh` — «Version: A → B», `verify.sh` сверяет версию образов с `VERSION`. `release.sh patch|minor|X.Y.Z` переносит «Unreleased» в раздел версии, пишет `VERSION` и `frontend/package*.json`,
делает commit «Релиз X.Y.Z» и аннотированный тег `vX.Y.Z`; push тега запускает workflow «Release» (GitHub Release с описанием из CHANGELOG); CI проверяет согласованность (`release.sh check`). Теги и релизы — с `0.1.4` (0.1.0–0.1.3 описаны ретроспективно).
Главная страница (README): не более двух снимков интерфейса (комната, админка), без сообщений об ошибках; актуализируется при каждом выпуске.

**Общая доска, чат, гостевой доступ** (`api/collab.py`, `api/guest.py`, `auth/guests.py`, `services/{whiteboard,materials}.py`, таблицы `guest_participants`, `meeting_chat_messages`, `meeting_whiteboards`, поля комнаты
`guest_access_enabled`/`guest_token`, `transcript_segments.guest_id`, миграция 0006; подробно — `docs/COLLABORATION.md`). Доска — draw.io v32.3.0 (Apache-2.0), стадия `drawio` в `frontend/Dockerfile` (клон тега с повторами,
`frontend/drawio/prune.sh`), раздаётся nginx на `/drawio/` (свой CSP и CORS `*`, `frame-src 'self'` у приложения), встроена iframe'ом с sandbox без `allow-same-origin`; синхронизация — патчи `diffSync` с номером `seq` (Redis INCR),
рассылка через pub/sub, снимки полного XML, перезагрузка при пропуске номера/расхождении сумм. Чат привязан к встрече; ссылки в новой вкладке. Для протокола собирается пакет «стенограмма + чат + описание схемы»
(без чата и схемы текст прежний). Гость — отдельный тип участника (`participant_type=guest`, identity `g-<uuid>`, сессия в Redis по заголовку `X-Guest-Token`), не начинает встречу, без админ-функций/истории/стенограммы/показа экрана;
ссылку можно перевыпустить/отозвать (гости отключаются). Пока в вкладке идёт встреча, разделы приложения открываются в новых вкладках (`activeMeeting.ts`). Чат и схема выгружаются (`chat.txt`, `whiteboard.drawio`) и удаляются по сроку
хранения текста. **Не проверено на реальном сервере:** сборка стадии draw.io в Docker, раздача настоящим nginx, звонок гостя через живой LiveKit.

**Роли, презентационные комнаты, «слово»** (`services/roles.py`, `api/{room_manage,moderation,clientcfg}.py`, `services/meetings.py`, `services/livekit.py`, поля комнаты `room_type`, `auto_record`, `board_allowed`, миграция 0007; подробно — `docs/ROOMS_AND_ROLES.md`).
Роли: администратор сервера → руководитель комнаты (несколько; список `moderators`) → ведущий (имеет слово на текущей встрече) → участник → гость. Всё, что можно публиковать, определяет `publish_sources` и попадает в токен LiveKit (`can_publish_sources`);
в презентационной комнате слушатель получает `can_publish=false`; слово (`floor:{meeting}` в Redis, сбрасывается по окончании встречи) меняет разрешения на лету (`update_participant`). `Meeting.transcription_enabled` — состояние транскрибации (по умолчанию включена),
`Meeting.record_audio` — запись звука (включается автоматически при `auto_record`); руководитель управляет обоими раздельно. «Настройки комнаты» для руководителя — `GET/PATCH /rooms/{id}/manage`, гостевая ссылка и поиск в AD; системные поля недоступны, комната не остаётся без руководителей,
действия пишутся в аудит. Удаление участника — `moderation/kick` (блокировка повторного входа 10 минут).

**Единый слой хранения и вложения чата** (`services/{filestore,chat_files,storage}.py`, `api/admin_system.py` — `/admin/storages`, группа настроек `chat_files`, таблицы `storage_profiles`, `meeting_chat_attachments`, миграция 0007; подробно — `docs/STORAGE.md`).
Профиль хранилища (SMB/каталог, пароль зашифрован) создаётся один раз; функции выбирают профиль через `profile_id` в своей группе; в профиле — подпапки `Audio/ Transcripts/ Protocols/ Chat/ Boards/ Logs/`. Старые настройки без профиля работают как раньше. Вложения: сырое тело запроса, путь формирует сервер,
тип — по сигнатуре содержимого, запрещённые расширения, лимиты размера/числа в настройках, безопасные заголовки отдачи, удаление вместе с перепиской, очистка неотправленных через 2 часа; отказ хранилища — понятная ошибка и событие журнала. Предел тела запроса nginx — 100 МБ.

**Верхнее меню, настройки комнаты, модель и рассылка по уровням, SIP (следующий релиз)** (`frontend/src/{navMenu.ts,components/NavMenu.tsx,components/{LlmChoiceEditor,TelephonyEditor,MeetingSettingsDialog,PhoneDialog}.tsx,pages/admin/SipAdmin.tsx,phone.ts}`, `backend/app/services/{llm_choice,sip}.py`, `api/{admin_sip,telephony,meeting_settings}.py`, миграция 0009, `scripts/{sip.sh,lib/siplib.sh}`, `docs/SIP.md`).
Модель: `resolve_llm` (система — `system_llm()`: первичен режим общих настроек local|external|off, профиль «Внешний API по умолчанию» берётся только при external → `rooms.llm_mode`/`llm_local_model`/профиль → `meetings.llm_override`, политика `on_missing` system|unavailable). Рассылка: `rooms.mail_delivery` + `meetings.delivery_override`, опция `archive` (zip). SIP: `SipProfile` (пароль шифруется, наружу `secret_set`), синхронизация с LiveKit (транки + правило направления на время идущей встречи), `CreateSIPParticipant`; телефонный участник — `GuestParticipant(participant_type="phone")`, identity `p-…`/`sip_…`, ASR принимает префиксы `u-`, `p-`, `sip_`. Контейнер `livekit-sip` — профиль compose `sip` (по умолчанию не запускается, порты не публикуются), LiveKit получает Redis db 1 через `LIVEKIT_REDIS_LINE`; включение — `scripts/sip.sh enable` или исправление `sip_enable` помощника. Проверки при выключенной телефонии — «пропущено».

**Локальный администратор, LDAP и CA из веб-интерфейса, установка одной командой (0.3.0)** (`services/{local_admin,ldap_profiles,ca_bundle}.py`, `auth/{service,directory}.py`, `api/admin_access.py`, `app/cli.py`, `install.sh`, `scripts/{setup,bootstrap-admin,admin-reset}.sh`, таблицы `ldap_profiles`, `ca_certificates`, поля `users.auth_source/password_hash/must_change_password`, миграция 0008; подробно — `docs/ADMIN_SETUP.md`, `docs/INSTALL_AND_UPDATE.md`).
Локальный администратор (`auth_source=local`, пароль argon2id) проверяется первым и не зависит от каталога; первичный пароль генерируется случайно (`python -m app.cli bootstrap-admin` в контейнере backend), печатается только в терминал, при первом входе обязательна смена (`must_change_password` блокирует остальные запросы, кроме `/auth/change-password`). Сброс — `scripts/admin-reset.sh` (`app.cli admin-reset`: новый пароль, закрытие сеансов, снятие блокировки, аудит `local_admin.reset_by_console`).

**Несколько API и обезличивание по желанию** (`services/api_profiles.py`, таблица `api_profiles`, поля комнаты `anonymize_mode`, `llm_profile_id`, `anonymizer_profile_id`): для LLM и для обезличивания можно завести несколько профилей, выбрать один «по умолчанию для всех»,
а комнате назначить свой. «Основной» профиль — прежние общие настройки (после обновления всё работает как раньше). Обезличивание: `inherit` (как в общих настройках: включено → fail closed, выключено → текст идёт в LLM как есть и ничему не мешает),
`on` (всегда; если сервис не настроен — протокол не создаётся), `off` (выключено для комнаты). В метаданных протокола — `anonymized`, `llm_profile`, `anonymizer_profile`; окно «Сформировать протокол» честно показывает, будет ли текст обезличен.

**Комната (браузер)**: круглые кнопки-пиктограммы (микрофон, камера, шумоподавление, показ экрана, запись, выход) с состояниями «включено / выключено / идёт процесс» и анимацией; шумоподавление, эхоподавление и автоусиление включаются и применяются «на лету»
(перезапуск захвата), есть режим «освобождать микрофон при выключении». Занятый другой программой микрофон не блокирует вход: пользователь остаётся в комнате без звука, видит причину (включая «монопольный режим» Windows) и кнопку «Повторить»; в журнал уходит
число и названия устройств, состояние разрешений. Первое подключение при сетевых/ICE-сбоях (`could not establish pc connection`, таймауты) автоматически повторяется до 3 раз со свежим токеном; итоговый отказ и медленное установление ICE (> 4 с) записываются
в журнал с данными о сети клиента (тип и задержка соединения, ядра, память, экран, браузер и ОС).

**Защита (быстрый аудит)**: логин принимается по белому списку (буквы, цифры, `. _ -`; `ДОМЕН\логин`, `логин@домен`; на клиенте и на сервере), пароль по символам не фильтруется (допустимы любые); блокировка входа после 20 неверных вводов на логин на 5 минут
(с 0.41.4 пороги задаются в веб-интерфейсе: «Безопасность → Защита входа от перебора»); события диагностики клиента ограничены 240 в минуту на пользователя; CSV-выгрузка экранирует ячейки, начинающиеся с `= + - @`; ответы API не кэшируются (`Cache-Control: no-store`);
изменение значений по умолчанию не затрагивает уже существующий `.env` — для действующих установок строки нужно поправить вручную. Небезопасное (http) подключение по-прежнему работает, если `COOKIE_SECURE=false`.

**Realtime-аудит** (`docs/realtime-performance-audit.md`, статусы hypothesis/confirmed/fixed/measured): критический путь входа — `Room.connect`; `getUserMedia`,
WebSocket событий и ASR идут параллельно/независимо; жизненный цикл Room и показа экрана логируется с `client_instance_id` (фазы `ROOM_CREATE … ROOM_DISPOSE`, `SCREEN_*`);
статистика WebRTC (кодек, FPS, битрейт, потери, jitter, RTT, NACK/PLI/FIR, кадры, путь ICE) + детектор заморозки по `framesDecoded`; запись аудио ASR — через ограниченную очередь
и поток-писатель; тайминги каждого сегмента (`vad_wait_ms … end_to_end_ms`); VAD-параметры меняются в админке на лету; realtime-директивы nginx (`proxy_buffering off`, `tcp_nodelay on`).

**Диагностика** (`services/diagnostics.py`, `timings.py`, `api/client.py`): отчёт (версии, ядро, WebSocket-проба `/rtc/v1`,
RTC TCP/UDP, зависимости, ASR, тайминги) с маскированием секретов; метрики времени входа по этапам (backend, браузер, ASR);
события и статистика WebRTC из браузера (screen share).
