## 2026-10-06 — Создание Peregovorka на базе существующего PHP-проекта: архитектура, инфраструктура и вертикальный путь

**Основа.** Существовал PHP-сервис «Корпоративный AI-чат» (LDAPS-вход, группы AD, админка,
шлюз обезличивания DocClean, LLM-шлюз, SQLite). Изучены: `LdapClient`, `ChatAuthenticator`,
`AnonymizationGateway`/`AnonymizationSettings`, `SecretBox`, `RateLimiter`, `SessionManager`,
структура админки и дизайн-токены, PROJECT.md/HISTORY.md старого проекта. Решение: новый продукт
строится на стеке из ТЗ (FastAPI/React/LiveKit/Postgres/Redis/ASR-сервис); PHP-код не вписывается
в этот стек и перенесён в `legacy/php/` как справочный источник, а проверенные решения портированы.

**Сохранено/портировано из старого проекта.**
- LDAPS-вход: проверка сертификата, DN-поиск, группы через `LDAP_MATCHING_RULE_IN_CHAIN`, классификация
  кодов bind (775/533/532/773/52f) → `backend/app/auth/directory.py`.
- AES-256-GCM для секретов → `backend/app/security/secretbox.py`; защита от перебора и серверные сессии
  (HttpOnly, idle/absolute таймауты, CSRF) → `auth/{throttle,sessions,deps}.py` (Redis вместо SQLite/файлов).
- Шрифт IBM Plex Sans и нейтральная палитра → `frontend/public/fonts`, `frontend/src/styles.css`.
- Состав админки, DocClean-шлюз и LLM-адаптеры — отмечены к переносу на следующих этапах (остаются в `legacy/php`).

**Изменено/удалено из прежней структуры.** Старые `HISTORY.md` и `PROJECT.md` сохранены в
`docs/legacy/`; весь PHP-проект (кроме рабочих данных `var/`, исключённых из Git) перемещён в
`legacy/php/`; создан `legacy/README.md`. Функциональность AI-чата, проектов, файлов, лимитов токенов
новой системе не нужна.

**Сделано.**
1. Документы: `ARCHITECTURE.md`, `DEPLOYMENT.md`, `.env.example`, `docs/ASR_CONTRACT.md`, `docs/MIGRATIONS.md`, `README.md`.
2. Инфраструктура: `deployment/compose.yml` (+`compose.gpu.yml`, образ LiveKit, шаблоны nginx), скрипты
   `preflight/install/deploy/rollback/backup/restore/status/logs/smoke-test/models` (+`lib/common.sh`),
   профили shared-host/standalone, `--dry-run`.
3. Backend: конфигурация, JSON-логи с request-id и маскированием, модели и миграция `0001`, вход AD,
   сессии, ACL комнат, встречи (reaper, webhook LiveKit), токены LiveKit (identity `u-<uuid>`), приём реплик
   из Redis-стрима, WebSocket, admin-API комнат с аудитом, health/ready/version, внутренний smoke.

   инференса, конвейер на трек, LiveKit-воркер (скрытый участник, подписка только на микрофоны), менеджер сессий, health.
5. Frontend: вход, список комнат, комната (LiveKit, плитки участников, микрофон/камера/экран, живая

**Проверка.** Backend — 60 тестов pytest проходят; ASR — 19 тестов проходят; frontend — `tsc`, 3 теста vitest и

## 2026-10-07 — Исправления по итогам первой реальной установки (shared-host, Ubuntu 24.04)

**Дефекты, найденные при установке, и исправления (универсальные, не под конкретный сервер).**
1. `DATA_ROOT` принимал UNC/SMB-путь. Теперь `validate_local_dir` (мастер, preflight, install, models) отвергает `\srv\share`, `smb://`, URL, относительные пути, пробелы, `..` и объясняет, что SMB настраивается в админке → «Хранилище»; мастер предлагает `/srv/<имя>-data`.
2. `.env` ломался на значениях с пробелами. Единая `dotenv_quote` (литералы в одинарных кавычках; значения со смесью символов, которые нельзя записать безопасно, отвергаются); после записи мастер проверяет чтение и через bash `source`, и через `load_env` — значения совпадают буквально, stderr пуст.
3. `LDAP_URIS` с «/» ломал preflight. Разбор через `parse_ldap_uri` (хост/порт, путь игнорируется), мастер нормализует список, backend покрыт тестом на обе формы.
4. Ложный FAIL `CHANGE_ME`: теперь проверяются только строки-присваивания, комментарии игнорируются.
5. RAM: сравнение в КиБ с допуском (≥90% номинала ок, 75–90% предупреждение, иначе отказ) вместо округления вниз до ГБ.
6. `models.sh`: **по указанию владельца проверка контрольной суммы удалена** (upstream может менять файлы; в приложенном отчёте рекомендовалось оставить — выбрана прямая инструкция владельца). Остались проверка размера, вывод каталога назначения, сохранение `.part`/`.failed` для диагностики, отказ при некорректном `DATA_ROOT`.
7. Мастер и установщик печатают сетевую схему: кто куда проксирует, какие порты нужны клиентам напрямую, что HTTP-прокси ICE-порты не заменяет.
Дополнительно: мастер работает и с piped-вводом, флаг `--env-only`, валидаторы имени/хоста/IP/путей; shared-host изоляция не менялась.

**Проверка.** Новые 45 shell-тестов (`tests/scripts/run.sh`, в CI): квотирование (DN с кириллицей и пробелами, `# $ \ " '`, подстановки команд), CHANGE_ME в комментарии, DATA_ROOT, LDAP URI, RAM, сквозной прогон мастера с неверными ответами, models.sh. Backend — 105 тестов. Скрипты `bash -n` без ошибок.

**Не проверялось.** Чистая переустановка на реальном сервере после исправлений; проверка прав `.env` (600) выполняется только на Linux.

## 2026-10-07 — Установщик: этапы, возобновление, BuildKit-fallback, свой nginx-site (по итогам реального развёртывания)

**Найдено на сервере** (Ubuntu 24.04.1, docker.io 29.1.3, containerd 2.2.1, Compose 2.40.3, overlayfs): `docker compose build` стабильно падает на стадии `exporting to image` (`mount callback failed on /var/lib/containerd/tmpmounts/containerd-mount…`, `failed to open writer: ref … locked`), остаются stale mount'ы; воспроизведено на одном `backend` без параллельной сборки — гипотеза «виновата параллельная сборка backend+ASR» **опровергнута**. `DOCKER_BUILDKIT=0` собирает backend/asr/web. Также: installer включал nginx до сборки; повторный preflight считал порт собственного nginx чужим (без root `ss -p` не показывает процесс); отсутствовала диагностика buildx/Bake.

**Сделано.**
1. `scripts/lib/dockerlib.sh`: диагностика (Docker, Compose, buildx, storage driver, Bake, stale `containerd-mount`), классификация ошибок сборки (infra vs project), пробная реальная сборка, выбор builder'а `BUILD_MODE=auto|buildkit|legacy` с явным **FALLBACK** на `DOCKER_BUILDKIT=0` (и `COMPOSE_BAKE=false`), автоматический повтор проблемной службы через legacy; сообщения `FAIL stage=build service=… subsystem=docker-buildkit|docker-build|dockerfile/project`. Stale mount'ы только диагностируются; никаких prune/umount/рестартов/удаления `/var/lib/*`.
2. `install.sh` переписан этапами с возобновлением: prerequisites → preflight → dirs → models → build → database → migrations → services → healthcheck → **nginx (последним)** → firewall; `--from`, `--force-build`, `--adopt-images`, `--skip-models`; при сбое — `FAIL stage=… subsystem=…` и подсказка продолжить; при нездоровых сервисах останавливаются только прикладные контейнеры проекта; откат собственных изменений nginx при ошибке `nginx -t` сохранён. Образы не пересобираются, если отпечаток исходников (и параметры) не менялся (`state/build-fingerprints`); `up` — только с `--no-build`, чтобы не запускать скрытую сборку BuildKit. `deploy.sh` использует ту же сборку.
3. `preflight.sh`: порт `NGINX_LISTEN_PORT` занят собственным site (marker + `listen` + symlink, без зависимости от прав на `ss -p`) — допустим; неопределённый владелец — FAIL с подсказкой `sudo ss`; отчёт Docker (`docker_diag`), `--probe-build`.
4. `deployment/livekit/Dockerfile`: `ARG LIVEKIT_IMAGE_TAG=v1.9.0` (warning `InvalidDefaultArgInFrom` убран). `frontend`: предупреждение Vite о размере чанка не блокирует сборку (порог 900 КБ; чанк комнаты грузится лениво).
5. Документация: `docs/INSTALL_AND_UPDATE.md` §2.5, `.env.example` (`BUILD_MODE`), PROJECT.md.

**Проверка.** Shell-тесты 74 (подставной docker: BuildKit ок / сломан с реальным текстом ошибки / оба сломаны / принудительные режимы; классификация; отпечатки исходников и возобновление; распознавание своего nginx-site и отказ при чужом; порядок этапов dry-run — nginx после healthcheck; в плане нет prune/umount). Backend не менялся.

## 2026-10-07 (поздний вечер) — Правки по итогам VPN-инцидента: nginx, обновлятор, диагностика подключения, IP клиента, README

Причина жалобы на подключение через VPN — сеть (Path MTU: после `MTU=1250` на VPN-адаптере всё заработало), не ПО. Но инцидент вскрыл дефекты приложения:

- **Критично: `frontend/nginx.conf`.** `map $http_x_forwarded_proto $xfp { default $xfp; "" $scheme; }` ссылался сам на себя («cycle while evaluating variable "xfp"», 499 при непустом X-Forwarded-Proto — то есть при любом запросе через внешний прокси). Исправлено на `default $http_x_forwarded_proto;`.
  Почему не поймали: `nginx -t` такую ошибку не видит (она проявляется при обработке запроса), а `verify.sh` ходил на web без заголовка. Теперь: `nginx -t` в собранном образе до замены контейнера, verify — запросом со схемой https и `nginx -t` в запущенном web, CI-задача `web-image` (настоящий nginx, стадия draw.io), статическая проверка самоссылки map.
- **Обновлятор.** Старая неудачная попытка из веб-интерфейса оставалась «текущим» ходом обновления после успешного обновления из терминала. `update.sh` теперь пишет `history.ndjson` при любом запуске; интерфейс разделяет установленную версию, последнее успешное обновление и историю попыток, прежний неудачный запуск помечается `stale`, карточка хода показывается только пока идёт обновление (или запускалось из этого окна).
- **Диагностика LiveKit.** Этапы сигнал (WebSocket) → ICE → медиа в подписях и сообщениях; `ERR_CONNECTION_RESET` — «сброшено на сетевом уровне: VPN/MTU/прокси/файрвол»; HTTPS-проверка сервера звонков при отказе; событие `livekit_connection` (URL без параметров, время сигнала и ICE, транспорт, состояние ICE, пара кандидатов); `connect_failed` — с этапом и результатом проверки.
- **Секреты в логах.** `redactSecrets` (клиент) и `scrub` (сервер) убирают `access_token`, `join_request`, JWT, Bearer; журнал библиотеки звонков понижен до warn. Нативное сообщение браузера «WebSocket connection to … failed» с адресом изменить нельзя.
- **IP клиента.** `pick_client_ip`: справа налево, пропуская `TRUSTED_PROXY_CIDRS` (по умолчанию loopback) и `TRUSTED_PROXY_HOPS-1` прокси; ранее при цепочке «клиент, 127.0.0.1» показывался 127.0.0.1.
- **Пустые протоколы.** Автопротокол для встречи без реплик, чата и схемы не создаётся (событие `protocol_skipped` уровня info); ручное создание — 409 «не из чего».
- **Самопроверка после обновления.** Итог по этапам PASS/FAIL в `update.sh`/`verify.sh`; `rebuild.sh` после пересборки запускает verify.
- **README** сокращён до продуктового (73 строки); прежний текст целиком — в `docs/INTERNALS.md`; добавлены порты для участников и подсказка про MTU (DEPLOYMENT.md, строка в таблице проблем).

## 2026-10-08 — Расследование качества Qwen3 0.6B (стенд, код продукта не менялся)

Поводом стал реальный протокол 14-минутной встречи: «Тема: Поручение» и повтор `[Факт: Поручение]` вместо содержания. Стенд (вне репозитория): настоящий llama-server сборки `b11371` (как в compose) с моделью Qwen3-0.6B-Q4_K_M (SHA-256 совпал с манифестом), флаги как в production (`-c 8192 --parallel 1 --jinja`), настоящий код проекта (`SYSTEM_PROMPT`, `LOCAL_HINT`, `split_for_llm`, `LlmClient`), синтетические стенограммы с эталоном (IT-летучка ≈20 мин, 6 участников; административная планёрка), 23 прогона, сырые запросы и ответы сохранены.

- **Механизм 1 — нарезка.** Лимит фрагмента для локальной модели 12 000 знаков; встреча ≈20 минут (≈15 000 знаков) идёт в два фрагмента. Шаг «подробные заметки по фрагменту (факты, решения, поручения)» **дословно переписывает стенограмму** и упирается в `max_tokens=1200` (`finish_reason=length`, продукт его не проверяет): заметки покрывают только начало фрагмента, остальное молча теряется. Итог строится по «заметкам» и содержит выдумки.
- **Механизм 2 — эхо шаблона.** Подробная инструкция (нумерованная структура, таблицы) в системном промпте: модель на ряде входов возвращает только каркас инструкции (96 токенов, 0 фактов), в том числе на 3-минутной встрече без нарезки. Короткие инструкции работают заметно лучше.
- **Механизм 3 — подражание примеру.** Системный промпт просит «сохранять метки вроде [ФИО_1]» даже при выключенном обезличивании; в одном прогоне модель выдала `[ФИО_1]…[ФИО_4]` вместо реальных имён. Скобочный формат `[Факт: …]` дословно воспроизвести не удалось (встречается ли он у модели при инструкции владельца — не проверено).
- **Предел самой модели.** Даже при лучшем конвейере (вся стенограмма одним запросом, простой промпт) из 11 задач найдено 4–7 (с итоговой репликой в конце 7/11, без неё 4/11), ответственные путаются («Борис и Елена»), статусы искажаются («тесты устранены»), числа и сроки выдумываются, открытые вопросы придумываются. Не годится для «официального протокола»; пригодна для краткого резюме и черновика.
- **Находка по памяти.** llama-server держит кэш промптов до 8 ГиБ (`--cache-ram` по умолчанию 8192): после нескольких разных длинных запросов RSS вырос с 1,6 до 4–5 ГБ при `mem_limit: 3g` контейнера. С `--cache-ram 0` RSS ровно 1,59 ГБ на всех последующих запросах.
- **Время на i5-4440, 2 потока (как в production):** обработка ≈53 ток/с, генерация ≈3,4 ток/с (1200 токенов ≈ 6 минут); на 4 потоках ≈105–177 и 5–9 ток/с.
- Не сделано: Qwen3 1.7B, повтор на реальных записях, проверка скобочного `[Факт:]` с точной инструкцией владельца. Исправления конвейера **не внесены** — ждут решения владельца.

## 2026-10-09 — 0.8.3: исправление сборки web и защита от повторения

**Причина.** При добавлении теста `publicAssets.test.ts` (читает файлы через `node:fs`) я не перезапустил `tsc` после его создания: `npm run build` (= `tsc --noEmit && vite build`) в последний раз запускался ДО добавления файла. **Что неверно в общей картине.** CI на 0.8.2 был КРАСНЫМ (frontend, web-image, backend), а не зелёным: ошибку поймало и задание `frontend`, и `web-image`. Зелёным был только workflow «Release» — он публиковал страницу релиза независимо от CI. Я результат CI перед выпуском не смотрел.

**Исправлено:** тесты исключены из `tsconfig.json`, типы тестов — `tsconfig.test.json` (+ `@types/node` в devDependencies), CI выполняет `typecheck:tests`, `test`, `build`; «Release» ждёт зелёный CI (`ci-gate`); CI собирает web через `docker compose build` с аргументами обновления. Проверено локально: чистая копия с тем же набором файлов, что копирует Dockerfile (`package*.json`, `tsconfig.json`, `vite.config.ts`, `index.html`, `public`, `src`) → `npm ci` → `npm run build` проходит.
